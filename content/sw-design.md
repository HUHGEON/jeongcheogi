# SW 설계

21개 회차 420문제 가운데 이론이 242문제인데, 그중 SW 설계에서 가장 자주 나온 묶음은 디자인 패턴(14회차), 응집도·결합도(9회차), UML(6회차) 세 가지다. 문제 형태는 거의 "설명 1~4줄을 주고 보기에서 고르기"이고, 디자인 패턴과 결합도는 영문 표기를 요구하는 경우가 많다. 그리고 2024년 이후로는 2~5년 전 문제가 지문째 다시 나오는 일이 잦다. 26-1 Bridge·Observer, 26-2 Abstract Factory, 25-1 결합도 세트, 26-1 응집도 세트가 모두 그렇게 다시 나온 문제다.

## 디자인 패턴 총론 (생성·구조·행위 분류)
출제: 24-3, 21-2, 20-4
형태: 분류를 설명하고 예시 패턴 몇 개를 보여 준 뒤 분류 이름 쓰기. "생성·구조·( )" 빈칸형도 있음

### 개념
디자인 패턴이란 설계하다 보면 반복해서 만나는 문제들에 이름을 붙여 둔 해법 모음을 말한다. 흔히 말하는 GoF 23개 패턴은 목적에 따라 세 갈래로 나눈다. 표로 정리하면 이렇다.

| 분류 | 관심사 | 패턴 |
|---|---|---|
| **생성(Creational)** 5개 | 객체를 만드는 방법. 생성 과정을 감춰서 어떤 구체 클래스가 만들어지는지 호출 쪽이 몰라도 되게 한다 | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| **구조(Structural)** 7개 | 클래스와 객체를 조합해 더 큰 구조를 만드는 방법. 인터페이스 변환·분리·단순화 | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **행위(Behavioral)** 11개 | 객체들이 서로 어떻게 상호작용하고 책임을 나누는가. 알고리즘과 제어 흐름 | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

외울 때는 두음으로 묶어 두면 편하다. 생성은 "빌프팩앱싱"(또는 "싱팩빌프앱"), 구조는 "브데퍼플프컴어"(또는 "어데퍼프 브플컴")이고, 나머지 11개는 전부 행위다. 행위까지 따로 외우고 싶다면 "전옵중방이상인 매커책템"을 쓰면 되는데, 차례로 전략·옵저버·중재자·방문자·이터레이터·상태·인터프리터·메멘토·커맨드·책임 연쇄·템플릿 메서드를 가리킨다.

그런데 GoF는 목적 말고 범위로도 패턴을 나눈다. 상속으로 관계가 정해지면 **클래스 패턴**이고, Factory Method, 클래스 Adapter, Interpreter, Template Method가 여기 든다. 객체 합성으로 관계가 정해지면 **객체 패턴**이고, 이 네 개를 뺀 나머지 패턴은 모두 객체 패턴이다.

### 분류 하나씩 보기
세 분류의 이름만 외워 두면 지문에서 막히기 쉽다. 그래서 분류마다 코드 한 장면씩을 붙여 두었다.

#### 1. 생성 패턴 (Creational Pattern)
- **객체를 만드는 방법**에 관한 패턴
- 생성 과정을 감춰 호출하는 쪽이 구체 클래스를 몰라도 되게 함
- 5개: Singleton, Factory Method, Abstract Factory, Builder, Prototype
- 지문 단서: "객체 생성 방식", "인스턴스화 과정을 캡슐화", "어떤 클래스를 만들지"

```java
// 호출하는 쪽은 new WinButton()처럼 구체 클래스를 직접 쓰지 않는다
Button b = factory.createButton();   // 어떤 클래스의 객체가 나올지는 factory가 정한다
```

`new`로 구체 클래스를 직접 부르지 않고 생성을 다른 곳에 맡긴다는 점이 다섯 패턴의 공통점이다.

#### 2. 구조 패턴 (Structural Pattern)
- 클래스와 객체를 **조합해 더 큰 구조**를 만드는 방법
- 인터페이스 변환·분리·단순화
- 지문 단서: "클래스나 객체를 조합", "인터페이스를 변환·분리", "더 큰 구조"

```java
// 이미 있는 객체를 감싸고 이어 붙여서 새 구조를 만든다
Reader r = new BufferedReader(new FileReader("a.txt"));
```

위 코드에서 이미 있는 FileReader 객체를 BufferedReader가 감싸듯, 구조 패턴은 있는 객체를 어떻게 엮느냐를 다룬다. 객체를 만드는 방법을 다루는 생성 패턴과는 여기서 갈린다.

#### 3. 행위 패턴 (Behavioral Pattern)
- 객체들이 **어떻게 상호작용하고 책임을 나누는가**
- 알고리즘과 제어 흐름에 관한 패턴, 11개로 가장 많음
- 지문 단서: "객체 간 상호작용", "책임 분담·분산", "알고리즘·제어 흐름"

```java
// 버튼은 눌렸다는 사실만 알리고, 그다음 일은 등록된 객체들이 나눠 맡는다
button.addListener(logger);
button.addListener(counter);
button.click();   // logger와 counter에 차례로 알림이 간다
```

위 코드는 객체를 만들지도, 엮지도 않는다. 버튼이 클릭을 알리고 logger와 counter가 그 알림을 받아 각자 일을 나눠 맡는다. 이렇게 지문이 "누가 무엇을 맡아 어떻게 주고받는가"를 말하고 있다면 행위다. 분류를 묻는 기출 세 문제(24-3, 21-2, 20-4)는 정답이 모두 행위였다.

### 한눈에 구분
| 분류 | 지문 단서 | 비고 |
|---|---|---|
| 생성 | "객체 생성 방식", "인스턴스화 과정을 캡슐화", "어떤 클래스를 만들지" | |
| 구조 | "클래스나 객체를 조합", "인터페이스를 변환·분리", "더 큰 구조" | |
| 행위 | "객체 간 상호작용", "책임 분담·분산", "알고리즘·제어 흐름" | 분류 문제 3번 모두 정답이 행위 |

### 기출에서 이렇게 나왔다
- 24-3: "객체 간 상호작용과 책임 분담" 설명, 예시로 Mediator·Interpreter·Iterator → **행위**
- 21-2: "상호작용·책임 분산" 설명, 예시로 Observer 등 → **행위**
- 20-4: 생성·구조·( ) 빈칸 → **행위**

### 답 쓸 때
"행위 패턴"과 "행동 패턴"은 둘 다 Behavioral을 옮긴 말로 쓰인다. 개별 패턴 이름은 대부분 영문 보기에서 고르지만, 26-1·25-2·25-1·24-2처럼 "영어로 쓰시오"라고 못 박은 회차도 있었기 때문에 철자까지 외워 둬야 한다.

## 생성 패턴
출제: 26-2, 24-1, 23-2, 21-3
형태: 1~3줄 설명 → 보기에서 영어로. Singleton은 Java 코드 출력 문제로도 나옴(24-1, 21-3)

### 개념
생성 패턴은 객체를 `new`로 바로 만들지 않고 그 과정을 감추는 패턴들이다. 표 아래에 다섯 개를 하나씩 코드로 풀어 두었다.

| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Singleton** | 인스턴스를 하나만 만들고 어디서나 그 하나에 접근하게 한다 | "인스턴스 하나", "전역 접근점", 생성자 private + static getInstance(). 예: DB 커넥션 풀, 설정 관리자 |
| **Factory Method** | 객체 생성 인터페이스는 상위 클래스에 두고, 어떤 클래스를 만들지는 서브클래스가 정한다 | "서브클래스가 결정", "상위 클래스는 생성 인터페이스만", Virtual Constructor |
| **Abstract Factory** | 서로 관련된 객체들의 묶음(제품군)을 구체 클래스를 지정하지 않고 생성하는 인터페이스 | "제품군", "연관된 객체 조합", **Kit** |
| **Builder** | 복잡한 객체의 생성 절차와 표현을 분리해, 같은 절차로 다른 표현을 만든다 | "생성 과정과 표현 분리", "단계적으로 조립". (참고: 텔레스코핑 생성자 해결은 Java 실무식 Builder의 용도이고, 시험 정의는 "생성 절차와 표현 분리") |
| **Prototype** | 원형 인스턴스를 복제해 새 객체를 만든다 | "복제(clone)", "원형", "생성 비용이 큰 객체", "복사 후 필요한 부분만 수정" |

### 패턴 하나씩 보기

#### 1. 싱글톤 (Singleton)
- 인스턴스를 **하나만** 생성, 어디서나 그 하나에 접근(전역 접근점)
- 생성자 private + static getInstance()
- 쓰는 곳: DB 커넥션 풀, 설정 관리자

Singleton은 코드로도 나오니 뼈대를 한 번 눈에 익혀 두자. 생성자를 private으로 막아 두고 static getInstance()로만 그 하나를 꺼내 쓰는 구조인데, 24-1·21-3 코딩 문제가 바로 이 모양이었다.

```java
class Config {
    private static Config instance;
    private Config() {}
    public static Config getInstance() {
        if (instance == null) instance = new Config();
        return instance;
    }
}
public class Main {
    public static void main(String[] args) {
        Config a = Config.getInstance();
        Config b = Config.getInstance();
        System.out.println(a == b);
    }
}
```
출력: `true`

`a == b`가 `true`인 이유는 두 번째 호출 때 instance가 이미 있어서 새로 만들지 않고 같은 객체를 돌려주기 때문이다.

#### 2. 팩토리 메서드 (Factory Method)
- 생성 인터페이스(메서드)는 **상위 클래스**에, 어떤 클래스를 만들지는 **서브클래스가 결정**
- 별칭: Virtual Constructor
- 지문 단서: "서브클래스가 결정", "상위 클래스는 생성 인터페이스만"

```java
abstract class Dialog {
    abstract Button createButton();          // 생성 메서드의 모양만 정해 둔다
    void render() { createButton().draw(); }
}
class WinDialog extends Dialog {
    Button createButton() { return new WinButton(); }   // 무엇을 만들지는 서브클래스가 정한다
}
```

Dialog는 버튼이 필요하다는 것만 알고, 실제로 어떤 버튼이 나올지는 WinDialog 같은 서브클래스가 메서드를 재정의해서 결정한다.

#### 3. 추상 팩토리 (Abstract Factory)
- 서로 관련된 객체들의 묶음(**제품군**)을 구체 클래스 지정 없이 생성하는 인터페이스
- 지문 단서: "제품군", "연관된 객체 조합", **Kit**

```java
interface GUIFactory {                 // 버튼과 체크박스를 한 벌로 만든다
    Button createButton();
    Checkbox createCheckbox();
}
class MacFactory implements GUIFactory {
    public Button createButton()     { return new MacButton(); }
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}
```

GUIFactory 타입 변수에 MacFactory 객체를 넣으면 MacButton과 MacCheckbox가 한 벌로 나온다. 팩토리 객체 하나만 다른 것으로 바꾸면 버튼과 체크박스가 같은 계열로 한꺼번에 바뀌는 구조다. 26-2·24-1 모두 지문에 Kit이 나왔다.

#### 4. 빌더 (Builder)
- 복잡한 객체의 **생성 절차와 표현을 분리**, 같은 절차로 다른 표현 생성
- 객체를 단계적으로 조립
- 지문 단서: "생성 과정과 표현 분리", "단계적으로 조립"

```java
class Director {
    void construct(DocBuilder b) {   // 조립 절차는 하나로 고정
        b.title("보고서");
        b.body("내용");
    }
}
director.construct(new HtmlBuilder());   // 같은 절차로 HTML 문서를 만들고
director.construct(new TextBuilder());   // 텍스트 문서도 만든다
```

Java 실무에서 자주 보는 `.name().age().build()` 같은 체이닝은 텔레스코핑 생성자(매개변수 개수만 다른 생성자를 여러 개 겹쳐 두는 방식)를 해결하는 용도다. 시험 정의는 어디까지나 "생성 절차와 표현 분리"이니 이 문장으로 기억한다.

#### 5. 프로토타입 (Prototype)
- **원형 인스턴스를 복제(clone)**해 새 객체 생성
- 생성 비용이 큰 객체를 복사한 뒤 필요한 부분만 수정
- 지문 단서: "복제(clone)", "원형", "생성 비용이 큰 객체", "복사 후 필요한 부분만 수정"

```java
Shape copy = original.clone();   // 처음부터 만들지 않고 원형을 복제한 뒤
copy.setColor("red");            // 필요한 부분만 고친다
```

다른 네 패턴은 클래스로 객체를 새로 만들지만, Prototype은 이미 있는 객체(original)를 복제해서 새 객체를 얻는다.

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Factory Method vs Abstract Factory | Factory Method는 메서드 하나로 제품 하나를 만들고 서브클래스가 그 메서드를 재정의한다. Abstract Factory는 여러 제품으로 이루어진 제품군을 팩토리 객체 하나가 통째로 만든다. 지문에 "제품군·Kit"이 있으면 Abstract Factory, "서브클래스에서 결정"이면 Factory Method |
| Builder vs Abstract Factory | Builder는 복잡한 객체 하나를 단계적으로 조립, Abstract Factory는 관련 객체 여러 개를 한 번에 생성 |
| Prototype vs Factory Method | Prototype은 기존 객체를 복제, Factory Method는 클래스에서 새로 생성 |

### 기출에서 이렇게 나왔다
- 26-2: "제품군을 생성하는 인터페이스, Kit" → **Abstract Factory** (24-1 재출제)
- 24-1: "연관된 객체를 조합해 생성하는 인터페이스, Kit" → **Abstract Factory**
- 23-2: 설명 2개 → **Singleton / Visitor**
- 21-3: "상위 클래스는 생성 인터페이스만 정의, 서브클래스가 생성할 클래스를 결정" → **Factory Method**

### 답 쓸 때
Abstract Factory와 Factory Method는 띄어 쓰는 두 단어라는 점을 기억해 두자. Singleton도 Singletone처럼 끝에 e를 붙여 쓰지 않도록 조심한다.

## 구조 패턴
출제: 26-1, 25-2, 25-1, 23-1, 22-3
형태: 한 줄 설명 → 보기에서 영어로. Bridge는 Observer와 한 문제에 묶여 두 번 나옴

### 개념
구조 패턴은 이미 있는 클래스와 객체를 감싸고 이어 붙여서 더 큰 구조를 만드는 패턴들이다. 일곱 개 가운데 Adapter와 Decorator는 별칭(Wrapper)까지 같아서, 표를 본 다음 코드 모양으로 한 번 더 구분해 두는 게 좋다.

| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Adapter** | 호환되지 않는 인터페이스를 변환해 함께 동작하게 한다 | "서로 다른 인터페이스 연결", "호환되지 않는", "변환", Wrapper |
| **Bridge** | 추상부(기능 계층)와 구현부(구현 계층)를 분리해 각각 독립적으로 확장한다 | "추상과 구현 분리", "독립적으로 확장·변형", "기능 계층·구현 계층" |
| **Composite** | 부분-전체 트리 구조를 만들어 개별 객체와 복합 객체를 같은 방식으로 다룬다 | "트리 구조", "부분-전체", "단일 객체와 복합 객체를 동일하게" |
| **Decorator** | 객체에 기능을 동적으로 덧붙인다. 서브클래스를 늘리지 않고 확장 | "동적으로 기능 추가", "장식", "상속 대신", Wrapper(Adapter와 같은 별칭이므로 "기능 추가"인지 "변환"인지로 가른다) |
| **Facade** | 복잡한 서브시스템에 단순한 통합 인터페이스 하나를 제공한다 | "단일 창구", "단순화된 인터페이스", "서브시스템", "결합도를 낮춤" |
| **Flyweight** | 공유 가능한 부분을 공유해 많은 수의 객체를 적은 메모리로 다룬다 | "공유", "메모리 절약", "다수의 작은 객체", "경량화" |
| **Proxy** | 다른 객체를 대신하는 대리 객체를 두어 접근을 제어한다 | "대리", "대신", "접근 제어", "지연·원격·보호" |

### 패턴 하나씩 보기

#### 1. 어댑터 (Adapter)
- **호환되지 않는 인터페이스를 변환**해 함께 동작하게 함
- 별칭: Wrapper
- 지문 단서: "서로 다른 인터페이스 연결", "호환되지 않는", "변환"

```java
// 기존 코드는 Printer의 print()를 부르는데, 들여온 라이브러리에는 output()만 있다
class LibAdapter implements Printer {
    private final NewLib lib = new NewLib();
    public void print(String s) { lib.output(s); }   // print 호출을 output 호출로 바꿔 준다
}
```

기존 코드가 부르는 Printer의 print()와 라이브러리 NewLib의 output()은 이름이 달라 그대로는 안 맞는다. LibAdapter가 그 사이에 끼어 print 호출을 output 호출로 바꿔 준다. 해외 여행에서 쓰는 콘센트 변환 플러그와 같은 역할이다.

#### 2. 브리지 (Bridge)
- **추상부(기능 계층)와 구현부(구현 계층)를 분리**, 각각 독립적으로 확장
- 지문 단서: "추상과 구현 분리", "독립적으로 확장·변형", "기능 계층·구현 계층"

```java
abstract class Remote {              // 기능 계층(추상부)
    protected Device device;         // 구현 계층(구현부)을 필드로 들고 있다
    Remote(Device d) { device = d; }
    abstract void power();
}
class AdvancedRemote extends Remote { /* 기능 쪽은 이렇게 따로 늘리고 */ }
class TV implements Device { /* 구현 쪽도 */ }
class Radio implements Device { /* 따로 늘린다 */ }
```

AdvancedRemote 같은 리모컨 종류를 늘려도 TV·Radio는 고치지 않고, 기기 종류를 늘려도 Remote 쪽은 고치지 않는다. Adapter는 이미 만들어진 두 인터페이스를 나중에 맞추는 패턴이고, Bridge는 설계할 때부터 추상부(Remote)와 구현부(Device)를 나눠 두는 패턴이다.

#### 3. 컴포지트 (Composite)
- **부분-전체 트리 구조**, 개별 객체와 복합 객체를 같은 방식으로 다룸
- 지문 단서: "트리 구조", "부분-전체", "단일 객체와 복합 객체를 동일하게"

```java
interface Node { int size(); }
class File implements Node { public int size() { return 10; } }
class Folder implements Node {
    List<Node> children = new ArrayList<>();
    public int size() {                  // 폴더도 파일과 똑같이 size()로 부른다
        int sum = 0;
        for (Node c : children) sum += c.size();
        return sum;
    }
}
```

폴더 안에 파일도 폴더도 들어갈 수 있고, 쓰는 쪽은 그게 파일인지 폴더인지 따지지 않고 `size()`만 부른다.

#### 4. 데코레이터 (Decorator)
- 객체에 **기능을 동적으로 추가**, 서브클래스를 늘리지 않는 확장
- 별칭: Wrapper(Adapter와 같음), "기능 추가"면 Decorator·"변환"이면 Adapter
- 지문 단서: "동적으로 기능 추가", "장식", "상속 대신"

```java
Coffee c = new Milk(new Syrup(new Espresso()));   // 한 겹 감쌀 때마다 기능이 하나씩 붙는다
c.cost();   // Espresso 값 + Syrup 값 + Milk 값
```

우유 넣은 커피, 시럽 넣은 커피를 클래스로 하나하나 만들지 않고 실행 중에 겹겹이 감싸서 조합한다.

#### 5. 퍼사드 (Facade)
- 복잡한 서브시스템 앞의 **단순한 통합 인터페이스 하나**
- 지문 단서: "단일 창구", "단순화된 인터페이스", "서브시스템", "결합도를 낮춤"

```java
class HomeTheater {           // 서브시스템 앞의 단일 창구
    void watchMovie() {
        amp.on();
        projector.on();
        player.play();
    }
}
theater.watchMovie();         // 쓰는 쪽은 이 메서드 하나만 안다
```

쓰는 쪽이 앰프·프로젝터·플레이어를 하나하나 알 필요가 없으니 서브시스템과의 결합도가 낮아진다.

#### 6. 플라이웨이트 (Flyweight)
- **공유 가능한 부분을 공유**, 많은 수의 객체를 적은 메모리로 처리
- 지문 단서: "공유", "메모리 절약", "다수의 작은 객체", "경량화"

```java
class GlyphFactory {
    static Map<Character, Glyph> pool = new HashMap<>();
    static Glyph get(char c) {
        return pool.computeIfAbsent(c, Glyph::new);   // 이미 있으면 만들지 않고 있던 객체를 준다
    }
}
// 문서에 'a'가 만 번 나와도 'a' 글리프 객체는 하나뿐이다
```

'a'가 만 번 나와도 객체를 만 개 만들지 않고, pool에 들어 있는 'a' 객체 하나를 만 번 같이 쓴다.

#### 7. 프록시 (Proxy)
- 다른 객체를 **대신하는 대리 객체**로 접근 제어
- 용도: 지연·원격·보호
- 지문 단서: "대리", "대신", "접근 제어"

```java
class ImageProxy implements Image {      // 실제 객체와 같은 인터페이스
    private RealImage real;
    public void show() {
        if (real == null) real = new RealImage("big.png");   // 정말 필요할 때 비로소 만든다(지연)
        real.show();
    }
}
```

쓰는 쪽은 Image의 `show()`를 부를 뿐, 받은 객체가 ImageProxy인지 RealImage인지 모른다. Proxy는 인터페이스(Image)를 그대로 두고, Adapter는 인터페이스를 바꾼다.

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Adapter vs Bridge | Adapter는 이미 만들어진 두 인터페이스가 안 맞을 때 사후에 변환한다(키워드 호환·변환). Bridge는 설계 단계에서 추상과 구현을 처음부터 분리한다(키워드 분리·독립 확장) |
| Facade vs Adapter | Facade는 여러 클래스 묶음 앞에 단순한 창구 하나를 세운다. Adapter는 인터페이스 모양을 바꾼다. "단순화·서브시스템"이면 Facade |
| Proxy vs Adapter | Proxy는 실제 객체와 같은 인터페이스를 유지한 채 앞에서 접근을 통제한다. Adapter는 인터페이스를 바꾼다 |
| Decorator vs Proxy | 둘 다 같은 인터페이스로 실제 객체를 감싼다. Decorator는 기능 추가가 목적이고 겹겹이 쌓인다. Proxy는 접근 제어가 목적이고 보통 한 겹이다 |
| Composite vs Decorator | 둘 다 재귀 구조다. Composite는 자식이 여러 개인 트리, Decorator는 하나를 감싼 사슬 |

### 답 쓸 때
구조 패턴에서 헷갈리기 쉬운 쌍이 Bridge와 Adapter다. Bridge 지문에 나오는 "구현부"라는 말이 Adapter의 "인터페이스 변환"과 섞여 보이기 쉽기 때문이다. 이때는 낱말 하나에 끌려가지 말고, "분리·독립 확장"이 보이면 Bridge, "변환·호환"이 보이면 Adapter로 가른다.

22-3 Bridge 지문은 한 번 더 함정이 있다. "부수적인 새로운 기능을 지속적으로 추가", "기존 프로그램 변경 없이 기능 확장"처럼 Decorator로 읽히는 문장이 함께 나온다. 그래도 답은 Bridge다. 왜냐하면 첫 문장의 "기능 클래스와 구현 추상 클래스를 구별", "구현뿐 아니라 추상화도 독립적으로 변경"이 결정적 단서이기 때문이다.

### 개념
행위 패턴은 객체들이 일을 어떻게 나눠 맡고 서로 어떻게 주고받는지를 다루는 패턴들이다. 11개로 가장 많고, "상태"처럼 같은 낱말이 State·Observer·Memento 지문에 두루 나온다. 그래서 표 다음에 패턴마다 짧은 코드를 하나씩 붙였다.

| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Chain of Responsibility** | 요청을 처리할 수 있는 객체가 나올 때까지 사슬을 따라 넘긴다 | "처리자 사슬", "요청을 다음으로 전달" |
| **Command** | 요청 자체를 객체로 캡슐화해 저장·취소·큐잉한다 | "요청을 객체로", "실행 취소(undo)·재실행", "매개변수화", "로그·큐" |
| **Interpreter** | 언어의 문법을 클래스로 표현하고 문장을 해석한다 | "문법", "해석기", "언어·표현식" |
| **Iterator** | 집합체의 내부 구조를 드러내지 않고 요소에 순차적으로 접근한다 | "내부 구조 노출 없이", "순차 접근", "반복자", "Cursor" |
| **Mediator** | 객체 사이의 상호작용을 중재자 하나에 모아 결합도를 낮춘다 | "중재자", "다대다 상호작용을 중앙 집중", "객체끼리 직접 참조하지 않음" |
| **Memento** | 객체 내부 상태를 저장해 두었다가 복원한다 | "상태 저장·복원", "스냅샷", "되돌리기", "캡슐화를 깨지 않고(내부 상태를 외부에 노출하지 않고)" |
| **Observer** | 한 객체의 상태가 바뀌면 그에 의존하는 객체들에 자동으로 알린다. 일대다 | "상태 변화", "자동 통지·갱신", "일대다", "발행-구독(Publish-Subscribe)", "이벤트 리스너" |
| **State** | 상태를 객체로 분리해, 상태에 따라 행동이 바뀌게 한다 | "상태에 따라 행동 변화", "상태 객체" |
| **Strategy** | 알고리즘 군을 각각 캡슐화해 서로 바꿔 끼울 수 있게 한다 | "알고리즘 교체", "실행 중 선택" |
| **Template Method** | 알고리즘 골격은 상위 클래스에 두고 세부 단계만 서브클래스에서 재정의한다 | "골격", "단계 재정의", "상속" |
| **Visitor** | 객체 구조는 그대로 두고 수행할 연산을 방문자 클래스로 분리한다 | "연산을 분리", "방문", "각 클래스를 돌아다니며", "구조 변경 없이 새 기능 추가" |

### 패턴 하나씩 보기

#### 1. 책임 연쇄 (Chain of Responsibility)
- 처리할 수 있는 객체가 나올 때까지 요청을 **사슬을 따라 다음으로 전달**
- 지문 단서: "처리자 사슬", "요청을 다음으로 전달"

```java
abstract class Approver {
    Approver next;                       // 다음 처리자
    void approve(int amount) {
        if (canApprove(amount)) sign(amount);
        else if (next != null) next.approve(amount);   // 내가 못 하면 다음에게 넘긴다
    }
    abstract boolean canApprove(int amount);
    abstract void sign(int amount);
}
// 팀장 → 부장 → 사장 순으로 이어 두면, 금액에 맞는 사람이 결재한다
```

결재를 올리는 쪽은 첫 고리인 팀장의 approve()만 부르고, 팀장·부장·사장 가운데 누가 결재할지는 모른다.

#### 2. 커맨드 (Command)
- **요청 자체를 객체로 캡슐화**, 저장·취소·큐잉 가능
- 지문 단서: "요청을 객체로", "실행 취소(undo)·재실행", "매개변수화", "로그·큐"

```java
interface Command { void execute(); void undo(); }

cmd.execute();
history.push(cmd);      // 요청이 객체라서 쌓아 둘 수 있고
history.pop().undo();   // 꺼내서 취소할 수도 있다
```

cmd가 객체이기 때문에 history에 쌓아 두었다가 꺼내서 undo()로 취소할 수 있다. "붙여넣기" 같은 요청 하나가 객체가 되면 기록하고, 줄 세우고, 되돌릴 수 있게 된다.

#### 3. 인터프리터 (Interpreter)
- 언어의 **문법을 클래스로 표현**, 문장 해석
- 지문 단서: "문법", "해석기", "언어·표현식"

```java
interface Expr { int interpret(); }                // 문법 규칙 하나가 클래스 하나
class Num implements Expr {
    int v; Num(int v) { this.v = v; }
    public int interpret() { return v; }
}
class Add implements Expr {
    Expr l, r; Add(Expr l, Expr r) { this.l = l; this.r = r; }
    public int interpret() { return l.interpret() + r.interpret(); }
}
// "1 + 2"를 new Add(new Num(1), new Num(2))로 표현하고 interpret()로 해석한다
```

숫자, 덧셈 같은 문법 요소마다 클래스를 두고 그 객체들을 엮어서 문장을 해석한다.

#### 4. 이터레이터 (Iterator)
- 집합체의 **내부 구조를 드러내지 않고** 요소에 순차 접근
- 별칭: Cursor
- 지문 단서: "내부 구조 노출 없이", "순차 접근", "반복자"

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {               // list가 배열 기반인지 연결 리스트인지 몰라도
    System.out.println(it.next());   // 같은 방법으로 하나씩 꺼낸다
}
```

24-2 지문의 "내부 구조를 노출하지 않고 순차 접근"이 바로 이 코드가 하는 일이다.

#### 5. 중재자 (Mediator)
- 객체 사이 상호작용을 **중재자 하나에 집중**, 결합도 감소
- 지문 단서: "중재자", "다대다 상호작용을 중앙 집중", "객체끼리 직접 참조하지 않음"

```java
class Tower {                                // 관제탑이 중재자
    void requestLanding(Plane p) { /* 활주로 사정을 보고 허가 여부를 알린다 */ }
}
class Plane {
    Tower tower;
    void land() { tower.requestLanding(this); }   // 다른 비행기를 직접 참조하지 않는다
}
```

비행기끼리 서로 연락하면 연결선이 다대다로 얽힌다. 관제탑 하나를 거치게 하면 각 비행기(Plane)는 Tower 하나만 참조한다.

#### 6. 메멘토 (Memento)
- 객체의 **내부 상태를 저장해 두었다가 복원**
- 캡슐화 유지(내부 상태를 외부에 노출하지 않음)
- 지문 단서: "상태 저장·복원", "스냅샷", "되돌리기"

```java
Memento saved = editor.save();   // 지금 상태를 스냅샷으로 떠 두고
editor.type("실수로 쓴 글");
editor.restore(saved);           // 저장해 둔 상태로 되돌린다
```

editor.save()는 그 시점의 상태를 게임 세이브 파일처럼 통째로 떠 두고, restore()는 그 상태로 돌아간다. Command의 undo는 저장해 둔 상태를 쓰지 않는다. 실행했던 요청의 반대 동작(붙여넣기라면 붙여 넣은 글 지우기)을 실행해서 되돌린다.

#### 7. 옵저버 (Observer)
- 한 객체의 **상태 변화를 의존 객체들에 자동 통지**, 일대다
- 다른 이름: 발행-구독(Publish-Subscribe)
- 지문 단서: "상태 변화", "자동 통지·갱신", "일대다", "이벤트 리스너"

```java
class Channel {
    List<Subscriber> subs = new ArrayList<>();
    void upload(String video) {
        for (Subscriber s : subs) s.update(video);   // 상태가 바뀌면 구독자 모두에게 자동 통지
    }
}
```

채널(발행자) 하나에 구독자 여럿이 붙는 일대다 구조다. 행위 패턴 가운데 정답으로 가장 많이 나왔다.

#### 8. 상태 (State)
- **상태를 객체로 분리**, 상태에 따라 행동이 바뀜
- 지문 단서: "상태에 따라 행동 변화", "상태 객체"

```java
class Door {
    DoorState state = new Closed();
    void push() { state = state.push(); }   // 같은 push()라도 지금 상태 객체가 동작을 정한다
}
class Closed implements DoorState { public DoorState push() { return new Opened(); } }
class Opened implements DoorState { public DoorState push() { return new Closed(); } }
```

Door는 if문으로 상태를 검사하지 않는다. 지금 상태가 Closed면 push()가 Opened를 돌려주고, Opened면 Closed를 돌려준다. 행동도, 다음 상태로의 전이도 상태 객체가 정한다.

#### 9. 전략 (Strategy)
- **알고리즘 군을 각각 캡슐화**, 서로 교체 가능
- 지문 단서: "알고리즘 교체", "실행 중 선택"

```java
sorter.setStrategy(new QuickSort());   // 알고리즘을 골라 끼우고
sorter.sort(data);
sorter.setStrategy(new MergeSort());   // 실행 중에 바꿔 끼워도 Sorter 코드는 그대로다
sorter.sort(data);
```

State와 코드 모양은 비슷한데, 갈리는 기준은 "다음에 쓸 객체를 누가 정하느냐"다. Strategy에서는 바깥의 클라이언트가 정한다. 바로 위 코드에서 setStrategy()로 QuickSort나 MergeSort를 골라 끼우는 쪽이 클라이언트다. State에서는 상태 객체가 정한다. 앞의 Door 코드에서 Closed 객체의 push()가 다음 상태인 Opened를 돌려주는 식이다.

#### 10. 템플릿 메서드 (Template Method)
- 알고리즘 **골격은 상위 클래스**, 세부 단계만 서브클래스에서 재정의
- 지문 단서: "골격", "단계 재정의", "상속"

```java
abstract class Beverage {
    final void make() {      // 골격(순서)은 상위 클래스가 고정한다
        boilWater();
        brew();              // 이 단계만
        pour();
    }
    abstract void brew();    // 서브클래스가 채운다
}
class Tea extends Beverage { void brew() { /* 찻잎 우리기 */ } }
```

Tea가 brew() 하나만 재정의하듯, Template Method는 상속으로 빈 단계만 채운다. Strategy는 알고리즘 객체를 통째로 바꿔 끼우고 그 객체에 일을 맡기는 위임 방식이다.

#### 11. 방문자 (Visitor)
- 객체 구조는 그대로, **수행할 연산을 방문자 클래스로 분리**
- 지문 단서: "연산을 분리", "방문", "각 클래스를 돌아다니며", "구조 변경 없이 새 기능 추가"

```java
interface Visitor { void visit(Book b); void visit(Fruit f); }
class PriceVisitor implements Visitor { /* 품목마다 가격 계산 */ }
class TaxVisitor implements Visitor { /* 새 연산이 필요하면 방문자만 추가한다 */ }

for (Item i : cart) i.accept(new TaxVisitor());   // Book·Fruit 클래스는 고치지 않는다
```

세금 계산이라는 새 연산이 필요해도 TaxVisitor 클래스 하나만 추가하고, Book·Fruit 같은 요소 클래스는 고치지 않는다. 지문의 "각 클래스를 돌아다니며"는 방문자 객체 하나가 cart의 요소를 차례로 방문하며 연산을 수행하는 모습을 가리킨다.

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Strategy vs State | Strategy는 클라이언트가 알고리즘을 골라 끼우고 알고리즘끼리는 서로 모른다. State는 객체가 자기 상태에 따라 스스로 행동을 바꾸고 상태 객체가 다음 상태로 전이시킨다. 지문이 "상태에 따라 행동이 바뀐다"면 State다. "상태가 바뀌면 다른 객체들에 통지"는 Observer(20-2 정답), "상태를 저장했다가 복원"은 Memento이므로 "상태"라는 낱말만 보고 고르지 않는다 |
| Strategy vs Template Method | Strategy는 위임(객체 교체), Template Method는 상속(골격 고정 + 빈 단계만 하위에서 채움) |
| Observer vs Mediator | Observer는 일대다 통지(발행자 → 구독자). Mediator는 다대다 상호작용을 객체 하나로 모은다 |
| Command vs Memento | Command는 "요청"을 객체화하고, Memento는 "상태"를 객체화한다. 되돌리기가 요청의 역연산이면 Command, 저장해 둔 상태 복원이면 Memento |
| Iterator vs Visitor | Iterator는 순회 자체. Visitor는 순회하면서 각 요소에 적용할 연산을 바깥 클래스로 뺀 것 |

### 기출에서 이렇게 나왔다
- 26-1: 설명 2개 → **Bridge / Observer**
- 24-2: "내부 구조를 노출하지 않고 순차 접근" → **Iterator**
- 23-2: 설명 2개 → **Singleton / Visitor**
- 22-3: 설명 2개 → **Bridge / Observer**
- 20-2: "상태 변화 시 의존 객체에 자동 통지, 일대다" → **Observer**

### 답 쓸 때
행위 패턴에서 정답으로 나온 건 Observer가 3회, Iterator와 Visitor가 각 1회였다. 그러니 Observer부터 확실히 잡아 두는 게 좋다. 참고로 24-3·21-2 분류 문제에서는 Mediator·Interpreter·Iterator·Observer가 행위 패턴의 예시로 지문에 등장했었다.

## 모듈 응집도·결합도
출제: 26-2, 26-1, 25-1, 24-2, 24-1, 21-3, 21-2, 21-1, 20-1
형태: 설명 3개 → 보기에서 3개 고르기가 기본. 한 줄 설명 → 하나, 높은 순 나열, 응집도·결합도 정의 자체. 보기에 응집도와 결합도가 섞여 있기도 함

### 개념
먼저 설계 원리 네 가지부터 짚고 가자. **모듈화**는 시스템을 기능 단위 모듈로 나누는 것이고, **추상화**는 세부 사항을 덜어 내고 핵심만 드러내는 것으로, 과정 추상화·자료 추상화·제어 추상화로 나뉜다. **단계적 분해**(Stepwise Refinement)는 상위 개념부터 하향식으로 구체화해 내려가는 것이며, **정보 은닉**은 모듈 내부를 감추고 인터페이스로만 접근하게 하는 것이다.

그럼 모듈을 잘 나눴는지는 무엇으로 잴까? 이때 쓰는 두 척도가 응집도와 결합도다. **응집도(Cohesion)** 란 모듈 안의 요소들이 하나의 기능에 얼마나 집중되어 있는가를 말하고, 높을수록 좋다. 반대로 **결합도(Coupling)** 는 모듈 사이의 의존이 얼마나 강한가를 말하고, 낮을수록 좋다. 정리하자면 좋은 설계란 응집도는 높고 결합도는 낮은 설계다. 20-1에서는 이 두 정의 자체가 출제됐다.

응집도는 7종이고, 아래 표는 높은 것부터 낮은 것 순서다.

| 순위 | 응집도 | 핵심 단서 |
|---|---|---|
| 1 | **기능적(Functional)** | 모든 요소가 단일 기능 하나를 위해 존재. "하나의 문제와 연관된 기능만 수행" |
| 2 | **순차적(Sequential)** | 한 요소의 출력이 다음 요소의 입력. "이전 활동의 출력이 다음 활동의 입력" |
| 3 | **교환적(Communicational)** | 같은 입력 데이터를 쓰거나 같은 출력을 만드는 요소들이 모임. 순서는 무관. "동일한 입출력 데이터를 사용". 통신적이라고도 함 |
| 4 | **절차적(Procedural)** | 여러 기능을 정해진 순서대로 수행하지만 데이터는 넘기지 않음. NCS "다수의 관련 기능을 순차적으로 수행", 기출(21-2·26-1) "기능적으로 연관성은 없으나 순차적으로 실행". "순차적으로"가 보여도 출력→입력 연결이 없으면 절차적 |
| 5 | **시간적(Temporal)** | 특정 시점에 함께 실행되어야 하는 것들을 묶음. "초기화", "같은 시간대에 처리" |
| 6 | **논리적(Logical)** | 비슷한 성격의 기능을 한 모듈에 넣고 매개변수로 골라 수행. "논리적으로 유사", "선택적으로 수행" |
| 7 | **우연적(Coincidental)** | 서로 관련 없는 요소들이 모임. "관련 없음", "임의로" |

두음은 "기순교절시논우"로 외운다.

결합도는 6종인데, 응집도와 달리 표를 낮은 것부터 높은 것 순서로 놓았다. 결합도는 낮을수록 좋기 때문에, 이렇게 놓으면 두 표 모두 1번이 가장 바람직한 쪽이 된다.

| 순위 | 결합도 | 핵심 단서 |
|---|---|---|
| 1 | **자료(Data)** | 매개변수로 단순 값만 주고받음. "값 전달", "가장 바람직" |
| 2 | **스탬프(Stamp)** | 배열·구조체 같은 자료 구조 전체를 전달. "자료 구조", "레코드 통째로" |
| 3 | **제어(Control)** | 플래그·제어 신호를 넘겨 상대 모듈의 논리 흐름을 바꿈. "제어 요소", "제어 신호", "논리적 흐름을 제어", "처리 대상뿐 아니라 처리 방법까지 전달". 하위 모듈이 상위 모듈에 처리 방법을 지시하면 권리 전도 현상이 생김 |
| 4 | **외부(External)** | 어떤 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈이 참조. 외부에서 정한 데이터 형식·통신 프로토콜·장치 인터페이스를 함께 쓰는 경우도 여기 든다. "외부 데이터", "프로토콜 공유" |
| 5 | **공통(Common)** | 전역 변수를 여러 모듈이 공유. "전역 변수", "공유 영역" |
| 6 | **내용(Content)** | 다른 모듈의 내부 데이터나 코드를 직접 참조·수정. "내부를 직접 참조", "가장 높음" |

두음은 "자스제외공내"다. 높은 쪽부터 외우고 싶다면 거꾸로 "내공외제스자"로 읽으면 되고, 응집도를 낮은 쪽부터 외울 때는 "우논시절통순기"가 된다.

### 응집도 하나씩 보기
표만 보면 다 비슷해 보이니, 단계마다 어떤 모듈이 되는지 짧은 코드로 하나씩 본다. 1번(기능적)에서 7번(우연적)으로 내려갈수록 응집도가 낮아진다.

#### 1. 기능적 응집도 (Functional Cohesion)
- 모듈 안의 모든 요소가 **단일 기능 하나**를 위해 존재하는 경우
- 응집도 중 가장 높음 (가장 바람직)
- 지문 단서: "하나의 문제와 연관된 기능만 수행"

```java
// 넓이를 구하는 일 하나만 한다
int area(int w, int h) {
    return w * h;
}
```

모듈이 하는 일을 "넓이를 구한다"처럼 한 문장으로 말할 수 있으면 기능적 응집도다.

#### 2. 순차적 응집도 (Sequential Cohesion)
- 한 요소의 **출력이 다음 요소의 입력**이 되는 경우
- 지문 단서: "이전 활동의 출력이 다음 활동의 입력"

```java
String raw   = readFile(path);   // 읽어 온 결과가
String clean = trim(raw);        // 다음 단계의 입력이 되고
save(clean);                     // 그 결과가 또 다음 입력이 된다
```

raw가 trim()으로, clean이 save()로 넘어가기 때문에 세 줄의 순서를 바꿀 수 없다.

#### 3. 교환적 응집도 (Communicational Cohesion)
- **같은 입력 데이터를 쓰거나 같은 출력을 만드는** 요소들이 모인 경우
- 처리 순서 무관, 통신적 응집도라고도 함
- 지문 단서: "동일한 입출력 데이터를 사용"

```java
Report r = load(id);   // 같은 데이터 r을
print(r);              // 출력에도 쓰고
send(r);               // 전송에도 쓴다. print와 send는 순서를 바꿔도 된다
```

순차적 예시에서는 raw가 trim()의 입력이 되고 clean이 save()의 입력이 되어 값이 이어졌다. 여기서는 print(r)의 결과가 send()로 넘어가지 않고, print와 send가 같은 r을 나눠 쓴다. 그래서 둘의 순서를 바꿔도 된다.

#### 4. 절차적 응집도 (Procedural Cohesion)
- 여러 기능을 **정해진 순서대로** 수행하지만 앞 결과를 뒤로 넘기지 않는 경우
- NCS 표현: "다수의 관련 기능을 순차적으로 수행"
- 기출(21-2·26-1) 표현: "기능적으로 연관성은 없으나 순차적으로 실행"

```java
void openShop() {
    unlockDoor();     // 하는 순서는 정해져 있지만
    turnOnLights();   // 앞 단계가 만든 값을 뒤에 넘기지는 않는다
    openRegister();
}
```

순서는 정해져 있지만 unlockDoor()가 만든 값이 turnOnLights()로 넘어가지는 않는다. 지문에 "순차적으로"가 보여도 이렇게 출력에서 입력으로 이어지는 값이 없으면 순차적이 아니라 절차적이다.

#### 5. 시간적 응집도 (Temporal Cohesion)
- **특정 시점에 함께 실행**되어야 하는 것들을 묶은 경우
- 지문 단서: "초기화", "같은 시간대에 처리"

```java
void init() {      // "시작할 때" 해야 하는 일만 모았다
    count = 0;
    openLog();
    loadConfig();
}
```

서로 하는 일은 다르지만 "언제 하느냐"가 같아서 한 모듈에 들어 있다.

#### 6. 논리적 응집도 (Logical Cohesion)
- **비슷한 성격의 기능**을 한 모듈에 넣고 매개변수로 골라 수행하는 경우
- 지문 단서: "논리적으로 유사", "선택적으로 수행"

```java
void output(int type) {   // 성격이 비슷한 출력 기능을 모아 두고
    switch (type) {       // 매개변수로 하나를 골라 실행한다
        case 1: toScreen(); break;
        case 2: toPrinter(); break;
        case 3: toFile(); break;
    }
}
```

#### 7. 우연적 응집도 (Coincidental Cohesion)
- **서로 관련 없는 요소**들이 한 모듈에 모인 경우
- 응집도 중 가장 낮음
- 지문 단서: "관련 없음", "임의로"

```java
void misc() {        // 서로 아무 관련 없는 일이 한곳에 있다
    sortScores();
    sendEmail();
    resizeImage();
}
```

논리적 응집도와 구분할 때는 성격이 비슷하기라도 하면 논리, 아무 관련이 없으면 우연으로 가른다.

### 결합도 하나씩 보기
결합도도 같은 방식으로 단계마다 코드를 붙였다. 이번에는 1번(자료)에서 6번(내용)으로 내려갈수록 결합도가 높아지고, 그만큼 나쁜 설계다.

#### 1. 자료 결합도 (Data Coupling)
- 매개변수로 **단순한 값만** 주고받는 경우
- 결합도 중 가장 낮음 (가장 바람직)
- 지문 단서: "값 전달"

```java
int total = add(price, tax);   // 값 두 개만 넘긴다
```

#### 2. 스탬프 결합도 (Stamp Coupling)
- 배열·구조체 같은 **자료 구조를 통째로** 넘기는 경우
- 지문 단서: "자료 구조", "레코드 통째로"

```java
int total = calc(order);   // 값 하나가 아니라 Order 객체를 통째로 넘긴다
```

자료 결합도 예시는 price, tax 같은 값만 넘겼고, 여기서는 Order 구조 전체를 넘긴다. 그래서 Order의 구조가 바뀌면 calc도 함께 고쳐야 할 수 있다.

#### 3. 제어 결합도 (Control Coupling)
- 플래그·제어 신호를 넘겨 **상대 모듈의 논리 흐름을 바꾸는** 경우
- 처리 대상뿐 아니라 처리 방법까지 전달
- 하위 모듈이 상위 모듈에 처리 방법을 지시하면 권리 전도 현상 발생
- 지문 단서: "제어 요소", "제어 신호", "논리적 흐름을 제어"

```java
print(data, true);   // true면 요약만, false면 전체를 출력한다
                     // 넘긴 플래그가 print 안의 흐름을 정해 버린다
```

#### 4. 외부 결합도 (External Coupling)
- 어떤 모듈에서 **선언한 데이터를 외부의 다른 모듈이 참조**하는 경우
- 외부에서 정한 데이터 형식·통신 프로토콜·장치 인터페이스를 함께 쓰는 경우도 포함
- 지문 단서: "외부 데이터", "프로토콜 공유"

```java
// Config 모듈이 선언해 둔 값을 다른 모듈이 가져다 쓴다
int limit = Config.MAX_USER;
```

#### 5. 공통 결합도 (Common Coupling)
- **전역 변수** 같은 공유 영역을 여러 모듈이 함께 쓰는 경우
- 지문 단서: "전역 변수", "공유 영역"

```java
static int count;          // 전역 변수 하나를
void a() { count++; }      // 여러 모듈이
void b() { count = 0; }    // 함께 읽고 고친다
```

count를 한 곳에서 잘못 바꾸면 count를 쓰는 모든 모듈이 영향을 받는다. 외부 결합도와 비교하면 차이가 보인다. 외부 결합도 예시의 `Config.MAX_USER`는 선언한 모듈이 Config 하나로 정해져 있고, 다른 모듈은 그 값을 읽어 가기만 했다. 여기서 count는 어느 한 모듈의 것이 아닌 전역 변수이고, a()와 b()가 함께 읽고 고친다. 그래서 지문이 "전역 변수·공유 영역"을 여러 모듈이 함께 쓴다고 하면 공통, "한 모듈이 선언한 데이터"를 다른 모듈이 참조한다고 하면 외부다.

#### 6. 내용 결합도 (Content Coupling)
- 다른 모듈의 **내부 데이터나 코드를 직접** 참조·수정하는 경우
- 결합도 중 가장 높음
- 지문 단서: "내부를 직접 참조", "가장 높음"

```java
// 모듈 B가 모듈 A의 내부 변수를 인터페이스를 거치지 않고 직접 바꾼다
moduleA.internalCount = 100;
```

공통 결합도는 count 같은 공유 영역을 거쳐서 값을 주고받는다. 내용 결합도는 `moduleA.internalCount`처럼 상대 모듈의 내부 변수를 인터페이스 없이 직접 바꾼다.

### 한눈에 구분
| 혼동 쌍 | 가르는 기준 |
|---|---|
| 순차 vs 절차 | 데이터가 앞에서 뒤로 흐르면 순차, 순서만 있고 데이터는 안 넘기면 절차 |
| 교환 vs 순차 | 같은 데이터를 쓰되 순서가 없으면 교환, 앞 출력이 뒤 입력이면 순차 |
| 시간 vs 절차 | "특정 시점(초기화·종료)"이면 시간, "실행 순서"면 절차 |
| 논리 vs 우연 | 성격이 비슷하기는 하면 논리, 아무 관련 없으면 우연 |
| 스탬프 vs 자료 | 구조체·배열을 통째로 넘기면 스탬프, 값 하나하나면 자료 |
| 공통 vs 외부 | 여러 모듈이 공유 영역(전역 변수)을 함께 쓰면 공통, 한 모듈이 선언한 데이터를 다른 모듈이 참조하거나 외부 환경(프로토콜·장치·파일 형식)을 공유하면 외부 |
| 공통 vs 내용 | 공유 영역을 거치면 공통, 상대 모듈 내부를 직접 건드리면 내용 |
| 내용 vs 외부 | 지문에 "다른 모듈 **내부**의 변수·기능을 사용(참조·수정)"이 있으면 내용(21-1·25-1 정답). 외부는 "외부에서 정한 데이터 형식·프로토콜·장치 인터페이스"나 "외부에 선언(공개)된 데이터"처럼 '외부'가 단서다 |

### 답 쓸 때
빈칸이 "( ) Coupling"처럼 나오면 영문 한 단어(Control)를 쓴다. 교환적과 통신적은 둘 다 Communicational을 옮긴 같은 말이라서 어느 쪽을 써도 된다. 보기에 응집도와 결합도가 섞여 나오면 실수하기 쉬운데, 이럴 때는 지문이 "모듈 사이"를 말하는지 "모듈 안"을 말하는지부터 본다. 위에서 결합도는 모듈 사이의 의존, 응집도는 모듈 안의 집중이라고 했었다. 그래서 "모듈 사이"면 결합도, "모듈 안"이면 응집도로 먼저 가르고 시작한다.

## Fan-in / Fan-out
출제: 22-2, 20-1
형태: 모듈 호출 구조도 → 특정 모듈의 Fan-in·Fan-out 값, 또는 Fan-in이 n 이상인 모듈 모두 고르기

### 개념
**Fan-in(공유도)** 이란 어떤 모듈을 호출하는 상위 모듈의 수를 말한다. 구조도에서는 그 모듈로 들어오는 화살표 수다. 반대로 **Fan-out(제어도)** 은 그 모듈이 호출하는 하위 모듈의 수이고, 그림에서는 나가는 화살표 수다. 각 값이 높으면 무슨 뜻이고 어느 쪽으로 설계해야 하는지는 표로 보면 이렇다.

| 지표 | 높으면 | 설계 방향 |
|---|---|---|
| Fan-in | 여러 곳에서 재사용되는 공통 모듈. 바람직하지만 그 모듈이 바뀌면 영향 범위가 넓음 | 높게 |
| Fan-out | 한 모듈이 너무 많은 하위 모듈을 통제함. 복잡도 증가 | 낮게. 적정 수를 넘으면 중간 모듈로 묶음 |

아래 코드에서는 함수 호출 하나가 구조도의 화살표 하나에 해당한다.

```java
void a() { f(); }
void b() { f(); }             // f를 부르는 쪽이 a, b 둘이니 f의 Fan-in은 2
void f() { x(); y(); z(); }   // f가 부르는 쪽이 x, y, z 셋이니 f의 Fan-out은 3
```

같은 모듈 f라도 들어오는 화살표(a, b)를 세면 Fan-in, 나가는 화살표(x, y, z)를 세면 Fan-out이라 값이 다르다. 한글 이름도 거꾸로 외우기 쉬운데, "공유도"는 여러 곳이 함께 쓴다는 뜻이므로 들어오는 쪽(Fan-in), "제어도"는 아래를 거느린다는 뜻이므로 나가는 쪽(Fan-out)으로 기억한다.

구조도를 읽을 때는 모듈 이름에 신경 쓰지 말고, 그 모듈로 들어오는 화살표와 나가는 화살표를 따로 센다. 세는 법과 그림 예는 [계산] 페이지에 따로 정리해 두었다.

### 기출에서 이렇게 나왔다
- 22-2: 모듈 다이어그램 → 모듈 F의 Fan-in **3**, Fan-out **2**
- 20-1: Fan-in이 2 이상인 모듈 → **F, H**

## UML 다이어그램
출제: 25-3, 23-3, 22-3, 21-3, 20-4
형태: 그림 또는 설명 → 다이어그램 이름. 구성요소 3개 중 빈칸 채우기

### 개념
UML을 이루는 구성요소는 **사물(Things)**, **관계(Relationships)**, **다이어그램(Diagrams)** 세 가지다. 22-3에서는 이 중 "관계"가 빈칸으로 나왔다. 사물은 다시 네 종류로 나뉘는데, 아래 표와 같다.

| 사물 종류 | 내용 |
|---|---|
| 구조 사물 | 정적인 요소. 클래스, **인터페이스**, 유스케이스, 컴포넌트, 노드 등 |
| 행동 사물 | 시간과 공간에 따른 동작. 상호작용(메시지), 상태 머신 |
| 그룹 사물 | 요소를 묶는 단위. 패키지 |
| 주해 사물 | 부가 설명. 노트(note) |

구조 사물 중 **인터페이스(Interface)** 는 22-3 세 번째 빈칸의 답으로 나왔다. 인터페이스란 클래스나 컴포넌트가 외부에 보이는 동작(오퍼레이션)의 집합만 정의해 둔 것을 말한다. 인터페이스는 혼자서 쓰이지 않고, 그것을 구현하는 클래스·컴포넌트와 함께 쓴다.

다이어그램은 크게 둘로 나뉜다. 정적 구조를 그리는 구조(정적) 다이어그램이 6종, 동작을 그리는 행위(동적) 다이어그램이 7종이다. 사실 UML 2.5 표준은 구조 쪽에 프로파일(Profile) 다이어그램을 하나 더 두어서 모두 14종인데, 수험서는 보통 구조 6·행위 7로 정리한다. 요약 자료에 따라서는 상호작용 개요를 빼고 행위를 6종으로 적기도 하니, 숫자가 다르게 보여도 당황하지 않아도 된다.

먼저 구조 다이어그램 6종이다.

| 다이어그램 | 무엇을 그리나 | 단서 |
|---|---|---|
| **클래스(Class)** | 클래스의 속성·오퍼레이션과 클래스 간 관계. 시스템(도메인) 구조 | "속성과 메서드", "클래스 간 관계", "정적 구조" |
| **객체(Object)** | 특정 시점의 인스턴스와 그 관계. 클래스 다이어그램의 스냅샷 | "인스턴스", "특정 시점" |
| **컴포넌트(Component)** | 컴포넌트와 그 사이 인터페이스·의존 | "컴포넌트", "제공·요구 인터페이스" |
| **배치(Deployment)** | 노드(하드웨어)와 그 위에 놓인 산출물 | "물리적 배치", "노드" |
| **복합체 구조(Composite Structure)** | 클래스·컴포넌트의 내부 구조 | "내부 구조", "포트" |
| **패키지(Package)** | 요소를 패키지로 묶고 패키지 간 의존(import, access)을 표현. 유스케이스나 클래스 같은 요소를 그룹화 | 접힌 폴더 모양, 점선 화살표에 <<import>> |

다음은 행위 다이어그램 7종이다.

| 다이어그램 | 무엇을 그리나 | 단서 |
|---|---|---|
| **유스케이스(Use Case)** | 액터와 시스템 기능, include·extend 관계 | "사용자 관점", "액터" |
| **시퀀스(Sequence)** | 객체 간 메시지를 시간 순(세로축)으로 | "시간 순서", "생명선", "메시지" |
| **커뮤니케이션(Communication)** | 시퀀스와 같은 정보를 객체 연결선 위의 번호 메시지로. 구 협력(Collaboration) 다이어그램 | "객체 간 연관과 메시지", "번호" |
| **상태(State)** | 한 객체의 상태 변화와 전이 이벤트 | "상태 전이", "이벤트" |
| **활동(Activity)** | 처리 흐름. 분기·병합·스윔레인 | "흐름도와 유사", "병렬 처리" |
| **타이밍(Timing)** | 시간 제약에 따른 상태 변화 | "시간 제약" |
| **상호작용 개요(Interaction Overview)** | 활동 다이어그램 안에 시퀀스 등 상호작용을 노드로 배치 | "상호작용을 개요 수준에서" |

두음은 구조가 "클객컴배복패", 행위가 "유시커상활타상"이다.

행위 다이어그램 중 유스케이스 다이어그램은 구성요소와 관계까지 알아 두면 좋다. 표로 정리하면 이렇다.

| 요소·관계 | 표기 | 의미 |
|---|---|---|
| **액터(Actor)** | 막대 인간 | 시스템과 상호작용하는 사용자나 외부 시스템 |
| **유스케이스(Use Case)** | 타원 | 시스템이 제공하는 기능 단위 |
| **시스템 경계** | 사각형 | 시스템 범위 |
| 연관 | 실선 | 액터와 유스케이스 연결 |
| **포함(Include)** | 점선 화살표 + <<include>> | 기본 유스케이스를 실행하면 반드시 함께 실행되는 기능 |
| **확장(Extend)** | 점선 화살표 + <<extend>> | 특정 조건에서만 선택적으로 실행되는 기능 |
| 일반화 | 실선 + 빈 삼각형 | 공통 기능을 상위 유스케이스·액터로 추상화 |

### 다이어그램 하나씩 보기
13종을 모두 같은 무게로 볼 필요는 없다. 기출 정답으로 나온 클래스·패키지와, 서로 헷갈리기 쉬운 것들(객체와 클래스, 컴포넌트와 배치, 시퀀스와 커뮤니케이션, 상태와 활동)만 온라인 쇼핑몰 하나를 예로 들어 그림 모양까지 정리했다. 나머지(복합체 구조, 타이밍, 상호작용 개요)는 위 표의 단서로 충분하다.

#### 1. 클래스 다이어그램 (Class Diagram)
- 클래스의 **속성·오퍼레이션**과 클래스 간 관계, 시스템(도메인)의 정적 구조
- 세 칸(이름·속성·메서드)으로 나뉜 상자
- 지문 단서: "속성과 메서드", "클래스 간 관계", "정적 구조"

```text
+------------------+
| Member           |   이름
+------------------+
| - id : String    |   속성
+------------------+
| + order() : void |   오퍼레이션
+------------------+
```

21-3과 22-3에서 "속성·오퍼레이션(메서드)을 포함한다"는 말이 그대로 단서였다.

#### 2. 객체 다이어그램 (Object Diagram)
- **특정 시점의 인스턴스**와 그 관계, 클래스 다이어그램의 스냅샷
- 지문 단서: "인스턴스", "특정 시점"

```text
kim : Member  -----  o1 : Order
```

클래스 다이어그램이 "회원은 주문을 가진다"는 틀이라면, 객체 다이어그램은 "지금 kim 회원이 주문 o1을 가지고 있다"는 한 장면이다.

#### 3. 패키지 다이어그램 (Package Diagram)
- 요소를 **패키지로 묶고** 패키지 간 의존(import, access)을 표현
- 유스케이스나 클래스 같은 요소의 그룹화
- 그림 단서: 접힌 폴더 모양 상자, 점선 화살표에 <<import>>

```text
[ui] - - - <<import>> - - -> [order] - - - <<import>> - - -> [db]
```

23-3·25-3·20-4 세 번 모두 그림으로 나왔다. 폴더 탭이 달린 상자와 <<import>> 점선 화살표, 이 두 모양을 눈에 익혀 둔다.

#### 4. 컴포넌트 다이어그램 (Component Diagram)
- **컴포넌트**와 그 사이의 인터페이스·의존
- 지문 단서: "컴포넌트", "제공·요구 인터페이스"

예를 들어 결제 컴포넌트가 "결제" 인터페이스를 제공하고, 주문 컴포넌트가 그 인터페이스를 요구하는 관계를 그린다. 패키지는 요소를 묶는 그룹일 뿐이고, 컴포넌트는 실제로 조립되는 소프트웨어 부품이다.

#### 5. 배치 다이어그램 (Deployment Diagram)
- **노드(하드웨어)**와 그 위에 놓인 산출물
- 지문 단서: "물리적 배치", "노드"

예를 들어 "웹 서버" 노드 위에 쇼핑몰 애플리케이션을, "DB 서버" 노드 위에 데이터베이스를 올려 두고 두 노드를 선으로 잇는다. 소프트웨어끼리의 관계는 컴포넌트 다이어그램이 맡고, 그 소프트웨어가 어느 장비에 올라가는지는 배치 다이어그램이 그린다.

#### 6. 유스케이스 다이어그램 (Use Case Diagram)
- **액터**와 시스템 기능, include·extend 관계, 사용자 관점
- 지문 단서: "사용자 관점", "액터"

```text
고객(액터) ----- (주문하기) - - <<include>> - -> (로그인)
                 (주문하기) <- - <<extend>> - - (쿠폰 적용)
```

주문할 때 로그인은 빠짐없이 함께 실행되는 기능이라 포함(include)으로 잇는다. 쿠폰 적용은 쿠폰이 있을 때만 선택적으로 실행되므로 확장(extend)이다.

#### 7. 시퀀스 다이어그램 (Sequence Diagram)
- 객체 간 메시지를 **시간 순서(세로축)**로 표현
- 지문 단서: "시간 순서", "생명선", "메시지"

```text
Member        Order        Payment
  |  order()    |             |
  |------------>|   pay()     |
  |             |------------>|
  |             |<- - - - - - |
  |<- - - - - - |             |
```

각 객체 아래로 내려가는 세로선이 생명선이다(실제 그림에서는 점선). 위에서 아래로 내려갈수록 나중에 오간 메시지다.

#### 8. 커뮤니케이션 다이어그램 (Communication Diagram)
- 시퀀스와 같은 정보를 **객체 연결선 위의 번호 메시지**로 표현
- 예전 이름: 협력(Collaboration) 다이어그램
- 지문 단서: "객체 간 연관과 메시지", "번호"

```text
Member --1: order()--> Order --2: pay()--> Payment
```

시퀀스 다이어그램은 세로축이 시간이라 위에서 아래로 읽으면 순서가 보인다. 커뮤니케이션 다이어그램은 시간축이 없어서 순서를 `1: order()`, `2: pay()`처럼 번호로 적고, 대신 Member, Order, Payment가 서로 어떻게 연결되어 있는지가 잘 드러난다.

#### 9. 상태 다이어그램 (State Diagram)
- **한 객체의 상태 변화**와 전이를 일으키는 이벤트
- 지문 단서: "상태 전이", "이벤트"

```text
[주문됨] --결제--> [결제완료] --발송--> [배송중] --도착--> [배송완료]
```

그림 전체가 주문 객체 하나의 상태 변화다. 화살표 위에는 상태를 바꾸는 이벤트(결제, 발송, 도착)를 적는다.

#### 10. 활동 다이어그램 (Activity Diagram)
- 처리 흐름, 분기·병합·스윔레인
- 지문 단서: "흐름도와 유사", "병렬 처리"

```text
(시작) -> 장바구니 확인 -> <재고 있음?> --예--> 결제 -> (끝)
                                     --아니오--> 품절 안내 -> (끝)
```

상태 다이어그램이 한 객체가 "어떤 상태에 있는가"를 그린다면, 활동 다이어그램은 일이 "어떤 순서로 처리되는가"를 순서도처럼 그린다.

답은 "패키지"만 쓰지 말고 "패키지 다이어그램"까지 쓰는 편이 안전하다. 그림을 보고 고르는 문제라면 상자 모양부터 본다. 폴더 탭 모양 상자와 <<import>> 점선 화살표가 있으면 패키지이고, 상자가 세 칸(이름·속성·메서드)으로 나뉘어 있으면 클래스다.

## UML 클래스 다이어그램 관계
출제: 24-3, 21-3
형태: 관계 설명 2~3개 → 보기(한글 또는 영문)

### 개념
| 관계 | 의미 | 표기 | 단서 |
|---|---|---|---|
| **연관(Association)** | 서로 참조하는 일반적인 관계. 다중성(1, 0..*, 1..*)을 적음 | 실선. 방향이 있으면 화살표 | "관련이 있다", "다중성" |
| **집합(Aggregation)** | 전체-부분 관계. 부분이 전체 없이도 존재 가능 | 전체 쪽에 빈 마름모 + 실선 | "포함하지만 독립적", "공유 가능" |
| **포함(Composition)** | 전체-부분 관계. 부분의 생명주기가 전체에 종속 | 전체 쪽에 채운 마름모 + 실선 | "전체가 사라지면 부분도 사라짐", "강한 소유" |
| **일반화(Generalization)** | 상속. is-a | 자식에서 부모로 빈 삼각형 화살표, 실선 | "상위·하위", "일반적인 것과 구체적인 것" |
| **의존(Dependency)** | 한쪽이 바뀌면 다른 쪽이 영향을 받음. 매개변수·지역 변수로 잠깐 사용 | 점선 화살표 | "일시적으로 사용", "짧은 시간 동안만 연관", "영향을 받음" |
| **실체화(Realization)** | 인터페이스를 클래스가 구현. can-do | 점선 + 빈 삼각형 | "인터페이스 구현", "기능을 실제로 수행", "기능으로 묶인 관계" |

두음은 "포집 연의 일실"이다. 그냥 외우기보다 두 개씩 짝을 지어 보면 표기까지 한 번에 정리된다. 포함·집합은 마름모로 그리는데, 채우면 포함이고 비우면 집합이며 둘 다 실선이다. 연관·의존은 선으로 가르는데, 실선이면 연관이고 점선 화살표면 의존이다. 일반화·실체화는 둘 다 빈 삼각형이라 선으로 구분하는데, 실선이면 일반화, 점선이면 실체화다. 그리고 각 쌍에서는 앞에 오는 쪽이 더 강한 관계다.

클래스 다이어그램을 읽으려면 기초 표기도 알아야 한다.

| 표기 | 의미 |
|---|---|
| **가시성(Visibility)** | `+` public, `-` private, `#` protected, `~` package |
| **다중성(Multiplicity)** | `1` 정확히 하나, `0..1` 없거나 하나, `*` 또는 `0..*` 0개 이상, `1..*` 1개 이상, `n..m` n개 이상 m개 이하 |
| **스테레오타입(Stereotype)** | 기존 요소에 의미를 덧붙이는 확장 표기. 길러멧 `<< >>` 안에 쓴다. 예: <<interface>>, <<include>>, <<extend>> |

```mermaid
제목: 화살표 모양으로 관계를 구분한다. 속 찬 마름모 = 포함, 빈 마름모 = 집합, 빈 삼각형 실선 = 일반화, 빈 삼각형 점선 = 실체화
%% 폰: LR
classDiagram
  direction TB
  Car *-- Engine : 포함
  Team o-- Player : 집합
  Teacher --> Student : 연관
  Order ..> Payment : 의존
  Animal <|-- Dog : 일반화
  Flyable <|.. Bird : 실체화
```

### 관계 하나씩 보기
표기만 외우면 지문 문장과 연결이 잘 안 된다. 그래서 바로 위 그림의 클래스 이름(Teacher, Team, Car 등)을 그대로 써서, 각 관계가 Java 코드에서 어떤 모습인지 하나씩 붙였다.

#### 1. 연관 (Association)
- 서로 참조하는 **일반적인 관계**, 다중성(1, 0..*, 1..*) 표기
- 표기: 실선, 방향이 있으면 화살표
- 지문 단서: "관련이 있다", "다중성"

```java
class Teacher {
    List<Student> students;   // 멤버 변수로 계속 참조한다
}
```

Teacher가 students를 필드(멤버 변수)로 두고 계속 참조하는 모습이 연관이다. 메서드 안에서 잠깐 쓰고 마는 의존과는 바로 이 점에서 갈린다.

#### 2. 집합 (Aggregation)
- **전체-부분** 관계, 부분이 전체 없이도 존재 가능
- 표기: 전체 쪽에 빈 마름모 + 실선
- 지문 단서: "포함하지만 독립적", "공유 가능"

```java
class Team {
    List<Player> players;
    Team(List<Player> players) { this.players = players; }   // 바깥에서 만든 선수를 받아 온다
}
// 팀이 없어져도 Player 객체는 바깥에 그대로 남는다
```

Team은 Player를 직접 만들지 않고 생성자로 바깥에서 받아 온다. 그래서 팀이 해체돼도 Player 객체는 남고, 다른 팀에 들어갈 수도 있다.

#### 3. 포함 (Composition)
- **전체-부분** 관계, 부분의 생명주기가 전체에 종속
- 표기: 전체 쪽에 채운 마름모 + 실선
- 지문 단서: "전체가 사라지면 부분도 사라짐", "강한 소유"

```java
class Car {
    private final Engine engine = new Engine();   // 차가 생길 때 엔진도 안에서 함께 만든다
}
// 바깥에서는 이 Engine을 가리킬 수 없으니, Car가 없어지면 Engine도 함께 없어진다
```

집합의 Team은 Player를 바깥에서 받아 왔지만, 포함의 Car는 Engine을 안에서 직접 만든다. 이 Engine은 Car만 참조하므로 Car와 함께 생기고 함께 없어진다.

#### 4. 일반화 (Generalization)
- **상속**(is-a)
- 표기: 자식에서 부모로 빈 삼각형 화살표, 실선
- 지문 단서: "상위·하위", "일반적인 것과 구체적인 것"

```java
class Dog extends Animal { }   // 개는 동물이다(is-a)
```

Animal이 일반적인 쪽, Dog가 구체적인 쪽이다. 그림에서는 자식(Dog)에서 부모(Animal) 쪽으로 화살표를 긋고, 빈 삼각형 머리를 부모 쪽에 붙인다.

#### 5. 의존 (Dependency)
- 한쪽이 바뀌면 다른 쪽이 영향을 받는 관계, 매개변수·지역 변수로 **잠깐 사용**
- 표기: 점선 화살표
- 지문 단서: "일시적으로 사용", "짧은 시간 동안만 연관", "영향을 받음"

```java
class Order {
    void checkout(Payment p) {   // 매개변수로 받아서 잠깐 쓰고 끝난다
        p.pay();
    }
}
```

Order는 Payment를 필드로 들고 있지 않다. 그래도 Payment의 `pay()`가 바뀌면 Order 코드도 영향을 받으니 의존이다.

#### 6. 실체화 (Realization)
- **인터페이스를 클래스가 구현**하는 관계(can-do)
- 표기: 점선 + 빈 삼각형
- 지문 단서: "인터페이스 구현", "기능을 실제로 수행", "기능으로 묶인 관계"

```java
interface Flyable { void fly(); }
class Bird implements Flyable {   // 새는 날 수 있다(can-do)
    public void fly() { }
}
```

일반화와 똑같이 빈 삼각형을 쓰지만, `extends`(상속)면 실선, `implements`(구현)면 점선이다.

### 한눈에 구분
| 혼동 쌍 | 가르는 기준 |
|---|---|
| 집합 vs 포함 | 마름모가 비었으면 집합, 채워졌으면 포함. 부분이 전체 없이 살 수 있으면 집합 |
| 연관 vs 의존 | 멤버 변수로 계속 참조하면 연관(실선), 메서드 안에서 잠깐 쓰면 의존(점선) |
| 일반화 vs 실체화 | 둘 다 빈 삼각형. 실선이면 일반화(상속), 점선이면 실체화(인터페이스 구현) |

### 기출에서 이렇게 나왔다
- 24-3: 설명 3개 → **연관 / 일반화 / 의존**
- 21-3: 설명 2개 → **Aggregation / Generalization** (영문)

### 답 쓸 때
같은 관계를 다른 이름으로 부르기도 한다. 집합은 집약, 포함은 복합·합성이라고도 한다. 보기에 이 이름으로 나와도 같은 관계다. 영문을 요구하는 문제라면 Aggregation, Composition, Generalization, Realization의 철자를 그대로 쓴다.

## 요구사항 분류
출제: 26-1, 21-1
형태: 사례 3개 → 비기능 요구사항 유형 보기 / 설명 2개 → 기능·비기능 구분

### 개념
요구사항은 크게 두 가지로 나뉜다. **기능 요구사항(Functional)** 은 시스템이 "무엇을" 해야 하는가를 말하고, 입력·출력·처리·제공 기능이 여기 속한다. 반면 **비기능 요구사항(Non-functional)** 은 그 일을 "어떤 수준과 조건으로" 해야 하는가를 말한다. 품질이나 제약 사항에 관한 것이라서 시스템 장비 구성·성능·인터페이스·테스트·보안 요구사항이 여기 든다.

예를 들어 쇼핑몰 요구사항이 두 줄 있다. "회원은 상품을 장바구니에 담을 수 있어야 한다"는 시스템이 하는 일 자체를 말하니 기능 요구사항이다. 반면 "장바구니 화면은 2초 이내에 떠야 한다"는 같은 일을 얼마나 빨리 하느냐를 정한 조건이라서 비기능 요구사항, 그중에서도 성능에 든다.

비기능 요구사항은 다시 6가지 유형으로 나눈다.

| 유형 | 내용 | 사례 단서 |
|---|---|---|
| **운영** | 운영 환경·시간·인력에 관한 조건 | "24시간 무중단", "특정 OS 환경에서 운영" |
| **자원** | 하드웨어·메모리·저장 공간·네트워크 등 자원 조건 | "메모리 n GB 이상", "디스크 용량" |
| **성능** | 응답 시간·처리량·동시 사용자 수 | "n초 이내 응답", "동시 접속 n명" |
| **보안** | 접근 통제·암호화·인증 | "암호화 저장", "권한 없는 접근 차단" |
| **품질** | 신뢰성·가용성·사용성·유지보수성 | "가용성 n%", "장애 복구" |
| **문화·정책** | 법·규정·조직 정책·문화적 제약 | "개인정보보호법 준수", "다국어 지원" |

요구사항을 개발하는 과정, 곧 요구공학 프로세스는 도출(Elicitation), 분석(Analysis), 명세(Specification), 확인(Validation) 순서로 진행한다. 단계별로 어떤 기법을 쓰는지는 파일 끝 "요구사항 도출·명세 기법과 구조적 분석 도구" 묶음에서 다룬다.

### 비기능 요구사항 하나씩 보기
26-1처럼 요구사항 문장을 주고 유형을 고르게 하는 문제가 나오므로, 유형마다 요구사항 문장을 하나씩 붙였다.

#### 1. 운영 요구사항
- 운영 **환경·시간·인력**에 관한 조건
- 사례 단서: "24시간 무중단", "특정 OS 환경에서 운영"

> 시스템은 Linux 서버에서 24시간 무중단으로 운영되어야 한다.

"언제, 어떤 환경에서 돌아가느냐"를 말하면 운영이다.

#### 2. 자원 요구사항
- **하드웨어·메모리·저장 공간·네트워크** 등 자원 조건
- 사례 단서: "메모리 n GB 이상", "디스크 용량"

> 서버는 메모리 16GB 이상, 디스크 1TB 이상을 갖춰야 한다.

메모리, 디스크 같은 장비의 수치가 나오면 자원이다. 같은 수치라도 "3초 이내", "동시 접속 1,000명"처럼 시간이나 건수를 재면 성능이다.

#### 3. 성능 요구사항
- **응답 시간·처리량·동시 사용자 수**에 관한 조건
- 사례 단서: "n초 이내 응답", "동시 접속 n명"

> 상품 검색 결과는 3초 이내에 보여야 하고, 동시 접속 1,000명을 처리해야 한다.

얼마나 빨리, 얼마나 많이 처리하느냐를 말하므로 성능이다.

#### 4. 보안 요구사항
- **접근 통제·암호화·인증**에 관한 조건
- 사례 단서: "암호화 저장", "권한 없는 접근 차단"

> 비밀번호는 암호화해 저장하고, 관리자 권한이 없는 사용자는 관리 화면에 접근할 수 없어야 한다.

#### 5. 품질 요구사항
- **신뢰성·가용성·사용성·유지보수성**에 관한 조건
- 사례 단서: "가용성 n%", "장애 복구"

> 시스템 가용성은 99.9% 이상이어야 하고, 장애가 나면 자동으로 복구되어야 한다.

운영의 "24시간 무중단"과 비슷해 보인다. 운영 요구사항은 "언제, 어떤 환경에서" 돌리는지를 정하고, 품질 요구사항은 "가용성 99.9%"처럼 가용성·신뢰성 같은 품질 특성의 목표를 정한다. 지문에 "가용성", "장애 복구"처럼 품질 특성 이름이 보이면 품질이다.

#### 6. 문화·정책 요구사항
- **법·규정·조직 정책·문화적 제약**에 관한 조건
- 사례 단서: "개인정보보호법 준수", "다국어 지원"

> 회원 정보 처리는 개인정보보호법을 따라야 하고, 화면은 한국어와 영어를 지원해야 한다.

### 기출에서 이렇게 나왔다
- 26-1: 사례 3개 → **운영 / 자원 / 성능**
- 21-1: 설명 2개 → **기능적 / 비기능적**

### 답 쓸 때
사례를 주고 유형을 고르는 문제라면 사례에 무엇이 적혀 있는지부터 본다. "시간·환경"이 보이면 운영, "하드웨어 수치"가 보이면 자원, "응답·처리 속도"가 보이면 성능으로 먼저 가른다.

## UI 설계 원칙
출제: 21-2, 20-3, 20-2
형태: 한 줄 설명 → 원칙 이름 또는 영문 약어

### 개념
화면을 아무리 예쁘게 만들어도 사용자가 헤매면 소용이 없다. 그래서 UI를 설계할 때 지켜야 할 기본 원칙 네 가지를 정해 두는데, 표로 보면 이렇다.

| 원칙 | 내용 | 단서 |
|---|---|---|
| **직관성(Intuitiveness)** | 누구나 쉽게 이해하고 사용할 수 있어야 한다 | "쉽게 이해", "누구나" |
| **유효성(Validity)** | 사용자의 목표를 정확하고 완벽하게 달성할 수 있어야 한다. 20-2 기출 정답표의 영문 표기가 Validity다 | "정확하고 완벽하게", "목표 달성" |
| **학습성(Learnability)** | 누구나 쉽게 배우고 익힐 수 있어야 한다 | "쉽게 배움", "익힘" |
| **유연성(Flexibility)** | 사용자의 요구를 수용하고 실수를 최소화해야 한다 | "요구 수용", "실수 방지" |

### 원칙 하나씩 보기

#### 1. 직관성 (Intuitiveness)
- **누구나 쉽게 이해하고 사용**할 수 있어야 함
- 지문 단서: "쉽게 이해", "누구나"

> 처음 앱을 연 사람도 휴지통 아이콘을 보고 설명 없이 "삭제"라는 걸 안다.

20-3에서 정답으로 나왔다. 휴지통 아이콘처럼 배우는 과정 없이 보자마자 알아들으면 직관성이고, 써 보면서 익히는 학습성과는 여기서 갈린다.

#### 2. 유효성 (Validity)
- 사용자의 **목표를 정확하고 완벽하게 달성**할 수 있어야 함
- 영문: Validity (20-2 기출 정답표 표기)
- 지문 단서: "정확하고 완벽하게", "목표 달성"

> 송금 화면에서 받는 사람과 금액을 입력하고 끝까지 마치면, 원하는 사람에게 원하는 금액이 정확히 보내진다.

쓰기 편한가보다 "하려던 일을 제대로 끝낼 수 있는가"를 보는 원칙으로, 20-2 지문이 바로 이 내용이었다.

#### 3. 학습성 (Learnability)
- 누구나 **쉽게 배우고 익힐** 수 있어야 함
- 지문 단서: "쉽게 배움", "익힘"

> 처음에는 안내 화면을 따라 하지만, 두세 번 써 보면 안내 없이도 혼자 쓸 수 있다.

직관성처럼 "누구나 쉽게"로 시작하지만, 학습성은 위 예처럼 두세 번 써 보면서 익힌다는 데 무게가 있다.

#### 4. 유연성 (Flexibility)
- 사용자의 **요구를 수용**하고 **실수를 최소화**해야 함
- 지문 단서: "요구 수용", "실수 방지"

> 파일을 지우기 전에 확인 창을 띄우고, 지운 뒤에도 되돌리기를 할 수 있게 해 둔다.

사용자가 잘못 눌러도 받아 줄 여지를 두는 것이 유연성이다.

### UI와 UX, 화면 산출물
21-2에서는 UI와 UX를 영문 약어로 구분하는 문제가 나왔다. **UI(User Interface)** 란 사용자와 시스템이 만나는 접점, 곧 화면이나 조작 수단을 말한다. 반면 **UX(User Experience)** 는 그 제품을 사용하면서 느끼는 총체적 경험·반응·감정이다. UI를 설계할 때 따르는 지침으로는 사용자 중심, 일관성, 단순성, 결과 예측 가능, 가시성, 표준화, 접근성, 명확성, 오류 발생 해결 등이 있다.

UI 시나리오 문서를 쓸 때 갖춰야 할 요건은 완전성·일관성·이해성·가독성·수정 용이성·추적 용이성이다. 그리고 화면 설계의 기본 구성 요소는 윈도우·메뉴·아이콘·포인터로, 앞글자를 따서 WIMP라고 부른다.

화면 시안은 한 번에 완성하지 않고 단계를 밟아 만든다. 실제 완성품과 닮은 정도를 충실도라고 하는데, 충실도가 낮은 것부터 와이어프레임, 목업, 프로토타입 순서로 만든다. 스토리보드는 이렇게 만든 화면 설계에 설명·흐름·정책을 더한 최종 참고 문서이고, 유스케이스는 사용자 요구를 시나리오로 적은 것이다.

| 산출물 | 내용 |
|---|---|
| **와이어프레임(Wireframe)** | 선과 상자로 화면 뼈대·레이아웃만 잡은 것. 색·디자인 없음 |
| **목업(Mockup)** | 와이어프레임에 색·이미지·글꼴을 입힌 정적 시안. 동작하지 않음 |
| **프로토타입(Prototype)** | 클릭·화면 전환이 실제로 되는 동작 모형 |
| **스토리보드(Storyboard)** | 화면 설계에 설명과 화면 흐름까지 담은 최종 문서. 디자이너·개발자가 함께 보는 지침서 |
| 유스케이스 명세 | 사용자와 시스템의 상호작용 시나리오를 글로 쓴 것 |

### 기출에서 이렇게 나왔다
- 21-2: 설명 2개 → **UX / UI** (영문 약어)
- 20-3: "누구나 쉽게 이해하고 사용" → **직관성**
- 20-2: "정확하고 완벽하게 목표 달성" → **유효성**

### 답 쓸 때
직관성과 학습성은 둘 다 "누구나 쉽게"로 시작해서 헷갈리기 쉬운데, 지문에 "이해"가 있으면 직관성, "배움"이 있으면 학습성으로 가른다. 유효성과 효율성도 혼동하기 쉬운데, 효율성(Efficiency)은 ISO 9126의 품질 특성으로, 유효성과는 다른 말이니 바꿔 쓰지 않는다. 유효성을 영문으로 쓸 때는 Validity다.

## UI 종류
출제: 22-1, 21-3
형태: 한 줄 설명 → 영문 약어

### 개념
| 종류 | 내용 | 단서 |
|---|---|---|
| **CLI(Command Line Interface)** | 명령어를 텍스트로 입력 | "명령어", "텍스트" |
| **GUI(Graphical User Interface)** | 아이콘·메뉴·마우스를 쓰는 그래픽 환경 | "그래픽", "아이콘·메뉴" |
| **NUI(Natural User Interface)** | 말·몸짓·터치 등 사람의 자연스러운 행동으로 상호작용 | "자연스러운 표현", "말·행동" |
| **OUI(Organic User Interface)** | 현실의 사물 자체가 입출력 장치가 되는 유기적 인터페이스 | "사물 자체", "유기적" |
| **VUI(Voice User Interface)** | 음성으로 상호작용 | "음성" |

### 종류 하나씩 보기
다섯 가지 모두 영문 약어로 답한다. 약어를 풀어 쓴 이름과 쓰이는 장면을 함께 적었다.

#### 1. CLI (Command Line Interface)
- 명령어를 **텍스트로 입력**하는 방식
- 지문 단서: "명령어", "텍스트"

```text
$ ls -l
$ cd /home/user
```

마우스 없이 키보드로 명령을 쳐서 결과를 글자로 받는다.

#### 2. GUI (Graphical User Interface)
- **아이콘·메뉴·마우스**를 쓰는 그래픽 환경
- 지문 단서: "그래픽", "아이콘·메뉴"

> 바탕화면의 폴더 아이콘을 마우스로 더블클릭해서 연다.

같은 "폴더 열기"라도 CLI는 `cd` 명령으로, GUI는 아이콘 클릭으로 한다. 21-3에서는 "그래픽, 메뉴·아이콘"이 단서였다.

#### 3. NUI (Natural User Interface)
- 말·몸짓·터치 등 **사람의 자연스러운 행동**으로 상호작용
- 지문 단서: "자연스러운 표현", "말·행동"

> 스마트폰 사진을 두 손가락으로 벌려 확대하고, 손을 흔들어 화면을 넘긴다.

22-1에서 정답으로 나왔다. NUI에도 말이 들어가지만 몸짓·터치까지 아우르는 넓은 개념이고, VUI는 음성 하나만 가리킨다.

#### 4. OUI (Organic User Interface)
- 현실의 **사물 자체가 입출력 장치**가 되는 유기적 인터페이스
- 지문 단서: "사물 자체", "유기적"

> 휘어지는 디스플레이를 구부리는 동작이 그대로 입력이 되고, 구부러진 표면이 그대로 화면이 된다.

NUI는 두 손가락으로 벌리기, 손 흔들기처럼 사람의 행동에 초점을 두고, OUI는 휘어지는 디스플레이처럼 입출력을 맡는 사물 쪽에 초점을 둔다.

#### 5. VUI (Voice User Interface)
- **음성**으로 상호작용
- 지문 단서: "음성"

> AI 스피커에게 "오늘 날씨 알려 줘"라고 말하면 음성으로 대답한다.

- 21-3: "그래픽, 메뉴·아이콘" → **GUI**

## 객체지향 SOLID
출제: 22-2
형태: 한 원칙 설명 2줄 + 예시 → 보기

### 개념
SOLID란 객체지향 설계에서 변경에 강한 클래스를 만들려고 지키는 다섯 원칙의 앞글자를 모은 말이다. 원칙마다 붙인 짧은 코드는 표 아래에 있다.

| 원칙 | 내용 | 단서 |
|---|---|---|
| **SRP(Single Responsibility)** 단일 책임 | 클래스를 변경하는 이유는 하나여야 한다 | "책임 하나", "변경 이유" |
| **OCP(Open-Closed)** 개방-폐쇄 | 확장에는 열려 있고 수정에는 닫혀 있어야 한다 | "기존 코드 수정 없이 확장" |
| **LSP(Liskov Substitution)** 리스코프 치환 | 자식 클래스는 부모 클래스를 대체할 수 있어야 한다 | "하위 타입으로 치환" |
| **ISP(Interface Segregation)** 인터페이스 분리 | 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눈다 | "사용하지 않는 인터페이스", "복합기(인쇄·복사·팩스) 예" |
| **DIP(Dependency Inversion)** 의존 역전 | 구체 클래스가 아니라 추상(인터페이스)에 의존한다. 고수준 모듈이 저수준 모듈에 직접 의존하지 않는다 | "추상에 의존", "구체에 의존하지 않음", "고수준이 저수준에 의존하지 않음" |

### 원칙 하나씩 보기

#### 1. SRP, 단일 책임 원칙 (Single Responsibility Principle)
- 클래스를 **변경하는 이유는 하나**
- 지문 단서: "책임 하나", "변경 이유"

```java
class Report {              // 보고서 내용을 만드는 책임만
    String build() { /* ... */ return ""; }
}
class ReportPrinter {       // 출력 방식이 바뀌면 이 클래스만 고친다
    void print(Report r) { /* ... */ }
}
```

내용을 만드는 일과 출력하는 일을 한 클래스에 두면, 둘 중 무엇이 바뀌어도 그 클래스를 고쳐야 한다. 그래서 변경 이유마다 클래스를 나눈다.

#### 2. OCP, 개방-폐쇄 원칙 (Open-Closed Principle)
- **확장에는 열려** 있고 **수정에는 닫혀** 있음
- 지문 단서: "기존 코드 수정 없이 확장"

```java
interface Discount { int apply(int price); }
class VipDiscount implements Discount { public int apply(int p) { return p * 9 / 10; } }
class StudentDiscount implements Discount { public int apply(int p) { return p - 1000; } }
// 할인 종류가 늘면 클래스를 하나 더 만들 뿐, Discount를 쓰는 계산 코드는 고치지 않는다
```

확장(StudentDiscount 같은 새 할인 클래스 추가)에는 열려 있고, 수정(이미 돌아가는 계산 코드 고치기)에는 닫혀 있다는 뜻이다.

#### 3. LSP, 리스코프 치환 원칙 (Liskov Substitution Principle)
- **자식 클래스는 부모 클래스를 대체** 가능해야 함
- 지문 단서: "하위 타입으로 치환"

```java
Bird b = new Sparrow();   // 부모 타입 자리에 자식 객체를 넣어도
b.fly();                  // 프로그램이 그대로 올바르게 돌아가야 한다
```

반대로 `fly()`를 부르면 예외를 던지는 Penguin이 Bird를 상속했다고 하자. 위 코드의 `new Sparrow()`를 `new Penguin()`으로 바꾸면 b.fly()에서 예외가 나 프로그램이 깨지므로 LSP 위반이다.

#### 4. ISP, 인터페이스 분리 원칙 (Interface Segregation Principle)
- 클라이언트가 **쓰지 않는 메서드에 의존하지 않도록** 인터페이스를 작게 분리
- 지문 단서: "사용하지 않는 인터페이스", "복합기(인쇄·복사·팩스) 예"

```java
interface Printer { void print(); }
interface Copier  { void copy(); }
interface Fax     { void fax(); }

class SimplePrinter implements Printer { public void print() { } }   // 인쇄만 하는 기기
class MultiFunction implements Printer, Copier, Fax {                // 복합기는 셋 다
    public void print() { }
    public void copy() { }
    public void fax() { }
}
```

인쇄·복사·팩스를 큰 인터페이스 하나로 묶었다면, SimplePrinter처럼 인쇄만 하는 기기도 쓰지 않는 `fax()`에 의존하게 된다. 그러면 팩스 기능이 바뀔 때 SimplePrinter도 함께 영향을 받는다. 22-2 지문의 "관련 없는 인터페이스 변경에 영향을 받지 않음"이 바로 이 상황이다.

#### 5. DIP, 의존 역전 원칙 (Dependency Inversion Principle)
- 구체 클래스가 아닌 **추상(인터페이스)에 의존**
- 고수준 모듈이 저수준 모듈에 직접 의존하지 않음
- 지문 단서: "추상에 의존", "구체에 의존하지 않음", "고수준이 저수준에 의존하지 않음"

```java
class OrderService {                         // 고수준 모듈
    private final PaymentGateway gateway;    // 인터페이스에 의존한다
    OrderService(PaymentGateway g) { gateway = g; }
}
class CardPay implements PaymentGateway { /* ... */ }   // 저수준 모듈
class BankPay implements PaymentGateway { /* ... */ }
```

OrderService는 카드 결제인지 계좌 이체인지 모른다. 결제 수단을 바꿔도 OrderService 코드는 그대로다.

### 기출에서 이렇게 나왔다
- 22-2: "관련 없는 인터페이스 변경에 영향을 받지 않음, 복합기 예" → **ISP**

### 답 쓸 때
SOLID에서 많이들 헷갈리는 게 ISP와 SRP인데, 무엇을 두고 하는 말인지를 보면 갈린다. "인터페이스를 쪼갠다"면 ISP(Printer·Copier·Fax로 나눈 예)이고, "클래스의 책임 하나"면 SRP(Report와 ReportPrinter로 나눈 예)다.

## 럼바우 객체 모델링(OMT)
출제: 21-2
형태: 산출물 설명 3개 → 모델링 이름 영문

### 개념
럼바우(Rumbaugh)의 객체 모델링 기법은 세 가지 모델링으로 이루어지는데, 객체 모델링, 동적 모델링, 기능 모델링 순서로 수행한다. 각각 무엇을 그리고 무엇이 나오는지는 아래와 같다.

| 모델링 | 내용 | 산출물 |
|---|---|---|
| **객체 모델링(Object Modeling)**. 정보 모델링(Information Modeling)이라고도 함 | 객체·속성·연산과 객체 간 관계를 찾아 구조를 정의. 가장 먼저 | 객체 다이어그램(E-R 다이어그램 형태) |
| **동적 모델링(Dynamic Modeling)** | 시간 흐름에 따른 객체의 상태·이벤트·전이, 제어 흐름 | 상태 다이어그램(상태도) |
| **기능 모델링(Functional Modeling)** | 입력에서 출력까지 데이터의 흐름과 처리 | 자료 흐름도(DFD) |

### 모델링 하나씩 보기
은행 ATM 하나를 세 가지 모델링으로 차례로 그려 본다. 같은 시스템이라도 모델링마다 보는 곳이 다르다.

#### 1. 객체 모델링 (Object Modeling)
- 객체·속성·연산과 **객체 간 관계**를 찾아 구조 정의, 가장 먼저 수행
- 다른 이름: 정보 모델링(Information Modeling)
- 산출물: 객체 다이어그램(E-R 다이어그램 형태)

```text
[고객] 1 --------- * [계좌]
 이름, 전화번호        계좌번호, 잔액
```

"무엇이 있고 서로 어떻게 연결되는가"를 그리는 단계이고, 세 모델링 가운데 가장 먼저 한다.

#### 2. 동적 모델링 (Dynamic Modeling)
- 시간 흐름에 따른 객체의 **상태·이벤트·전이**, 제어 흐름
- 산출물: 상태 다이어그램(상태도)

```text
[대기] --카드 삽입--> [인증 중] --비밀번호 일치--> [거래 선택] --거래 종료--> [대기]
```

ATM이 시간에 따라 어떤 상태를 거치는지, 무슨 이벤트로 넘어가는지를 본다.

#### 3. 기능 모델링 (Functional Modeling)
- 입력에서 출력까지 **데이터의 흐름과 처리**
- 산출물: 자료 흐름도(DFD)

```text
고객 --출금 요청--> (출금 처리) --변경된 잔액--> = 계좌 파일 =
                    (출금 처리) --현금·명세표--> 고객
```

여기서는 상태가 아니라 데이터가 어디서 들어와 어떻게 바뀌어 어디로 나가는지를 본다.

두음은 순서 그대로 "객동기"다. 다른 방법론은 특징만 짧게 적어 둔다. Booch는 미시적·거시적 프로세스, Jacobson은 유스케이스 중심이 특징이다. Coad-Yourdon은 E-R 다이어그램을 활용하고, Wirfs-Brock은 분석과 설계를 구분 없이 연속으로 진행한다.

### 기출에서 이렇게 나왔다
- 21-2: DFD / 상태 다이어그램 / 객체 다이어그램 설명 → **Functional / Dynamic / Object**

### 답 쓸 때
21-2처럼 산출물 설명이 나오면 산출물을 보고 거꾸로 모델링을 맞춘다. DFD이면 기능, 상태도이면 동적, 객체 다이어그램이면 객체다.

## 애자일
출제: 20-2
형태: 특징 설명 → 용어

### 개념
**애자일(Agile)** 이란 하나의 방법론 이름이 아니라, 짧은 주기로 반복 개발하면서 고객과 소통하고 변화에 유연하게 대응하는 방법론들을 통틀어 부르는 말이다. 애자일 선언에는 4가지 가치가 있고, 넷 모두 "A를 B보다 중시한다"는 짝으로 되어 있다. 개인과 상호작용을 프로세스와 도구보다, 동작하는 소프트웨어를 포괄적 문서보다, 고객과의 협력을 계약 협상보다, 변화에 대응하는 것을 계획 준수보다 중시한다. 워터폴과 비교하면 차이가 더 잘 보인다.

| 구분 | 워터폴(폭포수) | 애자일 |
|---|---|---|
| 진행 | 단계를 순차로, 되돌아가기 어려움 | 짧은 반복(iteration)을 여러 번 |
| 중심 | 문서·계획 | 동작하는 소프트웨어·사람 |
| 변경 | 후반 변경 비용이 큼 | 변경을 수용 |
| 고객 참여 | 초기 요구 분석 위주 | 전 과정에 지속 |

예를 들어 쇼핑몰을 만든다고 해보자. 워터폴이라면 요구 분석서와 설계서를 다 쓴 뒤에 개발하고, 고객은 마지막에야 완성품을 본다. 그런데 그때 "결제 화면이 생각과 다르다"는 말이 나오면 앞 단계로 되돌아가기가 어렵다. 애자일이라면 2주쯤 되는 짧은 반복마다 회원 가입, 장바구니, 결제처럼 동작하는 기능을 하나씩 만들어 고객에게 보여 주고, 그 자리에서 나온 의견을 다음 반복에 반영한다.

애자일에 속하는 대표 방법론은 아래와 같다.

| 방법론 | 핵심 |
|---|---|
| **XP(eXtreme Programming)** | 5가지 가치(용기·단순성·의사소통·피드백·존중). 12가지 실천 사항: 짝 프로그래밍, 테스트 주도 개발(TDD), 리팩토링, 지속적 통합(CI), 소규모 릴리즈, 공동 코드 소유, 계획 게임, 단순한 설계, 지속 가능한 속도(주 40시간), 고객 상주, 메타포, 코딩 표준 |
| **스크럼(Scrum)** | 제품 책임자·스크럼 마스터·개발팀. 스프린트 단위 반복, 제품 백로그·스프린트 백로그, 데일리 스크럼, 번다운 차트 |
| **칸반(Kanban)** | 작업을 보드에 시각화하고 진행 중 작업(WIP) 수를 제한해 흐름을 관리하는 도구 |
| **린(Lean)** | 도요타 생산 방식에서 온 낭비 제거 철학. 가치 없는 활동을 없애 빠르게 전달 |
| 크리스탈, FDD | 프로젝트 규모·중요도에 맞춘 방법론군(크리스탈), 기능 단위 반복 개발(FDD) |

### 기출에서 이렇게 나왔다
- 20-2: "사람 중심, 변화에 유연, 워터폴과 대비" → **애자일**

## 코딩 컨벤션(표기법)
출제: 20-3
형태: 표기 규칙 설명 → 표기법 이름

### 개념
| 표기법 | 규칙 | 예 |
|---|---|---|
| **카멜(camelCase)** | 첫 단어는 소문자, 이후 단어의 첫 글자만 대문자 | userName |
| **파스칼(PascalCase)** | 모든 단어의 첫 글자 대문자 | UserName |
| **스네이크(snake_case)** | 단어를 밑줄로 연결, 소문자 | user_name |
| **케밥(kebab-case)** | 단어를 하이픈으로 연결 | user-name |
| **헝가리안(Hungarian)** | 변수명 앞에 자료형을 뜻하는 접두어 | strName, nCount |

20-3 정답이었던 헝가리안 표기법을 코드로 보면 이렇다.

```java
String  strName = "kim";   // str: 문자열
int     nCount  = 3;       // n: 정수
boolean bFound  = true;    // b: 불리언
```

이름 앞 접두어만 봐도 자료형을 알 수 있게 하는 방식이다. 나머지 넷은 단어를 어떻게 잇느냐로 갈린다. 카멜과 파스칼은 첫 글자가 소문자인지 대문자인지만 다르고, 스네이크와 케밥은 이음표가 밑줄인지 하이픈인지만 다르다.

### 기출에서 이렇게 나왔다
- 20-3: "변수명 앞에 자료형 접두어" → **헝가리안 표기법**

## 비용 산정
출제: 20-1
형태: LoC·인원·생산성 수치 → 개발 기간 계산

### 개념
| 방식 | 기법 | 내용 |
|---|---|---|
| 하향식 | **전문가 감정** | 경험 많은 전문가 몇 명이 추정. 빠르지만 주관적 |
| 하향식 | **델파이(Delphi)** | 조정자가 여러 전문가의 익명 추정을 모아 반복 수렴 |
| 상향식 | **LoC(원시 코드 라인 수)** | 낙관·기대·비관 라인 수의 가중 평균으로 규모 추정 |
| 상향식 | **개발 단계별 노력** | 단계별 인월(M/M)을 산정해 합산 |
| 수학적 | **COCOMO** | Boehm이 제안. LoC(KDSI)를 바탕으로 노력(인월)을 공식으로 계산. 프로젝트 유형을 셋으로 나눈다(아래 표) |
| 수학적 | **Putnam** | 생명주기 전체의 노력 분포를 Rayleigh-Norden 곡선으로. 도구 SLIM |
| 수학적 | **FP(기능 점수)** | 입력·출력·조회·파일·인터페이스 수에 가중치를 곱해 기능 점수 산출. 도구 ESTIMACS |

표에서는 수학적 기법을 따로 나눴지만, 크게 보면 수학적 산정 기법도 상향식에 속한다. 수학적 산정 기법은 경험적·실험적 추정 모형이라고도 부른다. 그중 COCOMO는 프로젝트 유형을 셋으로 나누는데, 표로 보면 이렇다.

| COCOMO 유형 | 규모(수험서 기준) | 특징 |
|---|---|---|
| **조직형(Organic)** | 5만(50 KDSI) 라인 이하 | 소규모, 익숙한 업무. 사무 처리·과학 기술 계산용 |
| **반분리형(Semi-detached)** | 30만(300 KDSI) 라인 이하 | 중규모. 조직형과 내장형의 중간. 컴파일러, 트랜잭션 처리 시스템 |
| **내장형(Embedded)** | 30만 라인 초과 | 하드웨어와 밀접한 대규모·실시간 시스템. 신호 제어, 미사일 유도 |

COCOMO는 유형 말고 세부 수준에 따라서도 기본형(Basic), 중간형(Intermediate), 발전형(Detailed)으로 나눈다. 참고로 반분리형을 반결합형이라고 적은 자료도 있다. 보기에서 이 이름이 보여도 같은 유형이다.

20-1에서는 LoC로 개발 기간을 계산하는 문제가 나왔다. 계산식은 아래 순서대로 이어진다.

- 예측 LoC = `(낙관치 + 4 × 기대치 + 비관치) / 6`
- 노력(인월) = `LoC / 1인당 월 생산성`
- 개발 기간(월) = `노력 / 투입 인원`
- 비용 = `노력 × 1인 월 단가`

숫자를 넣어 한 번 계산하면 이렇다. 낙관치 4,000라인, 기대치 6,000라인, 비관치 11,000라인이고, 1인당 월 생산성은 200라인, 투입 인원은 5명이다.

```steps
제목: LoC 기법으로 개발 기간 구하기
예측 LoC | (4,000 + 4 × 6,000 + 11,000) / 6 = 39,000 / 6 = 6,500라인
노력 | 6,500 / 200 = 32.5인월
개발 기간 | 32.5 / 5 = 6.5개월
```

기대치에만 4를 곱해 세 값을 더한 뒤 그 합을 6으로 나눈다는 점만 기억하면, 나머지는 나눗셈 두 번이다.

자세한 풀이는 [계산] 페이지에 있다.

### 기출에서 이렇게 나왔다
- 20-1: 36,000라인, 6명, 1인 월 300라인 → 개발 기간 **20개월** (36,000 / 300 = 120인월, 120 / 6 = 20)

## 리팩토링
출제: 20-3
형태: 정의 설명 → 용어

### 개념
**리팩토링(Refactoring)** 이란 쉽게 말해 외부 동작은 그대로 둔 채 내부 구조만 개선하는 작업이다. 이렇게 하는 목적은 가독성·유지보수성·확장성 향상, 중복 제거, 결함 발견 용이에 있다. 서술형으로 목적을 물으면 "프로그램을 쉽게 이해하고 수정할 수 있게 하여 빠르게 개발하기 위함"이라고 쓴다. 그리고 리팩토링은 기능을 바꾸는 게 아니기 때문에, 리팩토링 전후에 테스트를 돌려 동작이 같은지 확인한다.

예를 들어 아래 두 코드는 같은 값을 돌려준다. 바뀐 것은 읽는 사람이 이해하는 속도뿐이다.

```java
// 고치기 전: 숫자의 뜻을 알 수 없고, 같은 식이 두 번 나온다
double f(double p, int q) {
    if (q > 10) return p * q * 0.9;
    return p * q;
}

// 고친 후: 이름으로 뜻을 드러내고 중복을 없앴다. 결과는 그대로다
double totalPrice(double unitPrice, int quantity) {
    double total = unitPrice * quantity;
    return quantity > BULK_COUNT ? total * BULK_RATE : total;   // BULK_COUNT = 10, BULK_RATE = 0.9
}
```

비슷한 이름의 용어와 비교하면 이렇다.

| 용어 | 차이 |
|---|---|
| 리팩토링 | 동작 유지, 코드 내부 구조 개선. 작은 단위 |
| 리엔지니어링(재공학) | 기존 시스템을 분석해 새 요구에 맞게 재구성. 큰 단위 |
| 리버스 엔지니어링(역공학) | 코드·시스템에서 설계·명세를 거꾸로 추출 |

그럼 내부 구조를 어느 쪽으로 고쳐야 할까? 그 방향이 클린 코드 원칙, 곧 가독성·단순성·의존성 배제·중복 제거·추상화다.

### 기출에서 이렇게 나왔다
- 20-3: "외부 동작은 그대로, 내부 구조 개선" → **리팩토링**

## 릴리스 노트
출제: 20-1
형태: 항목 내용 설명 → 항목 이름 보기

### 개념
릴리스 노트란 릴리스 정보를 최종 사용자인 고객과 공유하려고 만드는 문서를 말한다. 작성은 개발팀이 직접 하는데, 정확하고 완전한 정보를 바탕으로 현재 시제로 쓴다. 한 번 쓰고 끝나는 문서도 아니어서, 초기 배포·기능 변경·패치·베타 등 버전이 바뀔 때마다 갱신한다. 들어가는 항목은 아래와 같다.

| 항목 | 내용 |
|---|---|
| **헤더(Header)**, 머릿말 | 문서 이름(릴리스 노트 이름), 제품 이름, 버전, 릴리스 날짜, 노트 날짜, 노트 버전 |
| **개요** | 제품과 이번 변경에 대한 간략한 전반 설명 |
| **목적** | 이번 릴리스의 새 기능 목록과 릴리스 노트의 목적 |
| **이슈 요약**(문제 요약) | 버그에 대한 간단한 설명 또는 추가된 항목 |
| **재현 항목** | 버그 발견에 이르는 재현 단계 |
| **수정/개선 내용** | 수정·개선된 내용의 간단한 설명 |
| **사용자 영향도** | 사용자가 받는 영향과 필요한 조치 |
| **SW 지원 영향도** | 지원 프로세스·조직에 미치는 영향 |
| **노트** | 설치·업그레이드 시 참고 사항 |
| **면책 조항** | 회사 및 표준 제품 관련 법적 고지 |
| **연락처** | 사용자 지원·문의 연락처 |

실제 릴리스 노트 앞부분은 대략 이런 모양이다. 맨 위 몇 줄이 20-1에서 답으로 나온 헤더다.

```text
[헤더]        쇼핑몰 앱 릴리스 노트 | 제품: 쇼핑몰 앱 | 버전: 2.3.0
              릴리스 날짜: 2026-03-02 | 노트 날짜: 2026-03-02 | 노트 버전: 1.0
[개요]        결제 화면을 개선하고 장바구니 오류를 고친 버전
[이슈 요약]   같은 상품을 두 번 담으면 장바구니 수량이 0으로 표시되는 버그
[재현 항목]   상품 상세 화면 → 장바구니 담기 두 번 → 장바구니 열기
[수정/개선]   수량 합산 로직 수정
```

### 기출에서 이렇게 나왔다
- 20-1: "문서 이름·제품 이름, 버전, 날짜" → **헤더**

### 답 쓸 때
항목이 많아 보여도 지문에 적힌 내용으로 가른다. "이름·버전·날짜"는 헤더, "변경 전반 설명"은 개요, "새 기능 목록"은 목적이다.

## 4+1 뷰
출제: 없음

### 개념
Kruchten의 4+1 뷰는 소프트웨어 아키텍처를 다섯 관점으로 나눠 기술하는 방법이다. 이름이 5가 아니라 4+1인 이유는, 유스케이스 뷰 하나가 가운데에서 나머지 네 뷰를 묶고 검증하는 역할을 맡기 때문이다.

| 뷰 | 관점 | 주 이해관계자 | 관련 UML |
|---|---|---|---|
| **유스케이스 뷰(시나리오 뷰)** | 시스템이 제공하는 기능 시나리오. 다른 4개 뷰의 근거 | 사용자·분석가 | 유스케이스 다이어그램 |
| **논리 뷰** | 기능 요구사항을 만족하는 클래스·패키지 구조 | 최종 사용자(기능 관점), 설계자 | 클래스·패키지·상태 |
| **프로세스 뷰** | 동시성·성능·프로세스와 스레드 | 통합자 | 활동·시퀀스 |
| **구현 뷰(개발 뷰)** | 모듈·컴포넌트 구성과 소스 조직 | 프로그래머 | 컴포넌트 |
| **배포 뷰(물리 뷰)** | 하드웨어 노드에 소프트웨어를 어떻게 배치하는가 | 시스템 엔지니어 | 배치 |

### 뷰 하나씩 보기
온라인 쇼핑몰 하나를 다섯 뷰로 나눠 보면 각 뷰가 무엇을 그리는지 금방 구분된다.

#### 1. 유스케이스 뷰 (Use Case View, 시나리오 뷰)
- 시스템이 제공하는 기능 시나리오
- 다른 4개 뷰의 근거, 곧 "+1"
- 주 이해관계자: 사용자·분석가 / 관련 UML: 유스케이스 다이어그램

> "고객이 상품을 장바구니에 담고 결제한다"는 시나리오

나머지 네 뷰의 설계로 이 시나리오를 실제로 처리할 수 있는지를 이 뷰로 확인한다.

#### 2. 논리 뷰 (Logical View)
- 기능 요구사항을 만족하는 클래스·패키지 구조
- 주 이해관계자: 최종 사용자(기능 관점), 설계자 / 관련 UML: 클래스·패키지·상태

> Member, Product, Order, Payment 클래스와 이들을 묶은 order·payment 패키지

#### 3. 프로세스 뷰 (Process View)
- 동시성·성능, 프로세스와 스레드
- 주 이해관계자: 통합자 / 관련 UML: 활동·시퀀스

> 주문 요청 수백 건이 동시에 들어올 때 몇 개의 스레드가 나눠 처리하고, 결제 응답을 기다리는 동안 무엇을 하는가

#### 4. 구현 뷰 (Implementation View, 개발 뷰)
- 모듈·컴포넌트 구성과 소스 조직
- 주 이해관계자: 프로그래머 / 관련 UML: 컴포넌트

> 소스를 order 모듈, payment 모듈, common 모듈로 나누고 각 모듈을 어떤 컴포넌트로 빌드하는가

#### 5. 배포 뷰 (Deployment View, 물리 뷰)
- 하드웨어 노드에 소프트웨어를 배치하는 방식
- 주 이해관계자: 시스템 엔지니어 / 관련 UML: 배치

> 웹 서버 두 대에 쇼핑몰 애플리케이션을, DB 서버 한 대에 데이터베이스를 올린다

논리 뷰와 구현 뷰가 헷갈리기 쉽다. 논리 뷰는 Member, Order 같은 클래스가 설계상 무엇이 있느냐를 그리고, 구현 뷰는 실제 소스를 order 모듈, payment 모듈처럼 어떻게 나눠 두느냐를 그린다.

### 한눈에 구분
위에서 말했듯 "+1"은 유스케이스 뷰다. 나머지 넷은 각 뷰가 던지는 질문으로 기억하면 쉽다. 논리 뷰는 "무엇이 있는가", 프로세스 뷰는 "어떻게 동시에 도는가", 구현 뷰는 "코드가 어떻게 나뉘는가", 배포 뷰는 "어느 장비에 올라가는가"다.

## 소프트웨어 생명주기 모델
출제: 없음

### 개념
| 모델 | 특징 |
|---|---|
| **폭포수(Waterfall)** | 앞 단계를 끝내야 다음 단계로 가는 순차·단방향 모델. 고전적 생명주기. 되돌아가기 어렵다 |
| **프로토타입(Prototype)** | 시제품을 먼저 만들어 사용자에게 보여 주고 요구사항을 확인·보완한다 |
| **나선형(Spiral)** | 계획 수립 → 위험 분석 → 개발·검증 → 고객 평가를 반복. 위험 분석이 핵심이고 대규모 시스템에 맞다 |
| **반복적·점진적(Iterative/Incremental)** | 여러 번 반복하며 기능을 조금씩 더해 완성한다 |
| **진화적(Evolutionary)** | 핵심 기능부터 만들고 사용자 피드백으로 점점 발전시킨다 |
| **V 모델** | 폭포수를 확장해 개발 단계마다 대응하는 테스트 단계를 V자로 짝지었다. 검증·확인 강조 |
| **RAD(Rapid Application Development)** | CASE 도구와 재사용으로 매우 짧은 기간에 개발한다 |
| **4GT(4세대 기법)** | 4세대 언어(4GL)와 자동 생성 도구로 코드를 만든다 |
| **애자일(Agile)** | 짧은 반복, 고객 협력, 변화 수용. 위 "애자일" 묶음 참고 |

### 모델 하나씩 보기
표의 아홉 개 가운데 단서가 뚜렷하고 서로 헷갈리기 쉬운 여섯 개만 장면으로 풀어 본다. RAD, 4GT, 애자일은 표의 한 줄로 충분하다.

#### 1. 폭포수 모델 (Waterfall Model)
- 앞 단계를 끝내야 다음 단계로 가는 순차·단방향 모델
- 고전적 생명주기
- 이전 단계로 되돌아가기 어려움

> 요구 분석서가 확정돼야 설계를 시작하고, 설계서가 끝나야 코딩을 시작한다

물이 위에서 아래로만 떨어지듯 한 방향으로만 흐른다는 데서 이름이 왔다. 지문에 "순차", "단계 완료"가 보이면 폭포수다.

#### 2. 프로토타입 모델 (Prototype Model)
- 시제품을 먼저 만들어 사용자에게 보여 줌
- 사용자 반응으로 요구사항을 확인·보완

> 화면만 대충 움직이는 시제품을 보여 주자 고객이 "검색 버튼은 위에 있어야 한다"고 말하고, 그 의견을 요구사항에 반영한다

요구사항이 처음부터 분명하지 않을 때, 말로 묻는 대신 눈으로 보여 주고 확인하는 방식이다.

#### 3. 나선형 모델 (Spiral Model)
- 계획 수립, 위험 분석, 개발·검증, 고객 평가를 반복
- 위험 분석이 핵심
- 대규모 시스템에 적합

> 한 바퀴를 돌 때마다 "이번 단계에서 가장 큰 위험이 무엇인가"부터 따지고, 위험을 줄인 뒤 개발해서 고객 평가를 받는다

반복한다는 점은 다른 반복형 모델과 같지만, 매 바퀴 위험 분석을 한다는 점이 나선형만의 단서다.

#### 4. 반복적·점진적 모델 (Iterative/Incremental Model)
- 여러 번 반복하며 기능을 조금씩 더해 완성

> 1차에 회원 가입, 2차에 장바구니, 3차에 결제를 붙여서 완성한다

#### 5. 진화적 모델 (Evolutionary Model)
- 핵심 기능부터 만들고 사용자 피드백으로 점점 발전

> 상품 검색만 되는 첫 버전을 내놓고, 사용자 의견을 받아 다음 버전을 다듬는다

반복적·점진적 모델과 비슷하게 보인다. 위 예에서 반복적·점진적 모델은 회원 가입, 장바구니, 결제를 차례로 붙여서 완성하고, 진화적 모델은 첫 버전을 내놓은 뒤 사용자 의견을 받아 다음 버전을 다듬는다. 지문에 "사용자 피드백으로 발전"이 보이면 진화적, "기능을 조금씩 더해 완성"이 보이면 반복적·점진적이다.

#### 6. V 모델 (V Model)
- 폭포수의 확장
- 개발 단계마다 대응하는 테스트 단계를 V자로 짝지음
- 검증·확인 강조

> 요구사항 분석은 인수 테스트와, 기능 명세 분석은 시스템 테스트와, 설계는 통합 테스트와, 개발(구현)은 단위 테스트와 짝을 이룬다

V자의 왼쪽 획은 위에서 아래로 요구사항 분석, 기능 명세 분석, 설계, 개발(구현) 순서로 개발 단계를 적는다. 오른쪽 획은 아래에서 위로 단위, 통합, 시스템, 인수 테스트 순서로 테스트 단계를 적는다. 같은 높이에 놓인 두 단계가 위에서 말한 짝이다.

### 한눈에 구분
모델마다 알아볼 단서가 하나씩 있다. "순차·단계 완료"는 폭포수, "시제품"은 프로토타입, "위험 분석"은 나선형, "개발 단계와 테스트 단계 대응"은 V 모델이다. 참고로 V 모델의 테스트 쪽은 [SW 개발] 페이지에서 다루는 테스트 레벨과 같다.

## 요구사항 도출·명세 기법과 구조적 분석 도구
출제: 없음

### 개념
요구사항을 끌어내는 도출 기법으로는 **인터뷰**, **브레인스토밍**, **JAD(Joint Application Development)** 워크숍, 설문, **델파이**, 프로토타이핑, 관찰, 유스케이스가 있다. 이 중 JAD 워크숍은 개발자와 사용자가 함께 모여 집중 회의를 하는 것이고, 델파이는 전문가에게 익명 설문을 반복해 합의에 이르는 방식이다.

도출한 요구사항은 명세서로 적는데, 명세 기법은 정형과 비정형 두 가지로 나뉜다.

| 명세 기법 | 내용 | 예 |
|---|---|---|
| **정형(Formal) 명세** | 수학·논리 기반 표기. 모호성이 적고 검증이 쉽지만 작성·이해가 어렵다 | VDM, Z, Petri-net, CSP |
| **비정형(Informal) 명세** | 자연어·다이어그램으로 기술. 쓰고 읽기 쉽지만 모호할 수 있다 | 자연어 서술, FSM, 결정 테이블, 상태도 |

어떤 기법으로 쓰든 명세서는 명확성, 완전성, 검증 가능성, 추적 가능성을 갖춰야 한다.

구조적 분석에 쓰는 도구로는 **DFD(자료 흐름도)**, **DD(자료 사전)**, **소단위 명세서(Mini-Spec)**, ERD, STD(상태 전이도)가 있다. 이 중 DFD는 네 가지 요소로 그린다.

| DFD 요소 | 기호 | 의미 |
|---|---|---|
| 프로세스(Process) | 원 | 입력 자료를 처리·변환 |
| 자료 흐름(Data Flow) | 화살표 | 자료의 이동 |
| 자료 저장소(Data Store) | 평행선 | 파일·DB |
| 단말(Terminator) | 사각형 | 시스템 밖의 자료 발생지·도착지 |

자료 사전(DD)은 기호로 자료를 정의한다. `=` 는 정의, `+` 는 연결, `( )` 는 생략 가능, `[ | ]` 는 선택, `{ }` 는 반복, `* *` 는 주석이다.

기호만 따로 외우면 금방 섞이니, 주문 자료 하나를 이 기호로 정의하면 아래와 같다.

```text
주문     = 주문번호 + 고객명 + {상품} + (메모)
결제수단 = [카드 | 계좌이체 | 포인트]
*주문번호는 주문 날짜와 일련번호를 이어 붙인 값*
```

첫 줄은 "주문은 주문번호, 고객명, 여러 개의 상품, 생략할 수 있는 메모를 연결해 이루어진다"로 읽는다. 둘째 줄의 결제수단은 카드, 계좌이체, 포인트 셋 중 하나를 고르고, 마지막 줄은 `* *`로 감싼 주석이다.

## 구조적 설계 도구 (HIPO·N-S 차트)
출제: 없음

### 개념
**HIPO(Hierarchy Input Process Output)** 란 이름 그대로 시스템의 입력·처리·출력 기능을 계층적으로 그리는 하향식 설계·문서화 도구를 말한다. 기능과 자료의 관계를 한눈에 보여 주고, 유지보수가 쉽다는 장점도 있다. HIPO는 세 가지 도표로 이루어진다.

| HIPO 도표 | 내용 |
|---|---|
| **가시적 도표**(도식 목차, Visual Table of Contents) | 전체 기능을 트리 구조로 보여 줌 |
| **총체적 도표**(총괄·개요 도표) | 기능별 입력·처리·출력을 개괄적으로 표현 |
| **세부적 도표**(상세 도표) | 총체적 도표의 각 기능을 자세히 기술 |

성적 관리 시스템으로 예를 들면, 가시적 도표는 아래처럼 기능을 트리로 펼친 그림이다.

```text
성적 관리 시스템
├─ 성적 입력
├─ 성적 계산
│   ├─ 총점 계산
│   └─ 평균 계산
└─ 성적 출력
```

총체적 도표는 여기서 "성적 계산"의 입력(과목별 점수), 처리(총점·평균 계산), 출력(성적표 자료)을 한 장에 개괄하고, 세부적 도표는 그 처리 내용을 더 자세히 적는다.

**N-S 차트(Nassi-Schneiderman Chart)** 는 논리 흐름을 박스로만 표현하는 구조적 설계 도구다. 순차·선택(IF, CASE)·반복 구조만 쓰고 화살표와 GOTO가 없는데, 바로 이 점 때문에 구조적 프로그래밍에 맞다. 대신 순서도와 달리 임의의 제어 이동은 표현하기 어렵다.

## 코드 설계 (코드 종류)
출제: 없음

### 개념
여기서 말하는 코드란 프로그램 코드가 아니라, 자료를 식별·분류하려고 붙이는 기호를 말한다. 시험에서는 예시를 보여 주고 어떤 종류인지 고르게 하므로, 표의 예까지 같이 봐 둔다.

| 코드 | 방식 | 예 |
|---|---|---|
| **순차 코드(Sequence)** | 일련번호를 차례로 부여 | 1, 2, 3, 4 |
| **블록 코드(Block)** | 공통 특성별로 구간을 정하고 그 안에서 번호 부여 | 총무부 100~199, 영업부 200~299 |
| **그룹 분류 코드(Group)** | 대·중·소 분류 자릿수마다 의미를 부여 | 1-01-001 |
| **10진 코드(Decimal)** | 10진 분할로 대·중·소 분류를 세분화 | 도서 분류(KDC·DDC) |
| **표의 숫자 코드(Significant Digit)** | 길이·무게 등 실제 수치를 그대로 코드로 | 지름 100, 길이 200 → 100-200 |
| **연상 코드(Mnemonic)** | 대상을 떠올리게 하는 문자·기호 | TV-40, KR |
| **합성 코드(Combined)** | 두 가지 이상 코드를 조합 | 연상 + 순차 |

## 소프트웨어 아키텍처 패턴과 품질 속성
출제: 없음

### 개념
| 패턴 | 내용 |
|---|---|
| **계층화(Layered)** | 기능을 계층으로 나누고 하위 계층이 바로 위 계층에 서비스를 제공. OSI 7계층이 예 |
| **클라이언트-서버(Client-Server)** | 클라이언트가 요청하고 서버가 응답 |
| **MVC(Model-View-Controller)** | 데이터·로직(Model), 화면(View), 입력 처리·제어(Controller)를 분리 |
| **파이프-필터(Pipe-Filter)** | 데이터 스트림을 필터가 차례로 처리하고 파이프로 넘김. 필터 재사용이 쉽다 |
| **브로커(Broker)** | 분산된 컴포넌트 사이의 요청을 중개자가 연결 |
| **마스터-슬레이브(Master-Slave)** | 마스터가 작업을 슬레이브에 나눠 주고 결과를 모음 |

### 패턴 하나씩 보기
여섯 패턴은 이름이 곧 구조를 말해 준다. 장면 하나씩만 붙여 두면 지문에서 고르기 쉽다.

#### 1. 계층화 패턴 (Layered)
- 기능을 계층으로 나눈 구조
- 하위 계층이 바로 위 계층에 서비스 제공
- 예: OSI 7계층

> 웹 애플리케이션을 화면 계층, 업무 처리 계층, 데이터 접근 계층으로 나누고, 화면 계층은 업무 처리 계층만 부른다

#### 2. 클라이언트-서버 패턴 (Client-Server)
- 클라이언트의 요청, 서버의 응답

> 브라우저가 상품 목록을 요청하면 웹 서버가 목록을 보내 준다

#### 3. MVC 패턴 (Model-View-Controller)
- Model: 데이터·로직
- View: 화면
- Controller: 입력 처리·제어

> 사용자가 "상품 목록" 버튼을 누르면 Controller가 요청을 받아 Model에서 목록을 가져오고, View가 그 목록을 화면에 그린다

화면을 바꿔도 데이터·로직 코드는 그대로 둘 수 있다는 점이 MVC로 나누는 이유다.

#### 4. 파이프-필터 패턴 (Pipe-Filter)
- 데이터 스트림을 필터가 차례로 처리
- 필터 사이 전달은 파이프
- 필터 재사용이 쉬움

```text
cat access.log | grep ERROR | sort | uniq -c
```

`grep`, `sort`, `uniq` 하나하나가 필터이고 그 사이의 `|`가 파이프다. 필터를 빼거나 순서를 바꿔 다른 처리에 다시 쓸 수 있다.

#### 5. 브로커 패턴 (Broker)
- 분산된 컴포넌트 사이 요청을 중개자가 연결

> 클라이언트는 결제 서비스가 어느 서버에 있는지 모른 채 브로커에게 요청하고, 브로커가 해당 서버를 찾아 이어 준다

#### 6. 마스터-슬레이브 패턴 (Master-Slave)
- 마스터의 작업 분배와 결과 수집
- 실제 처리는 슬레이브

> 큰 이미지 하나를 마스터가 네 조각으로 나눠 슬레이브 네 대에 맡기고, 처리된 조각을 모아 다시 합친다

브로커는 요청을 이어 주기만 하고, 마스터는 일을 직접 나눠 주고 결과까지 모은다.

### 품질 속성·프레임워크·영속 계층 객체

아키텍처가 갖춰야 할 품질 속성으로는 **가용성**, **변경 용이성**, **성능**, **보안성**, **사용성**, **시험 용이성**이 있다. 이 중 가용성은 장애 없이 서비스를 유지하는 것을 말한다. MSA·SOA는 [신기술] 페이지에서 다룬다.

**소프트웨어 프레임워크**란 소프트웨어를 구성하는 기본 뼈대, 곧 코드 라이브러리·인터페이스·설정 정보를 재사용할 수 있게 제공하는 집합이다. 스프링이나 전자정부 표준 프레임워크가 그 예다. 특징은 네 가지다. **모듈화**는 인터페이스 캡슐화로 변경 영향을 최소화하는 것이고, **재사용성**은 제공된 뼈대를 여러 프로그램에서 다시 쓸 수 있다는 것이다. **확장성**은 다형성으로 인터페이스를 확장하는 것이다. 마지막 **제어의 역흐름(IoC)** 은 이름이 낯선데, 실행 흐름을 애플리케이션이 아니라 프레임워크가 정한다는 뜻이다. 애플리케이션은 프레임워크가 정해 둔 메서드를 확장(재정의)해 두기만 하고, 그 메서드를 언제 호출할지는 프레임워크가 정한다.

영속 계층에서 쓰는 객체도 세 가지가 있다. **DAO**(Data Access Object)는 DB 세부를 감추고 데이터 조작 기능을 제공한다. **DTO**(Data Transfer Object)는 계층·프로세스 사이에서 데이터를 전달하는 용도이고 값이 바뀔 수 있다. 반면 **VO**(Value Object)는 getter만 있는 불변 값 객체다.

```java
interface MemberDAO {                 // DAO: DB 세부(SQL, 연결)를 감추고 조작 기능만 내놓는다
    MemberDTO findById(String id);
}
class MemberDTO {                     // DTO: 계층 사이 전달용, setter가 있어 값이 바뀔 수 있다
    private String name;
    public String getName() { return name; }
    public void setName(String n) { name = n; }
}
final class Money {                   // VO: getter만 있는 불변 값 객체
    private final int amount;
    Money(int amount) { this.amount = amount; }
    public int getAmount() { return amount; }
}
```

DTO와 VO가 헷갈린다면 setter가 있는지를 본다. MemberDTO처럼 setName()으로 값을 바꿀 수 있으면 DTO, Money처럼 한 번 만들면 못 바꾸면 VO다.

## 일정 관리 (PERT·CPM·간트 차트)
출제: 없음

### 개념
| 기법 | 내용 |
|---|---|
| **PERT** | 작업마다 낙관·보통(기대)·비관 시간을 추정해 불확실성을 반영. 기대 시간 = `(낙관 + 4 × 보통 + 비관) / 6` |
| **CPM(Critical Path Method)** | 작업 간 선후 관계로 네트워크를 그리고, 시작부터 끝까지 가장 긴 경로(임계 경로)를 찾는다. 임계 경로 길이가 프로젝트 최소 완료 기간이다 |
| **간트 차트(Gantt Chart)** | 작업별 시작·종료 시점을 막대로 그려 일정과 진척을 보여 준다. 막대 길이는 작업 기간이다(인원수가 아니다). CPM 네트워크로 만들 수 있고 자원 배치 계획에 쓰지만, 작업 간 의존 관계는 잘 드러나지 않는다 |

### 기법 하나씩 보기
세 기법을 작업 네 개(A, B, C, D)짜리 작은 프로젝트 하나로 이어서 설명한다.

#### 1. PERT (Program Evaluation and Review Technique)
- 작업마다 낙관·보통(기대)·비관 시간 추정
- 불확실성 반영
- 기대 시간 = `(낙관 + 4 × 보통 + 비관) / 6`

작업 C는 낙관적으로 2일, 보통 4일, 비관적으로 12일이 걸린다.

```steps
제목: 작업 C의 PERT 기대 시간
식에 넣기 | (2 + 4 × 4 + 12) / 6
계산 | 30 / 6 = 5일
```

보통 시간은 4일인데 비관치가 크게 벌어져 있어서 기대 시간이 5일로 늘었다. 불확실성이 숫자에 반영된다는 게 이런 뜻이다.

#### 2. CPM (Critical Path Method)
- 작업 간 선후 관계로 그린 네트워크
- 시작부터 끝까지 가장 긴 경로가 임계 경로
- 임계 경로 길이 = 프로젝트 최소 완료 기간

A(3일)가 끝나야 D(2일)를 하고, B(4일)가 끝나야 C(5일)를 한다고 하자.

```text
시작 - A(3일) - D(2일) - 끝     경로 길이 3 + 2 = 5일
시작 - B(4일) - C(5일) - 끝     경로 길이 4 + 5 = 9일   <- 임계 경로
```

두 경로를 동시에 진행해도 B-C 쪽이 끝나야 프로젝트가 끝나니, 최소 완료 기간은 9일이다. 임계 경로에 있는 B나 C가 하루 늦으면 프로젝트 전체가 하루 늦어진다.

#### 3. 간트 차트 (Gantt Chart)
- 작업별 시작·종료 시점을 막대로 표시
- 막대 길이는 작업 기간(인원수 아님)
- CPM 네트워크로 작성 가능, 자원 배치 계획에 사용
- 작업 간 의존 관계는 잘 드러나지 않음

위 CPM 예를 그대로 막대로 옮기면 이렇다.

```text
Day  123456789
A    ###
D       ##
B    ####
C        #####
```

D가 4일째, C가 5일째에 시작한다는 건 보이지만, D가 A를 기다린 것인지는 막대만 봐서는 알 수 없다. 의존 관계가 잘 드러나지 않는다는 말이 이 뜻이다.

### 한눈에 구분
"불확실성·세 가지 추정치"가 보이면 PERT, "최장 경로·임계 경로"면 CPM, "막대그래프"면 간트 차트다. 그리고 PERT 기대 시간식은 앞의 "비용 산정" 묶음에서 본 예측 LoC 식 `(낙관치 + 4 × 기대치 + 비관치) / 6`과 모양이 같다. 둘은 따로 외우지 말고 식 하나로 기억해 둔다.

## 소프트웨어 개발 프로세스·품질 표준
출제: 없음

### 개념
**CMMI(Capability Maturity Model Integration)** 란 미국 SEI가 만든 성숙도 모델로, 조직의 개발 프로세스가 얼마나 성숙했는지를 1~5의 5단계로 평가한다.

| 단계 | 이름 | 상태 |
|---|---|---|
| 1 | **초기(Initial)** | 정해진 프로세스 없이 개인 역량에 의존 |
| 2 | **관리(Managed)** | 프로젝트 단위로 계획·관리. 비슷한 프로젝트를 반복할 수 있음 |
| 3 | **정의(Defined)** | 조직 표준 프로세스를 정하고 문서화 |
| 4 | **정량적 관리(Quantitatively Managed)** | 수치 데이터로 프로세스를 관리 |
| 5 | **최적화(Optimizing)** | 프로세스를 지속적으로 개선 |

비슷한 것으로 **SPICE(ISO/IEC 15504)** 가 있다. 프로세스 평가·개선 국제 표준인데, CMMI와 달리 0부터 시작해서 프로세스 능력을 0~5의 6수준으로 평가한다. 순서대로 0 **불완전(Incomplete)**, 1 **수행(Performed)**, 2 **관리(Managed)**, 3 **확립(Established)**, 4 **예측(Predictable)**, 5 **최적화(Optimizing)** 다.

| 표준·용어 | 내용 |
|---|---|
| **ISO/IEC 12207** | 소프트웨어 생명주기 프로세스 표준. 개발·운영·유지보수에 필요한 프로세스를 정의 |
| **ISO/IEC 25000(SQuaRE)** | 소프트웨어 품질 요구와 평가를 통합한 표준군. 예전의 ISO/IEC 9126(품질 모델)과 14598(품질 평가)을 묶었다. 품질 특성은 그 안의 25010이 정한다 |
| **재사용(공통 모듈)** | 공통 모듈은 자주 쓰는 기능을 재사용할 수 있게 패키지로 제공하는 독립 모듈이다. NCS는 재사용을 범위에 따라 함수와 객체 재사용 → 컴포넌트 재사용(인터페이스로 통신) → 애플리케이션 재사용(공통 기능을 제공하는 애플리케이션과 통신해 기능 공유)으로 나눈다 |
| **CBD(Component Based Development)** | 이미 만든 컴포넌트를 조립해 개발하는 방식. 재사용 범위는 함수와 객체 → 컴포넌트 → 애플리케이션 순으로 커진다 |

재사용 방법은 두 가지로 나눈다. **합성 중심**(Composition-Based)은 블록 구성 방법이라고도 하는데, 모듈을 만들어 두고 끼워 맞추는 방식이다. **생성 중심**(Generation-Based)은 패턴 구성 방법이라고도 하며, 추상화한 형태를 구체화해서 생성하는 방식이다.

ISO/IEC 25010(2011판)은 제품 품질 특성을 8가지로 정한다. **기능 적합성**, **성능 효율성**, **호환성**, **사용성**, **신뢰성**, **보안성**, **유지보수성**, **이식성**이다. 이 중 호환성은 다른 시스템과 상호 운용·공존할 수 있는가이고, 이식성은 다른 환경으로 옮기기 쉬운가를 말한다.

25010 이전 품질 모델인 ISO/IEC 9126은 품질 특성이 6가지였다. **기능성**(적절성·정밀성·상호 운용성·보안성·호환성), **신뢰성**(성숙성·고장 허용성·회복성), **사용성**(이해성·학습성·운용성), **효율성**(시간 효율성·자원 활용성), **유지보수성**(분석성·변경성·안정성·시험성), **이식성**(적응성·설치성·대체성)이다. NCS 화면설계는 UI 품질 요구사항을 이 표로 정리한다. 그럼 6개가 어떻게 8개가 됐을까? 25010이 9126의 기능성 안에 있던 보안성·호환성을 독립 특성으로 떼어 냈기 때문이다.

### 한눈에 구분
CMMI와 SPICE는 섞이기 쉬운데, 둘 다 마지막 이름이 "최적화"이고 2번이 "관리"이기 때문이다. 먼저 개수와 시작점으로 가른다. 0수준(불완전)이 있고 6개면 SPICE, 1단계부터 5개면 CMMI다. 그다음으로 4번 이름이 다르다. CMMI 4단계는 "정량적 관리", SPICE 4수준은 "예측"이다.

## 배치 프로그램
출제: 없음

### 개념
**배치 프로그램**이란 사용자와 상호작용 없이 작업들을 묶어서, 정기적으로 반복하거나 정해진 규칙에 따라 일괄 처리하는 프로그램을 말한다.

배치 프로그램이 갖춰야 할 필수 요소는 다섯 가지다. **대용량 데이터**는 대량의 데이터를 처리할 수 있어야 한다는 뜻이고, **자동화**는 심각한 오류가 아니면 사용자 개입 없이 동작해야 한다는 뜻이다. **견고함**은 잘못된 데이터가 들어와도 처리해서 비정상적으로 중단되지 않는 것, **안정성**은 언제 무슨 문제가 생겼는지 추적할 수 있는 것이다. 마지막으로 **성능**은 정해진 시간 안에 끝나고 다른 애플리케이션을 방해하지 않는 것을 말한다.

언제 돌리느냐에 따라서도 나눈다. **정기 배치**는 정해진 날짜·시간에, **이벤트성 배치**는 설정한 조건이 충족될 때만, **On-Demand 배치**는 사용자가 요청할 때 수행한다.

배치를 돌리는 스케줄러로는 **스프링 배치**, **Quartz**, **Cron**이 있다. 스프링 배치는 Spring Source와 Accenture가 2007년에 함께 만든 것이고, Quartz는 스프링에 플러그인되는 Job 스케줄러다. Cron은 유닉스 계열에서 작업을 주기적으로 실행하는 도구로, 크론 표현식으로 주기를 적는다.

예를 들어 매일 새벽 2시에 정산 배치를 돌리는 정기 배치라면 유닉스 crontab에 이렇게 적는다. 앞의 다섯 칸이 차례로 분, 시, 일, 월, 요일이다.

```text
0 2 * * * /batch/settle.sh
```
