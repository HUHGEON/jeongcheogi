# SW 설계

21개 회차 420문제 중 이론이 242문제이고, 그중 SW 설계에서 가장 자주 나온 묶음은 디자인 패턴(14회차), 응집도·결합도(9회차), UML(6회차)이다. 형태는 거의 "설명 1~4줄 → 보기에서 고르기"이며, 디자인 패턴과 결합도는 영문 표기를 요구하는 경우가 많다. 2024년 이후에는 2~5년 전 문제가 지문째 다시 나오는 일이 잦다(26-1 Bridge·Observer, 26-2 Abstract Factory, 25-1 결합도 세트, 26-1 응집도 세트).

## 디자인 패턴 총론 (생성·구조·행위 분류)
출제: 24-3, 21-2, 20-4
형태: 분류를 설명하고 예시 패턴 몇 개를 보여 준 뒤 분류 이름 쓰기. "생성·구조·( )" 빈칸형도 있음

### 개념
디자인 패턴은 반복해서 만나는 설계 문제에 이름을 붙여 둔 해법 모음이다. GoF 23개 패턴을 목적에 따라 세 갈래로 나눈다.

| 분류 | 관심사 | 패턴 |
|---|---|---|
| **생성(Creational)** 5개 | 객체를 만드는 방법. 생성 과정을 감춰서 어떤 구체 클래스가 만들어지는지 호출 쪽이 몰라도 되게 한다 | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| **구조(Structural)** 7개 | 클래스와 객체를 조합해 더 큰 구조를 만드는 방법. 인터페이스 변환·분리·단순화 | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| **행위(Behavioral)** 11개 | 객체들이 서로 어떻게 상호작용하고 책임을 나누는가. 알고리즘과 제어 흐름 | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

두음: 생성 "빌프팩앱싱"(또는 "싱팩빌프앱"), 구조 "브데퍼플프컴어"(또는 "어데퍼프 브플컴"), 나머지 11개는 행위. 행위를 외우려면 "전옵중방이상인 매커책템"(전략·옵저버·중재자·방문자·이터레이터·상태·인터프리터·메멘토·커맨드·책임 연쇄·템플릿 메서드).

GoF는 목적 말고 범위로도 나눈다. 상속으로 관계가 정해지는 **클래스 패턴**(Factory Method, 클래스 Adapter, Interpreter, Template Method)과 객체 합성으로 관계가 정해지는 **객체 패턴**(나머지)이다.

### 한눈에 구분
| 분류 | 지문 단서 | 비고 |
|---|---|---|
| 생성 | "객체 생성 방식", "인스턴스화 과정을 캡슐화", "어떤 클래스를 만들지" | |
| 구조 | "클래스나 객체를 조합", "인터페이스를 변환·분리", "더 큰 구조" | |
| 행위 | "객체 간 상호작용", "책임 분담·분산", "알고리즘·제어 흐름" | 분류 문제 3번 모두 정답이 행위 |

### 기출에서 이렇게 나왔다
- 24-3: "객체 간 상호작용과 책임 분담" 설명, 예시로 Mediator·Interpreter·Iterator → **행위**
- 21-2: "상호작용·책임 분산" 설명, 예시로 Observer 등 → **행위**
- 20-4: 생성·구조·( ) 빈칸 → **행위**

### 답 쓸 때
"행위 패턴"과 "행동 패턴" 모두 Behavioral의 번역으로 쓰인다. 개별 패턴 이름은 영문으로 요구하는 경우가 대부분이므로(23-1 이후 거의 "보기에서 영어로") 철자까지 외운다.

## 생성 패턴
출제: 26-2, 24-1, 23-2, 21-3
형태: 1~3줄 설명 → 보기에서 영어로. Singleton은 Java 코드 출력 문제로도 나옴(24-1, 21-3)

### 개념
| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Singleton** | 인스턴스를 하나만 만들고 어디서나 그 하나에 접근하게 한다 | "인스턴스 하나", "전역 접근점", 생성자 private + static getInstance(). 예: DB 커넥션 풀, 설정 관리자 |
| **Factory Method** | 객체 생성 인터페이스는 상위 클래스에 두고, 어떤 클래스를 만들지는 서브클래스가 정한다 | "서브클래스가 결정", "상위 클래스는 생성 인터페이스만", Virtual Constructor |
| **Abstract Factory** | 서로 관련된 객체들의 묶음(제품군)을 구체 클래스를 지정하지 않고 생성하는 인터페이스 | "제품군", "연관된 객체 조합", **Kit** |
| **Builder** | 복잡한 객체의 생성 절차와 표현을 분리해, 같은 절차로 다른 표현을 만든다 | "생성 과정과 표현 분리", "단계적으로 조립", 생성자 인자가 많아지는 텔레스코핑 생성자 문제 해결 |
| **Prototype** | 원형 인스턴스를 복제해 새 객체를 만든다 | "복제(clone)", "원형", "생성 비용이 큰 객체", "복사 후 필요한 부분만 수정" |

Singleton의 코드 뼈대는 다음과 같다. 24-1·21-3 코딩 문제가 이 구조였다.

```java
class Config {
    private static Config instance;
    private Config() {}
    public static Config getInstance() {
        if (instance == null) instance = new Config();
        return instance;
    }
}
public class Main {
    public static void main(String[] args) {
        Config a = Config.getInstance();
        Config b = Config.getInstance();
        System.out.println(a == b);
    }
}
```
출력: `true`

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Factory Method vs Abstract Factory | Factory Method는 메서드 하나로 제품 하나를 만들고 서브클래스가 그 메서드를 재정의한다. Abstract Factory는 여러 제품으로 이루어진 제품군을 팩토리 객체 하나가 통째로 만든다. 지문에 "제품군·Kit"이 있으면 Abstract Factory, "서브클래스에서 결정"이면 Factory Method |
| Builder vs Abstract Factory | Builder는 복잡한 객체 하나를 단계적으로 조립, Abstract Factory는 관련 객체 여러 개를 한 번에 생성 |
| Prototype vs Factory Method | Prototype은 기존 객체를 복제, Factory Method는 클래스에서 새로 생성 |

### 기출에서 이렇게 나왔다
- 26-2: "제품군을 생성하는 인터페이스, Kit" → **Abstract Factory** (24-1 재출제)
- 24-1: "연관된 객체를 조합해 생성하는 인터페이스, Kit" → **Abstract Factory**
- 23-2: 설명 2개 → **Singleton / Visitor**
- 21-3: "상위 클래스는 생성 인터페이스만 정의, 서브클래스가 생성할 클래스를 결정" → **Factory Method**

### 답 쓸 때
Abstract Factory, Factory Method는 두 단어다. Singleton은 Singletone으로 쓰지 않는다.

## 구조 패턴
출제: 26-1, 25-2, 25-1, 23-1, 22-3
형태: 한 줄 설명 → 보기에서 영어로. Bridge는 Observer와 한 문제에 묶여 두 번 나옴

### 개념
| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Adapter** | 호환되지 않는 인터페이스를 변환해 함께 동작하게 한다 | "서로 다른 인터페이스 연결", "호환되지 않는", "변환", Wrapper |
| **Bridge** | 추상부(기능 계층)와 구현부(구현 계층)를 분리해 각각 독립적으로 확장한다 | "추상과 구현 분리", "독립적으로 확장·변형", "기능 계층·구현 계층" |
| **Composite** | 부분-전체 트리 구조를 만들어 개별 객체와 복합 객체를 같은 방식으로 다룬다 | "트리 구조", "부분-전체", "단일 객체와 복합 객체를 동일하게" |
| **Decorator** | 객체에 기능을 동적으로 덧붙인다. 서브클래스를 늘리지 않고 확장 | "동적으로 기능 추가", "장식", "상속 대신" |
| **Facade** | 복잡한 서브시스템에 단순한 통합 인터페이스 하나를 제공한다 | "단일 창구", "단순화된 인터페이스", "서브시스템", "결합도를 낮춤" |
| **Flyweight** | 공유 가능한 부분을 공유해 많은 수의 객체를 적은 메모리로 다룬다 | "공유", "메모리 절약", "다수의 작은 객체", "경량화" |
| **Proxy** | 다른 객체를 대신하는 대리 객체를 두어 접근을 제어한다 | "대리", "대신", "접근 제어", "지연·원격·보호" |

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Adapter vs Bridge | Adapter는 이미 만들어진 두 인터페이스가 안 맞을 때 사후에 변환한다(키워드 호환·변환). Bridge는 설계 단계에서 추상과 구현을 처음부터 분리한다(키워드 분리·독립 확장) |
| Facade vs Adapter | Facade는 여러 클래스 묶음 앞에 단순한 창구 하나를 세운다. Adapter는 인터페이스 모양을 바꾼다. "단순화·서브시스템"이면 Facade |
| Proxy vs Adapter | Proxy는 실제 객체와 같은 인터페이스를 유지한 채 앞에서 접근을 통제한다. Adapter는 인터페이스를 바꾼다 |
| Decorator vs Proxy | 둘 다 같은 인터페이스로 실제 객체를 감싼다. Decorator는 기능 추가가 목적이고 겹겹이 쌓인다. Proxy는 접근 제어가 목적이고 보통 한 겹이다 |
| Composite vs Decorator | 둘 다 재귀 구조다. Composite는 자식이 여러 개인 트리, Decorator는 하나를 감싼 사슬 |

### 기출에서 이렇게 나왔다
- 26-1: 설명 2개 → **Bridge / Observer** (22-3과 같은 조합)
- 25-2: "대리 객체로 접근 제어" → **Proxy** (23-1 재출제)
- 25-1: "서로 다른 인터페이스를 연결" → **Adapter**
- 23-1: "객체의 대리자" → **Proxy**
- 22-3: 설명 2개 → **Bridge / Observer**

### 답 쓸 때
Bridge 지문의 "구현부"라는 말이 Adapter의 "인터페이스 변환"과 섞여 보일 수 있다. "분리·독립 확장"은 Bridge, "변환·호환"은 Adapter로 가른다.

## 행위 패턴
출제: 26-1, 24-2, 23-2, 22-3, 20-2
형태: 1~2줄 설명 → 보기에서 영어로. Observer가 3번으로 가장 많음

### 개념
| 패턴 | 목적 | 지문 단서 |
|---|---|---|
| **Chain of Responsibility** | 요청을 처리할 수 있는 객체가 나올 때까지 사슬을 따라 넘긴다 | "처리자 사슬", "요청을 다음으로 전달" |
| **Command** | 요청 자체를 객체로 캡슐화해 저장·취소·큐잉한다 | "요청을 객체로", "실행 취소(undo)·재실행", "매개변수화", "로그·큐" |
| **Interpreter** | 언어의 문법을 클래스로 표현하고 문장을 해석한다 | "문법", "해석기", "언어·표현식" |
| **Iterator** | 집합체의 내부 구조를 드러내지 않고 요소에 순차적으로 접근한다 | "내부 구조 노출 없이", "순차 접근", "반복자", "Cursor" |
| **Mediator** | 객체 사이의 상호작용을 중재자 하나에 모아 결합도를 낮춘다 | "중재자", "다대다 상호작용을 중앙 집중", "객체끼리 직접 참조하지 않음" |
| **Memento** | 객체 내부 상태를 저장해 두었다가 복원한다 | "상태 저장·복원", "스냅샷", "되돌리기", "캡슐화를 깨지 않고(내부 상태를 외부에 노출하지 않고)" |
| **Observer** | 한 객체의 상태가 바뀌면 그에 의존하는 객체들에 자동으로 알린다. 일대다 | "상태 변화", "자동 통지·갱신", "일대다", "발행-구독(Publish-Subscribe)", "이벤트 리스너" |
| **State** | 상태를 객체로 분리해, 상태에 따라 행동이 바뀌게 한다 | "상태에 따라 행동 변화", "상태 객체" |
| **Strategy** | 알고리즘 군을 각각 캡슐화해 서로 바꿔 끼울 수 있게 한다 | "알고리즘 교체", "실행 중 선택" |
| **Template Method** | 알고리즘 골격은 상위 클래스에 두고 세부 단계만 서브클래스에서 재정의한다 | "골격", "단계 재정의", "상속" |
| **Visitor** | 객체 구조는 그대로 두고 수행할 연산을 방문자 클래스로 분리한다 | "연산을 분리", "방문", "각 클래스를 돌아다니며", "구조 변경 없이 새 기능 추가" |

### 한눈에 구분
| 혼동 쌍 | 차이 |
|---|---|
| Strategy vs State | Strategy는 클라이언트가 알고리즘을 골라 끼우고 알고리즘끼리는 서로 모른다. State는 객체가 자기 상태에 따라 스스로 행동을 바꾸고 상태 객체가 다음 상태로 전이시킨다. 지문에 "상태"가 있으면 State |
| Strategy vs Template Method | Strategy는 위임(객체 교체), Template Method는 상속(골격 고정 + 빈 단계만 하위에서 채움) |
| Observer vs Mediator | Observer는 일대다 통지(발행자 → 구독자). Mediator는 다대다 상호작용을 객체 하나로 모은다 |
| Command vs Memento | Command는 "요청"을 객체화하고, Memento는 "상태"를 객체화한다. 되돌리기가 요청의 역연산이면 Command, 저장해 둔 상태 복원이면 Memento |
| Iterator vs Visitor | Iterator는 순회 자체. Visitor는 순회하면서 각 요소에 적용할 연산을 바깥 클래스로 뺀 것 |

### 기출에서 이렇게 나왔다
- 26-1: 설명 2개 → **Bridge / Observer**
- 24-2: "내부 구조를 노출하지 않고 순차 접근" → **Iterator**
- 23-2: 설명 2개 → **Singleton / Visitor**
- 22-3: 설명 2개 → **Bridge / Observer**
- 20-2: "상태 변화 시 의존 객체에 자동 통지, 일대다" → **Observer**

### 답 쓸 때
Observer 3번, Iterator·Visitor 각 1번이 정답이었다. 24-3·21-2 분류 문제에서는 Mediator·Interpreter·Iterator·Observer가 행위 패턴의 예시로 지문에 등장했다.

## 모듈 응집도·결합도
출제: 26-2, 26-1, 25-1, 24-2, 24-1, 21-3, 21-2, 21-1, 20-1
형태: 설명 3개 → 보기에서 3개 고르기가 기본. 한 줄 설명 → 하나, 높은 순 나열, 응집도·결합도 정의 자체. 보기에 응집도와 결합도가 섞여 있기도 함

### 개념
모듈화 품질을 재는 두 척도다. **응집도(Cohesion)** 는 모듈 안의 요소들이 하나의 기능에 얼마나 집중되어 있는가로, 높을수록 좋다. **결합도(Coupling)** 는 모듈 사이의 의존이 얼마나 강한가로, 낮을수록 좋다. 좋은 설계는 응집도는 높고 결합도는 낮은 것이다. 20-1에서 두 정의 자체가 출제됐다.

응집도 7종 (높음 → 낮음)

| 순위 | 응집도 | 핵심 단서 |
|---|---|---|
| 1 | **기능적(Functional)** | 모든 요소가 단일 기능 하나를 위해 존재. "하나의 문제와 연관된 기능만 수행" |
| 2 | **순차적(Sequential)** | 한 요소의 출력이 다음 요소의 입력. "이전 활동의 출력이 다음 활동의 입력" |
| 3 | **교환적(Communicational)** | 같은 입력 데이터를 쓰거나 같은 출력을 만드는 요소들이 모임. 순서는 무관. "동일한 입출력 데이터를 사용". 통신적이라고도 함 |
| 4 | **절차적(Procedural)** | 여러 기능을 정해진 순서대로 수행하지만 데이터는 넘기지 않음. "다수의 관련 기능을 순차적으로 수행" |
| 5 | **시간적(Temporal)** | 특정 시점에 함께 실행되어야 하는 것들을 묶음. "초기화", "같은 시간대에 처리" |
| 6 | **논리적(Logical)** | 비슷한 성격의 기능을 한 모듈에 넣고 매개변수로 골라 수행. "논리적으로 유사", "선택적으로 수행" |
| 7 | **우연적(Coincidental)** | 서로 관련 없는 요소들이 모임. "관련 없음", "임의로" |

두음: 기순교절시논우.

결합도 6종 (낮음 → 높음)

| 순위 | 결합도 | 핵심 단서 |
|---|---|---|
| 1 | **자료(Data)** | 매개변수로 단순 값만 주고받음. "값 전달", "가장 바람직" |
| 2 | **스탬프(Stamp)** | 배열·구조체 같은 자료 구조 전체를 전달. "자료 구조", "레코드 통째로" |
| 3 | **제어(Control)** | 플래그·제어 신호를 넘겨 상대 모듈의 논리 흐름을 바꿈. "제어 요소", "제어 신호", "논리적 흐름을 제어", "처리 대상뿐 아니라 처리 방법까지 전달". 하위 모듈이 상위 모듈에 처리 방법을 지시하면 권리 전도 현상이 생김 |
| 4 | **외부(External)** | 어떤 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈이 참조. 외부에서 정한 데이터 형식·통신 프로토콜·장치 인터페이스를 함께 쓰는 경우도 여기 든다. "외부 데이터", "프로토콜 공유" |
| 5 | **공통(Common)** | 전역 변수를 여러 모듈이 공유. "전역 변수", "공유 영역" |
| 6 | **내용(Content)** | 다른 모듈의 내부 데이터나 코드를 직접 참조·수정. "내부를 직접 참조", "가장 높음" |

두음: 자스제외공내. 높은 쪽부터 외우려면 거꾸로 "내공외제스자", 응집도는 낮은 쪽부터 "우논시절통순기"다.

### 한눈에 구분
| 혼동 쌍 | 가르는 기준 |
|---|---|
| 순차 vs 절차 | 데이터가 앞에서 뒤로 흐르면 순차, 순서만 있고 데이터는 안 넘기면 절차 |
| 교환 vs 순차 | 같은 데이터를 쓰되 순서가 없으면 교환, 앞 출력이 뒤 입력이면 순차 |
| 시간 vs 절차 | "특정 시점(초기화·종료)"이면 시간, "실행 순서"면 절차 |
| 논리 vs 우연 | 성격이 비슷하기는 하면 논리, 아무 관련 없으면 우연 |
| 스탬프 vs 자료 | 구조체·배열을 통째로 넘기면 스탬프, 값 하나하나면 자료 |
| 공통 vs 외부 | 여러 모듈이 공유 영역(전역 변수)을 함께 쓰면 공통, 한 모듈이 선언한 데이터를 다른 모듈이 참조하거나 외부 환경(프로토콜·장치·파일 형식)을 공유하면 외부 |
| 공통 vs 내용 | 공유 영역을 거치면 공통, 상대 모듈 내부를 직접 건드리면 내용 |

## Fan-in / Fan-out
출제: 22-2, 20-1
형태: 모듈 호출 구조도 → 특정 모듈의 Fan-in·Fan-out 값, 또는 Fan-in이 n 이상인 모듈 모두 고르기

### 개념
**Fan-in(공유도)** 은 어떤 모듈을 호출하는 상위 모듈의 수, 즉 그 모듈로 들어오는 화살표 수다. **Fan-out(제어도)** 은 그 모듈이 호출하는 하위 모듈의 수, 즉 나가는 화살표 수다.

| 지표 | 높으면 | 설계 방향 |
|---|---|---|
| Fan-in | 여러 곳에서 재사용되는 공통 모듈. 바람직하지만 그 모듈이 바뀌면 영향 범위가 넓음 | 높게 |
| Fan-out | 한 모듈이 너무 많은 하위 모듈을 통제함. 복잡도 증가 | 낮게. 적정 수를 넘으면 중간 모듈로 묶음 |

구조도를 읽을 때는 모듈 이름이 아니라 화살표 방향만 센다. → 세는 법과 그림 예는 [계산] 페이지.

### 기출에서 이렇게 나왔다
- 22-2: 모듈 다이어그램 → 모듈 F의 Fan-in **3**, Fan-out **2**
- 20-1: Fan-in이 2 이상인 모듈 → **F, H**

## UML 다이어그램
출제: 25-3, 23-3, 22-3, 21-3, 20-4
형태: 그림 또는 설명 → 다이어그램 이름. 구성요소 3개 중 빈칸 채우기

### 개념
UML 구성요소는 **사물(Things)**, **관계(Relationships)**, **다이어그램(Diagrams)** 세 가지다. 22-3에서 "관계"가 빈칸으로 나왔다.

| 사물 종류 | 내용 |
|---|---|
| 구조 사물 | 정적인 요소. 클래스, **인터페이스**, 유스케이스, 컴포넌트, 노드 등 |
| 행동 사물 | 시간과 공간에 따른 동작. 상호작용(메시지), 상태 머신 |
| 그룹 사물 | 요소를 묶는 단위. 패키지 |
| 주해 사물 | 부가 설명. 노트(note) |

**인터페이스(Interface)** 는 클래스나 컴포넌트가 외부에 보이는 동작(오퍼레이션)의 집합만 정의한 것이다. 혼자 쓰이지 않고 그것을 구현하는 클래스·컴포넌트와 함께 쓴다(22-3 세 번째 빈칸).

다이어그램은 정적 구조를 그리는 구조(정적) 다이어그램 6종과 동작을 그리는 행위(동적) 다이어그램 7종으로 나뉜다. UML 2.5 표준은 구조 쪽에 프로파일(Profile) 다이어그램을 하나 더 두어 모두 14종이지만, 수험서는 보통 구조 6·행위 7로 정리한다. 요약 자료에 따라 상호작용 개요를 빼고 행위를 6종으로 적기도 한다.

구조 다이어그램 6종

| 다이어그램 | 무엇을 그리나 | 단서 |
|---|---|---|
| **클래스(Class)** | 클래스의 속성·오퍼레이션과 클래스 간 관계. 시스템(도메인) 구조 | "속성과 메서드", "클래스 간 관계", "정적 구조" |
| **객체(Object)** | 특정 시점의 인스턴스와 그 관계. 클래스 다이어그램의 스냅샷 | "인스턴스", "특정 시점" |
| **컴포넌트(Component)** | 컴포넌트와 그 사이 인터페이스·의존 | "컴포넌트", "제공·요구 인터페이스" |
| **배치(Deployment)** | 노드(하드웨어)와 그 위에 놓인 산출물 | "물리적 배치", "노드" |
| **복합체 구조(Composite Structure)** | 클래스·컴포넌트의 내부 구조 | "내부 구조", "포트" |
| **패키지(Package)** | 요소를 패키지로 묶고 패키지 간 의존(import, access)을 표현. 유스케이스나 클래스 같은 요소를 그룹화 | 접힌 폴더 모양, 점선 화살표에 <<import>> |

행위 다이어그램 7종

| 다이어그램 | 무엇을 그리나 | 단서 |
|---|---|---|
| **유스케이스(Use Case)** | 액터와 시스템 기능, include·extend 관계 | "사용자 관점", "액터" |
| **시퀀스(Sequence)** | 객체 간 메시지를 시간 순(세로축)으로 | "시간 순서", "생명선", "메시지" |
| **커뮤니케이션(Communication)** | 시퀀스와 같은 정보를 객체 연결선 위의 번호 메시지로. 구 협력(Collaboration) 다이어그램 | "객체 간 연관과 메시지", "번호" |
| **상태(State)** | 한 객체의 상태 변화와 전이 이벤트 | "상태 전이", "이벤트" |
| **활동(Activity)** | 처리 흐름. 분기·병합·스윔레인 | "흐름도와 유사", "병렬 처리" |
| **타이밍(Timing)** | 시간 제약에 따른 상태 변화 | "시간 제약" |
| **상호작용 개요(Interaction Overview)** | 활동 다이어그램 안에 시퀀스 등 상호작용을 노드로 배치 | "상호작용을 개요 수준에서" |

두음: 구조 "클객컴배복패", 행위 "유시커상활타상".

유스케이스 다이어그램의 구성요소와 관계

| 요소·관계 | 표기 | 의미 |
|---|---|---|
| **액터(Actor)** | 막대 인간 | 시스템과 상호작용하는 사용자나 외부 시스템 |
| **유스케이스(Use Case)** | 타원 | 시스템이 제공하는 기능 단위 |
| **시스템 경계** | 사각형 | 시스템 범위 |
| 연관 | 실선 | 액터와 유스케이스 연결 |
| **포함(Include)** | 점선 화살표 + <<include>> | 기본 유스케이스를 실행하면 반드시 함께 실행되는 기능 |
| **확장(Extend)** | 점선 화살표 + <<extend>> | 특정 조건에서만 선택적으로 실행되는 기능 |
| 일반화 | 실선 + 빈 삼각형 | 공통 기능을 상위 유스케이스·액터로 추상화 |

## UML 클래스 다이어그램 관계
출제: 24-3, 21-3
형태: 관계 설명 2~3개 → 보기(한글 또는 영문)

### 개념
| 관계 | 의미 | 표기 | 단서 |
|---|---|---|---|
| **연관(Association)** | 서로 참조하는 일반적인 관계. 다중성(1, 0..*, 1..*)을 적음 | 실선. 방향이 있으면 화살표 | "관련이 있다", "다중성" |
| **집합(Aggregation)** | 전체-부분 관계. 부분이 전체 없이도 존재 가능 | 전체 쪽에 빈 마름모 + 실선 | "포함하지만 독립적", "공유 가능" |
| **포함(Composition)** | 전체-부분 관계. 부분의 생명주기가 전체에 종속 | 전체 쪽에 채운 마름모 + 실선 | "전체가 사라지면 부분도 사라짐", "강한 소유" |
| **일반화(Generalization)** | 상속. is-a | 자식에서 부모로 빈 삼각형 화살표, 실선 | "상위·하위", "일반적인 것과 구체적인 것" |
| **의존(Dependency)** | 한쪽이 바뀌면 다른 쪽이 영향을 받음. 매개변수·지역 변수로 잠깐 사용 | 점선 화살표 | "일시적으로 사용", "짧은 시간 동안만 연관", "영향을 받음" |
| **실체화(Realization)** | 인터페이스를 클래스가 구현. can-do | 점선 + 빈 삼각형 | "인터페이스 구현", "기능을 실제로 수행", "기능으로 묶인 관계" |

두음: "포집 연의 일실"(포함·집합 마름모, 연관·의존 화살표, 일반화·실체화 빈 삼각형). 각 쌍에서 앞이 강한 쪽(채운 마름모, 실선), 뒤가 약한 쪽(빈 마름모, 점선)이다.

클래스 다이어그램 기초 표기

| 표기 | 의미 |
|---|---|
| **가시성(Visibility)** | `+` public, `-` private, `#` protected, `~` package |
| **다중성(Multiplicity)** | `1` 정확히 하나, `0..1` 없거나 하나, `*` 또는 `0..*` 0개 이상, `1..*` 1개 이상, `n..m` n개 이상 m개 이하 |
| **스테레오타입(Stereotype)** | 기존 요소에 의미를 덧붙이는 확장 표기. 길러멧 `<< >>` 안에 쓴다. 예: <<interface>>, <<include>>, <<extend>> |

```mermaid
제목: 화살표 모양으로 관계를 구분한다. 속 찬 마름모 = 포함, 빈 마름모 = 집합, 빈 삼각형 실선 = 일반화, 빈 삼각형 점선 = 실체화
%% 폰: LR
classDiagram
  direction TB
  Car *-- Engine : 포함
  Team o-- Player : 집합
  Teacher --> Student : 연관
  Order ..> Payment : 의존
  Animal <|-- Dog : 일반화
  Flyable <|.. Bird : 실체화
```

### 한눈에 구분
| 혼동 쌍 | 가르는 기준 |
|---|---|
| 집합 vs 포함 | 마름모가 비었으면 집합, 채워졌으면 포함. 부분이 전체 없이 살 수 있으면 집합 |
| 연관 vs 의존 | 멤버 변수로 계속 참조하면 연관(실선), 메서드 안에서 잠깐 쓰면 의존(점선) |
| 일반화 vs 실체화 | 둘 다 빈 삼각형. 실선이면 일반화(상속), 점선이면 실체화(인터페이스 구현) |

### 기출에서 이렇게 나왔다
- 24-3: 설명 3개 → **연관 / 일반화 / 의존**
- 21-3: 설명 2개 → **Aggregation / Generalization** (영문)

### 답 쓸 때
집합은 집약, 포함은 복합·합성이라고도 부른다. 영문을 요구하면 Aggregation, Composition, Generalization, Realization의 철자를 그대로 쓴다.

## 요구사항 분류
출제: 26-1, 21-1
형태: 사례 3개 → 비기능 요구사항 유형 보기 / 설명 2개 → 기능·비기능 구분

### 개념
**기능 요구사항(Functional)** 은 시스템이 무엇을 해야 하는가다. 입력·출력·처리·제공 기능이 여기 속한다. **비기능 요구사항(Non-functional)** 은 어떤 수준과 조건으로 해야 하는가다. 품질이나 제약 사항에 관한 것으로, 시스템 장비 구성·성능·인터페이스·테스트·보안 요구사항이 여기 속한다.

비기능 요구사항 유형 6종

| 유형 | 내용 | 사례 단서 |
|---|---|---|
| **운영** | 운영 환경·시간·인력에 관한 조건 | "24시간 무중단", "특정 OS 환경에서 운영" |
| **자원** | 하드웨어·메모리·저장 공간·네트워크 등 자원 조건 | "메모리 n GB 이상", "디스크 용량" |
| **성능** | 응답 시간·처리량·동시 사용자 수 | "n초 이내 응답", "동시 접속 n명" |
| **보안** | 접근 통제·암호화·인증 | "암호화 저장", "권한 없는 접근 차단" |
| **품질** | 신뢰성·가용성·사용성·유지보수성 | "가용성 n%", "장애 복구" |
| **문화·정책** | 법·규정·조직 정책·문화적 제약 | "개인정보보호법 준수", "다국어 지원" |

요구사항 개발(요구공학 프로세스)은 도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인(Validation) 순으로 진행한다. 단계별 기법은 파일 끝 "요구사항 도출·명세 기법과 구조적 분석 도구" 묶음에 있다.

### 기출에서 이렇게 나왔다
- 26-1: 사례 3개 → **운영 / 자원 / 성능**
- 21-1: 설명 2개 → **기능적 / 비기능적**

### 답 쓸 때
사례형은 "시간·환경"이면 운영, "하드웨어 수치"면 자원, "응답·처리 속도"면 성능으로 먼저 가른다.

## UI 설계 원칙

### 개념
| 원칙 | 내용 | 단서 |
|---|---|---|
| **직관성(Intuitiveness)** | 누구나 쉽게 이해하고 사용할 수 있어야 한다 | "쉽게 이해", "누구나" |
| **유효성(Efficiency)** | 사용자의 목표를 정확하고 완벽하게 달성할 수 있어야 한다 | "정확하고 완벽하게", "목표 달성" |

**UI(User Interface)** 는 사용자와 시스템이 만나는 접점(화면·조작 수단)이고, **UX(User Experience)** 는 제품을 사용하면서 느끼는 총체적 경험·반응·감정이다. UI 설계 지침으로는 사용자 중심, 일관성, 단순성, 결과 예측 가능, 가시성, 표준화, 접근성, 명확성, 오류 발생 해결 등이 있다.

UI 설계 산출물은 실제 완성품과 닮은 정도(충실도)가 낮은 것에서 높은 것 순으로 만든다.

| 산출물 | 내용 |
|---|---|
| **와이어프레임(Wireframe)** | 선과 상자로 화면 뼈대·레이아웃만 잡은 것. 색·디자인 없음 |
| **목업(Mockup)** | 와이어프레임에 색·이미지·글꼴을 입힌 정적 시안. 동작하지 않음 |
| **프로토타입(Prototype)** | 클릭·화면 전환이 실제로 되는 동작 모형 |
| **스토리보드(Storyboard)** | 화면 설계에 설명과 화면 흐름까지 담은 최종 문서. 디자이너·개발자가 함께 보는 지침서 |
| 유스케이스 명세 | 사용자와 시스템의 상호작용 시나리오를 글로 쓴 것 |

### 기출에서 이렇게 나왔다

## 객체지향 SOLID
출제: 22-2
형태: 한 원칙 설명 2줄 + 예시 → 보기

### 개념
| 원칙 | 내용 | 단서 |
|---|---|---|
| **SRP(Single Responsibility)** 단일 책임 | 클래스를 변경하는 이유는 하나여야 한다 | "책임 하나", "변경 이유" |
| **OCP(Open-Closed)** 개방-폐쇄 | 확장에는 열려 있고 수정에는 닫혀 있어야 한다 | "기존 코드 수정 없이 확장" |
| **LSP(Liskov Substitution)** 리스코프 치환 | 자식 클래스는 부모 클래스를 대체할 수 있어야 한다 | "하위 타입으로 치환" |
| **ISP(Interface Segregation)** 인터페이스 분리 | 클라이언트가 쓰지 않는 메서드에 의존하지 않도록 인터페이스를 작게 나눈다 | "사용하지 않는 인터페이스", "복합기(인쇄·복사·팩스) 예" |
| **DIP(Dependency Inversion)** 의존 역전 | 구체 클래스가 아니라 추상(인터페이스)에 의존한다. 고수준 모듈이 저수준 모듈에 직접 의존하지 않는다 | "추상에 의존", "구체에 의존하지 않음", "고수준이 저수준에 의존하지 않음" |

### 기출에서 이렇게 나왔다
- 22-2: "관련 없는 인터페이스 변경에 영향을 받지 않음, 복합기 예" → **ISP**

### 답 쓸 때
ISP와 SRP가 헷갈린다. "인터페이스를 쪼갠다"면 ISP, "클래스의 책임 하나"면 SRP다.

## 럼바우 객체 모델링(OMT)
출제: 21-2
형태: 산출물 설명 3개 → 모델링 이름 영문

### 개념
럼바우(Rumbaugh)의 객체 모델링 기법은 세 가지 모델링을 객체 → 동적 → 기능 순으로 수행한다.

| 모델링 | 내용 | 산출물 |
|---|---|---|
| **객체 모델링(Object Modeling)**. 정보 모델링(Information Modeling)이라고도 함 | 객체·속성·연산과 객체 간 관계를 찾아 구조를 정의. 가장 먼저 | 객체 다이어그램(E-R 다이어그램 형태) |
| **동적 모델링(Dynamic Modeling)** | 시간 흐름에 따른 객체의 상태·이벤트·전이, 제어 흐름 | 상태 다이어그램(상태도) |
| **기능 모델링(Functional Modeling)** | 입력에서 출력까지 데이터의 흐름과 처리 | 자료 흐름도(DFD) |

두음: 객동기. 다른 방법론은 한 줄만 둔다. Booch(미시적·거시적 프로세스), Jacobson(유스케이스 중심), Coad-Yourdon(E-R 다이어그램 활용), Wirfs-Brock(분석과 설계 구분 없이 연속).

### 기출에서 이렇게 나왔다

### 답 쓸 때
산출물로 거꾸로 맞춘다. DFD이면 기능, 상태도이면 동적, 객체 다이어그램이면 객체.

## 애자일
출제: 20-2
형태: 특징 설명 → 용어

### 개념
**애자일(Agile)** 은 짧은 주기로 반복 개발하면서 고객과 소통하고 변화에 유연하게 대응하는 방법론의 총칭이다. 애자일 선언의 4가지 가치는 개인과 상호작용, 동작하는 소프트웨어, 고객과의 협력, 변화에 대응을 각각 프로세스와 도구, 포괄적 문서, 계약 협상, 계획 준수보다 중시한다.

| 구분 | 워터폴(폭포수) | 애자일 |
|---|---|---|
| 진행 | 단계를 순차로, 되돌아가기 어려움 | 짧은 반복(iteration)을 여러 번 |
| 중심 | 문서·계획 | 동작하는 소프트웨어·사람 |
| 변경 | 후반 변경 비용이 큼 | 변경을 수용 |
| 고객 참여 | 초기 요구 분석 위주 | 전 과정에 지속 |

대표 방법론

| 방법론 | 핵심 |
|---|---|
| **XP(eXtreme Programming)** | 5가지 가치(용기·단순성·의사소통·피드백·존중). 12가지 실천 사항: 짝 프로그래밍, 테스트 주도 개발(TDD), 리팩토링, 지속적 통합(CI), 소규모 릴리즈, 공동 코드 소유, 계획 게임, 단순한 설계, 지속 가능한 속도(주 40시간), 고객 상주, 메타포, 코딩 표준 |
| **스크럼(Scrum)** | 제품 책임자·스크럼 마스터·개발팀. 스프린트 단위 반복, 제품 백로그·스프린트 백로그, 데일리 스크럼, 번다운 차트 |
| **칸반(Kanban)** | 작업을 보드에 시각화하고 진행 중 작업(WIP) 수를 제한해 흐름을 관리하는 도구 |
| **린(Lean)** | 도요타 생산 방식에서 온 낭비 제거 철학. 가치 없는 활동을 없애 빠르게 전달 |
| 크리스탈, FDD | 프로젝트 규모·중요도에 맞춘 방법론군(크리스탈), 기능 단위 반복 개발(FDD) |

### 기출에서 이렇게 나왔다

## 비용 산정
출제: 20-1
형태: LoC·인원·생산성 수치 → 개발 기간 계산

### 개념
| 방식 | 기법 | 내용 |
|---|---|---|
| 하향식 | **전문가 감정** | 경험 많은 전문가 몇 명이 추정. 빠르지만 주관적 |
| 하향식 | **델파이(Delphi)** | 조정자가 여러 전문가의 익명 추정을 모아 반복 수렴 |
| 상향식 | **LoC(원시 코드 라인 수)** | 낙관·기대·비관 라인 수의 가중 평균으로 규모 추정 |

| 수학적 | **FP(기능 점수)** | 입력·출력·조회·파일·인터페이스 수에 가중치를 곱해 기능 점수 산출. 도구 ESTIMACS |

수학적 산정 기법도 크게 보면 상향식에 속한다(경험적·실험적 추정 모형이라고도 함).

| COCOMO 유형 | 규모(수험서 기준) | 특징 |
|---|---|---|
| **조직형(Organic)** | 5만(50 KDSI) 라인 이하 | 소규모, 익숙한 업무. 사무 처리·과학 기술 계산용 |
| **반분리형(Semi-detached)** | 30만(300 KDSI) 라인 이하 | 중규모. 조직형과 내장형의 중간. 컴파일러, 트랜잭션 처리 시스템 |
| **내장형(Embedded)** | 30만 라인 초과 | 하드웨어와 밀접한 대규모·실시간 시스템. 신호 제어, 미사일 유도 |

COCOMO는 세부 수준에 따라 기본형(Basic), 중간형(Intermediate), 발전형(Detailed)으로도 나눈다. 반분리형을 반결합형이라고 적은 자료도 있다.

LoC 계산식은 텍스트로 다음과 같다.

- 예측 LoC = `(낙관치 + 4 × 기대치 + 비관치) / 6`
- 노력(인월) = `LoC / 1인당 월 생산성`
- 개발 기간(월) = `노력 / 투입 인원`
- 비용 = `노력 × 1인 월 단가`

→ 풀이는 [계산] 페이지.

### 기출에서 이렇게 나왔다
- 20-1: 36,000라인, 6명, 1인 월 300라인 → 개발 기간 **20개월** (36,000 / 300 = 120인월, 120 / 6 = 20)

## 리팩토링
출제: 20-3
형태: 정의 설명 → 용어

### 개념
**리팩토링(Refactoring)** 은 외부 동작은 그대로 둔 채 내부 구조를 개선하는 작업이다. 목적은 가독성·유지보수성·확장성 향상, 중복 제거, 결함 발견 용이다. 서술형으로 목적을 물으면 "프로그램을 쉽게 이해하고 수정할 수 있게 하여 빠르게 개발하기 위함"이라고 쓴다. 기능 변경이 아니므로 리팩토링 전후에 테스트로 동작이 같음을 확인한다.

| 용어 | 차이 |
|---|---|
| 리팩토링 | 동작 유지, 코드 내부 구조 개선. 작은 단위 |
| 리엔지니어링(재공학) | 기존 시스템을 분석해 새 요구에 맞게 재구성. 큰 단위 |
| 리버스 엔지니어링(역공학) | 코드·시스템에서 설계·명세를 거꾸로 추출 |

클린 코드 원칙(가독성·단순성·의존성 배제·중복 제거·추상화)이 리팩토링의 방향이다.

### 기출에서 이렇게 나왔다
- 20-3: "외부 동작은 그대로, 내부 구조 개선" → **리팩토링**

## 4+1 뷰
출제: 없음

### 개념
Kruchten의 4+1 뷰는 소프트웨어 아키텍처를 다섯 관점으로 나눠 기술한다. 유스케이스 뷰가 가운데에서 나머지 네 뷰를 묶고 검증한다.

| 뷰 | 관점 | 주 이해관계자 | 관련 UML |
|---|---|---|---|
| **유스케이스 뷰(시나리오 뷰)** | 시스템이 제공하는 기능 시나리오. 다른 4개 뷰의 근거 | 사용자·분석가 | 유스케이스 다이어그램 |
| **논리 뷰** | 기능 요구사항을 만족하는 클래스·패키지 구조 | 최종 사용자(기능 관점), 설계자 | 클래스·패키지·상태 |
| **프로세스 뷰** | 동시성·성능·프로세스와 스레드 | 통합자 | 활동·시퀀스 |
| **구현 뷰(개발 뷰)** | 모듈·컴포넌트 구성과 소스 조직 | 프로그래머 | 컴포넌트 |
| **배포 뷰(물리 뷰)** | 하드웨어 노드에 소프트웨어를 어떻게 배치하는가 | 시스템 엔지니어 | 배치 |

### 한눈에 구분
"+1"은 유스케이스 뷰다. 논리 뷰는 무엇이 있는가, 프로세스 뷰는 어떻게 동시에 도는가, 구현 뷰는 코드가 어떻게 나뉘는가, 배포 뷰는 어느 장비에 올라가는가로 기억한다.

## 소프트웨어 생명주기 모델
출제: 없음

### 개념
| 모델 | 특징 |
|---|---|
| **폭포수(Waterfall)** | 앞 단계를 끝내야 다음 단계로 가는 순차·단방향 모델. 고전적 생명주기. 되돌아가기 어렵다 |
| **프로토타입(Prototype)** | 시제품을 먼저 만들어 사용자에게 보여 주고 요구사항을 확인·보완한다 |
| **나선형(Spiral)** | 계획 수립 → 위험 분석 → 개발·검증 → 고객 평가를 반복. 위험 분석이 핵심이고 대규모 시스템에 맞다 |
| **반복적·점진적(Iterative/Incremental)** | 여러 번 반복하며 기능을 조금씩 더해 완성한다 |
| **진화적(Evolutionary)** | 핵심 기능부터 만들고 사용자 피드백으로 점점 발전시킨다 |
| **V 모델** | 폭포수를 확장해 개발 단계마다 대응하는 테스트 단계를 V자로 짝지었다. 검증·확인 강조 |
| **RAD(Rapid Application Development)** | CASE 도구와 재사용으로 매우 짧은 기간에 개발한다 |
| **4GT(4세대 기법)** | 4세대 언어(4GL)와 자동 생성 도구로 코드를 만든다 |
| **애자일(Agile)** | 짧은 반복, 고객 협력, 변화 수용. 위 "애자일" 묶음 참고 |

### 한눈에 구분
"순차·단계 완료"는 폭포수, "시제품"은 프로토타입, "위험 분석"은 나선형, "개발 단계와 테스트 단계 대응"은 V 모델이다. V 모델의 테스트 쪽은 [SW 개발] 페이지의 테스트 레벨과 같다.

## 요구사항 도출·명세 기법과 구조적 분석 도구
출제: 없음

### 개념
도출 기법: **인터뷰**, **브레인스토밍**, **JAD(Joint Application Development)** 워크숍(개발자와 사용자가 함께 모여 집중 회의), 설문, **델파이**(전문가 익명 설문을 반복해 합의), 프로토타이핑, 관찰, 유스케이스.

| 명세 기법 | 내용 | 예 |
|---|---|---|
| **정형(Formal) 명세** | 수학·논리 기반 표기. 모호성이 적고 검증이 쉽지만 작성·이해가 어렵다 | VDM, Z, Petri-net, CSP |

명세서는 명확성, 완전성, 검증 가능성, 추적 가능성을 갖춰야 한다.

구조적 분석 도구는 **DFD(자료 흐름도)**, **DD(자료 사전)**, **소단위 명세서(Mini-Spec)**, ERD, STD(상태 전이도)다.

| DFD 요소 | 기호 | 의미 |
|---|---|---|
| 프로세스(Process) | 원 | 입력 자료를 처리·변환 |
| 자료 흐름(Data Flow) | 화살표 | 자료의 이동 |
| 자료 저장소(Data Store) | 평행선 | 파일·DB |
| 단말(Terminator) | 사각형 | 시스템 밖의 자료 발생지·도착지 |

자료 사전 기호: `=` 정의, `+` 연결, `( )` 생략 가능, `[ | ]` 선택, `{ }` 반복, `* *` 주석.

## 구조적 설계 도구 (HIPO·N-S 차트)
출제: 없음

### 개념
**HIPO(Hierarchy Input Process Output)** 는 시스템의 입력·처리·출력 기능을 계층적으로 그리는 하향식 설계·문서화 도구다. 기능과 자료의 관계를 한눈에 보여 주고 유지보수가 쉽다.

| HIPO 도표 | 내용 |
|---|---|
| **가시적 도표**(도식 목차, Visual Table of Contents) | 전체 기능을 트리 구조로 보여 줌 |
| **총체적 도표**(총괄·개요 도표) | 기능별 입력·처리·출력을 개괄적으로 표현 |
| **세부적 도표**(상세 도표) | 총체적 도표의 각 기능을 자세히 기술 |

**N-S 차트(Nassi-Schneiderman Chart)** 는 논리 흐름을 박스로만 표현하는 구조적 설계 도구다. 순차·선택(IF, CASE)·반복 구조만 쓰고 화살표와 GOTO가 없어서 구조적 프로그래밍에 맞다. 순서도와 달리 임의의 제어 이동을 표현하기 어렵다.

## 코드 설계 (코드 종류)
출제: 없음

### 개념
코드는 자료를 식별·분류하려고 붙이는 기호다. 시험에서는 예시를 보고 종류를 고르게 한다.

| 코드 | 방식 | 예 |
|---|---|---|
| **순차 코드(Sequence)** | 일련번호를 차례로 부여 | 1, 2, 3, 4 |
| **블록 코드(Block)** | 공통 특성별로 구간을 정하고 그 안에서 번호 부여 | 총무부 100~199, 영업부 200~299 |
| **그룹 분류 코드(Group)** | 대·중·소 분류 자릿수마다 의미를 부여 | 1-01-001 |
| **10진 코드(Decimal)** | 10진 분할로 대·중·소 분류를 세분화 | 도서 분류(KDC·DDC) |
| **표의 숫자 코드(Significant Digit)** | 길이·무게 등 실제 수치를 그대로 코드로 | 지름 100, 길이 200 → 100-200 |
| **연상 코드(Mnemonic)** | 대상을 떠올리게 하는 문자·기호 | TV-40, KR |
| **합성 코드(Combined)** | 두 가지 이상 코드를 조합 | 연상 + 순차 |

## 소프트웨어 아키텍처 패턴과 품질 속성
출제: 없음

### 개념
| 패턴 | 내용 |
|---|---|
| **계층화(Layered)** | 기능을 계층으로 나누고 하위 계층이 바로 위 계층에 서비스를 제공. OSI 7계층이 예 |

## 일정 관리 (PERT·CPM·간트 차트)
출제: 없음

### 개념
| 기법 | 내용 |
|---|---|
| **PERT** | 작업마다 낙관·보통(기대)·비관 시간을 추정해 불확실성을 반영. 기대 시간 = `(낙관 + 4 × 보통 + 비관) / 6` |
| **CPM(Critical Path Method)** | 작업 간 선후 관계로 네트워크를 그리고, 시작부터 끝까지 가장 긴 경로(임계 경로)를 찾는다. 임계 경로 길이가 프로젝트 최소 완료 기간이다 |
| **간트 차트(Gantt Chart)** | 작업별 시작·종료 시점을 막대로 그려 일정과 진척을 보여 준다. 작업 간 의존 관계는 잘 드러나지 않는다 |

### 한눈에 구분
"불확실성·세 가지 추정치"는 PERT, "최장 경로·임계 경로"는 CPM, "막대그래프"는 간트 차트다. LoC 비용 산정의 가중 평균식과 PERT 기대 시간식은 모양이 같다.

## 소프트웨어 개발 프로세스·품질 표준
출제: 없음

### 개념
**CMMI(Capability Maturity Model Integration)** 는 미국 SEI가 만든 조직의 개발 프로세스 성숙도 모델로, 1~5의 5단계로 평가한다.

| 단계 | 이름 | 상태 |
|---|---|---|
| 1 | **초기(Initial)** | 정해진 프로세스 없이 개인 역량에 의존 |
| 2 | **관리(Managed)** | 프로젝트 단위로 계획·관리. 비슷한 프로젝트를 반복할 수 있음 |
| 3 | **정의(Defined)** | 조직 표준 프로세스를 정하고 문서화 |
| 4 | **정량적 관리(Quantitatively Managed)** | 수치 데이터로 프로세스를 관리 |
| 5 | **최적화(Optimizing)** | 프로세스를 지속적으로 개선 |

**SPICE(ISO/IEC 15504)** 는 프로세스 평가·개선 국제 표준으로, 프로세스 능력을 0~5의 6수준으로 평가한다. 0 **불완전(Incomplete)** → 1 **수행(Performed)** → 2 **관리(Managed)** → 3 **확립(Established)** → 4 **예측(Predictable)** → 5 **최적화(Optimizing)**.

| 표준·용어 | 내용 |
|---|---|
| **ISO/IEC 12207** | 소프트웨어 생명주기 프로세스 표준. 개발·운영·유지보수에 필요한 프로세스를 정의 |
| **ISO/IEC 25000(SQuaRE)** | 소프트웨어 품질 요구와 평가를 통합한 표준군. 예전의 ISO/IEC 9126(품질 모델)과 14598(품질 평가)을 묶었다. 품질 특성은 그 안의 25010이 정한다 |
| **CBD(Component Based Development)** | 이미 만든 컴포넌트를 조립해 개발하는 방식. 재사용 단위는 함수 → 객체 → 컴포넌트 → 시스템 순으로 커진다 |

ISO/IEC 25010(2011판) 제품 품질 특성 8가지: **기능 적합성**, **성능 효율성**, **호환성**(다른 시스템과 상호 운용·공존), **사용성**, **신뢰성**, **보안성**, **유지보수성**, **이식성**(다른 환경으로 옮기기 쉬움).

### 한눈에 구분
0수준(불완전)이 있고 6개면 SPICE, 1단계부터 5개면 CMMI다. 둘 다 마지막 이름이 "최적화"이고 2번이 "관리"라서 섞이기 쉽다. CMMI 4단계는 "정량적 관리", SPICE 4수준은 "예측"이다.
