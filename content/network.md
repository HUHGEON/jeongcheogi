# 네트워크

21개 회차 420문제 가운데 네트워크 이론은 38문제다. 그중 서브넷·IP 계산이 7회차 8문제로 가장 많고, 라우팅 프로토콜·네트워크 계층 프로토콜·데이터 링크가 각 6문제로 뒤를 잇는다. 문제는 대부분 두 가지 모양으로 나온다. 설명 두 줄을 주고 영문 약어를 쓰게 하거나, 긴 지문에 뚫린 빈칸 4~5개를 보기에서 골라 채우게 한다. 그리고 2024년 이후에는 이미 나왔던 문제가 다시 나오기도 했다. 라우터 그림은 24-1 문제가 26-2에 수치까지 똑같이 다시 나왔고, 서브넷 계산은 22-2와 같은 유형이 25-2에 수치만 바뀌어 다시 나왔다. 계산 절차는 [계산] 페이지에서 따로 다루고, 여기서는 개념과 표기, 구분 단서만 정리한다.

## 서브넷 마스크·CIDR·프리픽스
출제: 26-2, 26-1, 25-2, 25-1, 24-1, 22-3, 22-2
형태: 호스트 IP + 마스크(또는 /n) → 네트워크 주소·사용 가능 호스트 수·같은 네트워크의 IP·프리픽스 길이 / 라우터 그림의 빈칸에 할당 가능한 IP

### 헷갈리기 쉬운 용어
이 묶음에는 이름이 비슷한 말이 여럿 나온다. 먼저 무엇을 구하는 데 쓰는지만 표로 갈라 두고 시작하자.

| 용어 | 설명 |
|---|---|
| 서브넷 마스크 | 네트워크 주소 구하는 데 사용 |
| CIDR 표기법 | 서브넷 마스크를 /26처럼 짧게 쓰는 방법 |
| 프리픽스 길이 | CIDR 표기 /24의 24, 서브넷 마스크의 1의 개수 |
| 블록 크기 | 256 − 서브넷 마스크의 마지막 자리 |
| 서브네팅(FLSM) | 서브넷 구하는 데 사용 |

### 서브넷 마스크
서브넷 마스크 문제는 IPv4 주소로만 나온다. IPv6는 주소가 너무 길어서다. IPv4 주소는 32비트이고 8비트씩 넷으로 나누는데, 8비트 하나가 0~255의 10진수가 되므로 IP 주소는 0.0.0.0부터 255.255.255.255까지 쓸 수 있다.

#### 서브넷 마스크를 쓰는 이유
서브넷 마스크를 쓰면 IP 주소 고갈이 해결된다고 오해하기 쉬운데, 그렇지 않다. IPv4 주소의 총량은 대략 43억 개로 정해져 있고, 2011년에 이미 모두 소진되었다. 그래서 지금은 아래 방법으로 버틴다.

- 신규 서비스·모바일에 IPv6 할당
- 이미 할당한 IPv4 주소의 중고 거래
- NAT 기술로 사설 IP 주소(192.168.x.x)를 써서 IPv4 주소 절약

IPv4가 이렇게 빨리 바닥난 데는 PC, 스마트폰 같은 기기가 급격히 늘어난 탓도 있지만, 주소를 빌려주던 방식도 문제였다. 예전의 클래스 할당 방식은 국가나 초대형 기업에 한 번에 많은 IP 주소(약 1650만 개)를 임대했다. 서브넷 마스크는 IPv4 주소를 이보다 잘게 나눠서 임대할 수 있게 해 준다.

#### IP 주소를 임대해 보자
내가 192.168.1.0 ~ 192.168.255.255의 IP 주소를 갖고 있다고 해보자. A기업에 256개를 빌려주고 싶다면 192.168.1.0 ~ 192.168.1.255를 주면 되고, 이렇게 말하면 된다.

> "A기업은 192.168.1.0 네트워크 주소를 사용하세요. 서브넷 마스크는 255.255.255.0입니다."

임대 계약서에는 늘 이 두 줄이 한 세트로 들어간다. 그럼 여기서 말하는 네트워크 주소는 IP 주소와 같은 걸까?

#### IP 주소 종류
IP 주소는 **네트워크 주소**, 호스트 주소, **브로드캐스트 주소**로 나뉜다. "192.168.1.0 네트워크 주소를 사용하세요"라는 말을 들은 A기업은 192.168.1.0이 자기가 할당받은 네트워크의 대표 주소라는 것을 알게 된다. 서브넷 마스크가 255.255.255.0이면 세 주소는 아래처럼 갈린다.

| 구분 | 주소 | 끝자리 2진수 |
|---|---|---|
| 네트워크 주소 | 192.168.1.0 | 00000000 |
| 호스트 주소 | 192.168.1.1 ~ 192.168.1.254 | 00000001 ~ 11111110 |
| 브로드캐스트 주소 | 192.168.1.255 | 11111111 |

끝자리 0은 네트워크, 255는 브로드캐스트, 그 사이가 호스트다. 그렇다면 "서브넷 마스크는 255.255.255.0입니다"라는 말은 무슨 뜻일까?

#### 서브넷 마스크는 쓸 수 있는 주소의 범위를 정한다
255.255.255.0을 2진수로 바꾸면 11111111.11111111.11111111.00000000이다. 서브넷 마스크는 이렇게 앞부분이 1, 뒷부분이 0으로 되어 있고, 뒤의 0의 개수가 쓸 수 있는 주소의 범위를 정한다. 00000000부터 11111111까지 모든 조합을 IP 주소로 쓸 수 있다는 뜻이다.

여기서 헷갈리기 쉬운 점이 있다. 네트워크 부분과 호스트 부분으로 나뉘는 것은 마스크가 아니라 **IP 주소**다. 서브넷 마스크는 IP 주소 옆에 나란히 대 보고 "여기까지가 네트워크 부분, 나머지는 호스트 부분"이라는 경계를 읽는 자(ruler)라고 보면 된다. 주소를 자르는 도구가 아니라 눈금을 읽는 도구이고, 마스크가 바뀌면 재는 자리도 바뀐다. 아래는 192.168.1.100 옆에 255.255.255.0을 댄 모습이다.

```bits
제목: 마스크의 1과 0이 바뀌는 자리가 곧 주소의 경계다. 192.168.1.100에 255.255.255.0(/24)을 대면 앞 24비트가 네트워크 부분이다
192.168.1.100/24
```

- **네트워크 부분**: 마스크의 1이 놓인 자리. 같은 그룹 안 모든 장치가 동일
- **호스트 부분**: 마스크의 0이 놓인 자리. 장치마다 하나씩 할당

여기서 '네트워크'는 하나로 묶인 장치들의 그룹이다. 아파트로 치면 네트워크 부분은 '몇 동', 호스트 부분은 '몇 호'다. 그래서 0의 개수가 곧 쓸 수 있는 주소의 범위가 된다. 비트 하나마다 0 아니면 1, 2가지 경우가 있으니, 255.255.255.0처럼 0이 8개면 2^8 = 256개의 IP 주소를 임대할 수 있다.

서브넷 마스크가 255.255.255.224라면 어떨까? 2진수로 11111111.11111111.11111111.11100000이라 뒤의 0이 5개다. 주소를 정하는 데 쓸 수 있는 비트가 5개이므로 2^5 = 32개의 IP 주소를 쓸 수 있다.

#### B기업이 쓰는 네트워크 주소 구하기
이번에는 B기업에 이렇게 말했다고 해보자.

> "B기업은 192.168.1.123이 포함된 IP 주소를 사용하세요. 서브넷 마스크는 255.255.255.192입니다."

B기업이 쓰는 네트워크 주소는 무엇일까? 네트워크 주소는 호스트 부분이 모두 0인 주소다. 서브넷 마스크는 네트워크 자리가 1, 호스트 자리가 0이므로, IP 주소와 AND 연산하면 호스트 부분만 모두 0이 되어 네트워크 주소가 나온다. AND 연산은 두 비트가 모두 1일 때만 1이 되는 계산법이다.

```
  11000000.10101000.00000001.01|111011  (IP 주소)
& 11111111.11111111.11111111.11|000000  (서브넷 마스크)
--------------------------------------
  11000000.10101000.00000001.01|000000  (네트워크 주소)
```

`|`는 마스크의 1과 0의 경계, 곧 네트워크 부분과 호스트 부분의 경계다. 왼쪽은 IP 주소의 원래 값이 그대로 남고, 오른쪽은 모두 0이 된다. 호스트 부분을 0으로 칠하면 네트워크 주소가 되는 셈이다. 결과 11000000.10101000.00000001.01000000을 10진수로 바꾸면 192.168.1.64이고, 이것이 B기업의 네트워크 주소다.

```bits
제목: 192.168.1.123에 255.255.255.192(/26)를 AND 하면 호스트 6비트가 0이 되어 네트워크 주소 192.168.1.64가 된다
192.168.1.123/26
```

B기업이 받은 전체 IP 주소는 마스크의 0이 6개라 64개이고, 범위는 192.168.1.64 ~ 192.168.1.127이다. 이 가운데 192.168.1.64는 네트워크 주소, 192.168.1.127은 브로드캐스트 주소라서 장치에 할당하지 않는다. 장치에 줄 수 있는 호스트 주소는 192.168.1.65 ~ 192.168.1.126, 모두 62개다.

### 호스트 주소와 서브넷 마스크로 네트워크 주소 구하기
방금 192.168.1.123을 그냥 IP 주소라고 불렀는데, 이것은 결국 호스트 주소다. 네트워크 주소도 브로드캐스트 주소도 아니면 호스트 주소이기 때문이다. 호스트 주소와 서브넷 마스크가 있으면 방금처럼 AND 연산으로 네트워크 주소를 거꾸로 알아낼 수 있다.

### 네트워크 주소와 서브넷 마스크로 브로드캐스트 주소 구하기
브로드캐스트 주소는 호스트 부분이 모두 1인 주소다. 서브넷 마스크를 반전(NOT)하면 호스트 부분만 1인 값이 되는데, 이것을 OR 연산하면 호스트 부분이 모두 1로 채워져 브로드캐스트 주소가 된다.

- **반전(NOT)**: 1은 0으로, 0은 1로 바꾸는 연산
- **OR 연산**: 두 비트 중 하나라도 1이면 1

25-2 기출 상황(호스트 223.13.234.132, 서브넷 마스크 255.255.255.192)으로 해보자. 네트워크 주소는 AND 연산으로 223.13.234.128이 나온다. 마스크 11111111.11111111.11111111.11000000을 반전하면 00000000.00000000.00000000.00111111이고, 이것을 네트워크 주소와 OR 연산하면 아래와 같다.

```
  11011111.00001101.11101010.10|000000  (네트워크 주소)
| 00000000.00000000.00000000.00|111111  (반전된 서브넷 마스크)
--------------------------------------
  11011111.00001101.11101010.10|111111  (브로드캐스트 주소)
```

이번에는 호스트 부분을 1로 칠한 셈이다. 그런데 네트워크 주소 대신 호스트 주소와 OR 연산해도 결과는 같다.

```
  11011111.00001101.11101010.10|000100  (호스트 주소)
| 00000000.00000000.00000000.00|111111  (반전된 서브넷 마스크)
--------------------------------------
  11011111.00001101.11101010.10|111111  (브로드캐스트 주소)
```

두 경우 모두 10진수로 223.13.234.191이다.

```bits
제목: 25-2 기출 223.13.234.132/26. 호스트 6비트를 0으로 칠하면 네트워크 주소 128, 1로 칠하면 브로드캐스트 주소 191이다
223.13.234.132/26
```

왜 네트워크 주소로 하든 호스트 주소로 하든 결과가 같을까? 반전된 마스크는 호스트 부분이 모두 1이고, OR 연산에서 1과 만나면 상대 값이 무엇이든 1이 된다. 그래서 호스트 부분은 원래 값이 모두 0이든 아무 값이든 상관없이 모두 1로 채워진다. 반대로 네트워크 부분은 반전된 마스크가 모두 0이라 원래 값이 그대로 남는데, 네트워크 주소와 호스트 주소는 네트워크 부분이 같으니 결과도 같을 수밖에 없다.

### 할당 가능 범위 구하기
네트워크 주소와 브로드캐스트 주소를 구했다면 마지막 한 단계가 남는다. 실제 장치(PC, 스마트폰 등)에 나눠 줄 수 있는 할당 가능 범위다. 두 주소는 장치에 할당할 수 없으므로 그 사이 주소만 할당할 수 있다. 맨 앞과 맨 뒤는 예약석이고 가운데만 장치 몫이라고 보면 된다.

> 할당 가능 범위 = (네트워크 주소 + 1) ~ (브로드캐스트 주소 − 1)

지금까지의 계산을 순서대로 이으면 이렇다.

| 순서 | 계산 | 결과 |
|---|---|---|
| 1 | IP 주소 AND 서브넷 마스크 | 네트워크 주소 |
| 2 | 네트워크 주소 OR 반전(NOT)된 서브넷 마스크 | 브로드캐스트 주소 |
| 3 | 네트워크 주소 + 1 ~ 브로드캐스트 주소 − 1 | 할당 가능 범위 |

#### 예시: 서브넷 마스크 255.255.255.192
앞의 25-2 상황(호스트 223.13.234.132, 마스크 255.255.255.192)을 그대로 이어 가면 결과는 아래와 같다.

| 구하는 것 | 결과 |
|---|---|
| 네트워크 주소 | 223.13.234.128 |
| 브로드캐스트 주소 | 223.13.234.191 |
| 할당 가능 범위 | 223.13.234.129 ~ 223.13.234.190 |

전체 주소 64개 가운데 네트워크 주소와 브로드캐스트 주소 2개를 뺀 62개를 장치에 할당할 수 있다.

서브넷 마스크가 255.255.255.0이면 더 단순하다. 호스트 부분이 마지막 자리 8비트 전체라서 네트워크 주소의 마지막 자리는 0, 브로드캐스트 주소의 마지막 자리는 255가 된다. 호스트 주소가 192.168.35.3이면 할당 가능 범위는 192.168.35.1 ~ 192.168.35.254다.

```bits
제목: 192.168.35.3/24는 호스트 부분이 마지막 자리 8비트 전체라서 네트워크 주소 끝자리가 0이다
192.168.35.3/24
```

두 예시 모두 앞의 세 자리(223.13.234, 192.168.35)는 그대로 두고 마지막 자리만 계산하면 된다.

#### 예시: 서브넷 마스크 255.255.252.0
이번에는 마스크의 셋째 자리가 255가 아닌 경우다. 호스트 부분이 셋째 자리까지 들어오니 셋째 자리도 계산해야 하지만, 순서는 똑같다. 호스트 주소 129.200.10.16, 서브넷 마스크 255.255.252.0으로 해보자. CIDR 표기법으로는 129.200.10.16/22이고, /22는 마스크의 1이 22개라는 뜻이다. 255.255.252.0은 2진수로 11111111.11111111.11111100.00000000이라 0이 10개, 곧 셋째 자리의 뒤 2비트와 넷째 자리 8비트 전체가 호스트 부분이다.

**1단계: 네트워크 주소 (AND 연산)**

```
  10000001.11001000.000010|10.00010000  (호스트 주소)
& 11111111.11111111.111111|00.00000000  (서브넷 마스크)
--------------------------------------
  10000001.11001000.000010|00.00000000  (네트워크 주소)
```

셋째 자리 00001010(10)의 뒤 2비트가 0이 되어 00001000(8)이 된다. 네트워크 주소는 129.200.8.0이다. 마지막 자리만 0으로 바꾼 129.200.10.0은 네트워크 주소가 아니다. 셋째 자리에도 호스트 부분이 2비트 들어 있기 때문이다.

```bits
제목: 129.200.10.16/22는 셋째 자리 뒤 2비트도 호스트 부분이라 10이 8로 내려가고, 네트워크 주소는 129.200.8.0이다
129.200.10.16/22
```

**2단계: 브로드캐스트 주소 (NOT → OR 연산)**

마스크를 반전하면 00000000.00000000.00000011.11111111이고, 이것을 네트워크 주소와 OR 연산한다.

```
  10000001.11001000.000010|00.00000000  (네트워크 주소)
| 00000000.00000000.000000|11.11111111  (반전된 서브넷 마스크)
--------------------------------------
  10000001.11001000.000010|11.11111111  (브로드캐스트 주소)
```

셋째 자리 뒤 2비트까지 1로 채워져 00001011(11)이 되고, 넷째 자리는 11111111(255)이 된다. 브로드캐스트 주소는 129.200.11.255다.

**3단계: 할당 가능 범위**

- 시작: 네트워크 주소 129.200.8.0 + 1 = 129.200.8.1
- 끝: 브로드캐스트 주소 129.200.11.255 − 1 = 129.200.11.254

할당 가능 범위는 129.200.8.1 ~ 129.200.11.254다. 호스트 비트가 10개이므로 전체 주소는 2^10 = 1024개이고, 2개를 뺀 1022개를 할당할 수 있다.

이 네트워크는 129.200.8.0부터 129.200.11.255까지 1024개 주소가 하나로 이어진 범위다. 그래서 할당할 수 없는 주소는 맨 처음(129.200.8.0)과 맨 끝(129.200.11.255) 두 개뿐이고, 중간에 끼어 있는 129.200.8.255나 129.200.9.0은 끝자리가 255, 0이어도 평범한 주소다. 아래 그림처럼 8.255와 9.0은 블록 경계에 붙은 이웃 주소일 뿐이다.

```mermaid
제목: 129.200.8.0/22는 8.0 ~ 11.255가 하나로 이어진 범위라서, 양 끝만 할당 불가이고 경계에 붙은 8.255와 9.0은 할당 가능하다
%% 폰: TB

  A["8.0<br/>네트워크 주소<br/>할당 불가"]:::no --- B["8.1 ~ 8.254"] --- C["8.255<br/>할당 가능"]:::ok --- D["9.0<br/>할당 가능"]:::ok --- E["9.1 ~ 11.254"] --- F["11.255<br/>브로드캐스트 주소<br/>할당 불가"]:::no
  classDef no fill:#fdecee,stroke:#f3a3a9,color:#7a1f27
  classDef ok fill:#e9f8ee,stroke:#86d19b,color:#1f5a2e
```

2진수로 보면 확실하다. 호스트 부분 10비트가 모두 0(네트워크 주소)이거나 모두 1(브로드캐스트 주소)인 주소는 맨 처음과 맨 끝뿐이다.

| 주소 | 호스트 부분 (10비트) | 할당 여부 |
|---|---|---|
| 129.200.8.0 | 00.00000000 (모두 0) | 불가 (네트워크 주소) |
| 129.200.8.255 | 00.11111111 | 가능 |
| 129.200.9.0 | 01.00000000 | 가능 |
| 129.200.11.255 | 11.11111111 (모두 1) | 불가 (브로드캐스트 주소) |

끝자리가 0이나 255여도 할당할 수 있는 주소가 있다는 점이 함정이다. 255.255.255.0에서는 끝자리 0과 255가 곧 네트워크 주소와 브로드캐스트 주소라서 '끝자리 0·255는 할당 불가'로 외우기 쉽다. 하지만 /22처럼 범위가 여러 블록에 걸치면, 할당할 수 없는 주소는 범위 전체의 맨 처음과 맨 끝 두 개뿐이다.

### CIDR 표기법
"192.168.1.0 네트워크 주소를 사용하세요. 서브넷 마스크는 255.255.255.0입니다."라는 두 줄은 `192.168.1.0/24` 한 줄로 줄여 쓸 수 있다. 이렇게 쓰는 방식을 **CIDR** 표기법이라고 하고, 24는 서브넷 마스크에서 1의 개수다. IPv4는 모두 32비트이므로 마스크의 0의 개수는 32 − 24 = 8이 된다.

```bits
제목: 192.168.1.0/24의 24는 서브넷 마스크 255.255.255.0에서 1의 개수다
192.168.1.0/24
```

마스크가 255.255.255.192라면 어떻게 쓸까? 2진수로 11111111.11111111.11111111.11000000이라 1이 26개다. 그래서 `192.168.1.0/26`이라고 쓰면 같은 뜻이 된다.

### 프리픽스 길이
CIDR 표기법에서 슬래시 뒤의 숫자(/24의 24)를 **프리픽스 길이(prefix length)**라고 부른다. 문제에 따라 프리픽스 비트 길이, 줄여서 프리픽스라고도 하는데 모두 같은 숫자다.

> 프리픽스 길이 = CIDR 표기의 슬래시 뒤 숫자 = 서브넷 마스크에서 1의 개수 = 네트워크 부분의 비트 수

prefix는 '앞에 붙는 부분'이라는 뜻이다. IP 주소 32비트 중 앞쪽 네트워크 부분이 몇 비트인지 세는 값이라 이런 이름이 붙었다. 결국 프리픽스는 네트워크 부분의 다른 이름이다. 마스크를 직접 다룰 때는 네트워크 부분, CIDR 표기법으로 그 길이를 셀 때는 프리픽스라고 부를 뿐 같은 자리를 가리킨다. 그래서 아래에서는 네트워크(프리픽스)로 함께 적는다.

#### 32비트는 두 조각으로만 나뉜다
IP 주소 32비트는 네트워크(프리픽스) 부분과 호스트 부분, 딱 두 조각으로 나뉜다. 서브넷 마스크는 주소의 일부가 아니라 그 경계를 재는 별도의 32비트 값이라, 같은 자리끼리 위아래로 맞춰 보면 한눈에 보인다.

```
주소   192.168.1.200   : 11000000.10101000.00000001.11|001000
마스크 255.255.255.192 : 11111111.11111111.11111111.11|000000
                         └──── 1이 26개 ────────────┘ └ 0이 6개 ┘
                              = 프리픽스 26비트         = 호스트 6비트
```

```bits
제목: 192.168.1.200/26은 프리픽스 26비트와 호스트 6비트 두 조각이다
192.168.1.200/26
```

그래서 두 조각의 비트 수를 더하면 항상 32다.

> 프리픽스 길이 + 호스트 비트 수 = 32

#### 하나의 표기에 담긴 정보
192.168.1.0/26이라는 한 줄에는 아래 내용이 모두 들어 있다.

| 표현 | 값 |
|---|---|
| 프리픽스 길이 | 26 |
| CIDR 표기법 | 192.168.1.0/26 |
| 서브넷 마스크 | 255.255.255.192 |
| 서브넷 마스크의 1의 개수 | 26개 |
| 호스트 비트 수 | 32 − 26 = 6개 |
| 전체 IP 주소 개수 | 2^6 = 64개 |

'프리픽스 비트 길이를 쓰시오'는 결국 CIDR 표기의 숫자를 묻는 것이다. 숫자만 쓰라는지, 슬래시까지 붙이라는지는 문제의 단서를 확인한다.

#### 주소 개수로 프리픽스 길이 거꾸로 구하기
지금까지는 마스크를 주고 "이건 /몇이냐"를 묻는 방향이었다. 반대로 마스크 없이 주소 개수나 주소 범위만 주고 프리픽스 길이를 되묻는 문제가 26-2에 나왔다. 순서는 이렇다.

1. 주소 개수를 구한다. 범위로 주어졌으면 끝 주소 − 시작 주소 + 1
2. 주소 개수를 2^n 꼴로 바꿔 호스트 비트 수 n을 구한다
3. 프리픽스 길이 = 32 − n

범위로 개수를 셀 때 마지막에 1을 더하는 것을 잊기 쉽다. 10.0.0.0 ~ 10.0.0.15는 15 − 0 = 15개가 아니라 시작과 끝을 모두 넣은 16개다. 이 1개 차이 때문에 프리픽스 길이가 한 칸 어긋나기 쉽다. 이 범위로 해보면 이렇다.

- 주소 개수: 15 − 0 + 1 = 16개
- 16 = 2^4이므로 호스트 비트 4개
- 프리픽스 길이: 32 − 4 = 28

이 서브넷은 10.0.0.0/28이고, 프리픽스 비트 길이는 28이다.

```bits
제목: 10.0.0.0 ~ 10.0.0.15는 주소 16개라 호스트 4비트, 프리픽스 28비트다
10.0.0.0/28
```

여기서 문제에 적힌 네트워크의 프리픽스와, 그 안을 쪼갠 서브넷의 프리픽스는 다르다는 점을 조심해야 한다. 10.0.0.0/27을 주소 16개짜리 서브넷 둘로 나누면 각 서브넷은 /28이 된다. 어느 쪽 프리픽스를 묻는지 먼저 확인한다. 아래 표를 익혀 두면 시험장에서 계산 시간을 줄일 수 있다.

| 주소 개수 | 호스트 비트 | 프리픽스 길이 | 서브넷 마스크 |
|---|---|---|---|
| 256 | 8 | /24 | 255.255.255.0 |
| 128 | 7 | /25 | 255.255.255.128 |
| 64 | 6 | /26 | 255.255.255.192 |
| 32 | 5 | /27 | 255.255.255.224 |
| 16 | 4 | /28 | 255.255.255.240 |
| 8 | 3 | /29 | 255.255.255.248 |
| 4 | 2 | /30 | 255.255.255.252 |

#### 서브넷 비트도 결국 프리픽스다
책에 따라 IP 주소를 네트워크 + 서브넷 + 호스트 세 조각으로 설명하기도 한다. 조각이 셋으로 늘어난 것 같지만, 결과를 CIDR 표기법으로 적으면 다시 두 조각으로 돌아온다. 서브네팅(FLSM)은 호스트 부분의 앞쪽 몇 비트를 떼어 서브넷을 구분하는 데 쓰는데, 이 서브넷 비트는 "여기까지가 네트워크"라는 경계를 뒤로 미는 역할이라 프리픽스에 그대로 합쳐진다. /24에서 서브넷 비트 2개를 떼면 아래처럼 24 + 2 = 26, 곧 /26이 된다.

```bits
제목: /24에서 서브넷 비트 2개를 떼면 조각이 느는 게 아니라 경계가 뒤로 밀려 24 + 2 = 26이 된다
192.168.1.0/24
192.168.1.0/26
```

CIDR 표기법은 네트워크냐 서브넷이냐를 구분하지 않는다. '앞에서 몇 비트인지'만 세자고 만든 표기법이라, 서브넷 비트도 프리픽스 안에 그대로 들어간다.

### 블록 크기
네트워크 주소와 브로드캐스트 주소는 AND/OR 연산만으로 모두 구할 수 있다. 블록 크기(block size)는 같은 답을 더 빨리 구하는 단축 기법일 뿐이라, AND/OR 연산이 익숙하면 건너뛰어도 된다. 주로 서브넷 마스크의 앞 세 자리가 모두 255인 경우(/25 ~ /30)에 쓴다. 255가 아닌 자리가 둘 이상인 경우(예: 255.255.128.0)에는 블록 크기를 적용할 자리부터 찾아야 해서 조금 까다롭지만, 실기 출제 범위에서는 마지막 자리만 255가 아닌 경우가 대부분이라 잘 통한다.

| 용어 | 설명 |
|---|---|
| 블록 크기 | 256 − 서브넷 마스크의 마지막 자리 |
| 블록 | 주소를 블록 크기만큼 끊은 한 구간 |
| 시작값 | 그 블록의 네트워크 주소 마지막 자리 |
| 끝값 | 그 블록의 브로드캐스트 주소 마지막 자리 |

크기 하나만 알면 왜 두 주소가 다 나올까? 우리가 구하려는 두 주소가 사실 무엇인지 보면 분명해진다.

| 구하려는 것 | 정체 |
|---|---|
| 네트워크 주소 | 내가 속한 구간의 시작값 |
| 브로드캐스트 주소 | 같은 구간의 끝값 |

두 주소를 구하는 일은 "내가 속한 구간이 어디서 시작해 어디서 끝나는가"를 찾는 일과 같다. 그런데 같은 서브넷 마스크를 쓰는 구간들은 0부터 같은 크기로 규칙적으로 끊긴다. 구간 크기가 32라면 경계는 0, 32, 64, 96 …처럼 32의 배수에서만 생기고, 중간에 어중간하게 끊기는 일이 없다. 구간 크기 하나만 알면 모든 경계가 정해지는 셈이고, 이 구간 크기가 바로 블록 크기다.

#### 블록 크기 공식

> 블록 크기 = 256 − 서브넷 마스크의 마지막 자리

서브넷 마스크가 255.255.255.224라면 블록 크기는 256 − 224 = 32다.

#### 왜 256에서 빼면 될까
255.255.255.224로 두 방법이 같은 곳에 도착하는지 보자. 마지막 자리 224는 2진수로 11100000이다.

- **호스트 비트로 세기**: 0이 5개, 2^5 = 32
- **256에서 빼기**: 256 − 224 = 32

256에서 빼는 것은 그 개수를 2진수 변환 없이 구하는 지름길이다. 왜 늘 같을까? 마스크의 마지막 자리는 앞쪽이 1, 뒤쪽이 0인 8비트다. 뒤쪽 0의 개수를 n이라고 하면, 그 값은 8비트 전체(256)에서 뒤쪽 n비트만큼(2^n)을 덜어 낸 값이다.

> 마스크 마지막 자리 = 256 − 2ⁿ  (n = 호스트 비트 수)

양변을 옮기면 2ⁿ = 256 − 마스크 마지막 자리, 곧 블록 크기 공식이 된다.

| 마스크 마지막 자리 | 2진수 | 호스트 비트 | 2^n | 256 − 마스크 |
|---|---|---|---|---|
| 128 | 10000000 | 7 | 128 | 128 |
| 192 | 11000000 | 6 | 64 | 64 |
| 224 | 11100000 | 5 | 32 | 32 |
| 240 | 11110000 | 4 | 16 | 16 |
| 248 | 11111000 | 3 | 8 | 8 |

다르게 보면 마스크에서 가장 오른쪽 1의 자릿값이 곧 블록 크기다. 11100000에서 마지막 1은 32의 자리이고, 네트워크 주소가 0, 32, 64, 96처럼 32씩 뛰는 이유가 이것이다.

#### 블록으로 끊어 호스트가 속한 구간 찾기
0 ~ 255를 블록 크기만큼 쪼개고, 호스트 주소의 마지막 자리가 어느 블록에 드는지 찾는다. 블록 크기가 32면 아래처럼 8개 블록이 된다.

| 블록 | 시작값 | 끝값 |
|---|---|---|
| 1 | 0 | 31 |
| 2 | 32 | 63 |
| 3 | 64 | 95 |
| 4 | 96 | 127 |
| 5 | 128 | 159 |
| 6 | 160 | 191 |
| 7 | 192 | 223 |
| 8 | 224 | 255 |

호스트 주소가 속한 블록에서

- 블록의 시작값: 네트워크 주소의 마지막 자리
- 블록의 끝값: 브로드캐스트 주소의 마지막 자리

시작값은 블록 크기의 배수이고, 끝값은 다음 시작값보다 1 작은 수다.

> 끝값 = 시작값 + 블록 크기 − 1

32씩 끊는다면 시작값이 128일 때 끝값은 128 + 32 − 1 = 159다.

#### 시험장에서 빠르게 구간 찾기
블록을 0부터 하나씩 늘어놓을 필요는 없다. 호스트 주소의 마지막 자리만 있으면 시작값이 바로 나온다.

- **방법 1, 나눗셈**: 마지막 자리 ÷ 블록 크기의 몫 × 블록 크기. 144, 블록 크기 32면 몫 4, 시작값 4 × 32 = 128, 끝값 128 + 32 − 1 = 159
- **방법 2, 더해 올라가기**: 0부터 블록 크기를 계속 더하다 호스트 주소를 넘으면 직전 값이 시작값. 0 → 32 → 64 → 96 → 128 → 160, 160이 144를 넘었으니 시작값 128, 끝값 159

블록 크기는 128, 64, 32, 16, 8, 4 같은 2의 거듭제곱이라 경계가 늘 깔끔하게 떨어지고, 암산으로 더해 올라가도 금방 찾는다.

#### 예시: 호스트 주소 203.14.234.144, 서브넷 마스크 255.255.255.224
- 블록 크기: 256 − 224 = 32
- 마지막 자리 144가 속한 블록: 128 ~ 159
- 네트워크 주소 203.14.234.128, 브로드캐스트 주소 203.14.234.159

```bits
제목: 144가 속한 블록 128 ~ 159의 시작값 128이 네트워크 주소, 끝값 159가 브로드캐스트 주소다
203.14.234.144/27
```

2진수 AND/OR 연산 결과와 같다. 원리는 B기업 예처럼 AND/OR 연산으로 이해하고, 시험장에서 빨리 풀 때는 블록 크기를 써도 된다.

### 서브네팅(FLSM)
서브넷 마스크로 A기업에 특정 IP 주소 범위를 임대할 수 있었다. 그런데 그보다 더 잘게 쪼개서 주고 싶다면 어떻게 할까?

> "A기업은 192.168.1.0 네트워크 주소를 사용하세요. 서브넷 마스크는 255.255.255.0입니다. 그런데 두 번째 64개 IP 주소만 사용하세요."

이럴 때 쓰는 것이 **서브네팅(FLSM)**이고, 두 번째 64개 IP 주소처럼 쪼갠 조각을 서브넷(서브 네트워크)이라고 한다. 케이크를 한 번 자르는 것이 서브넷 마스크라면, 그 조각을 또 자르는 것이 서브네팅이다.

#### FLSM (Fixed Length Subnet Mask)
**FLSM**은 고정 길이 서브넷 마스크, 곧 주어진 네트워크를 모두 같은 크기의 서브넷 여러 개로 나누는 방식이다. /24 네트워크를 4개 서브넷으로 나누면 모든 서브넷이 똑같이 /26 마스크를 갖는다. /24는 주소 256개짜리 묶음이니 이것을 같은 크기 4개로 나눠 보자.

- 서브넷 크기: 256 / 4 = 64개
- 새 CIDR 표기: 64 = 2^6이라 주소를 나타내는 데 6자리 필요
- 결론: 32자리 중 6자리를 뺀 32 − 6 = 26자리가 네트워크 식별용, 곧 /26

FLSM의 장단점은 이렇다.

- **장점**: 모든 서브넷 크기가 같아 관리가 단순함
- **단점**: 실제 필요한 호스트 수와 상관없이 같은 크기로 할당해 IP 주소 낭비 발생

이 단점을 보완하는 것이 **VLSM(Variable Length Subnet Mask)**이다. 같은 크기가 아니라 서브넷마다 필요에 따라 크기를 달리 나누는 기술로, 어떤 부서에는 IP가 100개, 다른 부서에는 10개만 필요할 때 VLSM을 쓰면 주소를 훨씬 효율적으로 할당할 수 있다.

#### 몇 비트로 나눌까
서브넷은 서브넷 마스크(2진수)에서 뒤쪽 0인 부분을 써서 나눈다. A기업의 마스크는 11111111.11111111.11111111.00000000이므로 뒤쪽 8자리 0을 쓰고, 이 8비트 중 앞쪽 n비트로 서브넷을 만든다. 몇 비트를 쓸지는 몇 개로 나누느냐에 달려 있다.

> i개로 나누는 경우: 2^n ≥ i를 만족하는 n개의 비트 사용

2^n ≥ 4를 만족하는 n은 2이므로 앞쪽 2비트를 쓴다. 그러면 서브넷 4개가 이렇게 생긴다.

| 서브넷 | 마지막 자리 |
|---|---|
| 첫 번째 | 00XXXXXX |
| 두 번째 | 01XXXXXX |
| 세 번째 | 10XXXXXX |
| 네 번째 | 11XXXXXX |

#### 서브넷 비트
이렇게 호스트 부분에서 떼어 서브넷을 구분하는 데 쓰는 비트를 **서브넷 비트**라고 한다. 위 예에서는 앞쪽 2개가 서브넷 비트다. 서브넷 비트는 서브네팅을 할 때만 생긴다. 서브넷을 나누지 않으면 호스트 부분은 전부 호스트 비트이고, 그중 일부를 서브넷 구분용으로 빌려 쓰는 순간 그 비트를 서브넷 비트라고 부르는 것이다.

앞에서 봤듯 서브넷 비트는 "여기까지가 네트워크"라는 경계를 뒤로 미는 역할이라, 호스트 쪽이 아니라 프리픽스에 합쳐진다. 그래서 각 서브넷은 24 + 2 = 26, 곧 /26이 된다.

#### 왜 하필 앞쪽 비트를 뗄까
뒤쪽 비트로 서브넷을 나눈다고 해보자. 마지막 2비트로 나누면 첫 번째 서브넷은 XXXXXX00, 곧 0, 4, 8, 12 …처럼 4칸씩 건너뛴 주소가 된다. 주소가 이렇게 흩어지면 문제가 생긴다.

- 연속된 구간이 아니라 "어디부터 어디까지"라고 범위를 말할 수 없음
- 호스트 부분이 모두 0인 네트워크 주소, 모두 1인 브로드캐스트 주소를 정할 수 없음
- 마스크는 앞이 전부 1, 뒤가 전부 0이어야 하는데 1과 0이 뒤섞여 마스크로 표현 불가

앞쪽 비트를 떼야 각 서브넷이 연속된 주소 블록이 되고, 경계가 한 군데라 서브넷 마스크로 나타낼 수 있다.

#### 서브넷 비트 수에 따른 변화
서브넷 비트를 몇 개 쓰느냐에 따라 서브넷 개수와 서브넷 하나의 크기는 반대로 움직인다. /24(주소 256개)를 나누는 경우다.

| 서브넷 비트 | 서브넷 개수 | 각 서브넷 크기 | 프리픽스 | 서브넷 마스크 |
|---|---|---|---|---|
| 1 | 2 | 128 | /25 | 255.255.255.128 |
| 2 | 4 | 64 | /26 | 255.255.255.192 |
| 3 | 8 | 32 | /27 | 255.255.255.224 |
| 4 | 16 | 16 | /28 | 255.255.255.240 |

잘게 나눌수록 서브넷 하나에 들어가는 주소가 줄어드는 이유는, 빌려 온 비트만큼 호스트 비트가 줄기 때문이다. 서브넷 비트 수와 호스트 비트 수를 더하면 원래 호스트 부분의 비트 수 그대로다.

#### 서브넷의 네트워크 주소 구하기
A기업이 받은 두 번째 64개 IP 주소의 첫 주소는 마지막 자리가 01000000, 10진수로 64다. 그래서 두 번째 서브넷의 네트워크 주소는 192.168.1.64다.

```bits
제목: 두 번째 서브넷은 서브넷 비트가 01이라 네트워크 주소 끝자리가 64다
192.168.1.64/26
```

같은 방법으로 4개 서브넷을 모두 구하면 아래와 같다. 서브넷 비트를 고정하고 나머지 호스트 비트를 모두 0으로 두면 네트워크 주소, 모두 1로 채우면 브로드캐스트 주소이고, 두 주소 사이가 할당 가능 범위다.

| 서브넷 | 마지막 자리 | 네트워크 주소 | 브로드캐스트 주소 | 할당 가능 범위 |
|---|---|---|---|---|
| 첫 번째 | 00XXXXXX | 192.168.1.0 | 192.168.1.63 | 192.168.1.1 ~ 192.168.1.62 |
| 두 번째 | 01XXXXXX | 192.168.1.64 | 192.168.1.127 | 192.168.1.65 ~ 192.168.1.126 |
| 세 번째 | 10XXXXXX | 192.168.1.128 | 192.168.1.191 | 192.168.1.129 ~ 192.168.1.190 |
| 네 번째 | 11XXXXXX | 192.168.1.192 | 192.168.1.255 | 192.168.1.193 ~ 192.168.1.254 |

각 서브넷의 네트워크 주소가 64씩 커진다. 이 64가 서브넷 하나의 크기이자 블록 크기다.

### 전체 그림
라우팅 프로토콜은 전체 갈래를 한 번에 머릿속에 그려 두면 잘 외워진다. 라우팅은 네트워크 계층(OSI 3계층)에서 이루어지고, 아래 순서대로 나뉜다.

- 라우팅 프로토콜 = 정적 라우팅 + 동적 라우팅
- 동적 라우팅 = 내부 라우팅 프로토콜(IGP) + 외부 라우팅 프로토콜(EGP)
- IGP에 RIP, OSPF 포함
- EGP에 BGP 포함

```mermaid
제목: 네트워크 계층에서 시작해 정적·동적으로, 동적은 IGP와 EGP로 나뉘고, IGP에 RIP·OSPF, EGP에 BGP가 속한다
%% 폰: TB
flowchart LR
  N["네트워크 계층<br/>(OSI 7계층 중 3계층)"] --> R["라우팅 프로토콜"]
  R --> S["정적 라우팅"]
  R --> D["동적 라우팅"]
  D --> I["내부 라우팅 프로토콜<br/>(IGP)"]
  D --> E["외부 라우팅 프로토콜<br/>(EGP)"]
  I --> RIP("RIP<br/>Routing Information Protocol")
  I --> OSPF("OSPF<br/>Open Shortest Path First")
  E --> BGP("BGP<br/>Border Gateway Protocol")
```

| 내부 라우팅 프로토콜(IGP) | 같은 네트워크 내 |
| 외부 라우팅 프로토콜(EGP) | 다른 네트워크 간 |
| RIP | 홉(hop) 수 사용 |
| OSPF | 경로 비용 사용, 링크 상태 알고리즘, AS를 지역(Area)으로 나눔 |
| BGP | 경로 벡터 알고리즘 사용, 초기 전체 라우팅 테이블 교환 |

### 라우팅
**라우팅(Routing)**이란 네트워크에서 데이터 패킷을 출발지에서 목적지까지 보낼 때 최적의 경로를 정하는 과정을 말한다. 인터넷에서 데이터는 한 번에 목적지로 가지 않고 여러 라우터를 거쳐 전달된다. 라우터는 네트워크 계층에서 라우팅을 맡는 장비로, 서로 다른 네트워크를 잇고 패킷의 경로를 정한다. 이때 각 라우터는 **라우팅 테이블**, 곧 목적지 네트워크 주소와 그쪽으로 보내기 위한 다음 경로 정보가 적힌 표를 보고 패킷을 다음에 어디로 보낼지 결정한다. 이 라우팅 테이블을 만드는 방법에 따라 정적 라우팅과 동적 라우팅으로 나뉜다.

### 정적 라우팅과 동적 라우팅
정적 라우팅은 깔아 둔 선로를 그대로 달리는 기차, 동적 라우팅은 상황에 따라 길을 다시 찾는 내비게이션에 가깝다.

- **정적 라우팅**: 라우터 설정 시 미리 경로를 정의하고 고정된 경로를 사용하는 방식
- **동적 라우팅**: 라우터끼리 경로 정보를 주고받아 경로를 자동으로 계산하고 동적으로 바꾸는 방식

### 내부 라우팅 프로토콜(IGP)과 외부 라우팅 프로토콜(EGP)
동적 라우팅은 같은 네트워크 안에서 쓰는지, 다른 네트워크 사이에서 쓰는지로 다시 나뉜다. 이름에 붙은 게이트웨이는 다른 네트워크로 나가는 출입구를 뜻하는데, 라우팅 프로토콜 이름에서는 경로 정보를 주고받는 라우터를 가리킨다. 그래서 게이트웨이 프로토콜은 라우팅 프로토콜과 같은 뜻으로 보면 된다.

- **IGP(Interior Gateway Protocol)**: 같은 네트워크 내에서 사용하는 라우팅 프로토콜
- **EGP(Exterior Gateway Protocol)**: 다른 네트워크 간에 사용하는 라우팅 프로토콜

그럼 같은 네트워크와 다른 네트워크는 무엇으로 가를까? 기준은 하나의 조직이 관리하는 네트워크 영역인 자율 시스템(AS)이다. 아래 그림처럼 AS 안에서는 IGP로, AS 사이의 경계에서는 EGP로 경로 정보를 주고받는다.

```mermaid
제목: AS 안은 IGP, AS 사이는 EGP로 경로 정보를 주고받는다
%% 폰: TB
flowchart LR
  subgraph AS1["AS 1"]
    R1("라우터") <-->|"IGP"| R2("라우터")
  end
  subgraph AS2["AS 2"]
    R3("라우터") <-->|"IGP"| R4("라우터")
  end
  R2 <==>|"EGP"| R3
```

### 자율 시스템(AS)
같은 네트워크와 다른 네트워크를 가르는 가장 중요한 기준이 **자율 시스템(AS, Autonomous System)**이다. AS는 하나의 도메인(같은 관리 주체)에 속하는 라우터들의 집합이다.

- **같은 네트워크(같은 AS)**: 하나의 조직이나 기관이 관리하는 네트워크 영역
- **다른 네트워크(다른 AS)**: 서로 다른 조직이나 기관이 관리하는 네트워크 영역

관리 주체로 말하면, 같은 네트워크는 동일한 관리자나 조직이 제어하는 영역이고 다른 네트워크는 서로 다른 관리 주체가 운영하는 네트워크다. 예를 들면 이렇다.

| 구분 | 예 |
|---|---|
| 같은 네트워크 (IGP 사용) | 한 회사 내부의 여러 부서 네트워크, 대학교 캠퍼스 안 건물별 네트워크 |
| 다른 네트워크 (EGP 사용) | KT와 SKT 같은 서로 다른 통신사 네트워크, 한국과 미국의 인터넷 연결, 서로 다른 ISP(인터넷 서비스 제공업체) 간 연결 |

각 AS는 AS 번호로 구분한다.

- **공인 AS 번호**: 통신사·대형 기관처럼 인터넷 전체에 자기 경로를 알리는 조직에 할당, 인터넷 전체에서 겹치지 않음. 예: KT(AS 4766), SK브로드밴드(AS 9318), 구글(AS 15169)
- **사설 AS 번호**: 인터넷 전체에 알리지 않고 통신사와 고객망 사이처럼 특정 연결 안에서만 쓰는 번호. 대표적으로 64512 ~ 65534
- AS 번호는 원래 약 6만 5천 개(2바이트)였지만 부족해져 지금은 약 43억 개(4바이트)까지 사용

### 내부 라우팅 프로토콜(IGP)

#### 1. RIP (Routing Information Protocol)
RIP는 목적지까지 거쳐 가는 라우터 수, 곧 홉(hop) 수로 거리를 잰다. 라우터를 하나 건널 때마다 1홉씩 늘어난다.

```mermaid
제목: 라우터를 하나 건널 때마다 1홉씩 늘어 목적지까지 3홉이다. 최대 15홉까지 지원한다
flowchart LR
  S("출발") -->|"1홉"| R1("라우터") -->|"2홉"| R2("라우터") -->|"3홉"| R3("목적지 라우터")
```

- 거리 벡터 알고리즘, 벨만-포드 알고리즘 사용
- 각 라우터가 인접 라우터로부터 거리 정보를 받아 라우팅 테이블 갱신
- 홉 카운트 기준 최대 15홉까지 지원(16홉부터 도달 불가로 간주)
- UDP(520번 포트)로 경로 정보 교환

여기서 벡터는 방향과 크기를 함께 나타내는 값이다. 그래서 거리 벡터는 "어느 이웃 쪽으로(방향) 몇 홉(거리)"이라는 정보라고 보면 된다.

#### 2. OSPF (Open Shortest Path First)
OSPF는 링크마다 매긴 비용(느린 링크일수록 큰 값)을 더해 합계가 가장 작은 경로를 고른다. 거치는 라우터 수가 가장 적은 경로를 고르는 RIP와 다른 점이 이것이다.

- 링크 상태(Link-State) 알고리즘, 다익스트라(Dijkstra) 알고리즘 사용
- 경로 비용(Cost) 기준으로 최적 경로 선택
- 하나의 AS를 여러 지역(Area)으로 나누어 라우팅을 효과적으로 관리
- 각 라우터가 같은 지역 안의 연결 구조(토폴로지)를 모두 파악한 뒤 최단 경로 계산
- 변경이 생겼을 때만 같은 지역 안 모든 라우터에 변경 정보 전송
- 대규모 네트워크에 적합, 네트워크가 바뀌어도 모든 라우터의 경로 정보가 빠르게 새 상태로 맞춰짐(빠른 수렴)

지역(Area)은 AS 안을 다시 나눈 작은 구역이다. 자세한 링크 상태 정보는 같은 지역 안에서만 주고받아 라우터의 부담을 줄인다.

**OSPF 경로 비용 계산**

OSPF의 비용은 기본적으로 링크의 대역폭(전송 속도)으로 정한다. 대역폭이 클수록, 곧 빠른 링크일수록 비용이 작고, 관리자가 링크마다 비용을 직접 지정할 수도 있다. 경로는 이렇게 고른다.

- 각 링크의 비용을 합산해 전체 경로 비용 계산
- 여러 경로 중 총비용이 가장 낮은 경로 선택

예를 들어 비용 10인 링크 하나로 가는 길(합계 10)보다 비용 1인 링크 세 개를 거치는 길(합계 3)을 고른다. 라우터를 더 거쳐도 합계가 작은 쪽이 최단 경로다.

```mermaid
제목: 느린 길(비용 10) 대신 비용 1인 구간 세 개를 거치는 빠른 길(1 + 1 + 1 = 3)을 고른다
flowchart LR
  S("출발") ---|"10 (느린 길)"| T("목적지")
  S ---|"1"| A("라우터") ---|"1"| B("라우터") ---|"1"| T
```

### 외부 라우팅 프로토콜(EGP)

#### 3. BGP (Border Gateway Protocol)
BGP(경계 게이트웨이 프로토콜)의 Border는 서로 다른 자율 시스템(AS) 사이의 경계를 뜻한다. 그래서 서로 다른 AS에 속한 라우터들이 BGP로 경로 정보를 주고받는다고 이어서 외우면 된다.

- 경로 벡터 알고리즘 사용
- 목적지마다 거쳐 갈 AS 목록(AS 경로, 예: AS1 → AS2 → AS3)을 함께 교환
- 경로 선택 시 AS 경로 정보와 각 조직의 정책(어느 통신사 경로를 우선할지 등)을 함께 고려
- 처음 연결할 때 전체 라우팅 테이블 교환, 이후 변경된 경로 정보만 교환
- 인터넷 백본(여러 통신사와 기관의 네트워크를 잇는 인터넷의 중심 연결망)에서 쓰는 핵심 프로토콜

```mermaid
제목: BGP 라우터들이 AS 경계에서 거쳐 갈 AS 목록(AS1 → AS2 → AS3)을 주고받는다
%% 폰: TB
flowchart LR
  A1["AS 1"] <==>|"BGP"| A2["AS 2"] <==>|"BGP"| A3["AS 3"]
```

이 AS 목록이 경로 벡터다. 거리 벡터가 "어느 이웃 쪽으로 몇 홉"인지 알려 준다면, 경로 벡터는 "어느 AS들을 거쳐 가는지"를 알려 준다.

### 라우팅 알고리즘 비교
세 알고리즘은 경로 정보를 얻는 방법이 다르다. 거리 벡터는 이웃에게 듣고(RIP), 링크 상태는 전체 지도를 보고(OSPF), 경로 벡터는 AS 목록을 받는다(BGP).

| 구분 | 거리 벡터 | 링크 상태 | 경로 벡터 |
|---|---|---|---|
| 대표 프로토콜 | RIP | OSPF | BGP |
| 경로 선택 기준 | 홉 수 사용 | 경로 비용 사용 | AS 경로와 정책 사용 |
| 교환 정보 | 거리(홉 수) | 지역 안 연결 구조(토폴로지) | 목적지까지의 AS 경로 |
| 알고리즘 | 벨만-포드 | 다익스트라 | 경로 벡터 |
| 사용 범위 | 소규모 네트워크 | 대규모 네트워크 | AS 간 연결 |

( 2 )는 서로 다른 AS 간 라우팅 프로토콜이며, 대표적으로 ( 4 )가 있다. 초기에 전체 라우팅 테이블을 교환하고 이후에는 변화된 정보만 교환하는 방식이다.

## 네트워크 계층 프로토콜 (IP·ARP·RARP·ICMP·IGMP·NAT)
출제: 25-1, 23-3, 23-1, 21-1, 20-4, 20-3
형태: 한두 줄 설명 → 보기에서 고르기 또는 영문 약어

### 네트워크 계층 주요 기술 한눈에 보기
네트워크 계층은 데이터가 최종 목적지까지 정확히 도달하도록 경로를 설정(Routing)하고, 논리적인 주소(IP 주소)를 관리하는 역할을 맡는다. 이 계층에서 쓰는 프로토콜과 기술은 각자 맡은 일이 뚜렷해서, 역할과 특징을 정확히 갈라 외우는 것이 중요하다. 표로 먼저 모아 보면 이렇다.

| 기술/프로토콜 | 주요 기능 | 특징 |
|---|---|---|
| IP | 데이터그램의 주소 지정 및 경로 설정 | 비연결성, 비신뢰성 |
| ARP | 논리 주소(IP)를 물리 주소(MAC)로 변환 | 동적, 브로드캐스트 기반 요청 |
| RARP | 물리 주소(MAC)를 논리 주소(IP)로 변환 | ARP의 역기능, 부팅 시 IP 주소 할당에 사용 |
| ICMP | 오류 보고 및 네트워크 상태 진단 | IP에 의존해 동작, 제어 메시지 전송 |
| IGMP | 멀티캐스트 그룹 관리 | 특정 그룹에만 데이터 전송, 대역폭 효율화 |
| 라우팅 프로토콜 | 최적의 데이터 전송 경로 탐색 | RIP, OSPF, BGP |
| NAT | 사설 IP 주소를 공인 IP 주소로 변환 | IP 주소 절약, 내부 네트워크 보안 강화 |

### 네트워크 계층 프로토콜 하나씩 보기

#### 1. IP (Internet Protocol)
IP는 송신 측과 수신 측 사이의 데이터 전송을 위해 주소 지정과 경로 설정을 맡는 핵심 프로토콜이다. 데이터를 패킷(Packet) 또는 데이터그램(Datagram) 단위로 캡슐화해 보내지만, 신뢰성은 보장하지 않는다.

- **비연결성(Connectionless)**: 데이터 전송 전에 연결을 설정하지 않음
- **비신뢰성(Unreliable)**: 패킷의 도착 순서나 전송 여부를 보장하지 않음, 오류 제어 기능 없음 (신뢰성은 상위 계층인 TCP가 담당)

#### 2. ARP (Address Resolution Protocol)
ARP는 호스트의 IP 주소를 그 호스트의 물리적인 네트워크 주소(MAC 주소)로 바꿔 주는 프로토콜이다. 로컬 네트워크(LAN) 안에서 통신하려면 꼭 필요하다. 동작은 세 단계로 보면 된다.

- **요청**: 송신 측이 특정 IP 주소의 MAC 주소를 찾으려고 네트워크 전체에 ARP 요청 메시지를 브로드캐스트
- **응답**: 그 IP 주소를 쓰는 장비가 자기 MAC 주소를 담아 ARP 응답 메시지를 송신 측에 유니캐스트로 전송
- **캐시**: 송신 측이 받은 MAC 주소를 ARP 캐시에 일정 시간 저장해 불필요한 요청을 줄임

#### 3. RARP (Reverse Address Resolution Protocol)
RARP는 ARP와 반대로, 물리 주소(MAC 주소)는 알지만 IP 주소를 모를 때 쓰는 프로토콜이다. 주로 디스크가 없는 워크스테이션이나 프린터 등이 부팅할 때 자기 IP 주소를 할당받으려고 쓴다.

다만 RARP는 오래된 기술이다. 지금은 응용 계층 프로토콜인 DHCP(Dynamic Host Configuration Protocol)가 이 기능을 대신해 IP 주소 할당과 관리를 더 효율적으로 한다.

#### 4. ICMP (Internet Control Message Protocol)
ICMP는 IP 패킷을 처리하다 생긴 문제를 보고하거나, 네트워크 상태를 진단하기 위한 제어 메시지를 보내는 프로토콜이다. 왜 이런 게 따로 있냐면, IP에는 오류 보고 기능이 없기 때문이다. ICMP가 그 빈자리를 메운다. 주요 메시지 유형은 아래와 같다.

- **Echo Request/Reply**: 네트워크 연결 상태 확인 (ping 명령어)
- **Destination Unreachable**: 목적지에 도달할 수 없음
- **Time Exceeded**: 패킷의 TTL(Time To Live)이 0이 되어 패킷이 폐기됨
- **Redirect**: 더 나은 경로 안내

#### 5. IGMP (Internet Group Management Protocol)
IGMP는 호스트가 멀티캐스트 그룹에 가입하거나 탈퇴할 때 쓰는 프로토콜이다. 멀티캐스트는 특정 그룹에 속한 여러 호스트에게만 데이터를 한 번에 보내는 방식으로, IPTV나 온라인 게임 등에서 데이터를 효율적으로 보내는 데 쓴다. 라우터는 IGMP로 어떤 호스트가 어떤 멀티캐스트 그룹에 속해 있는지 파악하고, 그 그룹으로 가는 트래픽만 골라서 전달한다.

#### 6. 라우팅 프로토콜 (Routing Protocol)
라우팅 프로토콜은 라우터끼리 통신하며 최적의 데이터 전송 경로를 동적으로 찾고 설정하는 규약이다. 크게 내부 게이트웨이 프로토콜(IGP)과 외부 게이트웨이 프로토콜(EGP)로 나뉘고, 자세한 내용은 [라우팅 프로토콜] 묶음에서 다룬다.

- **RIP(Routing Information Protocol)**: 거리 벡터 알고리즘 기반, 홉 카운트(거치는 라우터 수)가 가장 적은 경로를 최적 경로로 선택, 소규모 네트워크에 적합
- **OSPF(Open Shortest Path First)**: 링크 상태 알고리즘 기반, 네트워크 변화에 빠르게 대처, 대규모 네트워크에 적합
- **BGP(Border Gateway Protocol)**: 자율 시스템(AS) 간 라우팅에 쓰는 외부 게이트웨이 프로토콜, 현재 인터넷의 핵심 역할

#### 7. NAT (Network Address Translation)
NAT는 사설 IP 주소를 쓰는 내부 네트워크 장치가 인터넷에 접속할 때, 사설 IP 주소를 공인 IP 주소로 바꿔 주는 기술이다. IPv4 주소 고갈 문제를 해결하고, 내부 네트워크를 외부로부터 보호하는 역할을 한다.

동작은 이렇다. 내부 장치가 밖으로 패킷을 보내면 NAT 장비(주로 라우터)가 출발지 사설 IP 주소를 자기 공인 IP 주소로 바꿔 보낸다. 밖에서 응답이 오면 다시 원래 사설 IP 주소로 바꿔 내부 장치에 전달한다.

## 데이터 링크 프로토콜 (HDLC·PPP·프레임 릴레이·ATM)
출제: 26-1, 23-3, 23-2
형태: HDLC 프레임 3종 + 전송 모드 2종의 5칸을 보기에서 채우기, 한 줄 설명 → 영문 약어

### 데이터 링크 계층 한눈에 보기
데이터 링크 계층은 OSI 7계층의 2계층으로, 물리적 링크를 통해 데이터를 신뢰성 있게 전송하는 역할을 맡는다. 노드와 노드 사이의 데이터 전송과 오류 수정이 이 계층의 일이고, 주요 기능은 프레이밍(Framing), 흐름 제어(Flow Control), 오류 제어(Error Control) 세 가지다.

- **데이터 링크 프로토콜**: 노드 대 노드(Point-to-Point) 간 데이터 교환을 관리하는 통신 규약
- **프레이밍**: 네트워크 계층에서 받은 패킷에 정보를 붙여 프레임으로 만드는 과정. 프레임 = 헤더 + 패킷 + 트레일러 (가상 메모리의 프레임과는 다른 개념)
- **흐름 제어**: 송신이 너무 빨라 수신 측이 처리하지 못하는 경우를 막는 기술
- **오류 제어**: 전송 중 생길 수 있는 데이터 오류를 감지하고 수정하는 기술

이 계층에서 나오는 내용은 크게 두 갈래다. 오류 제어 방식은 바로 다음 [오류 제어] 묶음에서 다룬다.

| 구분 | 주요 프로토콜 및 기술 | 특징 |
|---|---|---|
| 데이터 링크 프로토콜 | HDLC, PPP, 프레임 릴레이, ATM | 비트 중심, 문자 중심, 고속 데이터 전송 등 |
| 오류 제어 방식 | 순방향 오류 수정(FEC), 역방향 오류 수정(BEC) | 오류 감지 후 재전송 요청 또는 스스로 수정 |

용어별 키워드를 먼저 모아 두면 아래와 같다.

| 용어 | 키워드 |
|---|---|
| HDLC | 비트 위주 프로토콜, 프레임 구조, 비트 스터핑 |
| 정보 프레임 | 제어부 '0' 시작, 사용자 데이터 전달 |
| 감독 프레임 | 제어부 '10' 시작, 오류/흐름 제어 |
| 비번호 프레임 | 제어부 '11' 시작, 링크 동작 모드 설정 |
| NRM | 정규 응답 모드, 불균형 구성, 한 개의 주국과 하나 이상의 종국 |
| ARM | 비동기 응답 모드, 포인트 투 포인트 불균형 링크, 종국이 허가 없이 송신 가능 |
| ABM | 비동기 균형 모드, 포인트 투 포인트 균형 링크, 혼합국, 허가 없이 전송 |
| ATM | 53바이트 셀 단위, 비동기 전송 모드, 고속 스위칭 |

### 데이터 링크 프로토콜
데이터 링크 프로토콜은 인접한 두 장치(노드) 사이의 데이터 전송을 관리하고 오류를 수정한다.

### HDLC (High-level Data Link Control)
- 비트(Bit) 중심 프로토콜, 점대점(Point-to-Point)·다중점(Multi-point) 링크 모두 지원
- 프레임 구조: 헤더(플래그 - 주소부 - 제어부) - 패킷(정보부) - 트레일러(FCS - 플래그)
- 전송 효율과 신뢰성이 높음
- 데이터 투명성 보장을 위해 비트 스터핑(Bit Stuffing) 사용
- 주로 동기식 전송에 사용

프레임 구조를 칸으로 그리면 아래와 같다. 플래그가 앞뒤로 프레임을 감싼다.

| 플래그 | 주소부 | 제어부 | 정보부 | FCS | 플래그 |
|---|---|---|---|---|---|
| 헤더 | 헤더 | 헤더 | 정보부 | 트레일러 | 트레일러 |
| 프레임의 시작 | 받을 노드(수신자)의 주소 | 프레임 종류 구별 | 사용자 데이터 | 오류 검출 코드(Frame Check Sequence) | 프레임의 끝 |

용어 몇 개를 풀어 두면 이렇다.

- **비트 스터핑**: 플래그와 플래그가 아닌 부분을 구분하려고 쓰는 기법
- **동기식 전송**: 송신 측과 수신 측이 같은 박자(클록 신호)로 데이터를 보내는 방식

#### HDLC 프레임의 종류

제어부의 첫 번째, 두 번째 비트로 프레임의 종류를 구별한다.

| 프레임 | 제어부 시작 | 키워드 |
|---|---|---|
| I(정보) 프레임 | 0 | 데이터 전달 역할 |
| S(감독) 프레임 | 10 | 오류/흐름 제어 역할 |
| U(비번호) 프레임 | 11 | 링크 동작 모드 설정 역할 |

- **정보(Information) 프레임**: 제어부가 0으로 시작, 사용자 데이터 전달, 데이터와 함께 확인 응답(ACK)도 포함 가능
- **감독(Supervisory) 프레임**: 제어부가 10으로 시작, 오류 제어와 흐름 제어에 사용, 데이터 없이 제어 정보만 전달(ACK, NAK 등)
- **비번호(Unnumbered) 프레임**: 제어부가 11로 시작, 링크의 동작 모드(HDLC 데이터 전송 모드) 설정과 관리, 링크 설정(Setup)·해제(Disconnect) 등 제어 명령에 사용

ACK(Acknowledgment)는 "잘 받았으니 다음 것을 보내라"는 확인 응답이고, NAK(Negative Acknowledgment)는 "잘못 받았으니 다시 보내라"는 부정 확인 응답이다.

#### HDLC 데이터 전송 모드

HDLC는 세 가지 데이터 전송 모드를 제공한다.

| 동작 모드 | 키워드 |
|---|---|
| 정규 응답 모드(NRM) | 보조국(종국)은 폴 메시지를 수신한 경우에만 송신 |
| 비동기 응답 모드(ARM) | 포인트 투 포인트 불균형 링크에서 사용, 종국은 주국의 허가 없이 송신 가능 |
| 비동기 균형 모드(ABM) | 포인트 투 포인트 균형 링크에서 사용, 혼합국끼리 허가 없이 전송 가능 |

교실로 빗대면 이해가 쉽다. 선생님은 통신을 제어하고 관리하는 주국(예: 통신탑, 기지국), 학생은 주국의 지시에 따라 데이터를 주고받는 종국(예: 스마트폰)이다. 여기서 Station은 노드를 뜻하는데, 데이터 링크 계층에서는 제어 역할을 강조하려고 Station이라고 부른다.

- **NRM**: 선생님이 지목한(폴, Poll) 학생만 말할 수 있는 교실
- **ARM**: 학생이 허가 없이 말할 수 있지만, 수업 시작·끝·바로잡기(링크 설정·해제, 오류 복구)는 선생님만 하는 교실
- **ABM**: 선생님과 학생 구분 없이 대등한 두 사람이 서로 허가 없이 언제나 말하는 교실. 두 사람 모두 주국과 종국 기능을 함께 하는 혼합국

폴은 주국이 특정 종국에게 보낼 데이터가 있으면 보내라고 허가하는 신호다. NRM의 종국은 폴을 받아야만 송신할 수 있다.

**정규 응답 모드 (NRM, Normal Response Mode)**

- 불균형(Unbalanced) 구성, 한 개의 주국(Primary Station)과 하나 이상의 종국(Secondary Station)
- 반이중 통신, 포인트 투 포인트 링크와 다중점(Multi-point) 링크 모두 사용
- 종국은 주국의 허가가 있을 때만 전송 가능

불균형이라는 이름은 많은 권한이 주국에 쏠려 있어서 붙었다. 반이중 통신은 동시에는 안 되고 번갈아 가며 송수신하는 방식(예: 무전기)이고, 포인트 투 포인트 링크는 주국 1개와 종국 1개로 된 링크, 다중점 링크는 주국 1개와 종국 여럿으로 된 링크다.

**비동기 응답 모드 (ARM, Asynchronous Response Mode)**
- 전이중 통신을 하는 포인트 투 포인트 불균형 링크 구성에 사용
- 종국은 주국의 허가 없이 송신 가능
- 링크 설정, 오류 복구 등 제어 기능은 주국만 수행

여기서 비동기는 주국의 허가 없이 송신할 수 있는 모드라는 뜻이다. 전이중 통신은 송수신이 동시에 되는 방식(예: 전화)이다.

**비동기 균형 모드 (ABM, Asynchronous Balanced Mode)**
- 포인트 투 포인트 균형 링크에서 사용
- 모든 국(Station)이 혼합국(Combined Station)이 되어 주국과 종국 기능 모두 수행
- 혼합국은 허가 없이 언제나 전송 가능
- 가장 널리 쓰는 모드, 효율적인 양방향 통신 가능

혼합국은 주국 기능(링크 제어, 오류 복구)과 종국 기능(데이터 송수신)을 모두 하는 국이다. 세 모드 이름은 두 쌍의 차이만 알면 뜻을 유추할 수 있다.

- **정규 vs 비동기**: 정규는 허가가 있을 때만 전송, 비동기는 허가 없이 전송 가능
- **응답 vs 균형**: 응답은 주국 + 종국(불균형, 종국이 주국에 응답), 균형은 혼합국

그래서 비동기 응답 모드는 "허가 없이 전송할 수 있는, 주국 + 종국 형태"라고 풀어 읽으면 된다.

### PPP (Point-to-Point Protocol)
- 문자(Character) 중심 프로토콜, 주로 두 컴퓨터 간 직렬 인터페이스 통신에 사용
- HDLC와 달리 문자 중심이고 프레임 구조가 더 유연함
- 오류 감지만 수행, 오류 복구는 상위 계층에 맡김
- IP 주소 할당, 인증(PAP, CHAP) 같은 다양한 네트워크 제어 프로토콜(NCP) 지원
- 주로 비동기식 전송에 사용, 동기식도 지원

HDLC가 비트 단위로 처리한다면 PPP는 문자 단위로 처리한다는 점이 둘을 가르는 기준이다.

### 프레임 릴레이 (Frame Relay)
- 고속 데이터 전송을 위해 개발, X.25의 단점 개선
- 오류 제어와 흐름 제어를 단순화해 전송 속도 향상 (오류 발생 시 프레임을 폐기하고 상위 계층에서 처리)
- 가상 회선(Virtual Circuit) 방식으로 논리적인 연결 설정
- 주로 LAN과 LAN을 연결하는 WAN 또는 MAN 서비스에 사용

정해진 가상 회선으로 보내고, 오류는 고치지 않고 버려서 빠르다고 기억하면 된다. LAN(Local Area Network)은 건물·사무실 같은 근거리, WAN(Wide Area Network)은 국가·대륙 같은 먼 지역, MAN(Metropolitan Area Network)은 도시·대형 캠퍼스 규모를 잇는 네트워크다.

### ATM (Asynchronous Transfer Mode, 비동기 전송 모드)
- 53바이트(헤더 5바이트, 페이로드 48바이트) 크기의 작은 셀(Cell) 단위로 전송하는 고속 스위칭 기술
- 음성, 비디오, 데이터 등 여러 유형의 정보를 하나의 네트워크로 통합 전송
- 고정 길이 셀을 써서 하드웨어 스위칭이 가능하므로 매우 빠름
- B-ISDN의 핵심 기술

| 헤더 | 페이로드 |
|---|---|
| 5바이트 | 48바이트 |

셀 하나가 늘 53바이트로 같다는 것이 핵심이다. 고정 길이라서 하드웨어로 바로 스위칭할 수 있고, 그래서 빠르다.

## 오류 제어 (FEC·BEC·패리티·CRC·해밍·ARQ)

형태: 긴 지문 5칸을 보기에서 채우기, 설명 3줄의 공통 빈칸 → 영문 약어

### 데이터 링크 오류 제어
오류 제어는 전송 과정에서 생긴 오류를 감지하고 수정하는 방식이다. 수정하는 쪽이 누구냐에 따라 둘로 나뉘는데, 한마디로 FEC는 되묻지 않고 혼자 고치고, BEC는 다시 보내 달라고 되묻는다.

| 용어 | 키워드 |
|---|---|
| FEC | 순방향 오류 수정, 재전송 요구 없이 스스로 수정, 해밍 코드 |
| BEC | 역방향 오류 수정, 재전송 요구, ARQ |
| 패리티 검사 | 1비트 추가, 짝수/홀수 개수 검증 |
| CRC | 순환 중복 검사, 다항식 코드, 집단 오류 검출 |
| 해밍 코드 | FEC 방식, 오류 위치 검출, 패리티 비트, 2의 거듭제곱 위치 |

#### 1. FEC (Forward Error Correction, 순방향 오류 수정)
- 수신 측에서 오류를 스스로 감지하고 수정하는 방식
- 데이터 전송 시 오류 수정에 필요한 잉여 비트(Redundant Bits)를 함께 전송 (예: 해밍 코드)
- 역방향 채널이 필요 없고 재전송 요청이 없어 실시간 통신·단방향 통신에 적합
- 구현이 복잡하고, 추가 비트 때문에 전송 효율이 낮아질 수 있음

그럼 잉여 비트는 왜 붙일까? 원본 데이터만 보내면 수신 측은 받은 데이터가 전송 중에 변했는지, 그대로 도착했는지 판단할 방법이 없다. 잉여 비트가 그 판단의 근거가 된다. 두 방식 모두 잉여 비트를 쓰지만 목적과 정보량이 다르다.

- **역방향 오류 수정(BEC)**: 오류를 탐지할 수 있을 정도의 최소한의 정보('지문') 추가
- **순방향 오류 수정(FEC)**: 오류를 탐지하고 직접 수정까지 할 수 있을 만큼 충분한 정보('해설지') 추가

#### 2. 해밍 코드 (Hamming Code)
해밍 코드는 FEC의 대표적인 예로, 단일 비트 오류를 자동으로 감지하고 수정할 수 있는 오류 수정 코드다.

- **여러 개의 패리티 비트**: 2의 거듭제곱 위치(1, 2, 4, 8, 16, …)에 패리티 비트 배치
- **오류 위치 검출**: 각 패리티 비트는 특정 비트들의 XOR 연산 결과 저장
- **단일 비트 오류 수정**: 오류가 난 정확한 위치를 찾아 수정 가능

7비트로 보면 1, 2, 4번 자리가 패리티 비트(P), 나머지가 데이터 비트(D)다.

| 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|
| P | P | D | P | D | D | D |

받은 쪽은 아래 순서로 오류 자리를 찾아 고친다.

```steps
제목: 틀린 패리티 위치를 더하면 오류 난 자리 번호가 나오고, 그 비트를 뒤집어 고친다
패리티 다시 계산 |
틀린 패리티 위치를 더함 | 오류 난 자리 번호
그 비트를 뒤집어 수정 |
```

패리티 검사와 견주면 차이가 분명하다.

- **해밍 코드**: 여러 패리티 비트로 오류 검출 + 수정 가능
- **패리티 검사**: 단일 패리티 비트로 오류 검출만 가능 (수정 불가)

#### 3. BEC (Backward Error Correction, 역방향 오류 수정)
- 수신 측이 오류를 감지하면 송신 측에 재전송을 요청하는 방식, ARQ(Automatic Repeat reQuest)라고도 함
- 오류를 '검출'하는 메커니즘 + 검출된 오류의 재전송을 요청하는 'ARQ 프로토콜'로 구성

오류를 검출하려고 데이터에 잉여 비트(Redundant Bits)를 붙여 보내는데, 그 검출 기법이 아래 세 가지다.

#### 4. 패리티 검사 (Parity Check)
- 데이터 블록에 1비트의 패리티 비트를 추가해 블록 안 1의 개수를 짝수(짝수 패리티) 또는 홀수(홀수 패리티)로 맞추는 가장 간단한 방법
- 한계: 짝수 개의 비트에 오류가 나면 검출 불가 (예: 2개 비트가 0에서 1로 바뀌면 1의 개수는 여전히 짝수)

짝수 패리티라면 아래처럼 데이터의 1이 5개일 때 패리티 비트 1을 붙여 전체 1의 개수를 6개, 곧 짝수로 맞춘다.

| 데이터 | | | | | | | 패리티 |
|---|---|---|---|---|---|---|---|
| 1 | 0 | 1 | 1 | 0 | 1 | 1 | 1 |

검출만 되고 수정은 안 된다. 2비트가 한꺼번에 바뀌면 1의 개수가 여전히 짝수라 검출에도 실패한다.

#### 5. CRC (Cyclic Redundancy Check, 순환 중복 검사)
- 다항식 코드로 오류를 검출하는 강력한 방법
- 송신 측: 데이터를 미리 정한 생성 다항식(Generator Polynomial)으로 나눠 나머지를 계산, 이 나머지를 데이터에 덧붙여 전송
- 수신 측: 받은 데이터를 같은 생성 다항식으로 나눠 나머지가 0인지 확인
- 집단 오류(Burst Errors) 검출에 매우 효과적, HDLC의 FCS(Frame Check Sequence)가 CRC 사용

```mermaid
제목: 생성 다항식으로 나눈 나머지(FCS)를 붙여 보내고, 수신 측은 같은 다항식으로 다시 나눠 나머지가 0인지 확인한다
%% 폰: TB
flowchart LR
  D["데이터"] -->|"÷ 생성 다항식"| F["데이터 + 나머지(FCS)"]
  F -->|"전송"| R{"수신 측<br/>÷ 같은 생성 다항식<br/>나머지 = 0 ?"}
  R -->|"0이면"| OK("정상")
  R -->|"0 아니면"| NG("오류")
```

#### 6. 블록 합 검사 (Block Sum Check)
- 데이터 블록을 고정 크기의 여러 행으로 나눈 뒤 각 열의 합(또는 XOR 연산)을 계산해 검사 블록 생성, 데이터와 함께 전송
- 수신 측이 같은 계산을 해 오류 검출

아래처럼 각 열을 XOR 해 검사 블록을 만든다. 수신 측이 다시 계산한 값이 같으면 정상, 다르면 오류다.

| 구분 | 1열 | 2열 | 3열 | 4열 |
|---|---|---|---|---|
| 데이터 1행 | 1 | 1 | 0 | 1 |
| 데이터 2행 | 0 | 1 | 1 | 0 |
| 데이터 3행 | 1 | 0 | 0 | 1 |
| 검사 블록 (각 열 XOR) | 0 | 0 | 1 | 0 |

### ARQ (자동 반복 요청) 프로토콜
ARQ는 오류가 검출되었을 때 재전송을 관리하는 절차다. 종류는 세 가지다.

- **정지-대기(Stop-and-Wait) ARQ**: 프레임 하나를 보내고 확인(ACK/NAK)을 받을 때까지 대기
- **Go-Back-N ARQ**: 오류가 난 프레임부터 모두 재전송
- **선택적 재전송(Selective Repeat) ARQ**: 오류가 난 프레임만 골라 재전송

프레임 2에 오류가 났을 때 세 방식을 나란히 놓으면 아래와 같다. 정지-대기는 하나 보내고 ACK를 기다려서 느리고, 선택적 재전송은 오류 난 것만 다시 보내서 효율이 가장 좋다.

| 방식 | 송신 측이 보내는 프레임 | 재전송 |
|---|---|---|
| 정지-대기 | 1 → ACK 1 → 2 → ACK 2 (하나씩 보내고 ACK 대기) | 느림 |
| Go-Back-N | 1, 2(오류), 3, 4 | 2, 3, 4 (오류 난 프레임부터 전부) |
| 선택적 재전송 | 1, 2(오류), 3, 4 | 2 (오류 난 프레임만, 효율 최고) |

### 네트워크 전달 방식
여기서 네트워크는 3계층이 아니라 네트워크 전체를 가리킨다. 네트워크가 데이터를 전달하는 방식은 두 가지이고, 둘을 가르는 기준은 전송 단위다.

- **패킷 교환 방식**: 전송 단위는 패킷
- **서킷 교환 방식**: 전송 단위는 연속적인 비트 스트림

패킷 교환 방식은 다시 데이터그램 방식과 가상 회선 방식으로 나뉜다.

```mermaid
제목: 네트워크 전달 방식은 패킷 교환과 서킷 교환으로, 패킷 교환은 다시 데이터그램과 가상 회선으로 나뉜다
%% 폰: TB
flowchart LR
  A["네트워크 전달 방식<br/>(3계층이 아닌 전체)"] --> B["패킷 교환 방식<br/>(전송 단위: 패킷)"]
  A --> C["서킷 교환 방식<br/>(전송 단위: 비트 스트림)"]
  B --> D("데이터그램 방식")
  B --> E("가상 회선 방식")
```

| 용어 | 키워드 |
|---|---|
| 가상 회선 (Virtual Circuit) | 논리적인 통신 경로를 미리 설정, 연결형 교환 방식, 목적지와 미리 연결 |
| 데이터그램 (Datagram) | 비연결형 교환 방식, 순서에 무관하게 독립적으로 전송, 헤더를 붙여 개별 전달 |
| 패킷 교환 방식 (Packet Switching) | 전송 단위는 패킷, 네트워크 계층에서 처리, 회선 효율성 높음 |
| 서킷 교환 방식 (Circuit Switching) | 전송 단위는 비트 스트림, 전용 회선 설정, 일정한 대역폭 보장 |

### 서킷 교환 방식 (Circuit Switching)
서킷 교환은 회선 교환이라고도 부른다. 통신하기 전에 길을 먼저 깔고 끝날 때까지 혼자 쓰는 방식이다.

- **전송 단위**: 연속적인 비트 스트림
- **연결 방식**: 통신 전에 송신자와 수신자 사이에 전용 회선 설정
- **동작 계층**: 물리 계층(1계층, 비트 단위)과 데이터 링크 계층(2계층, 프레임 단위)에서 회선 설정·관리
- **특징**: 한번 회선이 설정되면 통신이 끝날 때까지 그 회선을 독점 사용
- **장점**: 일정한 대역폭 보장, 지연 시간 예측 가능
- **단점**: 회선 이용률이 낮을 수 있음, 설정 시간 필요
- **예시**: 전통적인 전화 시스템(PSTN)

### 패킷 교환 방식 (Packet Switching)
패킷 교환은 데이터를 잘게 나눠 따로따로 보내는 방식이다.

- **전송 단위**: 패킷
- **연결 방식**: 데이터를 패킷 단위로 나눠 각각 독립적으로 전송
- **동작 계층**: 네트워크 계층(3계층)에서 패킷 처리·라우팅
- **특징**: 패킷마다 서로 다른 경로로 전송될 수 있음
- **장점**: 회선 효율성 높음, 다중 사용자 지원
- **단점**: 패킷 손실 가능성, 지연 시간 변동

패킷 교환 방식의 세부 유형은 아래 두 가지다.

#### 1. 데이터그램 (Datagram)
- 독립적인 패킷을 헤더와 함께 전송하는 방식
- 비연결형 교환 방식

#### 2. 가상 회선 (Virtual Circuit)
- 논리적인 회선을 설정하고 패킷을 전송하는 방식
- 연결형 교환 방식

### 비연결형과 연결형 비교
데이터그램은 비연결형, 가상 회선은 연결형이다. 둘을 표로 견주면 아래와 같다.

| 구분 | 비연결형 (데이터그램) | 연결형 (가상 회선) |
|---|---|---|
| 연결 설정 | 불필요 | 필요 |
| 패킷 독립성 | 독립적 | 종속적 |
| 경로 결정 | 패킷마다 다름 | 고정 경로 |
| 순서 보장 | 보장 안 됨 | 보장됨 |
| 대표 프로토콜 | IP, UDP | TCP, ATM, X.25 |

비연결형·연결형 개념은 특정 계층에만 있는 게 아니라 네트워크 계층(3계층)과 전송 계층(4계층)에 모두 있다.

- **네트워크 계층**: IP(비연결형), X.25(연결형)
- **전송 계층**: UDP(비연결형), TCP(연결형)

ATM은 데이터 링크 계층(2계층)부터 네트워크 계층(3계층)에 걸쳐 동작한다.

## 응용 계층 프로토콜과 포트 번호
출제: 25-2, 23-1, 22-2
형태: 한 줄 설명(포트 번호가 단서) → 용어, 설명 3개 → 보기

### 포트 번호와 키워드
응용 계층 프로토콜은 포트 번호가 지문의 단서로 자주 나온다. 포트 번호와 키워드를 한 표로 묶어 두고 하나씩 보자.

| 프로토콜 | 포트 번호 | 키워드 |
|---|---|---|
| SSH | 22 | 인증/암호화 제공, Telnet보다 강력한 보안, 원격 접속 |
| Telnet | 23 | 원격 접속 |
| HTTP | 80 | 요청/응답 처리, GET/POST/PUT |
| HTTPS | 443 | HTTP + 보안 통신, SSL/TLS 사용 |
| FTP | 21 | 파일 전송 |
| SMTP | 25 | 메일 전송 |
| POP3 | 110 | 메일 수신(다운로드) |
| IMAP | 143 | 메일 수신(동기화) |
| DNS | 53 | 도메인 이름 서비스 |
| DHCP | 67/68 | 동적 IP 자동 할당(DORA) |

### 응용 계층 프로토콜 하나씩 보기

#### 1. SSH (Secure Shell)
SSH는 22번 포트를 쓰는 원격 접속 프로토콜로, Telnet보다 강력한 보안을 제공한다. 자물쇠로 잠긴 암호화 터널로 서버와 대화한다고 보면 된다.

- **인증/암호화**: 사용자와 서버 사이의 모든 통신을 암호화, 제3자가 가로채도 내용을 알 수 없음
- **키 인증 방식**: 비밀번호 인증 외에 공개키-개인키 쌍을 이용한 인증 지원

키 인증을 쓰려면 클라이언트에서 만든 공개키를 서버의 `~/.ssh/authorized_keys` 파일에 미리 등록해야 한다. 그러면 비밀번호를 입력하지 않고도 안전하게 서버에 접속할 수 있다. 공개키를 등록하는 쪽이 서버라는 점은 필기에서 묻기도 했다.

#### 2. Telnet
Telnet은 23번 포트를 쓴다는 것만 기억하면 된다. SSH 22번, Telnet 23번이다.

Telnet은 네트워크로 다른 컴퓨터에 접속해 명령을 실행할 수 있는 원격 접속 프로토콜이다. 그런데 모든 데이터를 평문으로 보내기 때문에 보안에 취약하다. 뻥 뚫린 엽서를 보내는 것과 같아서, 사용자 이름이나 비밀번호 같은 민감한 정보가 네트워크에서 쉽게 노출된다.

- **보안 취약점**: 데이터 암호화가 없어 중간자 공격(Man-In-The-Middle)에 취약
- **SSH와의 비교**: Telnet의 보안 문제를 해결하려고 SSH 개발, SSH는 모든 통신 내용을 암호화해 훨씬 안전하므로 지금은 원격 접속·관리에 SSH 권장

#### 3. HTTP (HyperText Transfer Protocol)
HTTP는 웹에서 하이퍼미디어 문서를 전송하는 네트워크 프로토콜이다. 인터넷에서 요청(Request)과 응답(Response)으로 처리되는 방식으로 동작하고, 주로 웹 브라우저(클라이언트)와 웹 서버가 데이터를 주고받는 데 쓴다.

```mermaid
제목: 클라이언트가 요청을 보내면 서버가 처리한 뒤 응답을 돌려준다 (80번)
%%{init: {"sequence": {"width": 90, "actorMargin": 40, "mirrorActors": false}}}%%
sequenceDiagram
  participant C as 클라이언트
  participant S as 서버
  C->>S: 요청 (GET 등)
  S-->>C: 응답
```

- **요청-응답 구조**: 클라이언트가 서버에 요청을 보내면 서버가 처리한 뒤 응답 반환
- **HTTP 메서드**: 클라이언트가 서버에 어떤 작업을 요청할지 지정하는 방식
- **Stateless(무상태)**: 상태를 유지하지 않음, 각 요청을 독립적으로 처리하고 이전 요청 정보를 저장하지 않음

메서드는 네 가지를 알아 두면 된다.

| 메서드 | 용도 |
|---|---|
| GET | 서버에서 데이터 조회(읽기) |
| POST | 서버에 새 데이터 생성(쓰기) |
| PUT | 서버의 기존 데이터 수정(업데이트) |
| DELETE | 서버의 데이터 삭제 |

이런 특성 덕분에 HTTP는 웹에서 문서를 효율적으로 전송하고, RESTful 웹 서비스나 AJAX 요청 같은 동적 웹 애플리케이션의 기반이 된다.

`http://example.com/`에서 http는 URI의 일부로 스킴(scheme)을 나타낸다. 스킴이란 URL의 첫 부분에 와서 리소스에 접근할 프로토콜을 지정하는 것으로, 브라우저는 스킴을 보고 그 리소스에 어떤 방식으로 접근할지 안다. http 스킴을 쓰는 리소스는 보통 암호화되지 않은 연결로 전송되고, `https://developer.mozilla.org`처럼 https 스킴이면 HTTP로 전송하되 안전한 TLS 채널로 암호화해 전송한다.

웹 기본 용어 세 개는 22-2에 한 문제로 묶여 나왔다. 이름이 비슷해서 헷갈리는데, **HTTP**는 전송 프로토콜이고, **하이퍼텍스트(Hypertext)**는 링크로 다른 문서와 연결되는 텍스트이며, **HTML(HyperText Markup Language)**은 웹 문서를 만드는 마크업 언어다. (하이퍼텍스트와 HTML은 감자 페이지에 없고 22-2 기출 지문에서 가져온 설명이다.)

#### 4. HTTPS (HyperText Transfer Protocol Secure)
HTTPS는 HTTP에 보안 기능을 더한 프로토콜이다. SSL(Secure Socket Layer) 또는 TLS(Transport Layer Security) 프로토콜로 데이터를 암호화해, 중간에서 데이터가 도청되거나 변조되는 것을 막는다. 같은 요청·응답을 봉인된 보안막 안에서 주고받는 셈이다.

- **데이터 암호화**: 클라이언트와 서버 사이의 모든 통신을 암호화해 민감한 정보(예: 신용 카드 정보, 로그인 정보)를 안전하게 전송
- **신뢰성 향상**: 웹사이트의 신뢰도를 높이고 검색 엔진 최적화(SEO)에도 긍정적 영향

#### 5. FTP (File Transfer Protocol)
FTP는 네트워크로 클라이언트와 서버 사이에 파일을 전송하는 표준 프로토콜이다. 주로 21번 포트를 쓰며 파일을 업로드하거나 다운로드할 때 쓴다. 특이한 점은 연결을 두 개 따로 쓴다는 것이다.

- **제어 연결(Control Connection, 21번 포트)**: 사용자 인증, 명령어 전송 등 제어 정보 교환
- **데이터 연결(Data Connection, 20번 포트)**: 실제 파일 데이터 전송

```mermaid
제목: FTP는 제어(21번)와 데이터(20번) 두 통로를 따로 쓴다
%% 폰: TB
flowchart LR
  C("클라이언트") <-->|"제어 연결 21번<br/>인증·명령어"| S("서버")
  C <-->|"데이터 연결 20번<br/>파일 데이터"| S
```

일반 FTP는 데이터를 암호화하지 않아 보안에 취약할 수 있다. 그래서 중요한 파일은 암호화 기능을 더한 FTPS(FTP over SSL/TLS)나 SFTP(SSH File Transfer Protocol)로 보내는 것이 안전하다.

#### 6. 이메일 프로토콜: SMTP, POP3, IMAP
이메일을 주고받을 때는 여러 프로토콜이 함께 쓰인다. SMTP는 메일을 보낼 때, POP3와 IMAP은 메일을 받을 때 쓴다.

- **SMTP(Simple Mail Transfer Protocol, 포트 25)**: 이메일 전송용 프로토콜. 클라이언트가 쓴 메일을 서버로 보내고 서버끼리 메일 교환
- **POP3(Post Office Protocol 3, 포트 110)**: 메일 서버에서 클라이언트로 이메일을 다운로드. 가져오면 보통 서버에서 삭제되어 여러 장치에서 같은 계정 관리가 어려움
- **IMAP(Internet Message Access Protocol, 포트 143)**: 서버에서 이메일을 동기화. 클라이언트에서 읽거나 지우면 서버에도 반영되어 여러 장치에서 일관된 상태로 관리

```mermaid
제목: 보내기는 SMTP(25), 받기는 POP3(110, 다운로드)와 IMAP(143, 동기화)
%% 폰: TB
flowchart LR
  C("클라이언트") -->|"SMTP 25 · 보내기"| S("메일 서버")
  S -->|"POP3 110 · 다운로드"| C
  S <-->|"IMAP 143 · 동기화"| C
```

POP3와 IMAP은 두 가지에서 갈린다.

- **저장 위치**: POP3는 로컬 기기로 다운로드 후 서버에서 삭제, IMAP은 서버에 계속 저장
- **동기화**: IMAP은 여러 기기에서 메일 상태(읽음/안 읽음 등) 동기화, POP3는 동기화 기능 없음

#### 7. DNS (Domain Name System)
DNS는 `www.google.com` 같은 사람이 읽기 쉬운 도메인 이름을 컴퓨터가 이해하는 IP 주소(예: 172.217.175.68)로 바꿔 주는 시스템이다. 이름을 물으면 번호를 알려 주는, 인터넷의 전화번호부라고 보면 된다.

```mermaid
제목: 도메인 이름을 물으면 매핑된 IP 주소를 돌려준다 (53번)
%%{init: {"sequence": {"width": 110, "actorMargin": 40, "mirrorActors": false}}}%%
sequenceDiagram
  participant C as 클라이언트
  participant D as DNS
  C->>D: www.google.com
  D-->>C: 172.217.175.68
```

사용자가 브라우저에 도메인 이름을 입력하면, DNS는 여러 서버(Recursive Resolver, Root Server, TLD Server, Authoritative Name Server)를 거쳐 그 도메인에 매핑된 IP 주소를 찾아 돌려준다. 이 과정을 DNS 쿼리라고 한다. DNS는 주로 53번 포트를 쓰고, UDP를 기반으로 동작해 응답이 빠르다.

#### 8. DHCP (Dynamic Host Configuration Protocol)
DHCP는 네트워크에 연결된 기기에 IP 주소, 서브넷 마스크, 게이트웨이(다른 네트워크로 나가는 관문 장비의 주소), DNS 서버 주소 같은 설정을 자동으로 할당해 주는 프로토콜이다. 관리자가 기기마다 IP를 일일이 지정하지 않아도 되고, 접속을 끊은 기기의 IP를 회수해 다른 기기에 다시 빌려주므로 한정된 IP 주소를 효율적으로 나눠 쓸 수 있다.

- **포트 번호**: 서버 67번, 클라이언트 68번, UDP(확인·재전송 없이 빠르게 보내는 전송 계층 프로토콜) 기반
- **DORA 과정**: 클라이언트와 서버가 메시지를 번갈아 주고받는 네 단계(Discover → Offer → Request → Ack), 앞글자를 따서 DORA

다른 프로토콜과 달리 포트가 서버와 클라이언트로 나뉘는 이유는, 아직 IP가 없는 클라이언트가 서버를 찾아 통신을 시작해야 하는 특수한 상황이라 보내는 쪽과 받는 쪽이 각자 정해진 포트를 쓰기 때문이다. 서버 67, 클라이언트 68 순서로 기억하면 된다. DORA의 네 단계는 아래와 같다.

```mermaid
제목: 클라이언트(68)와 서버(67)가 Discover, Offer, Request, Ack를 번갈아 주고받아 IP를 할당한다
%%{init: {"sequence": {"width": 110, "actorMargin": 40, "mirrorActors": false}}}%%
sequenceDiagram
  participant C as 클라이언트 (68)
  participant S as DHCP 서버 (67)
  C->>S: Discover (브로드캐스트)
  S-->>C: Offer
  C->>S: Request
  S-->>C: Ack
```

- **Discover(클라이언트 → 서버)**: 같은 네트워크에 DHCP 서버가 있는지 브로드캐스트로 찾음
- **Offer(서버 → 클라이언트)**: 서버가 할당 가능한 IP 주소를 제안
- **Request(클라이언트 → 서버)**: 제안받은 IP를 쓰겠다고 요청. 여러 서버가 동시에 제안했을 수 있어 그중 하나를 골라 확정하려는 단계
- **Ack(서버 → 클라이언트)**: 서버가 요청을 승인(Acknowledgment)하며 IP 할당 확정

### 기출에서 이렇게 나왔다
- 25-2: 22번 포트, Telnet 보완 한 줄 → **SSH** (23-1 재출제)
- 23-1: 22번 포트, Telnet보다 강력한 보안 한 줄 → **SSH**
- 22-2: 설명 3개 → 보기에서 **HTTP / Hypertext / HTML**

### 답 쓸 때
SSH는 영문 약어로 쓴다. 포트 번호 22·23·25를 한 묶음으로 외워 두면 SSH·Telnet·SMTP를 바로 가를 수 있다.

## 라우터 인터페이스 IP 할당
출제: 26-2, 24-1
형태: 라우터·네트워크 그림과 CIDR 3개 → 각 인터페이스에 할당 가능한 IP를 보기에서 고르기

### 핵심 정리
이 묶음은 주소 계산보다, 구성도를 보고 어느 네트워크의 주소를 구해야 하는지 찾는 데 집중한다. IP 주소, CIDR 표기법, 서브넷 마스크는 [서브넷 마스크·CIDR·프리픽스] 묶음에서 본 내용을 그대로 쓴다. 판단할 것은 네 가지다.

| 확인할 것 | 판단 기준 |
|---|---|
| 인터페이스의 소속 | 라우터의 접속 지점이 어느 네트워크에 연결되는지 확인 |
| 설정할 IP 주소 | 연결된 네트워크의 할당 가능 범위 안에서 선택 |
| 제외할 주소 | 일반 장치용 주소를 고를 때 네트워크 주소와 브로드캐스트 주소 제외 |
| 주소 중복 | 같은 네트워크에서 이미 쓰는 IP 주소는 다시 할당하지 않음 |

### 라우터와 인터페이스

#### 라우터의 역할
PC에서 웹페이지를 요청하거나 메시지를 보내면, 보낼 데이터는 **패킷**이라는 단위에 나뉘어 담긴다. 패킷에는 데이터와 함께 목적지 IP 주소 같은 전달에 필요한 정보가 들어 있다.

라우터는 서로 다른 네트워크를 연결하고, 패킷의 목적지 IP 주소를 보고 다음에 어느 쪽으로 넘길지 정하는 장비다. 패킷을 받으면 목적지로 가는 경로를 확인하고, 그 경로에 연결된 쪽으로 내보낸다. 예를 들어 A 네트워크의 PC가 C 네트워크의 PC로 데이터를 보내려면 두 네트워크 사이를 이어 줄 장비가 필요하다. 아래 그림에서는 R1이 A와 B를, R2가 B와 C를 잇는다.

```mermaid
제목: A의 PC에서 보낸 패킷이 목적지를 확인하는 R1과 R2를 차례로 거쳐 C의 PC에 도착한다
%% 폰: TB
flowchart LR
  A("A의 PC") -->|"패킷"| R1["R1<br/>목적지 확인"] --> R2["R2<br/>목적지 확인"] --> C("C의 PC")
```

#### 인터페이스
라우터가 네트워크에 연결되는 접속 지점을 **인터페이스**라고 한다. 아래 구성도의 a, b, c, d는 별도 장비가 아니라 라우터 가장자리에 붙은 접속 지점이다.

```net
제목: R1의 a는 A 네트워크, b는 B 네트워크에, R2의 c는 B 네트워크, d는 C 네트워크에 연결된다. B의 b와 c는 10.0.0.1과 10.0.0.2를 쓴다
PC
192.168.10.10 | a 192.168.10.1 | A 192.168.10.0/24
라우터 R1
b 10.0.0.1 | c 10.0.0.2 | B 10.0.0.0/24
라우터 R2
d 192.168.20.1 | 192.168.20.10 | C 192.168.20.0/24
PC
```

#### A의 PC에서 C의 PC로 보내는 예시
그림에서 A의 PC가 C의 PC로 패킷을 보내면 다음 순서로 전달된다.

1. A의 PC → R1: 목적지가 다른 네트워크에 있으므로 먼저 R1에 전송
2. R1 → R2: R1이 목적지 IP를 확인하고 C로 가는 길에 있는 R2로 전달
3. R2 → C의 PC: R2가 자기에게 연결된 C 네트워크의 PC로 전달

#### 인터페이스마다 IP가 필요한 이유
라우터 한 대 안에서도 인터페이스마다 IP 주소를 따로 설정할 수 있다. R1은 a에 192.168.10.1, b에 10.0.0.1을 설정했다. IP를 두 개만 가질 수 있는 것도 아니고, 연결하는 네트워크와 인터페이스가 늘면 그만큼 주소를 설정한다. a로 패킷을 받으면 R1 안에서 목적지를 확인하고, 이 예에서는 b로 다음 장비에 넘긴다.

```mermaid
제목: R1 한 대 안에서 인터페이스 a와 b에 IP를 각각 설정하고, 받은 패킷의 목적지를 확인해 내보낼 인터페이스를 고른다
%% 폰: TB
flowchart LR
  subgraph R1["R1"]
    IA["인터페이스 a<br/>IP 192.168.10.1"] --> K{"목적지 확인<br/>보낼 인터페이스 선택"} --> IB["인터페이스 b<br/>IP 10.0.0.1"]
  end
  NA["A 네트워크"] --> IA
  IB --> NB["B 네트워크"]
```

그럼 왜 라우터 한 대에 서로 다른 IP 주소를 설정할까? 라우터가 A와 B라는 서로 다른 네트워크에 각각 참여해야 하기 때문이다. 각 인터페이스에는 그 네트워크의 장비들이 라우터로 데이터를 넘길 때 쓸 주소가 필요하다.

- **A 쪽에서 보면**: 왼쪽 PC 주소는 192.168.10.10/24. 다른 네트워크로 보내려면 먼저 같은 A 네트워크의 R1로 전달해야 하고, 이때 다음 장비 주소로 쓰는 것이 a의 192.168.10.1
- **B 쪽에서 보면**: R2가 B 네트워크를 거쳐 R1로 보낼 때는 같은 B 네트워크에 있는 b의 10.0.0.1 사용. A 쪽 주소 192.168.10.1은 B 네트워크 범위에 속하지 않음

```bits
제목: A 네트워크의 PC 192.168.10.10/24와 인터페이스 a 192.168.10.1/24는 네트워크 주소가 192.168.10.0으로 같다
192.168.10.10/24
192.168.10.1/24
```

```bits
제목: B 네트워크의 b 10.0.0.1/24와 c 10.0.0.2/24는 같은 네트워크 10.0.0.0이지만 주소는 서로 다르다
10.0.0.1/24
10.0.0.2/24
```

결국 각 인터페이스의 IP는 그 네트워크에서 라우터로 들어가는 입구 주소라고 보면 된다. R1은 한쪽 인터페이스로 받은 데이터를 목적지에 맞는 다른 쪽 인터페이스로 넘긴다. 그래서 라우터 한 대에 IP 하나를 정하는 게 아니라, 인터페이스마다 연결된 네트워크에 맞는 IP를 설정한다. 또 B 네트워크에는 R1의 b와 R2의 c가 함께 연결되는데, 두 접속 지점은 같은 네트워크 범위에 속하면서도 10.0.0.1과 10.0.0.2라는 서로 다른 주소를 쓴다.

인터페이스 IP를 꼭 끝자리 1로 정할 필요는 없다. 그림의 .1은 가능한 주소 하나를 고른 예일 뿐이다. 문제에 따로 조건이 없으면 할당 가능 범위 안에서 아직 쓰지 않는 주소를 고르면 된다.

## OSI 7계층
출제: 21-3, 20-1
형태: 계층 설명 3개 → 보기에서 계층 이름, 설명 한 줄 → 계층 이름

### 개념
**OSI(Open Systems Interconnection) 7계층**은 서로 다른 회사가 만든 컴퓨터·장비끼리도 통신할 수 있도록, 통신에 필요한 기능을 7개 계층으로 나눈 표준 모델이다. 기능을 계층으로 나누면 계층마다 따로 만들고 고칠 수 있어 편하다. 각 계층은 아래 계층이 제공하는 기능을 이용해 자기 역할만 처리하고, 고유한 데이터 단위(PDU)로 정보를 주고받는다. PDU(Protocol Data Unit)란 각 계층에서 다루는 데이터 단위를 말한다.

다만 OSI 7계층 전체 구조를 통째로 묻는 실기 문제는 드물다. 통째로 외우기보다 큰 그림을 잡는 용도로 보고, 각 계층에서 실제로 나오는 세부 내용은 데이터 링크·네트워크·응용 계층 묶음에서 익히면 된다.

### OSI 7계층 한눈에 보기
계층 번호는 위로 갈수록 커진다. 데이터를 실제로 주고받을 때는 위(응용)에서 아래(물리)로 내려갔다가, 받는 쪽에서 다시 아래에서 위로 올라온다.

| 이름 | 계층 | 핵심 역할 | 대표 프로토콜·형식·장비 | PDU |
|---|---|---|---|---|
| 응용 | 7 | 사용자와 직접 맞닿는 서비스 제공 | HTTP, FTP, SMTP, DNS | 데이터 |
| 표현 | 6 | 암·복호화, 압축, 코드 변환 | JPEG, MPEG, ASCII | 데이터 |
| 세션 | 5 | 연결(세션) 설정·유지·종료, 동기화 | RPC, NetBIOS | 데이터 |
| 전송 | 4 | 종단 간 신뢰성·흐름 제어 | TCP, UDP | 세그먼트 |
| 네트워크 | 3 | 경로 설정(라우팅), 논리 주소 지정 | IP, ICMP, 라우터 | 패킷 |
| 데이터 링크 | 2 | 인접 노드 간 전송, 오류 제어 | 이더넷, HDLC, 스위치 | 프레임 |
| 물리 | 1 | 비트를 전기 신호로 바꿔 전송 | 케이블, 허브, 리피터 | 비트 |

표는 7계층부터 1계층 순서지만, 아래 설명은 기초가 되는 1계층부터 하나씩 올라간다. 계층마다 PDU 이름이 다른 이유는 맨 아래 캡슐화에서 본다.

### 계층 하나씩 보기

#### 1. 물리 계층 (Physical Layer)
물리 계층은 가장 아래 계층으로, 데이터를 비트(Bit) 단위의 전기·광 신호로 바꿔 전송 매체 위로 흘려보내는 일만 맡는다. 데이터의 의미는 다루지 않는다.

- **다루는 단위**: 비트(0과 1)
- **정의하는 것**: 전기적·기계적·기능적 특성(신호 전압, 케이블 규격, 커넥터 핀 배열 등)
- **대표 장비**: 케이블, 허브(Hub), 리피터(Repeater)
- **아래 계층 보완**: 맨 아래라 더 아래가 없음, 대신 위 모든 계층이 올라탈 '비트 전달'의 토대
- **실제 예시**: PC와 공유기를 랜선(LAN 케이블)으로 연결해 0과 1 신호를 주고받는 것

#### 2. 데이터 링크 계층 (Data Link Layer)
데이터 링크 계층은 직접 연결된 두 노드(인접한 장치) 사이의 데이터 전송을 관리하고 오류를 제어한다. 사실 랜선에는 0과 1의 비트만 흐른다. 데이터 링크 계층은 이 비트를 의미 있는 덩어리인 프레임(Frame)으로 다루는데, 보낼 때는 데이터를 프레임으로 묶어 물리 계층에 내려보내고, 받을 때는 들어온 비트를 다시 프레임으로 조립한다.

- **다루는 단위**: 프레임(비트를 묶은 논리적 단위)
- **핵심 기능**: 프레이밍(비트를 프레임으로 묶기), 흐름 제어(보내는 속도 조절), 오류 제어(깨진 데이터 감지·재전송), 물리 주소(MAC 주소) 지정
- **대표 프로토콜**: 이더넷, HDLC, PPP, 프레임 릴레이, ATM
- **대표 장비**: 스위치(Switch), 브리지(Bridge)
- **아래 계층 보완**: 물리 계층이 나른 '의미 없는 비트'에 경계·주소(MAC)·오류 검사를 붙여 믿을 수 있는 프레임으로 만듦
- **실제 예시**: 같은 공유기(스위치)에 연결된 노트북과 프린터가 MAC 주소를 보고 데이터를 주고받는 것

MAC 주소(Media Access Control Address)는 네트워크 장비마다 붙은 물리적인 하드웨어 주소다. 변하지 않는 고유 주소라서, 상황에 따라 바뀔 수 있는 IP(논리 주소)와 구분된다.

그럼 왜 비트를 굳이 프레임으로 묶을까? 물리 계층은 0과 1을 신호로 흘려보낼 뿐, 이 비트가 어디서 시작해 어디서 끝나는지, 누구에게 가는지, 중간에 깨졌는지는 모른다. 데이터 링크 계층은 비트를 프레임으로 묶으면서 아래 정보를 붙여 이 한계를 메운다.

- **경계 표시(플래그)**: 프레임의 시작과 끝 표시, 끝없이 이어지는 비트에서 한 덩어리의 범위 구분
- **주소(MAC 주소)**: 이 프레임을 받을 인접 장치 지정
- **오류 검사(FCS)**: 전송 중 비트가 깨지지 않았는지 확인

물리 계층이 '비트를 나르는 길'이라면, 데이터 링크 계층은 그 비트를 경계·주소·오류 검사가 붙은 믿을 수 있는 덩어리로 만드는 층이다. 이렇게 각 계층은 바로 아래 계층이 못 하는 일을 위에서 채워 주며 쌓인다.

여기서 헷갈리기 쉬운 점이 있다. 프레임은 케이블 위를 통째로 지나가는 물건이 아니라 비트를 논리적으로 묶은 단위다. 프레임으로 묶는 것은 보내는 컴퓨터(랜카드)이고, 스위치는 그 프레임을 받아 MAC 주소를 보고 전달만 한다.

#### 3. 네트워크 계층 (Network Layer)
네트워크 계층은 데이터가 여러 네트워크를 거쳐 최종 목적지까지 가도록 최적의 경로를 설정(라우팅)하고, 논리 주소(IP 주소)를 지정한다.

- **다루는 단위**: 패킷(Packet)
- **핵심 기능**: 라우팅(경로 설정), 논리 주소 지정, 패킷 전달
- **대표 프로토콜**: IP, ICMP, ARP, RARP, IGMP, 라우팅 프로토콜(RIP·OSPF·BGP)
- **대표 장비**: 라우터(Router)
- **아래 계층 보완**: 데이터 링크는 바로 옆(같은 네트워크) 장치까지만 전달, 네트워크 계층은 IP와 라우팅으로 여러 네트워크를 건너 먼 목적지까지 연결
- **실제 예시**: 우리 집에서 멀리 있는 웹 서버까지 여러 라우터를 거쳐 IP 주소로 길을 찾아가는 것

#### 4. 전송 계층 (Transport Layer)
전송 계층은 출발지와 목적지의 프로그램 사이(종단 간, End-to-End)에서 데이터를 신뢰성 있게, 곧 빠짐없이 순서대로 전달한다. 어느 프로그램에 줄지는 포트 번호로 구분한다. 포트 번호란 한 컴퓨터 안에서 실행 중인 여러 프로그램(프로세스)을 구분하는 번호로, 웹은 80번, 메일 전송은 25번을 쓴다.

- **다루는 단위**: 세그먼트(Segment)
- **핵심 기능**: 종단 간 흐름 제어, 오류 제어, 포트 번호로 프로그램 구분
- **대표 프로토콜**: TCP(연결형, 순서·재전송으로 신뢰성 보장), UDP(비연결형, 빠르지만 신뢰성 미보장)
- **아래 계층 보완**: 네트워크 계층은 패킷을 목적지 컴퓨터까지 보내지만 순서·도착은 보장하지 않음, 전송 계층이 재전송·순서 정렬로 신뢰성을 채우고 포트 번호로 받을 프로그램 구분
- **실제 예시**: 빠짐없이 받아야 하는 파일 다운로드는 TCP, 조금 끊겨도 빨라야 하는 실시간 영상통화는 UDP

TCP는 다 도착하는 등기 택배, UDP는 조금 끊겨도 빠른 생방송이라고 보면 된다. 연결형(TCP)과 비연결형(UDP)의 차이는 [교환 방식] 묶음에서 비교했다.

#### 5. 세션 계층 (Session Layer)
세션 계층은 통신하는 두 프로그램 사이의 연결(세션)을 설정·유지·종료하고 대화를 관리한다. 통신이 끊겼을 때 어디서부터 다시 시작할지 정하는 동기화(체크포인트)도 이 계층이 맡는다.

- **핵심 기능**: 세션 설정·유지·종료, 대화 제어, 동기화
- **대표 프로토콜**: RPC, NetBIOS
- **아래 계층 보완**: 전송 계층은 데이터를 주고받게만 해 줌, 세션 계층은 그 주고받음을 하나의 '대화(세션)'로 묶어 시작·유지·종료와 동기화 관리
- **실제 예시**: 화상회의에 접속해 통화를 시작하고, 끝날 때까지 연결을 유지하다 종료하는 것

대화 제어는 두 장치가 한 번에 한 방향씩 번갈아 통신할지(반이중), 양방향으로 동시에 통신할지(전이중)를 정하고 관리하는 일이다. RPC(원격 프로시저 호출)는 다른 컴퓨터의 함수를 내 컴퓨터에서 부르듯 실행하는 방식이고, NetBIOS는 초기 PC 네트워크에서 이름으로 통신을 연결해 주던 방식이다.

#### 6. 표현 계층 (Presentation Layer)
표현 계층은 서로 다른 시스템이 데이터를 이해할 수 있도록 표현 형식을 맞춰 주는 계층이다. 데이터 압축, 코드 변환, 암호화·복호화를 맡는다. 큰 사진을 JPEG로 압축하거나, 보낼 내용을 암호로 잠갔다가(암호화) 받는 쪽에서 다시 푸는(복호화) 일이 여기서 일어난다.

- **핵심 기능**: 데이터 압축, 코드(포맷) 변환, 암호화·복호화
- **대표 형식**: JPEG(이미지), MPEG(영상), ASCII(문자 코드)
- **아래 계층 보완**: 아래 계층들은 데이터를 '그냥 바이트'로 나를 뿐, 표현 계층이 압축·코드 변환·암호화로 양쪽이 같은 형식으로 이해하게 맞춤
- **실제 예시**: 사진을 JPEG로 압축해 보내고, 카드 번호는 암호화해 안전하게 보내는 것

#### 7. 응용 계층 (Application Layer)
응용 계층은 가장 위 계층으로, 사용자(응용 프로그램)와 직접 맞닿아 네트워크 서비스를 제공한다. 웹 브라우저, 메일 프로그램이 쓰는 프로토콜이 여기에 속한다.

- **핵심 기능**: 사용자에게 직접 서비스 제공(웹, 메일, 파일 전송 등)
- **대표 프로토콜**: HTTP, HTTPS, FTP, SMTP, POP3, IMAP, DNS, Telnet, SSH
- **아래 계층 보완**: 아래 여섯 계층은 데이터를 나르는 '배관', 응용 계층은 그 위에서 웹·메일처럼 사람이 직접 쓰는 서비스 제공
- **실제 예시**: 크롬 브라우저로 웹사이트에 접속(HTTP)하거나, 메일 앱으로 이메일을 보내는(SMTP) 것

### 캡슐화와 PDU
데이터를 보낼 때는 응용 계층에서 시작해 아래로 내려가며 각 계층이 자기 헤더를 덧붙인다. 헤더는 데이터 앞에 붙이는 택배 송장 같은 정보이고, 이 과정을 **캡슐화(Encapsulation)**라고 한다. 받는 쪽에서는 반대로 아래에서 위로 올라가며 각 계층이 자기 헤더를 하나씩 벗겨 내는 **역캡슐화(Decapsulation)**가 일어난다.

- 계층을 내려갈 때마다 헤더가 붙으면서 PDU 이름이 계층마다 달라짐
- 내려가는 순서대로 전송(세그먼트) → 네트워크(패킷) → 데이터 링크(프레임) → 물리(비트)로 점점 감싸짐
- 5 ~ 7계층(세션·표현·응용)의 데이터 단위는 따로 구분하지 않고 '데이터'라고 부름

```steps
제목: 한 계층씩 내려갈 때마다 헤더(송장)가 겹겹이 붙고 PDU 이름이 바뀐다
응용·표현·세션 | 데이터
전송 | 헤더 + 데이터 = 세그먼트
네트워크 | 헤더 + 세그먼트 = 패킷
데이터 링크 | 헤더 + 패킷 = 프레임
물리 | 비트
```

계층과 데이터 단위는 짝지어 외워 둔다. 비트(1계층), 프레임(2계층), 패킷(3계층), 세그먼트(4계층)다.

### 답 쓸 때
지문에 "암호화·압축"이 나오면 표현 계층, "경로 설정·IP"가 나오면 네트워크 계층, "MAC·프레임·인접 노드"가 나오면 데이터 링크 계층이다. 그리고 많이들 헷갈리는 게 전송 계층과 네트워크 계층인데, "종단 간"이면 전송 계층, "경로 설정"이면 네트워크 계층으로 가른다.

## IP 주소 (IPv4·IPv6·클래스·사설 대역)
출제: 21-1, 20-4
형태: 비트 수 숫자 빈칸, 설명 → 버전 이름

### IP란
**IP(Internet Protocol)**는 인터넷에서 데이터를 주고받기 위한 통신 규약(프로토콜)이다. 우편물을 보내려면 주소가 필요하듯이, 인터넷에서 데이터를 주고받으려면 각 장치를 식별할 주소가 필요한데, 그것이 바로 IP 주소다. IP 주소는 PC, 스마트폰, 서버 등 네트워크에 연결된 모든 장치에 할당된다.

| 용어 | 설명 |
|---|---|
| IP | 인터넷에서 데이터를 주고받기 위한 통신 규약 |
| IP 주소 | IP 통신에서 각 장치를 식별하기 위한 고유한 번호 |

### IPv4와 IPv6
IP 주소에는 두 가지 버전이 있다.

- **IPv4**: Internet Protocol version 4 (4번째 버전)
- **IPv6**: Internet Protocol version 6 (6번째 버전)

그럼 IPv5는 어디 갔을까? IPv5(ST, Internet Stream Protocol)는 실험적으로 개발됐지만 상용화되지 못하고 사라졌다.

- 실시간 음성/영상 스트리밍을 위해 1979년에 실험적으로 개발
- 32비트 주소 체계를 그대로 써서 IPv4의 주소 고갈 문제를 해결하지 못함
- 결국 채택되지 않고 128비트의 IPv6가 후속 버전으로 선정

| 구분 | IPv4 | IPv6 |
|---|---|---|
| 비트 | 32비트 | 128비트 |
| 구분 | 8비트씩 4개 | 16비트씩 8개 |
| 표기 | 10진수(.) | 16진수(:) |
| 예시 | 192.168.0.1 | 2001:db8::1 |

#### 1. IPv4
IPv4 주소는 32비트이고, 32비트를 8비트씩 4개로 나눈다. 이 2진수를 10진수로 바꾸면 우리가 흔히 보는 IP 주소 모양이 된다.

```bits
제목: IPv4 주소 192.168.0.1은 32비트를 8비트씩 4개로 나눠 10진수로 적은 것이다
192.168.0.1/24
```

8비트로 만들 수 있는 가장 큰 10진수는 얼마일까? 11111111(2) = 2^7 + 2^6 + 2^5 + 2^4 + 2^3 + 2^2 + 2^1 + 2^0 = 255(10)이다. 여기서 (2)는 2진수라는 표시다. 그래서 IPv4 주소는 0.0.0.0부터 255.255.255.255까지 나타낼 수 있고, 총량은 2^32 = 4,294,967,296, 대략 43억 개다.

#### 2. IPv6
IPv6 주소는 128비트이고, 128비트를 16비트씩 8개로 나눈다. IPv4의 주소 고갈 문제를 해결하려고 나왔고, 128비트를 써서 사실상 무한에 가까운 주소를 제공한다.

| 구분 | IPv4 | IPv6 |
|---|---|---|
| 비트 길이 | 32비트 | 128비트 |
| 구분 방식 | 8비트씩 4개 (.으로 구분) | 16비트씩 8개 (:으로 구분) |
| 표기 방식 | 10진수 | 16진수 |
| 주소 예시 | 192.168.0.1 | 2001:0db8:85a3:0000:0000:8a2e:0370:7334 |
| 주소 개수 | 약 43억 개 (2^32) | 약 3.4 × 10^38개 (2^128) |

### IP 주소 종류
IP 주소는 네트워크 주소, 호스트 주소, 브로드캐스트 주소로 나눌 수 있다.

| 구분 | 설명 |
|---|---|
| 네트워크 주소 | 네트워크를 대표하는 주소 (호스트 부분이 모두 0) |
| 호스트 주소 | 호스트(장치, PC·스마트폰)에 할당하는 주소 |
| 브로드캐스트 주소 | 모든 호스트(장치)에 데이터를 한 번에 보낼 때 쓰는 주소 (호스트 부분이 모두 1) |

네트워크 주소와 브로드캐스트 주소는 장치에 할당할 수 없다. 그래서 실제로 쓸 수 있는 호스트 주소는 전체 IP 주소에서 2개를 뺀 값이다. 192.168.1.0/24 네트워크로 보자. /24는 32비트 중 앞 24비트가 네트워크 부분이라는 표기로, 자세한 것은 [서브넷 마스크·CIDR·프리픽스] 묶음에서 다룬다. 여기서는 앞 24비트(192.168.1)가 네트워크 부분, 나머지 8비트가 호스트 부분이다.

- **네트워크 주소**: 192.168.1.0, 호스트 부분 8비트가 모두 0 (00000000 → 10진수 0)
- **브로드캐스트 주소**: 192.168.1.255, 호스트 부분 8비트가 모두 1 (11111111 → 10진수 255)
- **호스트 주소**: 192.168.1.1 ~ 192.168.1.254 (254개)

```bits
제목: 192.168.1.0/24는 앞 24비트가 네트워크 부분, 뒤 8비트가 호스트 부분이다. 호스트 부분이 모두 0이면 네트워크 주소다
192.168.1.0/24
192.168.1.255/24 호스트 부분이 모두 1인 브로드캐스트 주소
```

## 프로토콜의 정의와 3요소
출제: 20-3, 20-1
형태: 정의 한 줄 → 용어, 요소 설명 3개 → 이름

### 개념
**프로토콜(Protocol)**이란 서로 다른 시스템이 데이터를 주고받기 위해 미리 정해 둔 규칙과 약속을 말한다. 문제 지문에는 톰 마릴(Tom Marill)이 컴퓨터 간 통신 규약을 가리켜 쓴 "기술적 은어"라는 표현이 단서로 나왔다.

### 한눈에 구분
| 요소 | 뜻 | 예 |
|---|---|---|
| **구문(Syntax)** | 데이터의 **형식·부호화·신호 수준** | 필드 순서와 길이, 어떤 비트가 주소인가 |
| **의미(Semantics)** | 각 비트·필드가 **무엇을 뜻하는지**, 제어 정보와 오류 처리 | 이 필드가 1이면 재전송 요구 |
| **타이밍(Timing)** | **속도 조절과 순서** 제어 | 언제 보내고 얼마나 빨리 보내는가 |

### 3요소 하나씩 보기
20-1은 요소 설명 3개를 주고 이름을 쓰게 했다. 헤더 하나짜리 간단한 프레임을 주고받는 장면에 세 요소를 하나씩 대어 보자.

#### 1. 구문 (Syntax)
- 데이터의 형식·부호화·신호 수준
- 지문 단서: "형식", "필드 순서와 길이"

"처음 8비트는 목적지 주소, 다음 8비트는 길이, 그 뒤가 데이터"처럼 프레임을 어떤 모양으로 짤지 정해 두는 것이 구문이다. 받는 쪽은 이 약속대로 비트를 잘라 읽는다.

모양만 정할 뿐, 그 값이 무슨 뜻인지는 아직 정하지 않는다.

#### 2. 의미 (Semantics)
- 각 비트·필드가 뜻하는 내용
- 제어 정보와 오류 처리 방법

같은 프레임에서 제어 필드 값이 1이면 "재전송 요구"로 받아들인다고 정해 두는 것이 의미다. 구문이 정한 자리에 들어간 값을 어떻게 해석할지가 여기서 정해진다.

#### 3. 타이밍 (Timing)
- 속도 조절과 순서 제어
- 지문 단서: "언제", "얼마나 빨리"

송신 측은 빠른데 수신 측이 느리면 송신 속도를 늦추고, 응답을 받은 뒤에 다음 프레임을 보내는 식으로 순서를 맞춘다.

구문은 "어떤 모양", 의미는 "무슨 뜻", 타이밍은 "언제, 얼마나 빨리"로 묶어 두면 설명 3개를 받아도 바로 짝이 맞는다.

프로토콜이 하는 일을 기능별로 나누면 아래 표와 같다. 이 중 흐름 제어·오류 제어·순서 제어는 데이터 링크와 전송 계층 양쪽에서 다 쓰는 용어다.

| 기능 | 뜻 |
|---|---|
| 단편화·재조립 | 큰 데이터를 보낼 수 있는 크기로 나누고 받는 쪽에서 다시 합침 |
| 캡슐화 | 데이터에 주소·제어 정보 등 헤더를 붙임 |
| 흐름 제어 | 수신 측이 처리할 수 있는 속도로 송신량을 조절 |
| 오류 제어 | 전송 오류를 검출하고 재전송하거나 정정 |
| 순서 제어 | 패킷이 보낸 순서대로 처리되게 번호를 붙임 |
| 동기화 | 송수신 측의 타이밍을 맞춤 |
| 주소 지정 | 송신지·수신지를 식별 |
| 다중화 | 하나의 통로를 여러 통신이 나눠 씀 |
| 연결 제어 | 연결 설정·유지·해제 |

### 기출에서 이렇게 나왔다
- 20-3: 톰 마릴, 기술적 은어 한 줄 → **프로토콜**
- 20-1: 요소 설명 3개 → **구문 / 의미 / 타이밍**

### 답 쓸 때
3요소는 한글 "구문·의미·타이밍"과 영문 Syntax·Semantics·Timing 가운데 문제가 요구한 쪽으로 쓴다.

### 기출 문제

:::q 20-3 13번

정답: 프로토콜 또는 Protocol
:::

- ( ① ): 데이터의 형식이나 부호화·신호 레벨 등을 규정한다.
- ( ② ): 데이터 전송의 제어 정보로, 무엇을 의미하는지 규정한다.
- ( ③ ): 두 객체 간의 통신 속도, 메시지 순서 제어를 규정한다.

정답: ①: 구문 또는 Syntax ②: 의미 또는 Semantics ③: 타이밍 또는 Timing 또는 시간

## 전송 계층 (TCP·UDP·흐름 제어·혼잡 제어)
출제: 없음

### 개념
전송 계층은 포트 번호로 프로세스를 구분해서 종단 간 전송을 맡는 계층이다. 대표 프로토콜이 TCP와 UDP인데, 둘을 비교하면 이렇다.

| 항목 | **TCP(Transmission Control Protocol)** | **UDP(User Datagram Protocol)** |
|---|---|---|
| 연결 | 연결형(3-way handshake) | 비연결형 |
| 신뢰성 | 재전송·순서 보장·흐름 제어·혼잡 제어 | 보장 없음 |
| 속도 | 상대적으로 느림 | 빠르고 헤더가 작음 |
| 쓰임 | 웹, 메일, 파일 전송 | 스트리밍, DNS 질의, 실시간 서비스 |

- **3-way handshake(연결 설정)**: SYN → SYN+ACK → ACK
- **4-way handshake(연결 해제)**: FIN → ACK → FIN → ACK, 마지막 ACK를 보낸 쪽은 TIME_WAIT 상태로 잠시 대기

연결을 맺을 때와 달리 해제할 때 ACK와 FIN이 따로 나뉘는 이유는, 첫 FIN을 받은 쪽(아래 그림의 서버)이 남은 데이터를 다 보낸 뒤에야 자기 FIN을 보내기 때문이다.

### 전송 계층 하나씩 보기
아직 기출로 나온 적은 없는 묶음이다. 다만 흐름 제어·오류 제어는 데이터 링크와 전송 계층 양쪽에서 쓰는 용어라 함께 봐 두면 좋다. 프로토콜 두 개, 연결 절차 두 개, 송신량 조절 기법 네 개 순서로 본다.

#### 1. TCP (Transmission Control Protocol)
- 연결형(3-way handshake)
- 재전송·순서 보장·흐름 제어·혼잡 제어
- 쓰임: 웹, 메일, 파일 전송

웹 페이지를 받다가 세그먼트 하나가 빠지면 TCP가 다시 받아 오고, 늦게 온 세그먼트는 순서대로 다시 맞춘 뒤 브라우저에 넘긴다. 그래서 페이지가 중간이 빠진 채로 보이는 일이 없다.

#### 2. UDP (User Datagram Protocol)
- 비연결형
- 신뢰성 보장 없음, 빠르고 헤더가 작음
- 쓰임: 스트리밍, DNS 질의, 실시간 서비스

DNS 질의는 질문 하나, 답 하나로 끝난다. 이걸 위해 매번 연결을 맺고 끊으면 오히려 느려진다. 그래서 연결 없이 바로 질문을 보내는 UDP가 맞는다.

영상 통화도 마찬가지다. 조금 깨진 화면을 다시 받느라 멈추는 것보다 그냥 다음 화면으로 넘어가는 편이 낫다.

#### 3. 3-way handshake (연결 설정)
- SYN → SYN+ACK → ACK
- TCP 연결을 맺는 절차

```mermaid
제목: 서버가 "좋다(ACK)"와 "나도 연결하자(SYN)"를 한 번에 보내서 세 번이면 연결이 맺어진다
sequenceDiagram
  participant C as 클라이언트
  participant S as 서버
  C->>S: SYN (연결하자)
  S->>C: SYN+ACK (좋다, 나도 연결하자)
  C->>S: ACK (확인했다)
```

서버가 "좋다"와 "나도 연결하자"를 한 번에 묶어 보내기 때문에 세 번이면 끝난다.

#### 4. 4-way handshake (연결 해제)
- FIN → ACK → FIN → ACK
- 마지막 ACK를 보낸 쪽은 TIME_WAIT 상태로 잠시 대기

```mermaid
제목: ACK와 FIN 사이에 서버가 남은 데이터를 마저 보내는 구간이 있어서 둘을 묶지 못하고 네 번이 된다
sequenceDiagram
  participant C as 클라이언트
  participant S as 서버
  C->>S: FIN (나는 다 보냈다)
  S->>C: ACK (알았다)
  Note over C,S: 서버가 남은 데이터를 마저 보냄
  S->>C: FIN (나도 다 보냈다)
  C->>S: ACK (확인했다)
  Note over C: TIME_WAIT 상태로 잠시 대기
```

그림에서 서버의 ACK와 FIN 사이에 남은 데이터를 마저 보내는 구간이 있다. 3-way에서 SYN+ACK를 하나로 묶었던 것과 달리, 여기서는 이 구간 때문에 둘을 묶지 못하고 네 번이 된다.

#### 5. 슬라이딩 윈도우 (Sliding Window)
- 흐름 제어 기법
- ACK 없이 윈도우 크기만큼 연속 전송, ACK를 받은 만큼 윈도우를 밀어 계속 전송
- TCP가 사용

윈도우 크기가 4라면 0~3번을 ACK 없이 연달아 보낸다. 0번과 1번의 ACK가 오면 윈도우가 두 칸 밀려 2~5번이 되고, 4번과 5번을 이어서 보낸다.

정지-대기는 한 번에 하나만 보내지만, 슬라이딩 윈도우는 윈도우 크기만큼 기다리지 않고 보낸다. 수신 측이 감당할 수 있는 만큼으로 윈도우 크기를 정하기 때문에 흐름 제어가 된다.

#### 6. 느린 시작 (Slow Start)
- 혼잡 제어 기법
- 혼잡 윈도우를 작게 시작해 왕복 시간마다 두 배로 증가
- 임계치(ssthresh)에 닿으면 혼잡 회피로 전환

#### 7. 혼잡 회피 (Congestion Avoidance)
- 혼잡 제어 기법
- 임계치 이후 1씩 선형 증가

#### 8. AIMD
- 혼잡 제어 기법
- 평소 합으로 증가(Additive Increase), 혼잡 감지 시 절반으로 감소(Multiplicative Decrease)

세 기법에 나오는 혼잡 윈도우는 네트워크가 막히지 않도록 송신 측이 ACK 없이 한 번에 보낼 양을 스스로 제한해 둔 값이다. 수신 측 버퍼에 맞추는 슬라이딩 윈도우와 달리 네트워크 상황에 맞춘다. 세 기법은 한 연결 안에서 이어서 일어나서 한 장면으로 보는 편이 쉽다. 아래 예는 혼잡 윈도우 1에서 시작하고 임계치는 8이다.

```
느린 시작(2배씩)   1 → 2 → 4 → 8      임계치 8 도달
혼잡 회피(1씩)     8 → 9 → 10 → 11
혼잡 감지          11 → 절반으로 감소   (AIMD의 Multiplicative Decrease)
```

이름은 "느린" 시작이지만 작게 시작할 뿐이고, 늘어나는 속도는 두 배씩이라 오히려 빠르다. 임계치 8에 닿은 뒤로는 1씩만 늘리고, 혼잡을 감지하면 크게 줄인다. 조금씩 늘리고 크게 줄인다는 이 원칙을 한 줄로 부른 이름이 AIMD다. 다만 혼잡을 무엇으로 감지했느냐에 따라 줄이는 폭이 다르다. 중복 ACK로 감지하면 절반으로 줄이지만, 타임아웃이면 혼잡 윈도우를 1로 되돌려 느린 시작부터 다시 하는 방식(TCP Tahoe 등)도 있다.

### 한눈에 구분
| 기법 | 목적 | 내용 |
|---|---|---|
| **정지-대기(Stop-and-Wait)** | 흐름 제어 | 프레임 하나를 보내고 ACK를 받은 뒤 다음을 보냄 |
| **슬라이딩 윈도우(Sliding Window)** | 흐름 제어 | ACK 없이 윈도우 크기만큼 연속 전송하고, ACK를 받은 만큼 윈도우를 밀어 계속 전송. TCP가 사용 |
| **느린 시작(Slow Start)** | 혼잡 제어 | 혼잡 윈도우를 작게 시작해 왕복 시간마다 두 배로 늘림. 임계치(ssthresh)에 닿으면 혼잡 회피로 전환 |
| **혼잡 회피(Congestion Avoidance)** | 혼잡 제어 | 임계치 이후에는 1씩 선형으로 늘림 |
| **AIMD** | 혼잡 제어 | 평소에는 합으로 증가(Additive Increase), 혼잡을 감지하면 절반으로 감소(Multiplicative Decrease) |

여기서 많이들 헷갈리는 게 흐름 제어와 혼잡 제어다. 둘 다 송신량을 조절하지만 무엇을 지키느냐가 다르다.

- **흐름 제어(Flow Control)**: 수신 측 버퍼가 넘치지 않게 송신량을 맞춤. 수신자 보호
- **혼잡 제어(Congestion Control)**: 네트워크 안의 라우터·회선이 막히지 않게 송신량을 줄임. 네트워크 보호
