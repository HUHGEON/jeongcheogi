# SW 개발

테스트·형상 관리·인터페이스 영역이다. 21개 회차 중 테스트 커버리지가 9회차, 블랙박스 테스트가 8회차에 나와 이 영역의 절반 이상을 차지한다. 문제 형태는 "설명 2~3줄을 주고 이름을 고르기"가 기본이고, 커버리지만 제어흐름도에서 경로 번호를 채우는 형태가 더해진다. 2023년 이후에도 커버리지·블랙박스·스텁/드라이버·AJAX·URL 구조가 계속 나오고, 그중 상당수가 2~3년 전 문제의 재출제다.

## 테스트 커버리지 (화이트박스)
출제: 25-3, 25-2, 25-1, 24-3, 24-1, 23-2, 23-1, 21-2, 20-3
형태: 설명 1~3줄 → 커버리지 이름 / 설명 3개 → 문장·분기·조건 구분 / 제어흐름도 → 커버리지를 만족하는 경로 번호 채우기

### 개념
화이트박스 테스트는 코드 내부 구조를 보고 테스트 케이스를 만든다. 커버리지는 "테스트가 코드의 어디까지를 한 번 이상 지나갔나"를 재는 기준이고, 종류는 **무엇을** 참·거짓으로 만들어야 하는지로 구분한다.

| 커버리지 | 한 번 이상 만족시켜야 하는 것 | 영문 |
|---|---|---|
| **구문(문장) 커버리지** | 모든 문장이 한 번 이상 실행 | Statement Coverage |
| **결정(분기) 커버리지** | 모든 결정(if·while 전체 조건식)의 결과가 참·거짓 각각 한 번 이상 | Decision / Branch Coverage |
| **조건 커버리지** | 결정 안의 개별 조건 각각이 참·거짓 한 번 이상 (전체 결과는 묻지 않음) | Condition Coverage |
| **조건/결정 커버리지** | 개별 조건과 전체 결정이 모두 참·거짓 한 번 이상 | Condition/Decision Coverage |
| **변경 조건/결정 커버리지(MC/DC)** | 각 개별 조건이 다른 조건과 무관하게 혼자서 전체 결정 결과를 바꾸는 경우를 포함 | Modified Condition/Decision Coverage |
| **다중 조건 커버리지** | 개별 조건의 모든 참·거짓 조합 | Multiple Condition Coverage |

`if (A and B)` 로 보면 차이가 선명하다.

| 테스트 세트 (A, B) | 결정 결과 | 만족하는 커버리지 |
|---|---|---|
| (T,T) (F,F) | T, F | 결정, 조건, 조건/결정 |
| (T,F) (F,T) | F, F | 조건만. 결정은 항상 거짓이라 미달 |
| (T,T) (T,F) (F,T) | T, F, F | MC/DC. A만 바꿔 결과가 변하는 쌍과 B만 바꿔 변하는 쌍이 모두 있음 |
| 네 조합 전부 | | 다중 조건 |

포함 관계는 **다중 조건 ⊃ MC/DC ⊃ 조건/결정 ⊃ 결정 ⊃ 구문** 이다. 조건 커버리지는 결정 커버리지를 보장하지 않는다(둘째 줄). 강한 쪽을 만족하면 약한 쪽은 자동으로 만족한다.

### 제어흐름도에서 경로 읽기
기출은 번호가 붙은 흐름도를 주고 "TC1: 1-2-3-...", "TC2: ..." 처럼 경로를 채우게 한다.

1. 마름모(결정 노드)를 찾는다. 결정 노드마다 참 화살표와 거짓 화살표가 하나씩 있다.
2. **분기 커버리지**는 모든 결정 노드의 참·거짓 화살표를 각각 한 번 이상 지나면 된다. 보통 두 경로면 된다. 첫 경로는 결정마다 참 쪽으로, 둘째 경로는 결정마다 거짓 쪽으로 간다.
3. **문장 커버리지**는 모든 처리 노드를 한 번 이상 지나면 된다. 반복문 본문을 지나려면 한 번은 참으로 들어가야 한다.
4. 반복문은 "조건 → 본문 → 다시 조건" 으로 되돌아오므로 경로에 같은 번호가 두 번 적힌다.

### 기출에서 이렇게 나왔다
- 25-3: 설명 2줄 → 한글 보기에서 **조건 커버리지** (23-2 재출제)
- 25-2: 제어흐름도 → 분기 커버리지를 만족하는 TC1·TC2 경로 번호 채우기 (23-1 재출제)
- 25-1: 코드와 제어흐름도 → 노드에 들어갈 문장과 실행 순서 채우기 (문장 커버리지)
- 24-3: 설명 3개 → **Statement / Branch / Condition** 영문으로
- 24-1: "중요 조합", "다른 조건과 무관하게 전체 결과에 영향" → **MC/DC**
- 23-2: 한 줄 설명 → **Condition Coverage**
- 23-1: 제어흐름도 → 분기 커버리지 경로 채우기
- 21-2: 설명 3개 → **문장 / 결정(분기) / 조건**
- 20-3: 설명 → **분기(결정) 커버리지**

### 답 쓸 때
보기가 영문이면 Statement·Branch·Condition 으로, 한글이면 문장(구문)·분기(결정)·조건으로 쓴다. 결정과 분기는 같은 것이고 문제에 따라 둘 중 하나로 표기된다. MC/DC는 약어 그대로 쓴다.

## 블랙박스 테스트 기법
출제: 26-2, 23-3, 22-3, 22-1, 21-3, 21-1, 20-4, 20-3
형태: 설명 또는 예시 데이터 → 기법 이름 / 보기 여러 개 중 블랙박스 기법 3개 고르기

### 개념
블랙박스 테스트는 코드를 보지 않고 **입력과 출력(명세)** 만으로 테스트 케이스를 만든다. 기출은 기법의 정의보다 "어떤 데이터를 골랐나"를 보여 주고 기법 이름을 묻는다. 그래서 문제가 주는 단서로 기법을 알아보는 연습이 핵심이다.

### 한눈에 구분
| 기법 | 문제가 주는 단서 | 무엇을 하는가 |
|---|---|---|
| **동등 분할(Equivalence Partitioning)** | 점수 구간 표, 구간별 대표값 하나씩, "유효/무효 그룹" | 입력을 같은 결과가 나오는 그룹으로 나누고 그룹마다 대표값 하나를 테스트 |
| **경계값 분석(Boundary Value Analysis)** | 경계 바로 앞뒤 값이 나열됨 (예: 0~59 구간이면 -1, 0, 59, 60) | 오류가 경계에 몰린다는 전제로 경계와 그 양옆 값을 테스트 |
| **원인-결과 그래프(Cause-Effect Graph)** | "입력 조건과 출력 결과의 관계를 그래프로", 결정 테이블로 변환 | 입력(원인)과 출력(결과)의 논리 관계를 그래프로 그려 효용 높은 케이스를 고름 |
| **결정 테이블(Decision Table)** | 조건 조합과 행동을 표로 | 조건의 참·거짓 조합마다 기대 행동을 표로 정리 |
| **상태 전이(State Transition)** | 상태, 이벤트, 전이 | 상태 변화를 일으키는 이벤트 조합을 테스트 |
| **오류 예측(Error Guessing)** | 경험, 직관, 과거 오류 | 테스터의 경험으로 오류가 날 만한 입력을 추측 |
| **비교(Comparison)** | 같은 입력을 여러 버전에 | 여러 버전의 프로그램에 같은 데이터를 넣고 출력을 비교 |
| **페어와이즈(Pairwise)** | 모든 두 인자 조합 | 인자 쌍의 모든 조합이 한 번 이상 나오도록 조합 수를 줄임 |
| **분류 트리(Classification Tree)** | 입력 영역을 트리로 | 입력 조건을 트리 구조로 분류한 뒤 조합 |
| **유스케이스(Use Case)** | 시나리오, 사용자 흐름 | 유스케이스의 흐름을 따라 케이스 작성 |

동등 분할과 경계값 분석은 같은 구간 표에서 나오므로 혼동하기 쉽다. 구간마다 값이 **하나**이고 구간 안쪽 값이면 동등 분할, 구간 **양 끝과 그 바깥** 값이면 경계값 분석이다.

### 기출에서 이렇게 나왔다
- 26-2: 점수 구간 표 + 구간별 대표값으로 테스트 → **동등 분할**
- 23-3: 유효/무효 그룹으로 나누고 대푯값 → **Equivalence Partitioning**
- 22-3: 예시 데이터 -1, 0, 59, 60 ... 경계값 포함 → **Boundary Value Analysis**
- 22-1: 보기 8개 중 블랙박스 기법 3개 → **BVA / Equivalence Partitioning / Cause-Effect Graph**
- 21-3: 입력·출력 조건을 그래프로 → **원인-결과 그래프**
- 21-1: 예시 2개 → **경곗값 분석 / 동등 분할**
- 20-4: 유효/무효, 대표값 → **동등 분할**
- 20-3: 동치 분할·경계값 분석을 포함하는 테스트 기법 → **블랙박스 테스트**

### 답 쓸 때
여러 보기 중 3개를 고르는 문제에는 화이트박스 기법(기초 경로, 조건·루프 검사, 데이터 흐름)이 섞일 수 있다. 블랙박스는 "입력 데이터를 고르는 방법" 이름이라는 점으로 가른다. 동등 분할은 동치 분할·동등 클래스 분해로도 불린다.

## 통합 테스트: 스텁·드라이버, 하향식·상향식, 회귀
출제: 26-1, 23-2, 22-2, 21-3, 21-2
형태: 하향식/상향식 설명 2줄 → 더미 모듈 이름 빈칸 / 설명 → 영문 용어

### 개념
통합 테스트는 단위 테스트가 끝난 모듈을 결합하며 **모듈 사이의 인터페이스** 오류를 찾는다. 아직 만들어지지 않은 모듈 자리에 임시 모듈을 넣어야 하는데, 어느 방향으로 통합하느냐에 따라 임시 모듈의 이름이 다르다.

| 방식 | 통합 순서 | 필요한 더미 모듈 | 특징 |
|---|---|---|---|
| **하향식(Top-down)** | 상위(제어) 모듈부터 아래로 | **스텁(Stub)**: 아직 없는 하위 모듈을 흉내 내는 간단한 모듈 | 깊이 우선·너비 우선 선택, 설계 결함을 일찍 발견 |
| **상향식(Bottom-up)** | 최하위 모듈부터 위로 | **드라이버(Driver)**: 하위 모듈을 호출해 주는 임시 상위 모듈 | 하위 모듈을 클러스터로 묶어 테스트 |
| **빅뱅(Big Bang)** | 전부 한 번에 결합 | 없음 | 소규모에만 가능, 오류 위치 찾기 어려움 |
| **샌드위치(혼합)** | 상위는 하향식, 하위는 상향식 | 스텁 + 드라이버 | 두 방식의 장점 결합 |

**회귀 테스트(Regression Test)** 는 통합 방식이 아니라, 모듈을 고치거나 새로 통합한 뒤 **이미 되던 기능이 깨지지 않았는지** 다시 돌리는 테스트다. 변경할 때마다 반복하므로 자동화 대상이 된다.

### 한눈에 구분
| 단서 | 답 |
|---|---|
| "하향식", "상위 모듈 먼저", "하위 모듈을 대신" | 스텁 |
| "상향식", "최하위부터", "상위 모듈 역할" | 드라이버 |
| "수정 후 기존 기능 재검증", "부작용 확인" | 회귀 테스트 |

### 기출에서 이렇게 나왔다
- 26-1: 하향식/상향식 설명 2줄 빈칸 → **스텁 / 드라이버** (23-2 재출제)
- 23-2: 하향식/상향식 설명 2줄 → **스텁 / 드라이버**
- 22-2: 회귀 테스트 설명 → 영문으로 **Regression**
- 21-3: "( ) 테스트는 최하위부터 위로, ( )가 필요" → **상향식 / 테스트 드라이버**
- 21-2: "상향식은 드라이버, 하향식은 테스트 ( )" → **스텁**

### 답 쓸 때
스텁은 하향식, 드라이버는 상향식이다. "드라이버가 운전(호출)한다" 로 기억하면 방향이 헷갈리지 않는다. 테스트 스텁·테스트 드라이버처럼 앞에 "테스트"가 붙어도 같은 답이다.

## 테스트 레벨과 V 모델, 알파·베타 테스트
출제: 22-2, 22-1, 21-1
형태: V 모델 그림의 빈칸 4개 → 레벨 이름 / 설명 2개 → 레벨 또는 알파·베타 구분

### 개념
테스트 레벨은 개발 단계와 짝을 이룬다. V 모델은 왼쪽에 개발 단계, 오른쪽에 대응하는 테스트 레벨을 놓은 그림이다.

| 개발 단계 | 대응 테스트 레벨 | 무엇을 확인하나 |
|---|---|---|
| 요구사항 분석 | **인수 테스트(Acceptance)** | 사용자 요구를 만족하는지, 사용자가 수행 |
| 시스템 설계 | **시스템 테스트(System)** | 전체 시스템의 기능·비기능(성능·보안 등) |
| 상세 설계 | **통합 테스트(Integration)** | 모듈 간 인터페이스 |
| 코딩(구현) | **단위 테스트(Unit)** | 모듈·함수 하나, 주로 화이트박스 |

순서는 **단위 → 통합 → 시스템 → 인수** 다. 그림에서 아래쪽(코딩 옆)이 단위, 위쪽(요구사항 옆)이 인수다.

인수 테스트는 누가 어디서 하느냐로 둘로 나뉜다.

| 구분 | 장소 | 개발자 | 단서 |
|---|---|---|---|
| **알파 테스트(Alpha)** | 개발자 환경(통제된 환경) | 입회함 | "개발자가 지켜보는 가운데", "통제된 환경" |
| **베타 테스트(Beta)** | 사용자 실제 환경 | 없음 | "다수의 사용자", "실제 업무 환경", "문제점을 보고" |

### 기출에서 이렇게 나왔다
- 22-2: 설명 2개 → **베타 / 알파** 순서로 답
- 22-1: V 모델 그림 4칸 → **단위 / 통합 / 시스템 / 인수**
- 21-1: 설명 2개 → **단위 / 통합**

### 답 쓸 때
V 모델 빈칸은 그림의 위치로 답이 정해진다. 설명형은 "개발자 환경 = 알파, 사용자 환경 = 베타" 한 줄이면 충분하다.

## 테스트 자동화 도구와 하네스, 테스트 오라클
출제: 22-1, 20-4, 20-2
형태: 설명 1~2개 → 용어 또는 영문

### 개념
**테스트 하네스(Test Harness)** 는 테스트를 돌리기 위해 준비하는 코드와 데이터의 묶음이다.

| 구성 요소 | 뜻 |
|---|---|
| **테스트 드라이버(Driver)** | 하위 모듈을 호출하는 임시 상위 모듈 (상향식) |
| **테스트 스텁(Stub)** | 하위 모듈을 대신하는 임시 모듈 (하향식) |
| **테스트 케이스(Test Case)** | 입력·조건·예상 결과 한 벌 |
| **테스트 슈트(Test Suite)** | 테스트 케이스의 집합 |
| **테스트 스크립트(Test Script)** | 테스트를 자동으로 실행하는 절차 |
| **목 오브젝트(Mock Object)** | 미리 정해 둔 행위를 하는 가짜 객체 |

자동화 도구는 코드를 실행하느냐로 나뉜다.

| 도구 | 실행 여부 | 찾는 것 |
|---|---|---|
| **정적 분석 도구(Static Analysis)** | 실행하지 않음 | 코딩 표준 위반, 복잡도, 결함 패턴 |
| **동적 분석 도구(Dynamic Analysis)** | 실행하면서 | 메모리 누수, 스레드 결함, 실제 커버리지 |

**xUnit** 은 언어별 단위 테스트 프레임워크를 통칭한다. Java의 **JUnit**(`@Test` 어노테이션), C++의 CppUnit, .NET의 NUnit, Python의 PyUnit(unittest) 등이다.

**테스트 오라클(Test Oracle)** 은 "결과가 맞는지 판단하는 기준(기댓값)" 이다.

| 오라클 | 기댓값 범위 |
|---|---|
| **참(True) 오라클** | 모든 입력에 대해 기댓값을 제공, 전수 검사 |
| **샘플링(Sampling) 오라클** | 특정 몇 개 입력에 대해서만 기댓값 제공 |
| **휴리스틱(Heuristic) 오라클** | 샘플링 + 나머지는 추정(휴리스틱)으로 처리 |
| **일관성 검사(Consistent) 오라클** | 변경 전후 수행 결과가 같은지 확인 |

### 기출에서 이렇게 나왔다
- 22-1: 실행하지 않고 / 실행하면서 분석하는 도구 → **static / dynamic**
- 22-1: 자바용 xUnit, `@Test` → **JUnit**
- 20-4: 일부 특정 입력값에 대해서만 기댓값 제공 → **샘플링 오라클**
- 20-2: 실행하지 않고 코딩 표준·복잡도·결함 → **정적 분석 도구**

### 답 쓸 때
"실행하지 않고"가 보이면 정적, "실행하면서"가 보이면 동적이다. 오라클은 "일부 입력만 = 샘플링, 전부 = 참, 추정 섞음 = 휴리스틱, 변경 전후 비교 = 일관성" 으로 가른다.

## 인터페이스 보안: VPN과 터널링, SSL/TLS
출제: 24-3, 23-1, 22-2
형태: 설명 공통 빈칸 → 영문 약어

### 개념
인터페이스 구간은 보통 세 층으로 나눠 보호한다. 네트워크 구간은 **VPN·IPSec·SSL/TLS**, 데이터는 암호화, 애플리케이션은 시큐어 코딩이다.

**VPN(Virtual Private Network)** 은 인터넷 같은 공중망을 전용선처럼 쓰는 기술이다. 두 지점 사이에 **터널링** 으로 가상 통로를 만들고 그 안을 암호화해 통과시킨다. 어느 계층에서 터널을 만드느냐로 프로토콜이 갈린다.

| 터널링 프로토콜 | 계층 | 단서 |
|---|---|---|
| **PPTP(Point-to-Point Tunneling Protocol)** | 2계층 | PPP 기반, Microsoft 계열 |
| **L2F(Layer 2 Forwarding)** | 2계층 | Cisco 계열 |
| **L2TP(Layer 2 Tunneling Protocol)** | 2계층 | **L2F와 PPTP를 결합** |
| **IPSec** | 3계층 | AH·ESP → 아래 IPSec 세트 |
| **SSL VPN** | 전송 계층 위 | 웹 브라우저로 접속, 별도 클라이언트 불필요 |

**SSL/TLS** 는 전송 계층과 응용 계층 사이에서 동작하며 인증서로 서버를 인증하고 통신을 암호화한다. HTTP 위에 SSL/TLS를 얹은 것이 **HTTPS** 다. **S-HTTP** 는 HTTP 메시지 하나하나를 암호화하는 방식으로, 연결 전체를 보호하는 HTTPS와 구분된다.

### 기출에서 이렇게 나왔다
- 24-3: "SSL ( ), IPSec ( )" 공통 빈칸 → **VPN** (22-2 재출제)
- 23-1: L2F와 PPTP를 결합한 VPN 프로토콜 → **L2TP**
- 22-2: 설명의 공통 빈칸 → **VPN**

### 답 쓸 때
영어 약자로 요구하면 VPN, L2TP 그대로 쓴다. L2TP 지문에는 반드시 "L2F + PPTP" 가 들어 있다.

## 형상 관리
출제: 22-3, 20-3, 20-2

### 개념
**형상 관리(SCM, Software Configuration Management)** 는 개발 과정에서 생기는 산출물(소스·문서·데이터)의 **변경 사항을 체계적으로 관리** 하는 활동이다. **베이스라인(Baseline)** 은 공식적으로 검토·합의되어 이후 변경 통제의 기준이 되는 시점의 산출물이다.

| 활동 | 하는 일 | 단서 |
|---|---|---|
| **형상 식별** | 관리 대상(형상 항목)을 정하고 이름·번호를 붙임 | "식별자 부여", "베이스라인 기준 설정" |
| **형상 통제** | 변경 요구를 검토·승인하고 베이스라인에 반영 | "변경 요청 검토·승인", "형상통제위원회(CCB)" |
| **형상 감사** | 변경이 제대로 되었는지, 베이스라인의 무결성을 검증 | "검증", "무결성 평가" |
| **형상 기록(상태 보고)** | 형상 항목의 변경 이력과 상태를 기록·보고 | "이력", "보고서" |

도구는 저장소 구조로 나뉜다.

| 구조 | 도구 | 특징 |
|---|---|---|
| 중앙 집중형 | **CVS**, **SVN(Subversion)** | 서버에 하나의 저장소, 커밋이 서버로 바로 감 |
| 분산형 | **Git** | 개발자마다 전체 저장소 복제, 로컬 커밋 후 push |

## 인터페이스 통신 기술: AJAX·Fetch·WebSocket·GraphQL
출제: 25-2, 23-1, 20-2
형태: 설명 1~4줄 → 보기에서 영문으로

### 개념
**AJAX(Asynchronous JavaScript and XML)** 는 자바스크립트가 **XMLHttpRequest** 객체로 서버와 **비동기** 통신해, 페이지 전체를 다시 불러오지 않고 **일부만** 갱신하는 기술이다. 이름에 XML이 있지만 실제로는 JSON을 더 많이 주고받는다.

| 기술 | 핵심 | 단서 |
|---|---|---|
| **AJAX** | XMLHttpRequest, 비동기, 부분 갱신 | "페이지 리로드 없이", "JavaScript + XML" |
| **Fetch API** | AJAX를 대체하는 표준 함수, Promise 기반 | "fetch()", "Promise" |
| **WebSocket** | 한 번 연결하면 양방향으로 계속 주고받음 | "실시간", "양방향", "지속 연결" |
| **GraphQL** | 클라이언트가 필요한 필드만 질의, 단일 엔드포인트 | "쿼리 언어", "과다/과소 조회 해결" |

AJAX의 흐름은 "이벤트 발생 → XMLHttpRequest로 서버에 요청 → 그동안 사용자는 페이지를 계속 사용 → 응답이 오면 콜백 함수가 DOM의 일부만 갱신" 이다. 동기 방식은 응답이 올 때까지 화면이 멈추고 페이지 전체를 다시 받는다는 점이 대비된다.

통신 방향으로도 가른다. AJAX와 Fetch는 클라이언트가 요청해야 서버가 응답하는 **단방향 요청-응답** 이고, WebSocket은 연결을 유지한 채 서버가 먼저 보낼 수도 있는 **양방향** 이다. 채팅·실시간 알림처럼 "서버가 밀어 준다"는 지문이면 WebSocket이다. GraphQL은 통신 방식이 아니라 **질의 언어** 라서, REST API처럼 자원마다 URL이 있는 것이 아니라 하나의 엔드포인트에 원하는 필드를 적어 보낸다.

### 기출에서 이렇게 나왔다
- 25-2: 비동기, JS + XML, 페이지 일부만 리로드 → **AJAX** (23-1 재출제)
- 23-1: 한 줄 설명 → **AJAX**
- 20-2: XMLHttpRequest, 일부만 로드 → **AJAX**

### 답 쓸 때
영문 보기에서 고르는 형태다. 단서는 늘 "비동기"와 "일부만" 두 가지다.

## 테스트 케이스 구성 요소
출제: 25-3, 21-3
형태: 테스트 케이스 표의 열 제목 빈칸 3개 → 보기

### 개념
**테스트 케이스(Test Case)** 는 "이 입력을 이 조건에서 넣으면 이 결과가 나와야 한다"를 적은 한 벌이다. 표로 쓰면 열 제목이 구성 요소가 된다.

| 구성 요소 | 내용 |
|---|---|
| **식별자(ID)** | 케이스 고유 번호 |
| **테스트 항목(Test Item)** | 무엇을 테스트하는지 (기능·모듈) |
| **테스트 조건(입력 명세)** | 어떤 상태·조건에서 수행하는지 |
| **테스트 데이터** | 실제로 넣는 입력값 |
| **예상 결과(출력 명세)** | 나와야 하는 결과 |
| 환경 설정·특수 절차·의존성 | 필요할 때만 |

케이스·시나리오·스크립트는 단위가 다르다.

| 용어 | 단위 |
|---|---|
| 테스트 케이스 | 입력·조건·예상 결과 한 벌 |
| **테스트 시나리오** | 케이스 여러 개를 수행 순서대로 묶은 것 |
| **테스트 스크립트** | 시나리오를 자동 실행하도록 적은 절차·코드 |

로그인 기능으로 보면, "올바른 아이디·비밀번호를 넣으면 메인 화면으로 간다"가 케이스 하나이고, "회원 가입 → 로그인 → 비밀번호 변경 → 재로그인"을 순서대로 적은 것이 시나리오, 그 시나리오를 도구가 반복 실행하도록 코드로 옮긴 것이 스크립트다. 테스트 케이스는 설계 단계에서 명세를 보고 미리 작성하므로, 실행 뒤에 채우는 "실제 결과"는 구성 요소가 아니라 수행 기록이다.

### 기출에서 이렇게 나왔다
- 25-3: 표 헤더 빈칸 3개 → **테스트 조건 / 테스트 데이터 / 예상 결과** (21-3 재출제)
- 21-3: 같은 형태의 표 헤더 3칸

### 답 쓸 때
빈칸의 순서는 표의 열 순서를 따른다. 보기에 "테스트 결과"가 있으면 함정이다. 실행 전에 적는 것은 **예상** 결과다.

## EAI와 ESB
출제: 21-1, 20-3
형태: 구축 유형 4가지 중 빈칸 2개 → 보기 / 유형 이름 나열 설명 → 용어

### 개념
**EAI(Enterprise Application Integration)** 는 기업 안의 여러 애플리케이션을 연결해 데이터를 주고받게 하는 통합 방식이다. 연결 구조로 4가지 유형을 나눈다.

| 유형 | 구조 | 특징 |
|---|---|---|
| **Point-to-Point** | 애플리케이션끼리 1:1 직접 연결 | 중간 매개 없음, 단순하지만 연결 수가 급증 |
| **Hub & Spoke** | 중앙 **허브** 하나에 모두 연결 | 단일 접점으로 관리 쉬움, 허브 장애가 전체에 영향 |
| **Message Bus** | 공통 **버스(미들웨어)** 에 연결 | 확장성·대용량 처리에 유리 |
| **Hybrid** | 그룹 안은 Hub & Spoke, 그룹 사이는 Message Bus | 두 방식 혼합 |

**ESB(Enterprise Service Bus)** 는 Message Bus 방식을 **서비스 중심(SOA)** 으로 발전시킨 것이다. 애플리케이션이 아니라 서비스 단위로 느슨하게 결합하며, 메시지 변환·라우팅을 버스가 담당한다. EAI가 "애플리케이션 통합"이라면 ESB는 "서비스 통합"이다.

### 기출에서 이렇게 나왔다
- 21-1: Point to Point, Hub & Spoke, Message Bus 유형 설명 → **EAI**
- 20-3: 4가지 유형 중 빈 2개 → **포인트 투 포인트 / 허브 앤 스포크**

### 답 쓸 때
유형 이름은 영문 그대로 또는 한글 음차(포인트 투 포인트, 허브 앤 스포크, 메시지 버스, 하이브리드) 둘 다 통용된다. 보기 표기를 따른다.

## IPSec
출제: 24-2, 20-2
형태: 설명 2줄(VPN, 3계층, AH·ESP) → 용어

### 개념
**IPSec(IP Security)** 은 **네트워크 계층(3계층)** 에서 IP 패킷 단위로 인증·암호화를 제공하는 프로토콜 묶음이다. VPN 구현에 쓰인다. 두 개의 보안 프로토콜과 두 개의 동작 모드로 구성된다.

| 프로토콜 | 제공하는 것 | 단서 |
|---|---|---|
| **AH(Authentication Header)** | 인증·무결성 (암호화 없음) | "출처 인증", "변조 탐지", "기밀성은 없음" |
| **ESP(Encapsulating Security Payload)** | 기밀성(암호화) + 인증·무결성 | "암호화", "페이로드 캡슐화" |

| 모드 | 보호 범위 | 쓰임 |
|---|---|---|
| **전송 모드(Transport)** | IP 헤더는 두고 **페이로드만** 보호 | 호스트 ↔ 호스트 |
| **터널 모드(Tunnel)** | 원래 IP 패킷 **전체** 를 보호하고 새 IP 헤더를 붙임 | 게이트웨이 ↔ 게이트웨이, VPN |

키 교환은 **IKE(Internet Key Exchange)** 가 맡고, 통신 양쪽이 어떤 알고리즘·키로 보호할지 합의한 묶음을 **SA(Security Association)** 라고 한다.

모드 차이는 "새 IP 헤더를 붙이느냐"로 기억한다. 전송 모드는 원래 IP 헤더를 그대로 쓰므로 양 끝 호스트 주소가 밖에서 보인다. 터널 모드는 원래 패킷 전체를 안에 넣고 게이트웨이 주소가 적힌 새 헤더를 붙이므로, 내부 주소가 숨겨진다. 지사와 본사의 게이트웨이를 잇는 VPN이 터널 모드를 쓰는 이유다.

### 한눈에 구분
| 단서 | 답 |
|---|---|
| "인증만", "암호화 없음" | AH |
| "암호화", "기밀성" | ESP |
| "페이로드만", "호스트 간" | 전송 모드 |
| "패킷 전체", "새 IP 헤더", "게이트웨이 간" | 터널 모드 |

### 기출에서 이렇게 나왔다
- 24-2: VPN, 3계층, AH·ESP → **IPSec**
- 20-2: AH·ESP, 네트워크 계층 → **IPSec**

### 답 쓸 때
지문에 AH·ESP가 보이면 바로 IPSec이다. 표기는 IPSec 또는 IPsec. SSL/TLS(전송 계층 위)와 계층으로 구분한다.

## 웹 서비스 인터페이스: SOAP·WSDL·UDDI·REST
출제: 21-1, 20-2
형태: 한 줄 설명 → 용어

### 개념
웹 서비스는 서비스 제공자가 서비스를 **등록(publish)** 하고, 요청자가 **검색(find)** 해 **연결(bind)** 하는 구조다. 세 요소가 각 단계를 맡는다.

| 요소 | 역할 | 단서 |
|---|---|---|
| **SOAP(Simple Object Access Protocol)** | HTTP 등 위에서 **XML 기반 메시지** 를 주고받는 프로토콜. Envelope·Header·Body 구조 | "XML 메시지 교환", "HTTP·SMTP 위에서", "RESTful로 대체 가능" |
| **WSDL(Web Services Description Language)** | 웹 서비스의 **상세 정보(위치·메서드·인터페이스)** 를 기술하는 XML 언어 | "서비스를 기술", "XML 형식 명세" |
| **UDDI(Universal Description, Discovery and Integration)** | 서비스를 **등록·검색** 하는 레지스트리 | "등록", "검색", "저장소" |

**REST(Representational State Transfer)** 는 HTTP 메서드(GET·POST·PUT·DELETE)로 **URI가 가리키는 자원** 을 조작하는 방식이다. 별도 프로토콜 없이 HTTP 자체를 쓰고, 상태를 서버에 두지 않으며(무상태), 주로 JSON으로 표현한다. REST 원칙을 지킨 API를 RESTful API라고 한다.

| 비교 | SOAP | REST |
|---|---|---|
| 형식 | XML 고정 | JSON 등 자유 |
| 무게 | 무겁고 표준이 많음 | 가볍고 단순 |
| 명세 | WSDL | 정해진 표준 없음 |

### 기출에서 이렇게 나왔다
- 21-1: 웹 서비스 상세 정보를 기술하는 XML 언어 → **WSDL**
- 20-2: HTTP 등으로 XML 기반 메시지 교환, RESTful로 대체 가능 → **SOAP**

### 답 쓸 때
"기술(describe)" 은 WSDL, "메시지 교환" 은 SOAP, "등록·검색" 은 UDDI다. 셋 다 XML 기반이라는 말만으로는 구분되지 않으니 동사를 본다.

## 테스트 7원칙과 성능 지표
출제: 20-1
형태: 설명 → 원칙 이름 / 표 빈칸 3개 → 지표 이름

### 개념
테스트의 7원칙은 다음과 같다.

| 원칙 | 뜻 |
|---|---|
| 결함 존재를 보여 줄 뿐 결함이 없음을 증명하지 못한다 | 테스트 통과가 무결함은 아니다 |
| 완벽한 테스트는 불가능하다 | 모든 입력 조합을 다 할 수 없다 |
| 초기에 테스트한다(Early Testing) | 일찍 찾을수록 수정 비용이 적다 |
| 결함 집중(Defect Clustering) | 소수 모듈에 결함이 몰린다(파레토 법칙) |
| **살충제 패러독스(Pesticide Paradox)** | 같은 테스트를 반복하면 새 결함을 찾지 못한다. 케이스를 계속 바꿔야 한다 |
| 테스트는 정황(Context)에 의존한다 | 시스템 성격에 따라 테스트 방법이 다르다 |
| 오류-부재의 궤변(Absence of Errors Fallacy) | 결함이 없어도 요구를 못 채우면 쓸모없다 |

성능 테스트 지표는 네 가지다.

| 지표 | 뜻 |
|---|---|
| **처리량(Throughput)** | 단위 시간당 처리하는 트랜잭션 수 |
| **응답 시간(Response Time)** | 요청을 보낸 뒤 **첫 응답이 오기까지** 의 시간 |
| **경과 시간(Turnaround Time)** | 요청을 보낸 뒤 **결과 출력이 끝날 때까지** 의 시간 |
| **자원 사용률(Resource Usage)** | CPU·메모리·네트워크 사용량 |

### 기출에서 이렇게 나왔다
- 20-1: 같은 테스트를 반복하면 새 결함 발견 확률이 줄어든다 → **살충제 패러독스**
- 20-1: 지표 표 빈칸 3개 → **처리량 / 응답시간 / 경과시간**

### 답 쓸 때
응답 시간과 경과 시간의 차이는 "첫 응답까지"와 "완료까지"다.

## 데이터 표현 형식: JSON·XML·YAML
출제: 20-1
형태: 설명 → 보기에서 고르기

### 개념
인터페이스로 주고받는 데이터를 적는 형식이다. 셋 다 사람이 읽을 수 있는 텍스트이고 계층 구조를 표현한다.

| 형식 | 구조 | 단서 |
|---|---|---|
| **JSON(JavaScript Object Notation)** | `"name": value` 쌍과 배열, 중괄호·대괄호 | "속성-값 쌍", "경량", "자바스크립트 객체 표기에서 유래", AJAX에서 XML 대신 |
| **XML(eXtensible Markup Language)** | 사용자가 정의하는 태그 `<tag>...</tag>` | "W3C", "SGML의 복잡함을 해결", "다목적 마크업 언어", "HTML의 한계 보완" |
| **YAML(YAML Ain't Markup Language)** | 들여쓰기와 `key: value`, 목록은 `-` | "들여쓰기", "사람이 읽기 쉬움", "설정 파일", JSON의 상위 호환 |

같은 데이터를 세 형식으로 적으면 다음과 같다. (python3 `json`·`xml.etree`·`yaml`로 파싱해 세 개 모두 `name=홍길동, age=20, skills=[C, Java]` 로 읽히는 것을 확인했다.)

```json
{"name": "홍길동", "age": 20, "skills": ["C", "Java"]}
```

```xml
<student>
  <name>홍길동</name>
  <age>20</age>
  <skills>
    <skill>C</skill>
    <skill>Java</skill>
  </skills>
</student>
```

```yaml
name: 홍길동
age: 20
skills:
  - C
  - Java
```

XML은 여는 태그와 닫는 태그가 쌍이라 길고, JSON은 괄호와 따옴표로 짧게 끝나며, YAML은 괄호 없이 들여쓰기만으로 구조를 나타낸다. JSON에는 주석이 없고 YAML에는 `#` 주석이 있다.

### 기출에서 이렇게 나왔다
- 20-1: name:value 쌍, 경량 → **JSON**
- 20-1: W3C, SGML의 복잡함 해결, 다목적 마크업 → **XML**

### 답 쓸 때
"마크업"이면 XML, "속성-값 쌍"이면 JSON, "들여쓰기"면 YAML이다.

## URL 구조
출제: 24-3
형태: 예시 URL을 5구간으로 나눠 각 구간 이름을 보기에서 고르기

### 개념
URL은 자원의 위치를 적는 문자열이고, 구간마다 이름이 있다.

```text
scheme://authority/path?query#fragment
https://www.example.com:443/docs/guide?page=2&lang=ko#section-3
```

| 구간 | 예시 부분 | 뜻 |
|---|---|---|
| **scheme** | `https` | 프로토콜 |
| **authority** | `www.example.com:443` | 호스트(+포트, 필요하면 사용자 정보) |
| **path** | `/docs/guide` | 서버 안의 자원 경로 |
| **query** | `page=2&lang=ko` | `?` 뒤의 매개변수, `&`로 구분 |
| **fragment** | `section-3` | `#` 뒤, 문서 안의 위치 |

authority 안은 다시 `사용자정보@호스트:포트` 로 나뉜다. 포트를 생략하면 scheme의 기본 포트(http는 80, https는 443)가 쓰인다. query는 `이름=값` 쌍을 `&` 로 이어 붙이고, fragment는 서버로 전송되지 않고 브라우저가 문서 안에서 위치를 찾는 데만 쓴다. 공백이나 한글처럼 URL에 직접 쓸 수 없는 문자는 `%` 뒤에 16진수를 붙이는 **퍼센트 인코딩** 으로 적는다.

**URI(Uniform Resource Identifier)** 는 자원을 식별하는 문자열 전체를 가리키고, 그중 위치로 식별하면 **URL(Locator)**, 이름으로 식별하면 **URN(Name)** 이다. URL은 URI의 한 종류다.

| 구분 | 식별 방법 | 예 |
|---|---|---|
| URL | 어디에 있는가 | `https://www.example.com/docs/guide` |
| URN | 무엇인가(이름) | `urn:isbn:...` 처럼 위치와 무관한 이름 |

### 기출에서 이렇게 나왔다
- 24-3: 예시 URL의 5구간 → **scheme / authority / path / query / fragment**

### 답 쓸 때
구분 기호로 찾는다. `://` 앞은 scheme, 첫 `/` 전까지가 authority, `?` 뒤가 query, `#` 뒤가 fragment다.
