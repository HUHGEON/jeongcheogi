# SW 개발

SW 개발 영역은 테스트, 형상 관리, 인터페이스를 다룬다. 이 중에서 가장 크게 봐야 할 주제는 두 개다. 21개 회차 중 테스트 커버리지가 9회차, 블랙박스 테스트가 8회차에 나왔는데, 이 둘이 이 영역 문제의 3분의 1 남짓을 차지한다. 문제 형태는 "설명 2~3줄을 주고 이름을 고르기"가 기본이고, 커버리지만 제어흐름도에서 경로 번호를 채우는 형태가 더해진다. 2023년 이후에도 커버리지·블랙박스·스텁/드라이버·AJAX·URL 구조는 계속 나오고 있는데, 가만히 보면 그중 상당수가 2~3년 전 문제를 다시 낸 것이다.

## 테스트 커버리지 (화이트박스)
출제: 25-3, 25-2, 25-1, 24-3, 24-1, 23-2, 23-1, 21-2, 20-3
형태: 설명 1~3줄 → 커버리지 이름 / 설명 3개 → 문장·분기·조건 구분 / 제어흐름도 → 커버리지를 만족하는 경로 번호 채우기

### 개념
화이트박스 테스트란 코드 내부 구조를 들여다보면서 테스트 케이스를 만드는 방식을 말한다. 그럼 테스트를 얼마나 했는지는 무엇으로 잴까? 이때 쓰는 기준이 커버리지다. 쉽게 말해 "테스트가 코드의 어디까지를 한 번 이상 지나갔나"를 재는 것이고, 커버리지 종류는 **무엇을** 참·거짓으로 만들어야 하는지에 따라 나뉜다. 표로 정리하면 이렇다.

| 커버리지 | 한 번 이상 만족시켜야 하는 것 | 영문 |
|---|---|---|
| **구문(문장) 커버리지** | 모든 문장이 한 번 이상 실행 | Statement Coverage |
| **결정(분기) 커버리지** | 모든 결정(if·while 전체 조건식)의 결과가 참·거짓 각각 한 번 이상 | Decision / Branch Coverage |
| **조건 커버리지** | 결정 안의 개별 조건 각각이 참·거짓 한 번 이상 (전체 결과는 묻지 않음) | Condition Coverage |
| **조건/결정 커버리지** | 개별 조건과 전체 결정이 모두 참·거짓 한 번 이상 | Condition/Decision Coverage |
| **변경 조건/결정 커버리지(MC/DC)** | 각 개별 조건이 다른 조건과 무관하게 혼자서 전체 결정 결과를 바꾸는 경우를 포함 | Modified Condition/Decision Coverage |
| **다중 조건 커버리지** | 개별 조건의 모든 참·거짓 조합 | Multiple Condition Coverage |

글로만 보면 비슷비슷해 보이는데, `if (A and B)` 하나를 놓고 테스트 세트를 바꿔 보면 차이가 선명하게 드러난다.

| 테스트 세트 (A, B) | 결정 결과 | 만족하는 커버리지 |
|---|---|---|
| (T,T) (F,F) | T, F | 결정, 조건, 조건/결정 |
| (T,F) (F,T) | F, F | 조건만. 결정은 항상 거짓이라 미달 |
| (T,T) (T,F) (F,T) | T, F, F | 결정, 조건, 조건/결정, **MC/DC**. A만 바꿔 결과가 변하는 쌍 (T,T)-(F,T)과 B만 바꿔 변하는 쌍 (T,T)-(T,F)이 모두 있음 |
| 네 조합 전부 | | 다중 조건 |

포함 관계는 **다중 조건 ⊃ MC/DC ⊃ 조건/결정 ⊃ 결정 ⊃ 구문** 이다. 강한 쪽을 만족하면 약한 쪽은 자동으로 만족한다는 뜻이다. 여기서 많이들 헷갈리는 게 조건 커버리지의 자리다. 위 표 둘째 줄을 보면 A와 B는 각각 참·거짓이 다 나왔는데 결정은 항상 거짓이었다. 그래서 조건 커버리지는 결정 커버리지를 보장하지 않는다. 그런데 수험서는 "강도" 순서를 **구문 < 결정 < 조건 < 조건/결정 < MC/DC < 다중 조건** 으로 한 줄에 적기도 한다. 이것은 필요한 테스트 케이스가 대체로 늘어나는 순서일 뿐이고, 조건과 결정 사이는 포함 관계가 아니다.

**순환 복잡도(McCabe Cyclomatic Complexity)** 란 제어흐름도에서 독립 경로가 몇 개인지 센 값이다. 공식은 `V(G) = E - N + 2` 인데, 여기서 E는 간선 수, N은 노드 수다. `결정 노드 수 + 1` 로 구해도 된다. 예를 들어 아래 25-2 흐름도는 간선 8개, 노드 7개라 8 - 7 + 2 = 3이고, 결정 노드 2개에 1을 더해도 똑같이 3이 나온다. 기초 경로 테스트는 이 수만큼 독립 경로를 만든다.

### 제어흐름도에서 경로 읽기
기출은 번호가 붙은 흐름도를 주고 "TC1: 1-2-3-...", "TC2: ..." 처럼 경로를 채우게 한다. 처음 보면 막막한데, 아래 순서대로 따라가면 된다.

1. 먼저 마름모(결정 노드)를 찾는다. 결정 노드마다 참 화살표와 거짓 화살표가 하나씩 있다.
2. **분기 커버리지**는 모든 결정 노드의 참·거짓 화살표를 각각 한 번 이상 지나면 되고, 보통 두 경로면 된다. 요령은 결정마다 첫 경로에서 고르지 않은 쪽 화살표를 둘째 경로에서 고르는 것이다. 다만 어느 결정을 "예"로 지나느냐는 그림의 화살표 방향이 정하기 때문에, 경로를 다 적은 뒤에는 결정마다 예·아니오가 한 번씩 나왔는지 확인한다.
3. **문장 커버리지**는 모든 처리 노드를 한 번 이상 지나면 된다. 이때 반복문 본문도 지나야 하니, 한 번은 참으로 들어가야 한다.
4. 반복문은 "조건 → 본문 → 다시 조건" 으로 되돌아오기 때문에 경로에 같은 번호가 두 번 적힌다.

```mermaid
제목: 25-2 기출 흐름도(23-1과 같은 유형, 그림은 다르다). TC1 ①②③④⑤⑥⑦은 ② 예·⑥ 아니오, TC2 ①②④⑤⑥①은 ② 아니오·⑥ 예로 지나 두 결정의 참·거짓을 한 번씩 덮는다 (분기 커버리지)
flowchart TB
  n1("① POINTER = FALSE") --> n2{{"② X > K ?"}}
  n2 -->|"예"| n3("③ POINTER = TRUE")
  n2 -->|"아니오"| n4("④ X = X + 2")
  n3 --> n4
  n4 --> n5("⑤ CALL SUB(X, POINTER, RESULT)")
  n5 --> n6{{"⑥ RESULT > 1 ?"}}
  n6 -->|"아니오"| n7("⑦ PRINT RESULT")
  n6 -->|"예"| n1
```

### 기출에서 이렇게 나왔다
- 25-3: 설명 2줄 → 한글 보기에서 **조건 커버리지** (23-2 재출제)
- 25-2: 제어흐름도 → 분기 커버리지를 만족하는 TC1·TC2 경로 번호 채우기 (23-1과 같은 유형. 위 그림이 25-2 그림이다). 그림에 적힌 짝 말고 TC1 ①②③④⑤⑥①(② 예·⑥ 예), TC2 ①②④⑤⑥⑦(② 아니오·⑥ 아니오)로 짝을 바꿔도 정답이다. 이렇게 짝을 지어도 두 결정의 참·거짓이 한 번씩 나오기 때문이다.
- 25-1: 코드와 제어흐름도 → 노드에 들어갈 문장과 문장 커버리지 실행 순서. 노드는 코드 순서대로 1 `int a = 0;`, 2 `a < m || b[a] < x`(while 조건, 결정), 3 `b[a] < 0`(if 조건, 결정), 4 `b[a] = -b[a];`, 5 `a++;`, 6 `return 1;`이다. 여기서 4는 if가 참일 때만 지나는 노드라서, 한 번은 3에서 참으로 들어가야 한다. 그리고 5 뒤에는 while 조건 2로 되돌아간 뒤 거짓이 되어 6으로 빠져나온다. 그래서 최소 순서는 1 → 2 → **3 → 4 → 5 → 2 → 6**이다.
- 24-3: 설명 3개 → **Statement / Branch / Condition** 영문으로
- 24-1: "중요 조합", "다른 조건과 무관하게 전체 결과에 영향" → **MC/DC**
- 23-2: 한 줄 설명 → **Condition Coverage**
- 23-1: 제어흐름도 → 분기 커버리지 경로 채우기. 그림은 ① FLAG=TRUE → ② Y<M? (예 → ③ Y=Y-1 → ⑤, 아니오 → ④ FLAG=FALSE → ⑤) → ⑤ CALL FUNC → ⑥ COUNT>=0? (아니오 → ⑦ 출력, 예 → ①)이다. 답은 TC1 ①②③**⑤⑥**⑦, TC2 ①**②④⑤⑥①**이다. 25-2와 달리 23-1은 if-else 구조라 ③ 뒤에 ④를 거치지 않는다. 그래서 빈칸 개수와 화살표는 그림에서 직접 확인해야 한다.
- 21-2: 설명 3개 → **문장 / 결정(분기) / 조건**
- 20-3: 설명 → **분기(결정) 커버리지**

### 답 쓸 때
답은 보기 언어를 따라간다. 보기가 영문이면 Statement·Branch·Condition 으로, 한글이면 문장(구문)·분기(결정)·조건으로 쓰면 된다. 결정과 분기는 이름만 다를 뿐 같은 것이라서, 문제에 따라 둘 중 하나로 표기된다. MC/DC는 약어 그대로 쓴다.

## 블랙박스 테스트 기법
출제: 26-2, 23-3, 22-3, 22-1, 21-3, 21-1, 20-4, 20-3
형태: 설명 또는 예시 데이터 → 기법 이름 / 보기 여러 개 중 블랙박스 기법 3개 고르기

### 개념
NCS는 테스트 기법을 세 이름으로 나눠 부른다. 블랙박스 기법은 **명세 기반 테스트**로, 여기에는 동등 분할·경계값 분석·결정 테이블·상태 전이(유한상태 기계)·유스케이스·페어와이즈·직교 배열이 들어간다. 화이트박스 커버리지는 **구조 기반 테스트**, 오류 예측처럼 테스터의 직관에 기대는 것은 **경험 기반 테스트** 다. 그래서 지문에 '명세 기반'이 보이면 블랙박스 기법 이름을 답하면 된다.

블랙박스 테스트란 코드를 들여다보지 않고 **입력과 출력(명세)** 만 보고 테스트 케이스를 만드는 방식이다. 그런데 기출은 기법의 정의를 묻기보다 "어떤 데이터를 골랐나"를 보여 주고 기법 이름을 맞히게 한다. 그러니 문제가 주는 단서를 보고 기법을 알아보는 연습을 해 두는 게 핵심이다.

### 한눈에 구분
| 기법 | 문제가 주는 단서 | 무엇을 하는가 |
|---|---|---|
| **동등 분할(Equivalence Partitioning)** | 점수 구간 표, 구간별 대표값 하나씩, "유효/무효 그룹" | 입력을 같은 결과가 나오는 그룹으로 나누고 그룹마다 대표값 하나를 테스트 |
| **경계값 분석(Boundary Value Analysis)** | 경계 바로 앞뒤 값이 나열됨 (예: 0~59 구간이면 -1, 0, 59, 60) | 오류가 경계에 몰린다는 전제로 경계와 그 양옆 값을 테스트 |
| **원인-결과 그래프(Cause-Effect Graph)** | "입력 조건과 출력 결과의 관계를 그래프로", 결정 테이블로 변환 | 입력(원인)과 출력(결과)의 논리 관계를 그래프로 그려 효용 높은 케이스를 고름 |
| **결정 테이블(Decision Table)** | 조건 조합과 행동을 표로 | 조건의 참·거짓 조합마다 기대 행동을 표로 정리 |
| **상태 전이(State Transition)** | 상태, 이벤트, 전이 | 상태 변화를 일으키는 이벤트 조합을 테스트 |
| **오류 예측(Error Guessing)** | 경험, 직관, 과거 오류 | 테스터의 경험으로 오류가 날 만한 입력을 추측 |
| **비교(Comparison)** | 같은 입력을 여러 버전에 | 여러 버전의 프로그램에 같은 데이터를 넣고 출력을 비교 |
| **페어와이즈(Pairwise)** | 모든 두 인자 조합 | 인자 쌍의 모든 조합이 한 번 이상 나오도록 조합 수를 줄임 |
| **분류 트리(Classification Tree)** | 입력 영역을 트리로 | 입력 조건을 트리 구조로 분류한 뒤 조합 |
| **유스케이스(Use Case)** | 시나리오, 사용자 흐름 | 유스케이스의 흐름을 따라 케이스 작성 |

아마 이 표에서 가장 헷갈리는 게 동등 분할과 경계값 분석일 것이다. 둘 다 같은 구간 표에서 나오기 때문이다. 가르는 기준은 고른 값이다. 구간마다 값이 **하나**이고 그 값이 구간 안쪽에 있으면 동등 분할, 구간 **양 끝과 그 바깥** 값을 골랐으면 경계값 분석이다.

### 기출에서 이렇게 나왔다
- 26-2: 점수 구간 표 + 구간별 대표값으로 테스트 → **동등 분할**
- 23-3: 유효/무효 그룹으로 나누고 대푯값 → **Equivalence Partitioning**
- 22-3: 예시 데이터 -1, 0, 59, 60 ... 경계값 포함 → **Boundary Value Analysis**
- 22-1: 보기 8개 중 블랙박스 기법 3개 → **BVA / Equivalence Partitioning / Cause-Effect Graph**
- 21-3: 입력·출력 조건을 그래프로 → **원인-결과 그래프**
- 21-1: 예시 2개 → **경곗값 분석 / 동등 분할**
- 20-4: 유효/무효, 대표값 → **동등 분할**
- 20-3: 동치 분할·경계값 분석을 포함하는 테스트 기법 → **블랙박스 테스트**

### 답 쓸 때
여러 보기 중 3개를 고르는 문제에는 기초 경로, 조건·루프 검사, 데이터 흐름 같은 화이트박스 기법이 섞여 나올 수 있다. 이때는 블랙박스 기법이 "입력 데이터를 고르는 방법"에 붙은 이름이라는 점으로 가르면 된다. 참고로 동등 분할은 동치 분할·동등 클래스 분해로도 불린다.

## 통합 테스트: 스텁·드라이버, 하향식·상향식, 회귀
출제: 26-1, 23-2, 22-2, 21-3, 21-2
형태: 하향식/상향식 설명 2줄 → 더미 모듈 이름 빈칸 / 설명 → 영문 용어

### 개념
통합 테스트란 단위 테스트가 끝난 모듈을 결합해 가면서 **모듈 사이의 인터페이스** 오류를 찾는 테스트다. 그런데 합치려는 모듈 중에 아직 만들어지지 않은 것이 있으면 그 자리에 임시 모듈을 넣어야 한다. 이 임시 모듈의 이름은 어느 방향으로 통합하느냐에 따라 달라진다.

| 방식 | 통합 순서 | 필요한 더미 모듈 | 특징 |
|---|---|---|---|
| **하향식(Top-down)** | 상위(제어) 모듈부터 아래로 | **스텁(Stub)**: 아직 없는 하위 모듈을 흉내 내는 간단한 모듈 | 깊이 우선·너비 우선 선택, 설계 결함을 일찍 발견 |
| **상향식(Bottom-up)** | 최하위 모듈부터 위로 | **드라이버(Driver)**: 하위 모듈을 호출해 주는 임시 상위 모듈 | 하위 모듈을 클러스터로 묶어 테스트 |
| **빅뱅(Big Bang)** | 전부 한 번에 결합 | 없음(실제 모듈로 테스트) | 단시간에 가능하고 작은 시스템에 유리, 모든 모듈이 완성되어야 하고 오류 위치 찾기 어려움 |
| **샌드위치(혼합)** | 상위는 하향식, 하위는 상향식 | 스텁 + 드라이버 | 두 방식의 장점 결합 |

여기서 **회귀 테스트(Regression Test)** 를 통합 방식 중 하나로 착각하기 쉬운데, 통합 방식이 아니다. 모듈을 고치거나 새로 통합한 뒤 **이미 되던 기능이 깨지지 않았는지** 다시 돌려 보는 테스트를 말한다. 변경할 때마다 반복해야 하기 때문에 자동화 대상이 된다.

```mermaid
제목: 하향식은 아래가 비어 있어 스텁을, 상향식은 위가 비어 있어 드라이버를 만든다 (점선이 임시 모듈)
%% 폰: LR
flowchart TB
  subgraph BU["상향식 통합"]
    direction TB
    D1("드라이버") --> L1("하위 모듈 (완성)")
    D1 --> L2("하위 모듈 (완성)")
  end
  subgraph TD["하향식 통합"]
    direction TB
    M1("상위 모듈 (완성)") --> S1("스텁")
    M1 --> S2("스텁")

  classDef fake fill:#fff4e5,stroke:#ffb45c,stroke-dasharray:5 4,color:#7a4a00

```

## 테스트 레벨과 V 모델, 알파·베타 테스트
출제: 22-2, 22-1, 21-1
형태: V 모델 그림의 빈칸 4개 → 레벨 이름 / 설명 2개 → 레벨 또는 알파·베타 구분

### 개념
테스트 레벨은 개발 단계와 짝을 이룬다. 이 짝을 그림으로 그린 것이 V 모델인데, 왼쪽에 개발 단계를, 오른쪽에 거기 대응하는 테스트 레벨을 놓는다.

| 개발 단계 | 대응 테스트 레벨 | 무엇을 확인하나 |
|---|---|---|
| 요구사항 분석 | **인수 테스트(Acceptance)** | 사용자 요구를 만족하는지, 사용자가 수행 |
| 기능 명세 분석 | **시스템 테스트(System)** | 전체 시스템의 기능·비기능(성능·보안 등) |
| 설계 | **통합 테스트(Integration)** | 모듈 간 인터페이스 |
| 개발(구현) | **단위 테스트(Unit)** | 모듈·함수 하나, 주로 화이트박스 |

위 표의 짝은 NCS 학습모듈(애플리케이션 테스트 관리)의 V 모델 그림을 따랐다. 순서는 **단위 → 통합 → 시스템 → 인수** 이고, 그림에서는 아래쪽 개발 옆이 단위, 위쪽 요구사항 옆이 인수다. 자료에 따라 짝이 조금 다를 수도 있다. 국제 표준(ISTQB)처럼 설계를 아키텍처 설계와 상세 설계로 나누는 자료는 상세 설계를 단위 테스트와 짝짓기도 한다. 하지만 기출이 묻는 것은 테스트 레벨 이름과 순서다.

맨 위의 인수 테스트는 다시 누가 어디서 하느냐에 따라 둘로 나뉜다.

| 구분 | 장소 | 개발자 | 단서 |
|---|---|---|---|
| **알파 테스트(Alpha)** | 개발자 환경(통제된 환경) | 입회함 | "개발자가 지켜보는 가운데", "통제된 환경" |
| **베타 테스트(Beta)** | 사용자 실제 환경 | 없음 | "다수의 사용자", "실제 업무 환경", "문제점을 보고" |

```vmodel
제목: 왼쪽 개발 단계를 같은 높이의 오른쪽 테스트가 검증한다. 테스트는 아래에서 위로 진행
요구사항 분석 | 인수 테스트
기능 명세 분석 | 시스템 테스트
설계 | 통합 테스트
개발(구현) | 단위 테스트
```

### 기출에서 이렇게 나왔다
- 22-2: 설명 2개 → **베타 / 알파** 순서로 답
- 22-1: V 모델 그림 4칸 → **단위 / 통합 / 시스템 / 인수**
- 21-1: 설명 2개 → **단위 / 통합**

### 답 쓸 때
V 모델 빈칸은 그림에서 칸의 위치만 보면 답이 정해진다. 설명을 주는 문제라면 "개발자 환경 = 알파, 사용자 환경 = 베타" 한 줄만 기억해 두면 충분하다.

## 테스트 자동화 도구와 하네스, 테스트 오라클
출제: 22-1, 20-4, 20-2
형태: 설명 1~2개 → 용어 또는 영문

### 개념
**테스트 하네스(Test Harness, NCS 표기 '테스트 장치')** 란 컴포넌트·모듈을 테스트하는 환경의 일부를 말한다. 쉽게 말해 테스트를 지원하려고 개발자가 따로 작성하는 코드와 데이터의 묶음이다. 어떤 것들이 들어가는지 표로 보면 이렇다.

| 구성 요소 | 뜻 |
|---|---|
| **테스트 드라이버(Driver)** | 하위 모듈을 호출하는 임시 상위 모듈 (상향식) |
| **테스트 스텁(Stub)** | 하위 모듈을 대신하는 임시 모듈 (하향식) |
| **테스트 케이스(Test Case)** | 입력·조건·예상 결과 한 벌 |
| **테스트 슈트(Test Suite)** | 테스트 케이스의 집합 |
| **테스트 스크립트(Test Script)** | 테스트를 자동으로 실행하는 절차 |
| **목 오브젝트(Mock Object)** | 미리 정해 둔 행위를 하는 가짜 객체 |

테스트 자동화 도구는 코드를 실행하느냐 안 하느냐로 나뉜다.

| 도구 | 실행 여부 | 찾는 것 |
|---|---|---|
| **정적 분석 도구(Static Analysis)** | 실행하지 않음 | 코딩 표준 위반, 복잡도, 결함 패턴 |
| **동적 분석 도구(Dynamic Analysis)** | 실행하면서 | 메모리 누수, 스레드 결함, 실제 커버리지 |

NCS는 자동화 도구를 다섯 가지로 나눈다. **정적 분석 도구**, 스크립트를 돌리는 **테스트 실행 도구**, 가상 사용자로 처리량·응답 시간을 재는 **성능 테스트 도구**, 테스트 관리·형상 관리·결함 추적을 맡는 **테스트 통제 도구**, 그리고 **테스트 장치(하네스)** 다. 이 중 테스트 실행 도구는 다시 테스트 데이터를 스프레드시트에 두는 **데이터 주도** 와, 동작 키워드와 데이터를 함께 두는 **키워드 주도** 로 갈린다. 대표 도구도 같이 알아 두자. 정적 분석은 pmd·cppcheck·SonarQube·checkstyle, 동적 분석은 Valgrind·Avalanche, 성능은 JMeter·LoadUI·OpenSTA, 모니터링은 Scouter·Zabbix·Nagios다.

**xUnit** 은 도구 하나의 이름이 아니라 언어별 단위 테스트 프레임워크를 통틀어 부르는 말이다. Java의 **JUnit**, C++의 CppUnit, .NET의 NUnit, Python의 PyUnit(unittest) 등이 여기에 속한다. 이 중 JUnit은 `@Test` 어노테이션, 그리고 Kent Beck·Erich Gamma라는 이름과 묶어서 기억해 둔다.

인터페이스 구현을 검증하는 자동화 도구는 하나씩 외우기보다 단위·프레임워크·웹 UI 세 계열로 묶어서 외우는 편이 낫다.

| 도구 | 계열 | 단서 |
|---|---|---|
| **xUnit** | 단위 | JUnit·CppUnit·NUnit 등 언어별 단위 테스트 |
| **STAF** | 프레임워크 | 서비스 호출·컴포넌트 재사용, 각 테스트 대상에 데몬을 두고 분산 환경 테스트 |
| **FitNesse** | 프레임워크 | 위키 기반, 표로 입력값·기대값을 적어 웹에서 실행·결과 확인 |
| **NTAF** | 프레임워크 | NHN이 만든 것, STAF와 FitNesse를 통합 |
| **Selenium** | 웹 UI | 여러 브라우저·언어를 지원하는 웹 애플리케이션 테스트 |
| **watir** | 웹 UI | Ruby로 쓰는 웹 애플리케이션 테스트 |

**테스트 오라클(Test Oracle)** 이란 테스트 결과가 맞는지 판단하는 기준, 즉 기댓값을 말한다. 이 기댓값을 어디까지 주느냐에 따라 아래처럼 나뉜다.

| 오라클 | 기댓값 범위 |
|---|---|
| **참(True) 오라클** | 모든 입력에 대해 기댓값을 제공, 전수 검사 |
| **샘플링(Sampling) 오라클** | 특정 몇 개 입력에 대해서만 기댓값 제공 |
| **휴리스틱(Heuristic) 오라클** | 샘플링 + 나머지는 추정(휴리스틱)으로 처리 |
| **일관성 검사(Consistent) 오라클** | 변경 전후 수행 결과가 같은지 확인 |

### 기출에서 이렇게 나왔다
- 22-1: 실행하지 않고 / 실행하면서 분석하는 도구 → **static / dynamic**
- 22-1: 자바용 xUnit, `@Test` → **JUnit**
- 20-4: 일부 특정 입력값에 대해서만 기댓값 제공 → **샘플링 오라클**
- 20-2: 실행하지 않고 코딩 표준·복잡도·결함 → **정적 분석 도구**

### 답 쓸 때
도구 문제는 지문에 "실행하지 않고"가 보이면 정적, "실행하면서"가 보이면 동적이다. 오라클은 일부 입력만이면 샘플링, 전부면 참, 추정이 섞이면 휴리스틱, 변경 전후 비교면 일관성으로 가른다.

## 인터페이스 보안: VPN과 터널링, SSL/TLS
출제: 24-3, 23-1, 22-2
형태: 설명 공통 빈칸 → 영문 약어

### 개념
인터페이스 구간은 보통 세 층으로 나눠서 보호한다. 네트워크 구간은 **VPN·IPSec·SSL/TLS** 로, 데이터는 암호화로, 애플리케이션은 시큐어 코딩으로 보호하는 식이다.

**VPN(Virtual Private Network)** 이란 인터넷 같은 공중망을 전용선처럼 쓰는 기술을 말한다. 공중망이 어떻게 전용선처럼 되느냐 하면, 두 지점 사이에 **터널링** 으로 가상 통로를 만들고 그 안을 암호화해 통과시키기 때문이다. 이 터널을 어느 계층에서 만드느냐에 따라 프로토콜이 갈린다.

| 터널링 프로토콜 | 계층 | 단서 |
|---|---|---|
| **PPTP(Point-to-Point Tunneling Protocol)** | 2계층 | PPP 기반, Microsoft 계열 |
| **L2F(Layer 2 Forwarding)** | 2계층 | Cisco 계열 |
| **L2TP(Layer 2 Tunneling Protocol)** | 2계층 | **L2F와 PPTP를 결합** |
| **IPSec** | 3계층 | AH·ESP → 아래 IPSec 세트 |
| **SSL VPN** | 전송 계층 위 | 웹 브라우저로 접속, 별도 클라이언트 불필요 |

**SSL/TLS** 는 전송 계층과 응용 계층 사이에서 동작한다. 인증서로 서버를 인증하고 통신을 암호화하는 역할이다. 우리가 흔히 보는 **HTTPS** 가 바로 HTTP 위에 SSL/TLS를 얹은 것이다. 여기서 이름이 비슷한 **S-HTTP** 와 혼동하기 쉬운데, S-HTTP는 HTTP 메시지 하나하나를 암호화하는 방식이라 연결 전체를 보호하는 HTTPS와는 구분된다.

### 기출에서 이렇게 나왔다
- 24-3: "SSL ( ), IPSec ( )" 공통 빈칸 → **VPN** (22-2 재출제)
- 23-1: L2F와 PPTP를 결합한 VPN 프로토콜 → **L2TP**
- 22-2: 설명의 공통 빈칸 → **VPN**

### 답 쓸 때
영어 약자로 쓰라고 하면 VPN, L2TP를 그대로 쓴다. L2TP를 묻는 지문에는 반드시 "L2F + PPTP" 가 들어 있으니, 이 조합이 보이면 L2TP다.

## 형상 관리
출제: 22-3, 20-3, 20-2
형태: 활동 설명 → 이름 / 도구 3개 고르기 / 정의 → 용어

### 개념
**형상 관리(SCM, Software Configuration Management)** 란 개발 과정에서 생기는 소스·문서·데이터 같은 산출물의 **변경 사항을 체계적으로 관리** 하는 활동을 말한다. 그럼 변경을 무엇에 대고 통제할까? 그 기준이 **베이스라인(Baseline)** 이다. 공식적으로 검토·합의를 거친 시점의 산출물이고, 이후의 변경 통제는 이 베이스라인을 기준으로 한다.

| 활동 | 하는 일 | 단서 |
|---|---|---|
| **형상 식별** | 관리 대상(형상 항목)을 정하고 이름·번호를 붙임 | "식별자 부여", "베이스라인 기준 설정" |
| **형상 통제** | 변경 요구를 검토·승인하고 베이스라인에 반영 | "변경 요청 검토·승인", "형상통제위원회(CCB)" |
| **형상 감사** | 변경이 제대로 되었는지, 베이스라인의 무결성을 검증 | "검증", "무결성 평가" |
| **형상 기록(상태 보고)** | 형상 항목의 변경 이력과 상태를 기록·보고 | "이력", "보고서" |

그런데 이 활동들의 순서는 자료마다 조금 다르다. NCS 학습모듈은 절차를 **형상 식별 → 변경 제어(형상 통제) → 형상 상태 보고 → 형상 감사** 순서로 적고, 수험서는 식별 → 통제 → 감사 → 기록 순으로 적기도 한다.

형상 관리 도구는 저장소를 어떤 구조로 두느냐로 나뉜다.

| 구조 | 도구 | 특징 |
|---|---|---|
| 중앙 집중형 | **CVS**, **SVN(Subversion)** | 서버에 하나의 저장소, 커밋이 서버로 바로 감 |
| 분산형 | **Git** | 개발자마다 전체 저장소 복제, 로컬 커밋 후 push |
| 로컬·파일 단위 | **RCS** | 파일 하나씩 잠금을 걸고 버전을 관리, CVS의 기반 |

여기서 주의할 게 하나 있다. 도구 고르기 문제의 보기에는 **빌드 자동화·CI 도구** 가 함께 나오는데, 이 도구들은 버전을 저장하지 않는다.

| 도구 | 하는 일 |
|---|---|
| **Ant** | XML로 빌드 절차를 적는 초기 자바 빌드 도구 |
| **Maven** | `pom.xml` 로 의존성(라이브러리)을 관리하고 정해진 빌드 생명주기를 제공 |
| **Gradle** | Groovy·Kotlin DSL로 빌드를 기술, 안드로이드 기본 빌드 도구 |
| **Jenkins** | 변경을 자주 합쳐 자동으로 빌드·테스트하는 **지속적 통합(CI)** 서버 |

### 기출에서 이렇게 나왔다
- 22-3: 보기에서 형상 관리 도구 3개 → **CVS / SVN / Git**
- 20-3: 변경 요구 검토·승인, 베이스라인 반영 → **형상 통제**
- 20-2: 변경 사항 관리, CVS·SVN·Git → **형상 관리**

### 답 쓸 때
도구 고르기 보기에는 Ant, Maven, Gradle, Jenkins 같은 빌드·CI 도구나 Spring 같은 프레임워크, OLAP 같은 것이 섞여 나온다. 이 중에서 버전을 저장하는 형상 관리 도구만 고르면 된다. CVS·SVN·Git이 기본이고, 보기에 있으면 RCS·Bitkeeper·Clear Case도 고른다. 활동을 묻는 문제는 "승인"이 보이면 통제, "검증"이 보이면 감사다.

## 인터페이스 통신 기술: AJAX·Fetch·WebSocket·GraphQL
출제: 25-2, 23-1, 20-2
형태: 설명 1~4줄 → 보기에서 영문으로

### 개념
**AJAX(Asynchronous JavaScript and XML)** 란 자바스크립트가 **XMLHttpRequest** 객체로 서버와 **비동기** 통신을 해서, 페이지 전체를 다시 불러오지 않고 **일부만** 갱신하는 기술을 말한다. 이름에 XML이 들어 있어서 XML만 주고받을 것 같지만, 실제로는 JSON을 더 많이 주고받는다.

| 기술 | 핵심 | 단서 |
|---|---|---|
| **AJAX** | XMLHttpRequest, 비동기, 부분 갱신 | "페이지 리로드 없이", "JavaScript + XML" |
| **Fetch API** | AJAX를 대체하는 표준 함수, Promise 기반 | "fetch()", "Promise" |
| **WebSocket** | 한 번 연결하면 양방향으로 계속 주고받음 | "실시간", "양방향", "지속 연결" |
| **GraphQL** | 클라이언트가 필요한 필드만 질의, 단일 엔드포인트 | "쿼리 언어", "과다/과소 조회 해결" |

AJAX가 동작하는 흐름을 따라가 보면 이렇다. 이벤트가 발생하면 XMLHttpRequest로 서버에 요청을 보낸다. 그동안 사용자는 페이지를 계속 사용하고, 응답이 오면 콜백 함수가 DOM의 일부만 갱신한다. 동기 방식과 견주면 차이가 분명한데, 동기 방식은 응답이 올 때까지 화면이 멈추고 페이지 전체를 다시 받는다.

통신 방향으로도 가를 수 있다. AJAX와 Fetch는 클라이언트가 요청해야 서버가 응답하는 **클라이언트 주도 요청-응답** 이다. 반면 WebSocket은 연결을 유지한 채로 서버가 먼저 보낼 수도 있는 **양방향(전이중)** 이다. 그래서 채팅·실시간 알림처럼 "서버가 밀어 준다"는 지문이 나오면 WebSocket이다. 여기서 GraphQL을 같은 줄에 놓고 헷갈리기 쉬운데, GraphQL은 통신 방식이 아니라 **질의 언어** 다. REST API처럼 자원마다 URL이 있는 것이 아니라, 하나의 엔드포인트에 원하는 필드를 적어 보낸다.

### 기출에서 이렇게 나왔다
- 25-2: 비동기, JS + XML, 페이지 일부만 리로드 → **AJAX** (23-1 재출제)
- 23-1: 한 줄 설명 → **AJAX**
- 20-2: XMLHttpRequest, 일부만 로드 → **AJAX**

### 답 쓸 때
영문 보기에서 고르는 형태로 나온다. 단서는 늘 "비동기"와 "일부만" 두 가지이니, 이 두 말이 보이면 AJAX를 고르면 된다.

## 테스트 케이스 구성 요소
출제: 25-3, 21-3
형태: 테스트 케이스 표의 열 제목 빈칸 3개 → 보기

### 개념
**테스트 케이스(Test Case)** 란 쉽게 말해 "이 입력을 이 조건에서 넣으면 이 결과가 나와야 한다"를 적어 둔 한 벌이다. 이걸 표로 쓰면 각 열 제목이 그대로 구성 요소가 된다.

| 구성 요소 | 내용 |
|---|---|
| **식별자(ID)** | 케이스 고유 번호 |
| **테스트 항목(Test Item)** | 무엇을 테스트하는지 (기능·모듈) |
| **테스트 조건(입력 명세)** | 어떤 상태·조건에서 수행하는지 |
| **테스트 데이터** | 실제로 넣는 입력값 |
| **예상 결과(출력 명세)** | 나와야 하는 결과 |
| 환경 설정·특수 절차·의존성 | 필요할 때만 |

케이스와 시나리오, 스크립트는 헷갈리기 쉬운데, 셋은 단위가 다르다.

| 용어 | 단위 |
|---|---|
| 테스트 케이스 | 입력·조건·예상 결과 한 벌 |
| **테스트 시나리오** | 케이스 여러 개를 수행 순서대로 묶은 것 |
| **테스트 스크립트** | 시나리오를 자동 실행하도록 적은 절차·코드 |

예를 들어 로그인 기능을 테스트한다고 해보자. "올바른 아이디·비밀번호를 넣으면 메인 화면으로 간다"가 케이스 하나다. "회원 가입 → 로그인 → 비밀번호 변경 → 재로그인"을 순서대로 적은 것이 시나리오이고, 그 시나리오를 도구가 반복 실행하도록 코드로 옮긴 것이 스크립트다. 하나 더 짚고 넘어가자. 테스트 케이스는 설계 단계에서 명세를 보고 미리 작성한다. 그러니 실행 뒤에 채우는 "실제 결과"는 구성 요소가 아니라 수행 기록이다.

### 기출에서 이렇게 나왔다
- 25-3: 표 헤더 빈칸 3개 → **테스트 조건 / 테스트 데이터 / 예상 결과** (21-3 재출제)
- 21-3: 같은 형태의 표 헤더 3칸

### 답 쓸 때
빈칸은 표의 열 순서대로 채우면 된다. 보기에 "테스트 결과"가 있으면 함정이다. 위에서 테스트 케이스는 실행 전에 미리 적는다고 했었다. 그러니 실행 전에 적는 것은 **예상** 결과다.

## EAI와 ESB
출제: 21-1, 20-3
형태: 구축 유형 4가지 중 빈칸 2개 → 보기 / 유형 이름 나열 설명 → 용어

### 개념
**EAI(Enterprise Application Integration)** 란 기업 안의 여러 애플리케이션을 연결해서 서로 데이터를 주고받게 하는 통합 방식을 말한다. 애플리케이션을 어떤 구조로 연결하느냐에 따라 4가지 유형으로 나뉜다.

| 유형 | 구조 | 특징 |
|---|---|---|
| **Point-to-Point** | 애플리케이션끼리 1:1 직접 연결 | 중간 매개 없음, 단순하지만 연결 수가 급증 |
| **Hub & Spoke** | 중앙 **허브** 하나에 모두 연결 | 단일 접점으로 관리 쉬움, 허브 장애가 전체에 영향 |
| **Message Bus** | 공통 **버스(미들웨어)** 에 연결 | 확장성·대용량 처리에 유리 |
| **Hybrid** | 그룹 안은 Hub & Spoke, 그룹 사이는 Message Bus | 두 방식 혼합 |

**ESB(Enterprise Service Bus)** 는 이 중 Message Bus 방식을 **서비스 중심(SOA)** 으로 발전시킨 것이다. 애플리케이션 단위가 아니라 서비스 단위로 느슨하게 결합하고, 메시지 변환·라우팅은 버스가 맡는다. 정리하자면 EAI가 "애플리케이션 통합"이라면 ESB는 "서비스 통합"이다.

### 기출에서 이렇게 나왔다
- 21-1: Point to Point, Hub & Spoke, Message Bus 유형 설명 → **EAI**
- 20-3: 4가지 유형 중 빈 2개 → **포인트 투 포인트 / 허브 앤 스포크**

### 답 쓸 때
유형 이름은 영문 그대로 써도 되고, 포인트 투 포인트, 허브 앤 스포크, 메시지 버스, 하이브리드처럼 한글 음차로 써도 된다. 둘 다 통용되니 보기 표기를 따른다.

## IPSec
출제: 24-2, 20-2
형태: 설명 2줄(VPN, 3계층, AH·ESP) → 용어

### 개념
**IPSec(IP Security)** 은 **네트워크 계층(3계층)** 에서 IP 패킷 단위로 인증·암호화를 제공하는 프로토콜 묶음을 말하고, VPN을 구현할 때 쓰인다. 구성은 보안 프로토콜 두 개와 동작 모드 두 개로 이루어진다.

| 프로토콜 | 제공하는 것 | 단서 |
|---|---|---|
| **AH(Authentication Header)** | 인증·무결성 (암호화 없음) | "출처 인증", "변조 탐지", "기밀성은 없음" |
| **ESP(Encapsulating Security Payload)** | 기밀성(암호화) + 인증·무결성 | "암호화", "페이로드 캡슐화" |

| 모드 | 보호 범위 | 쓰임 |
|---|---|---|
| **전송 모드(Transport)** | IP 헤더는 두고 **페이로드만** 보호 | 호스트 ↔ 호스트 |
| **터널 모드(Tunnel)** | 원래 IP 패킷 **전체** 를 보호하고 새 IP 헤더를 붙임 | 게이트웨이 ↔ 게이트웨이, VPN |

이 밖에 키 교환은 **IKE(Internet Key Exchange)** 가 맡는다. 그리고 통신 양쪽이 어떤 알고리즘과 키로 보호할지 합의한 묶음을 **SA(Security Association)** 라고 부른다.

두 모드의 차이는 "새 IP 헤더를 붙이느냐"로 기억하면 된다. 전송 모드는 원래 IP 헤더를 그대로 쓰기 때문에 양 끝 호스트 주소가 밖에서 보인다. AH 전송 모드는 인증 범위에 원래 IP 헤더의 바뀌지 않는 필드까지 넣기는 하지만, 그렇다고 헤더를 새로 붙이지는 않는다. 반면 터널 모드는 원래 패킷 전체를 안에 넣고 게이트웨이 주소가 적힌 새 헤더를 붙인다. 이때 ESP 터널 모드라면 안에 든 원래 패킷이 암호화되므로 내부 주소까지 숨겨진다. 그런데 AH는 암호화가 없으니 터널 모드여도 내부 주소가 보인다. 지사와 본사의 게이트웨이를 잇는 VPN이 ESP 터널 모드를 쓰는 이유가 바로 이것이다.

### 한눈에 구분
| 단서 | 답 |
|---|---|
| "인증만", "암호화 없음" | AH |
| "암호화", "기밀성" | ESP |
| "페이로드만", "호스트 간" | 전송 모드 |
| "패킷 전체", "새 IP 헤더", "게이트웨이 간" | 터널 모드 |

### 기출에서 이렇게 나왔다
- 24-2: VPN, 3계층, AH·ESP → **IPSec**
- 20-2: AH·ESP, 네트워크 계층 → **IPSec**

### 답 쓸 때
지문에 AH·ESP가 보이면 바로 IPSec이다. 표기는 IPSec과 IPsec 둘 다 쓴다. 헷갈리기 쉬운 SSL/TLS와는 계층으로 구분하면 된다. IPSec은 3계층이고, SSL/TLS는 전송 계층 위에서 동작한다.

## 웹 서비스 인터페이스: SOAP·WSDL·UDDI·REST
출제: 21-1, 20-2
형태: 한 줄 설명 → 용어

### 개념
웹 서비스는 서비스 제공자가 서비스를 **등록(publish)** 해 두면, 요청자가 그걸 **검색(find)** 해서 **연결(bind)** 하는 구조다. 아래 세 요소가 이 단계들을 나눠 맡는다.

| 요소 | 역할 | 단서 |
|---|---|---|
| **SOAP(Simple Object Access Protocol)** | HTTP 등 위에서 **XML 기반 메시지** 를 주고받는 프로토콜. Envelope·Header·Body 구조 | "XML 메시지 교환", "HTTP·SMTP 위에서", "RESTful로 대체 가능" |
| **WSDL(Web Services Description Language)** | 웹 서비스의 **상세 정보(위치·메서드·인터페이스)** 를 기술하는 XML 언어 | "서비스를 기술", "XML 형식 명세" |
| **UDDI(Universal Description, Discovery and Integration)** | 서비스를 **등록·검색** 하는 레지스트리 | "등록", "검색", "저장소" |

**REST(Representational State Transfer)** 는 HTTP 메서드(GET·POST·PUT·DELETE)로 **URI가 가리키는 자원** 을 조작하는 방식이다. 별도 프로토콜 없이 HTTP 자체를 쓴다. 또 상태를 서버에 두지 않는 무상태 방식이고, 주로 JSON으로 표현한다. 이런 REST 원칙을 지킨 API를 RESTful API라고 한다. SOAP와 나란히 놓으면 차이가 잘 보인다.

| 비교 | SOAP | REST |
|---|---|---|
| 형식 | XML 고정 | JSON 등 자유 |
| 무게 | 무겁고 표준이 많음 | 가볍고 단순 |
| 명세 | WSDL | 정해진 표준 없음 |

### 기출에서 이렇게 나왔다
- 21-1: 웹 서비스 상세 정보를 기술하는 XML 언어 → **WSDL**
- 20-2: HTTP 등으로 XML 기반 메시지 교환, RESTful로 대체 가능 → **SOAP**

### 답 쓸 때
세 요소는 모두 XML 기반이라서, XML 기반이라는 말만으로는 구분되지 않는다. 그러니 동사를 본다. "기술(describe)" 은 WSDL, "메시지 교환" 은 SOAP, "등록·검색" 은 UDDI다.

## 테스트 7원칙과 성능 지표
출제: 20-1
형태: 설명 → 원칙 이름 / 표 빈칸 3개 → 지표 이름

### 개념
테스트의 7원칙을 표로 정리하면 이렇다.

| 원칙 | 뜻 |
|---|---|
| 결함 존재를 보여 줄 뿐 결함이 없음을 증명하지 못한다 | 테스트 통과가 무결함은 아니다 |
| 완벽한 테스트는 불가능하다 | 모든 입력 조합을 다 할 수 없다 |
| 초기에 테스트한다(Early Testing) | 일찍 찾을수록 수정 비용이 적다 |
| 결함 집중(Defect Clustering) | 소수 모듈에 결함이 몰린다(파레토 법칙) |
| **살충제 패러독스(Pesticide Paradox)** | 같은 테스트를 반복하면 새 결함을 찾지 못한다. 케이스를 계속 바꿔야 한다 |
| 테스트는 정황(Context)에 의존한다 | 시스템 성격에 따라 테스트 방법이 다르다 |
| 오류-부재의 궤변(Absence of Errors Fallacy) | 결함이 없어도 요구를 못 채우면 쓸모없다 |

성능 테스트에서 재는 지표는 네 가지다.

| 지표 | 뜻 |
|---|---|
| **처리량(Throughput)** | 단위 시간당 처리하는 트랜잭션 수 |
| **응답 시간(Response Time)** | 요청을 보낸 뒤 **첫 응답이 오기까지** 의 시간 |
| **경과 시간(Turnaround Time)** | 요청을 보낸 뒤 **결과 출력이 끝날 때까지** 의 시간 |
| **자원 사용률(Resource Usage)** | CPU·메모리·네트워크 사용량 |

이 지표를 재는 성능 테스트는 부하를 어떻게 주느냐에 따라 나뉜다. **부하(Load)** 테스트는 목표 사용자 수까지 부하를 올리면서 지표를 확인하는 것이고, **스트레스(Stress)** 테스트는 한계를 넘는 부하를 줘서 어디서 어떻게 무너지는지 보는 것이다. 헷갈리기 쉬운 이 둘은 "목표 사용자 수까지"냐 "한계를 넘느냐"로 가르면 된다. **스파이크(Spike)** 테스트는 부하를 순간적으로 급증시키고, **내구성(Soak, Endurance)** 테스트는 일정 부하를 오래 유지해 메모리 누수 같은 장기 문제를 찾는다.

### 기출에서 이렇게 나왔다
- 20-1: 같은 테스트를 반복하면 새 결함 발견 확률이 줄어든다 → **살충제 패러독스**
- 20-1: 지표 표 빈칸 3개 → **처리량 / 응답시간 / 경과시간**

### 답 쓸 때
여기서 많이들 헷갈리는 게 응답 시간과 경과 시간이다. 둘 다 요청을 보낸 뒤부터 재는 시간이기 때문이다. 차이는 끝나는 지점에 있다. 응답 시간은 "첫 응답까지", 경과 시간은 "완료까지"다.

## 데이터 표현 형식: JSON·XML·YAML
출제: 20-1
형태: 설명 → 보기에서 고르기

### 개념
JSON·XML·YAML은 인터페이스로 주고받는 데이터를 적는 형식이다. 셋 다 사람이 읽을 수 있는 텍스트이고, 계층 구조를 표현한다는 공통점이 있다.

| 형식 | 구조 | 단서 |
|---|---|---|
| **JSON(JavaScript Object Notation)** | `"name": value` 쌍과 배열, 중괄호·대괄호 | "속성-값 쌍", "경량", "자바스크립트 객체 표기에서 유래", AJAX에서 XML 대신 |
| **XML(eXtensible Markup Language)** | 사용자가 정의하는 태그 `<tag>...</tag>` | "W3C", "SGML의 복잡함을 해결", "다목적 마크업 언어", "HTML의 한계 보완" |
| **YAML(YAML Ain't Markup Language)** | 들여쓰기와 `key: value`, 목록은 `-` | "들여쓰기", "사람이 읽기 쉬움", "설정 파일", JSON의 상위 호환 |

말로만 보면 감이 잘 안 오니 같은 데이터를 세 형식으로 적어 보자. 세 개 모두 python3 `json`·`xml.etree`·`yaml`로 파싱해서 `name=홍길동, age=20, skills=[C, Java]` 로 똑같이 읽히는 것을 확인했다.

```json
{"name": "홍길동", "age": 20, "skills": ["C", "Java"]}
```

```xml
<student>
  <name>홍길동</name>
  <age>20</age>
  <skills>
    <skill>C</skill>
    <skill>Java</skill>
  </skills>
</student>
```

```yaml
name: 홍길동
age: 20
skills:
  - C
  - Java
```

셋을 나란히 놓고 보면 차이가 바로 보인다. XML은 여는 태그와 닫는 태그가 쌍이라 길어지고, JSON은 괄호와 따옴표로 짧게 끝난다. YAML은 괄호 없이 들여쓰기만으로 구조를 나타낸다. 주석도 다른데, JSON에는 주석이 없고 YAML에는 `#` 주석이 있다.

### 기출에서 이렇게 나왔다
- 20-1: name:value 쌍, 경량 → **JSON**
- 20-1: W3C, SGML의 복잡함 해결, 다목적 마크업 → **XML**

### 답 쓸 때
지문에 "마크업"이 보이면 XML, "속성-값 쌍"이면 JSON, "들여쓰기"면 YAML이다.

## URL 구조
출제: 24-3
형태: 예시 URL을 5구간으로 나눠 각 구간 이름을 보기에서 고르기

### 개념
URL이란 자원의 위치를 적는 문자열을 말한다. 한 줄로 이어져 있지만 구간마다 이름이 따로 있다.

```text
scheme://authority/path?query#fragment
https://www.example.com:443/docs/guide?page=2&lang=ko#section-3
```

| 구간 | 예시 부분 | 뜻 |
|---|---|---|
| **scheme** | `https` | 프로토콜 |
| **authority** | `www.example.com:443` | 호스트(+포트, 필요하면 사용자 정보) |
| **path** | `/docs/guide` | 서버 안의 자원 경로 |
| **query** | `page=2&lang=ko` | `?` 뒤의 매개변수, `&`로 구분 |
| **fragment** | `section-3` | `#` 뒤, 문서 안의 위치 |

authority 안은 다시 `사용자정보@호스트:포트` 로 나뉜다. 포트를 생략하면 scheme의 기본 포트가 쓰이는데, http는 80, https는 443이다. query는 `이름=값` 쌍을 `&` 로 이어 붙인 것이다. fragment는 조금 특이한데, 서버로 전송되지 않고 브라우저가 문서 안에서 위치를 찾는 데만 쓴다. 마지막으로 공백이나 한글처럼 URL에 직접 쓸 수 없는 문자는 `%` 뒤에 16진수를 붙이는 **퍼센트 인코딩** 으로 적는다.

여기서 URL과 URI를 혼동하기 쉬운데, 둘은 포함 관계다. **URI(Uniform Resource Identifier)** 는 자원을 식별하는 문자열 전체를 가리키고, 그중 위치로 식별하면 **URL(Locator)**, 이름으로 식별하면 **URN(Name)** 이다. 그러니까 URL은 URI의 한 종류다.

| 구분 | 식별 방법 | 예 |
|---|---|---|
| URL | 어디에 있는가 | `https://www.example.com/docs/guide` |
| URN | 무엇인가(이름) | `urn:isbn:...` 처럼 위치와 무관한 이름 |

### 기출에서 이렇게 나왔다
- 24-3: 예시 URL의 5구간 → **scheme / authority / path / query / fragment**

### 답 쓸 때
구간은 구분 기호를 기준으로 찾으면 된다. `://` 앞은 scheme, 그 뒤로 첫 `/` 전까지가 authority, `?` 뒤가 query, `#` 뒤가 fragment다.

## 테스트 기본 용어: 정적·동적 테스트, V&V, 결함
출제: 없음

### 개념
테스트는 먼저 프로그램을 실행하느냐로 나눌 수 있다. **정적 테스트** 는 프로그램을 실행하지 않고 명세·설계·코드를 검토하는 것이고, **동적 테스트** 는 실행하면서 결과를 보는 것이다. 앞에서 본 화이트박스·블랙박스는 동적 테스트에 속한다. 정적 테스트 중 사람이 직접 검토하는 방식은 얼마나 공식적이냐에 따라 아래처럼 구분한다.

| 리뷰 기법 | 진행 | 단서 |
|---|---|---|
| **동료 검토(Peer Review)** | 작성자가 설명하고 동료 2~3명이 결함을 찾음 | 가장 비공식 |
| **워크스루(Walkthrough)** | 작성자가 주도, 미리 배포한 산출물을 짧은 회의로 검토 | 비공식, 작성자 주도 |
| **인스펙션(Inspection)** | 작성자가 아닌 중재자가 주도, 체크리스트·역할 분담·후속 조치 | 가장 공식적 |

**검증(Verification)** 과 **확인(Validation)** 은 말이 비슷해서 헷갈리기 쉽다. 검증은 "명세대로 올바르게 만들고 있는가(product right)"를, 확인은 "사용자가 원하는 것을 만들었는가(right product)"를 묻는다.

테스트 전체는 **계획 → 분석 → 디자인 → 케이스·시나리오 작성 → 수행 → 결과 평가·리포팅** 순서로 진행한다. 이 과정에서 나오는 산출물은 **테스트 계획서·테스트 케이스·테스트 시나리오·테스트 결과서** 다.

목적을 기준으로 하면 테스트는 7가지로 나뉜다.

| 테스트 | 확인하는 것 |
|---|---|
| **회복(Recovery)** | 고의로 실패를 유도해 정상 복귀하는지 |
| **안전(Security)** | 불법 침입·파괴를 막는지 |
| **강도(Stress)** | 과다한 정보량·부하에서도 정상 작동하는지 |
| **성능(Performance)** | 응답 시간·처리량·반응 속도 |
| **구조(Structure)** | 내부 논리 경로와 코드 복잡도 |
| **회귀(Regression)** | 수정한 뒤 새 결함이 생겼는지 |
| **병행(Parallel)** | 변경된 시스템과 기존 시스템에 같은 데이터를 넣고 결과를 비교 |

여기서 병행 테스트를 블랙박스의 비교(Comparison) 테스트와 혼동하기 쉽다. 둘 다 '같은 입력, 출력 비교'라는 점에서는 비슷한데, 병행 테스트는 신·구 시스템을 비교한다는 점이 다르다.

결함 관련 용어는 원인에서 결과 순서로 외우면 된다. NCS 기준으로 보면 먼저 개발자·분석가 같은 사람의 실수가 **에러(Error)/오류** 다. 그 결과 제품 안에 남은 잘못이 **결함(Defect)·결점(Fault)·버그(Bug)** 이고, 이 결함이 실행되어 드러나는 현상이 **실패(Failure)/문제(Problem)** 다. 한 줄로 쓰면 에러 → 결함 → 실패다. 다만 IEEE 등 교재에 따라서는 사람의 실수를 Mistake, 결함이 실행되어 생긴 잘못된 내부 상태를 Error로 나눠 4단계로 다르게 부르기도 한다. 그래도 답안에는 NCS 3단계 이름을 쓴다.

결함 관리 프로세스는 NCS 기준으로 **에러 발견 → 에러 등록 → 에러 분석 → 결함 확정 → 결함 할당 → 결함 조치 → 결함 조치 검토 및 승인** 순서다. 이름을 잘 보면 처음에는 '에러'로 등록했다가 분석을 거친 뒤에야 '결함'으로 확정된다. 이렇게 등록한 에러가 실제 결함으로 확정되면 그때 **심각도(Severity, 영향의 크기)** 와 **우선순위(Priority, 고칠 순서)** 를 따로 정한다. 이 프로세스도 교재에 따라 다르게 부르기도 하는데, 결함 관리 도구의 생명주기처럼 등록 → 검토 → 할당 → 수정 → 재확인 → 종료로 적는 식이다.

테스트가 끝나면 **결함 추이 분석** 을 해서 앞으로 결함이 생길 곳을 추정한다. 여기서 보는 것은 세 가지다. **결함 분포** 는 모듈·컴포넌트별 결함 수, **결함 추세** 는 시간 흐름에 따른 결함 수, **결함 에이징** 은 결함이 특정 상태에 머문 시간이다.

## 미들웨어 (DB 미들웨어·RPC·MOM·TP-Monitor·ORB·WAS)
출제: 없음

### 개념
**미들웨어(Middleware)** 란 운영체제와 응용 프로그램 사이, 또는 서로 다른 시스템 사이에 끼어서 통신과 데이터 교환을 대신 처리해 주는 소프트웨어를 말한다. 그래서 응용 프로그램은 상대 시스템의 세부 구현을 몰라도 미들웨어를 통해 연결된다. 종류는 "무엇을 중개하느냐"로 구분한다.

| 종류 | 무엇을 중개하나 | 지문 단서 |
|---|---|---|
| **DB 미들웨어** | 응용 프로그램과 데이터베이스 | ODBC, JDBC, "DB 연결" |
| **RPC(Remote Procedure Call)** | 원격지의 프로시저 호출 | "원격 함수를 로컬 함수처럼 호출" |
| **MOM(Message Oriented Middleware)** | 메시지 | "비동기 메시지", "메시지 큐", 대량 처리, 즉각 응답이 필요 없는 경우 |
| **TP-Monitor(Transaction Processing Monitor)** | 트랜잭션 | "트랜잭션 처리·감시", 항공·은행처럼 사용자가 많고 신뢰성이 중요한 업무 |
| **ORB(Object Request Broker)** | 분산 객체 사이의 요청 | CORBA 표준, "객체 요청 중개" |
| **WAS(Web Application Server)** | 웹 요청과 동적 콘텐츠 처리 | "동적 웹 페이지", Tomcat·JBoss 등 |

### 한눈에 구분
| 혼동 쌍 | 가르는 기준 |
|---|---|
| RPC vs MOM | RPC는 호출하고 결과를 기다리는 동기식, MOM은 메시지를 맡겨 두는 비동기식 |
| WAS vs 웹 서버 | 웹 서버는 정적 파일(HTML·이미지) 전달, WAS는 프로그램을 실행해 동적 결과를 만든다 |
| TP-Monitor vs MOM | 트랜잭션의 처리·감시가 핵심이면 TP-Monitor, 메시지 전달이 핵심이면 MOM |

### 답 쓸 때
설명에 "비동기"와 "메시지"가 같이 나오면 MOM, "트랜잭션"과 "감시"가 나오면 TP-Monitor다. 약어로 묻는 경우가 많기 때문에 영문 약어도 함께 외워 둔다.
