# DB

21개 회차 420문제 중 이론이 242문제이고, 그중 DB 영역은 매 회차 1~4문제가 나왔다. 형태는 "설명 3~4개를 보기와 짝짓기"(릴레이션 용어·스키마·키), "표를 보고 판별하기"(정규형·위반한 무결성·카디널리티와 차수), "연산 결과 표 채우기"(관계대수)가 대부분이다. 2024년 이후에는 23-1의 릴레이션 용어, 24-1의 정규형 표, 21-1의 카디널리티·차수처럼 2~5년 전 문제가 거의 그대로 다시 나오는 비율이 높다.

## 관계대수·관계해석
출제: 25-3, 25-2, 24-1, 23-3, 22-3, 22-2, 20-3
형태: 연산 결과 표 채우기 / 연산 이름 ↔ 기호 짝짓기 / 조인 종류 설명 → 이름

### 개념

**관계대수(Relational Algebra)**는 원하는 결과를 얻기 위해 어떤 연산을 어떤 순서로 할지 적는 **절차적** 언어다. 피연산자도 결과도 릴레이션이다. **관계해석(Relational Calculus)**은 원하는 결과의 조건만 적는 **비절차적** 언어로, 수학의 **술어 해석(Predicate Calculus)**에 기반하며 Codd가 제안했다. 변수가 튜플이면 **튜플 관계해석**, 도메인 값이면 **도메인 관계해석**이다. 둘의 표현력은 같다.

| 구분 | 연산 | 기호 | 뜻 |
|---|---|---|---|
| 순수 관계 연산 | **셀렉트(Select)** | **σ** | 조건을 만족하는 튜플(행)을 고른다. 수평 연산 |
| 순수 관계 연산 | **프로젝트(Project)** | **π** | 지정한 속성(열)만 뽑는다. 수직 연산. 중복 튜플은 제거된다 |
| 순수 관계 연산 | **조인(Join)** | **⋈** (▷◁로도 쓴다) | 공통 속성을 기준으로 두 릴레이션을 합친다 |
| 순수 관계 연산 | **디비전(Division)** | **÷** | R ÷ S: S의 모든 튜플과 짝을 이루는 R의 튜플에서 S의 속성을 뺀 것. 지문 단서는 "B의 조건에 맞는 것만 A에서 분리해 프로젝션" |
| 일반 집합 연산 | **합집합(Union)** | **∪** | 두 릴레이션의 튜플을 합치고 중복은 하나만 남긴다 |
| 일반 집합 연산 | **교집합(Intersection)** | **∩** | 양쪽에 모두 있는 튜플 |
| 일반 집합 연산 | **차집합(Difference)** | **−** | R − S: R에는 있고 S에는 없는 튜플 |
| 일반 집합 연산 | **카티션 프로덕트(Cartesian Product)** | **×** | 모든 튜플 쌍. 차수는 합, 카디널리티는 곱 |

합집합·교집합·차집합은 두 릴레이션의 차수가 같고 대응 속성의 도메인이 같아야 한다(합병 가능).

디비전 예: 수강(학번, 과목)에 (1, DB), (1, OS), (2, DB), (3, DB), (3, OS)가 있고 S(과목)에 DB, OS가 있으면, 수강 ÷ S는 두 과목을 모두 들은 학번만 남긴 (1), (3)이다. 결과에는 S의 속성인 과목이 빠지고 학번만 남는다.

### 한눈에 구분 (조인 종류)

| 종류 | 핵심 단서 | 비고 |
|---|---|---|
| **세타 조인(Theta Join)** | 비교 연산자(=, <, > 등) 조건으로 결합 | 조건이 =가 아니어도 된다 |
| **동등 조인(Equi Join)** | 세타 조인 중 **=** 조건 | 결과에 중복 속성이 남는다 |
| **자연 조인(Natural Join)** | 동등 조인 결과에서 **중복 속성을 하나로** | SQL의 NATURAL JOIN |
| **외부 조인(Outer Join)** | 짝이 없는 튜플도 남기고 빈 자리는 **NULL** | 왼쪽·오른쪽·완전 |
| **세미 조인(Semi Join)** | R ⋉ S: S와 짝이 있는 R의 튜플만 남기고, 속성도 R의 것만 남긴다 | 자연 조인 뒤 R의 속성으로 프로젝션한 것과 같다 |

## 릴레이션 용어
출제: 25-3, 25-2, 25-1, 24-2, 23-1, 21-1
형태: 설명 3~4개 → 보기(한글 또는 영문) / 표를 주고 개수 세기

### 개념

| 용어 | 뜻 | 세는 법 |
|---|---|---|
| **릴레이션(Relation)** | 표 하나 | |
| **튜플(Tuple)** | 표의 행 하나. 파일의 레코드에 해당 | |
| **속성(Attribute)** | 표의 열 하나. 파일의 데이터 항목(필드)에 해당 | |
| **도메인(Domain)** | 한 속성이 가질 수 있는 **원자값의 집합** | |
| **차수(Degree)** | **속성(열)의 개수** | 헤더 칸 수 |
| **카디널리티(Cardinality)** | **튜플(행)의 개수** | 헤더를 뺀 데이터 행 수 |
| **릴레이션 스키마(Schema)** | 릴레이션 이름과 속성들의 정의. 시간이 지나도 잘 안 변하는 틀(내포) | |
| **릴레이션 인스턴스(Instance)** | 어느 시점에 실제로 들어 있는 튜플들의 집합. 계속 변한다(외연) | |
| **식별자(Identifier)** | 튜플을 유일하게 구분하는 속성(집합). 키 | |

릴레이션의 특징: 튜플은 중복되지 않고 순서가 없다. 속성도 순서가 없다. 속성값은 더 쪼갤 수 없는 **원자값**이다.

표를 주고 세라고 하면, 열 제목이 몇 개인지가 차수, 데이터 행이 몇 줄인지가 카디널리티다. 제목 행을 카디널리티에 넣지 않는다.

## 정규화·반정규화
출제: 26-2, 24-2, 24-1, 21-2, 21-1, 20-1
형태: 표와 기본키를 주고 현재 정규형 고르기 / 분해 전후 표 → 몇 정규형 / 정의 → 반정규화

### 개념

**정규화(Normalization)**는 이상 현상의 원인인 불필요한 함수 종속을 없애려고 릴레이션을 작은 릴레이션으로 분해하는 과정이다. 단계가 올라갈수록 제약이 세진다.

| 정규형 | 조건 (제거하는 것) | 단서 |
|---|---|---|
| **1NF** | 모든 속성값이 **원자값** (반복 그룹·다중값 제거) | 한 칸에 값이 두 개 들어 있으면 1NF 위반 |
| **2NF** | 1NF + **부분 함수 종속 제거** (키가 아닌 속성이 기본키 전체에 완전 종속) | 기본키가 복합키일 때만 문제가 된다 |
| **3NF** | 2NF + **이행 함수 종속 제거** (키가 아닌 속성 → 키가 아닌 속성 없음) | A→B, B→C 꼴 |
| **BCNF** | **모든 결정자가 후보키** | 3NF인데 결정자가 후보키가 아닌 경우 |
| **4NF** | **다치 종속(MVD)** 제거 | A ↠ B |
| **5NF** | **조인 종속** 제거 (후보키를 통해서만 조인 종속) | PJ/NF |

두음: 도부이결다조 (도메인 원자값 → 부분 종속 → 이행 종속 → 결정자 → 다치 → 조인).

표를 보고 정규형을 판별하는 절차:

1. 한 칸에 값이 여러 개인가 → 있으면 1NF 미만. 없으면 1NF.
2. 기본키가 복합키인가 → 후보키가 모두 단일 속성이면 부분 종속이 생길 수 없으니 2NF는 자동이다. 복합키면 키의 일부만으로 결정되는 비키 속성이 있는지 본다. 있으면 1NF.
3. 비키 속성끼리 결정 관계가 있는가(A→B→C) → 있으면 2NF. 없으면 3NF.
4. 결정자 중 후보키가 아닌 것이 있는가 → 있으면 3NF에서 멈춘다(BCNF 아님). 없으면 BCNF.

**이행 종속처럼 보이지만 3NF인 경우**: 비키 속성이 기본키의 일부(주속성)를 결정하는 꼴은 "비키 → 비키"가 아니므로 이행 종속이 아니다. 3NF 조건은 만족하지만 결정자가 후보키가 아니므로 BCNF는 아니다. 26-2와 24-1의 표(기본키 고객아이디+과정명, 속성 강사번호)는 복합키 표였고 답이 **제3정규형**이었다. 복합키 표라고 바로 2NF라 단정하지 말고, 부분 종속·이행 종속이 실제로 있는지 위 절차대로 확인한다.

**반정규화(Denormalization)**는 성능을 위해 정규화된 구조를 의도적으로 되돌려 중복이나 통합을 허용하는 것이다. 역정규화·비정규화라고도 부른다. 기법: **테이블 통합**(1:1, 1:M, 슈퍼/서브타입), **테이블 분할**(수평·수직), **중복 테이블 추가**(집계·진행·특정 부분만), **중복 속성 추가**(조인을 줄이기 위해 다른 테이블의 컬럼을 복사), 파생 컬럼 추가. 조회는 빨라지고 갱신 비용과 정합성 관리 부담은 늘어난다.

```steps
제목: 단계마다 하나씩 없앤다 (도부이결다조)
비정규 릴레이션 |
1NF | 도메인을 원자값으로
2NF | 부분 함수 종속 제거
3NF | 이행 함수 종속 제거
BCNF | 결정자가 모두 후보키
4NF | 다치 종속 제거
5NF | 조인 종속 제거
```

### 기출에서 이렇게 나왔다

- 26-2, 24-1: 표(기본키 명시) → 현재 정규형 보기에서 → **제3정규형(3NF)** (같은 표)
- 21-2: 정규화 전/후 표, 부분 함수 종속 제거 → **제2정규형**
- 24-2, 21-1, 20-1: "성능 향상을 위해 중복·통합을 허용" 한 줄 정의 → **반정규화**

### 답 쓸 때

"제 ( ) 정규형" 빈칸이면 숫자만, 보기형이면 보기 표기대로. 분해 전후를 주고 묻는 문제는 "무엇을 제거했는가"가 답이다(부분 종속 제거 = 2NF, 이행 종속 제거 = 3NF).

## 트랜잭션
출제: 22-1, 21-2, 20-4, 20-2, 20-1
형태: 설명 → 특성 이름 / 회복 기법 이름 / 명령어

### 개념

**트랜잭션(Transaction)**은 하나의 논리적 작업 단위다.

| 상태 | 뜻 |
|---|---|
| **활동(Active)** | 실행 중 |
| **부분 완료(Partially Committed)** | 마지막 연산까지 실행했지만 아직 COMMIT 전 |
| **완료(Committed)** | COMMIT되어 결과가 DB에 반영됨 |
| **실패(Failed)** | 오류로 실행이 중단됨 |
| **철회(Aborted)** | ROLLBACK으로 실행 이전 상태로 되돌아감 |

정상 흐름은 활동 → 부분 완료 → 완료, 오류가 나면 실패 → 철회다.

| 특성 | 뜻 | 단서 |
|---|---|---|
| **원자성(Atomicity)** | 모두 반영되거나 하나도 반영되지 않는다 | All or Nothing, 회복 기법이 보장 |
| **일관성(Consistency)** | 실행 전후 DB는 모순 없는 상태 | 무결성 제약 유지 |
| **고립성(Isolation)** | 실행 중인 트랜잭션의 중간 결과를 다른 트랜잭션이 볼 수 없다 | 독립성, 동시성 제어가 보장 |
| **지속성(Durability)** | 완료된 결과는 장애가 나도 남는다 | 영속성 |

**회복(Recovery) 기법**: 장애가 나면 DB를 장애 전의 일관된 상태로 되돌린다. 지연 갱신과 즉각 갱신은 변경 내용을 로그에 기록해 두고 쓰는 **로그 기반 회복**이다.

| 기법 | 내용 |
|---|---|
| **지연 갱신(Deferred Update)** | 완료 전까지 DB에 쓰지 않고 로그에만 기록. 완료된 것은 **REDO**, 미완료는 로그만 버린다(UNDO 불필요) |
| **즉각 갱신(Immediate Update)** | 실행 중 바로 DB에 반영. 장애 시 **REDO와 UNDO 모두** 필요 |
| **검사점(Checkpoint)** | 일정 시점마다 체크포인트를 남겨 그 이후 로그만 회복에 사용 |
| **그림자 페이징(Shadow Paging)** | 갱신 전 페이지의 복사본을 두고, 실패하면 복사본으로 되돌린다. 로그 불필요 |

**REDO(재실행)**는 로그에 Start와 Commit 기록이 모두 있는 트랜잭션을 다시 실행해(이전 값 → 이후 값) 지속성을 맞추는 것, **UNDO(취소)**는 Start는 있지만 Commit 기록이 없는 트랜잭션의 변경을 취소해(이후 값 → 이전 값) 원자성을 맞추는 것이다.

**동시성(병행) 제어(Concurrency Control)**: 여러 트랜잭션이 동시에 돌아도 결과가 하나씩 차례로 실행한 것과 같도록 보장한다. 병행 제어를 안 하면 생기는 문제는 네 가지다.

| 문제 | 상황 |
|---|---|
| **갱신 분실(Lost Update)** | 두 트랜잭션이 같은 데이터를 갱신해 한쪽 변경이 덮여 사라진다 |
| **비완료 의존성(Uncommitted Dependency)** | COMMIT 전의 중간 값을 다른 트랜잭션이 읽었는데 원래 트랜잭션이 롤백된다. 현황 파악 오류, **Dirty Read**라고도 한다 |
| **모순성(Inconsistency)** | 서로의 연산에 끼어들어 데이터가 일관성을 잃는다 |
| **연쇄 복귀(Cascading Rollback)** | 한 트랜잭션이 롤백되면 그 미완료 값을 읽은 트랜잭션들도 줄줄이 롤백된다 |

기법:

- **로킹(Locking)**: 접근한 데이터에 lock을 걸어 연산이 끝날 때까지 다른 접근을 막는 상호 배제 직렬화 기법. **공유 lock(S-Lock)**은 읽기용으로 여러 트랜잭션이 함께 읽을 수 있고 쓰기는 막는다. **배타(전용) lock(X-Lock)**은 쓰기용으로 다른 트랜잭션의 읽기·쓰기를 모두 막는다. **로킹 단위**가 크면 병행성이 낮고 오버헤드가 적으며, 작으면 병행성이 높고 오버헤드가 크다.
- **2단계 로킹(2PL, Two-Phase Locking)**: 확장 단계에서는 lock만, 축소 단계에서는 unlock만 한다. 직렬성은 보장하지만 교착 상태는 생길 수 있다.
- **타임스탬프 순서(Timestamp Ordering)**: 트랜잭션마다 시작 시각 순서를 붙여 그 순서대로 실행되게 한다.
- **낙관적 검증(Optimistic Validation)**: 실행 중에는 검사하지 않고, 끝날 때 충돌을 검증한 뒤 반영한다.
- **다중 버전(Multi-Version)**: 데이터의 여러 버전을 두고 트랜잭션 시각에 맞는 버전을 읽게 한다.

**격리 수준(Isolation Level)**: 고립성을 얼마나 엄격하게 지킬지 정한 단계다. 낮은 쪽부터 다음과 같다.

| 격리 수준 | 내용 | 생길 수 있는 문제 |
|---|---|---|
| **Read Uncommitted** | COMMIT 안 된 데이터도 읽는다 | Dirty Read |
| **Read Committed** | COMMIT된 데이터만 읽는다 | Non-Repeatable Read (같은 행을 두 번 읽으면 값이 다름) |
| **Repeatable Read** | 읽은 행은 트랜잭션이 끝날 때까지 같은 값을 보장 | Phantom Read (같은 조건으로 다시 조회하면 없던 행이 나타남) |
| **Serializable** | 완전히 직렬 실행한 것처럼 처리 | 없음. 동시성은 가장 낮다 |

**TCL**: **COMMIT**(확정), **ROLLBACK**(트랜잭션 시작 이전 상태로 복구), **SAVEPOINT**(부분 복귀 지점).

## 무결성
출제: 26-2, 25-1, 24-3, 23-3
형태: 표에서 위반한 무결성 찾기 / 3종 비교표 → 이름 / CREATE DOMAIN 빈칸

### 개념

**무결성(Integrity)**은 DB에 들어 있는 값이 정확하고 모순 없음을 보장하는 제약이다.

| 종류 | 규칙 | 표에서 찾는 단서 |
|---|---|---|
| **개체 무결성(Entity Integrity)** | **기본키**는 **NULL**이 될 수 없고 **중복**될 수 없다 | 기본키 열에 빈 칸이 있거나 같은 값이 두 번 |
| **참조 무결성(Referential Integrity)** | **외래키** 값은 참조하는 테이블의 기본키에 있는 값이거나 NULL이어야 한다 | 외래키 열의 값이 참조 테이블에 없다 |
| **도메인 무결성(Domain Integrity)** | 속성값은 정의된 **도메인(자료형·범위·형식)** 안에 있어야 한다 | 성별에 '남녀' 외 값, 점수에 음수, 날짜 형식 틀림 |
| **키 무결성(Key Integrity)** | 한 릴레이션에 키가 최소 하나는 있어야 한다 | |
| **사용자 정의 무결성** | 업무 규칙으로 정한 제약 (CHECK, TRIGGER 등) | |

SQL에서 개체 무결성은 PRIMARY KEY, 참조 무결성은 FOREIGN KEY ... REFERENCES, 도메인 무결성은 자료형·CHECK·DEFAULT·NOT NULL·CREATE DOMAIN, 키 무결성은 UNIQUE, 사용자 정의 무결성은 TRIGGER로 구현한다. 참조 무결성을 지키려고 부모 행을 지울 때 자식 행을 어떻게 할지는 ON DELETE 옵션(CASCADE·SET NULL·SET DEFAULT·RESTRICT·NO ACTION)으로 정한다. 옵션별 동작과 실행 결과는 SQL 페이지에 있다. **CREATE DOMAIN**은 도메인 이름을 정의하면서 **CHECK (VALUE IN (...))**로 허용 값을 제한한다.

표가 두 개 나오면 참조 무결성을 먼저 의심한다. 외래키 열의 값을 하나씩 참조 테이블의 기본키 열에서 찾아 없는 값이 있으면 참조 무결성 위반이다. 표가 하나이고 기본키 열에 NULL이나 중복이 있으면 개체 무결성 위반이다.

### 기출에서 이렇게 나왔다

- 26-2: `CREATE DOMAIN ... ( ) (VALUE IN ...)` 빈칸 → **CHECK**
- 25-1: 제약 대상·관련 키·개수를 적은 비교표 3행 → **도메인 / 개체 / 참조**
- 24-3: 기본키(학번)에 NULL이 있는 표 → **개체 무결성**
- 23-3: 두 테이블, 외래키 값이 참조 테이블에 없음 → **참조 무결성**

### 답 쓸 때

"( ) 무결성" 형식이면 종류 이름(개체·참조·도메인)만 쓰면 된다. 개체 무결성의 영문은 Entity Integrity, 참조 무결성은 Referential Integrity다.

## DB 설계 절차
출제: 26-1, 23-2, 21-1, 20-2

### 개념

| 단계 | 하는 일 | 산출물 | 단서어 |
|---|---|---|---|
| **요구사항 분석** | 사용자 요구 수집·분석 | 요구사항 명세서 | |

## 스키마 3단계·데이터 독립성
출제: 23-1, 20-3
형태: 설명 3개 → 외부/개념/내부 구분

### 개념

**스키마(Schema)**는 DB의 구조와 제약조건을 정의한 것이다. ANSI/SPARC는 보는 관점에 따라 3단계로 나눈다.

| 단계 | 관점 | 핵심 단서 | 비고 |
|---|---|---|---|
| **외부 스키마(External Schema)** | 사용자·응용 프로그래머 | **사용자마다 다르다**, **서브 스키마**, 뷰 | 여러 개 존재 |
| **개념 스키마(Conceptual Schema)** | 조직 전체 | **전체 논리 구조**, DBA가 정의, 접근 권한·무결성 규칙 포함 | 하나만 존재. 보통 "스키마"라고 하면 이것 |
| **내부 스키마(Internal Schema)** | 물리적 저장 | **저장 구조**, 레코드 형식, 인덱스, 접근 경로 | 하나만 존재 |

**데이터 독립성**: 한 단계의 스키마를 바꿔도 위 단계가 영향을 받지 않는 성질.

| 종류 | 내용 |
|---|---|
| **논리적 데이터 독립성** | 개념 스키마를 바꿔도 외부 스키마(응용 프로그램)는 그대로 |
| **물리적 데이터 독립성** | 내부 스키마(저장 구조·장치)를 바꿔도 개념·외부 스키마는 그대로 |

외부-개념 사이의 변환이 논리적, 개념-내부 사이가 물리적이다.

```mermaid
제목: 외부와 개념 사이가 논리적 독립성, 개념과 내부 사이가 물리적 독립성
%% 폰: TB / LR
flowchart LR
  subgraph EXT["외부 단계 (여러 개)"]
    direction TB
    E1("학생 뷰")
    E2("교수 뷰")
    E3("행정 뷰")
  end
  C("개념 스키마<br/>조직 전체 논리 구조")
  I("내부 스키마<br/>저장 구조·인덱스")
  D[("저장 장치")]
  E2 -->|"논리적 독립성"| C
  C -->|"물리적 독립성"| I
  I --> D
```

## 키
출제: 24-3, 22-1
형태: 설명 4개 → 보기 / 특성 빈칸

### 개념

키의 두 특성: **유일성(Uniqueness)**은 그 키 값으로 튜플을 하나만 찾을 수 있는 것, **최소성(Minimality)**은 튜플을 구분하는 데 꼭 필요한 속성만 들어 있는 것이다.

| 종류 | 정의 | 특성 |
|---|---|---|
| **슈퍼키(Super Key)** | 유일성만 만족하는 속성 집합. 후보키에 다른 속성을 더 붙인 것도 슈퍼키 | 유일성 O, 최소성 X |
| **후보키(Candidate Key)** | 유일성과 최소성을 모두 만족. 기본키가 될 자격이 있는 것 | 유일성 O, 최소성 O |
| **기본키(Primary Key)** | 후보키 중 대표로 선택한 하나. NULL·중복 불가 | |
| **대체키(Alternate Key)** | 후보키 중 기본키로 뽑히지 않은 나머지 | 보조키 |
| **외래키(Foreign Key)** | 다른 릴레이션의 기본키를 참조하는 속성. 참조 무결성의 대상 | NULL 허용 |

포함 관계: 슈퍼키 ⊃ 후보키 ⊃ 기본키, 후보키 = 기본키 + 대체키.

```mermaid
제목: 슈퍼키 안에 후보키, 후보키 중 하나가 기본키이고 나머지가 대체키
flowchart TB
  subgraph S["슈퍼키: 유일성만 만족"]
    subgraph C["후보키: 유일성 + 최소성"]
      direction LR
      P("기본키<br/>후보키 중 고른 1개")
      A("대체키<br/>고르지 않은 나머지")
    end
  end
```

- 22-1: 슈퍼키는 ( ), 후보키는 ( )과 ( ) → **유일성 / 최소성** (슈퍼키는 유일성만, 후보키는 유일성과 최소성)

## 이상 현상
출제: 22-1, 20-4
형태: 설명 → 종류 이름 / 3가지 쓰기

### 개념

**이상(Anomaly)**은 한 릴레이션에 서로 다른 관심사의 속성이 섞여(불필요한 함수 종속) 데이터를 조작할 때 생기는 부작용이다. 정규화로 해결한다.

| 종류 | 상황 | 단서 |
|---|---|---|
| **삽입 이상(Insertion Anomaly)** | 원하는 데이터를 넣으려면 관계없는 값까지 함께 넣어야 하거나, 그 값이 없어 넣을 수 없다 | "불필요한 데이터까지", "NULL을 넣어야" |
| **삭제 이상(Deletion Anomaly)** | 튜플 하나를 지우면 의도하지 않은 다른 정보까지 함께 사라진다 | "연쇄 삭제", "의도치 않은 정보 손실" |
| **갱신 이상(Update Anomaly)** | 중복된 값 중 일부만 바뀌어 모순이 생긴다 | "불일치", "일부만 갱신" |

### 기출에서 이렇게 나왔다

- 22-1: 튜플 삭제 시 의도치 않은 정보 손실 → **삭제** 이상
- 20-4: 이상 현상 3가지 쓰기 → **삽입 / 삭제 / 갱신**

## 파일 접근 방법

### 개념

| 방법 | 내용 | 장단점 |
|---|---|---|
| **순차 접근(Sequential)** | 레코드를 물리적 순서대로 저장·읽기 | 공간 낭비 없음, 일괄 처리에 적합. 특정 레코드 검색·삽입·삭제가 느리다 |
| **인덱스(색인) 접근(Indexed)** | **<키 값, 주소> 쌍**으로 된 **인덱스**를 따로 두고, 인덱스를 찾은 뒤 데이터로 간다 | 검색이 빠르다. 인덱스 유지 비용과 저장 공간이 든다 |
| **해싱 접근(Hashing)** | 키 값을 **해시 함수**에 넣어 저장 주소를 직접 계산 | 가장 빠른 직접 접근. 충돌 처리 필요, 순차 처리에 불리 |

인덱스 보충: **기본 인덱스**는 기본키에, **보조 인덱스**는 그 외 속성에 만든다. 인덱스 순서대로 데이터가 물리적으로 정렬되어 있으면 **클러스터드(Clustered)**로 테이블당 하나만 만들 수 있고, 별도 구조로 두는 **넌클러스터드(Non-Clustered)**는 여러 개 만들 수 있다. 레코드마다 항목이 있으면 **밀집(Dense)**, 블록마다 하나면 **희소(Sparse)** 인덱스다. 구조로는 **B-트리**(트리 기반), **비트맵**, **해시** 인덱스가 있다. SQL로는 CREATE INDEX로 만든다.

해싱 용어:

| 용어 | 뜻 |
|---|---|
| **버킷(Bucket)** | 해시 주소 하나가 가리키는 저장 공간. 여러 슬롯으로 이뤄진다 |
| **슬롯(Slot)** | 버킷 안에서 레코드 하나가 들어가는 칸 |
| **충돌(Collision)** | 서로 다른 키가 같은 주소로 계산되는 것 |
| **동의어(Synonym)** | 같은 주소로 충돌한 키들 |
| **오버플로(Overflow)** | 버킷이 꽉 차서 더 넣을 수 없는 상태 |

충돌·오버플로 해결은 두 갈래다. **개방 주소법(Open Addressing)**은 테이블 안의 다른 빈 칸을 찾아 넣는다. 다음 칸을 차례로 보는 **선형 탐사**(데이터가 한곳에 뭉치는 군집이 생긴다), 1², 2² 간격으로 보는 **이차 탐사**, 두 번째 해시 함수로 간격을 정하는 **이중 해싱**이 있다. **폐쇄 주소법(Closed Addressing)**은 주소는 그대로 두고 동의어를 연결 리스트로 매다는 **체이닝(Chaining)**이다. 이름이 반대로 느껴지므로 "개방 = 다른 빈 칸 찾기, 폐쇄 = 체이닝"으로 외운다.

## 데이터 모델 3요소·E-R 표기
출제: 22-3, 21-1
형태: 3요소 설명 → 빈칸 / E-R 기호 설명 5개 → 보기

### 개념

**데이터 모델(Data Model)**은 현실 세계를 DB로 옮기기 위한 개념적 도구다. 구성 요소 세 가지:

| 요소 | 뜻 |
|---|---|
| **구조(Structure)** | 개체 타입과 개체 간 관계. 정적 성질 |
| **연산(Operation)** | 저장된 데이터를 처리하는 방법(검색·삽입·삭제·갱신). 동적 성질 |
| **제약조건(Constraint)** | 데이터에 대한 논리적 제약 |

**E-R(Entity-Relationship) 모델**은 개념적 설계 산출물로, Peter Chen이 제안했다. 다이어그램 기호:

| 기호 | 뜻 |
|---|---|
| **사각형** | **개체 집합(Entity Set)** |
| **마름모** | **관계 집합(Relationship Set)** |
| **타원** | **속성(Attribute)** |
| 밑줄 친 타원 | 기본키 속성 |
| 이중 타원 | 다중값 속성 |
| 점선 타원 | 유도 속성 |
| **실선** | 개체 집합과 속성, 개체 집합과 관계 집합을 연결하는 링크 |
| **점선** | **관계 집합과 관계 집합의 속성**을 연결하는 링크 |
| 관계 집합에 점선으로 붙은 타원 | **관계 집합의 속성** |

이 유형(22-3, 키워드 문제집 14번)에서 "관계 집합과 속성을 연결"은 **점선**, "개체 집합과 관계 집합을 연결"은 **실선**이다. 점선 타원(유도 속성)과 점선 링크를 구분한다.

관계의 종류는 1:1(예: 사원-사물함), 1:N(예: 부서-사원), N:M(예: 학생-과목)이고 선 옆에 숫자로 적는다. N:M은 테이블로 옮길 때 두 키를 묶은 교차 테이블이 필요하다. **까마귀발(Crow's Foot) 표기**는 선 끝 모양으로 나타낸다. 세로줄(|)은 1·필수, 동그라미(○)는 0·선택, 까마귀발 모양은 N(여럿)이다.

## 함수 종속
출제: 22-2
형태: 표와 설명 3칸 → 영문 보기

### 개념

속성 X의 값이 정해지면 Y의 값이 하나로 정해질 때 **Y는 X에 함수 종속**이라 하고 X → Y로 쓴다. X가 **결정자(Determinant)**, Y가 **종속자(Dependent)**다.

| 종류 | 조건 | 관련 정규형 |
|---|---|---|
| **완전 함수 종속(Full Functional Dependency)** | 복합키 전체에 종속하고, 키의 일부만으로는 결정되지 않는다 | 2NF가 요구 |
| **부분 함수 종속(Partial Functional Dependency)** | 복합키의 일부만으로 결정된다 | 2NF에서 제거 |
| **이행 함수 종속(Transitive Functional Dependency)** | X → Y, Y → Z 이면 X → Z | 3NF에서 제거 |

표에서 확인하는 법: 어떤 속성의 값이 같은 행끼리 다른 속성의 값도 항상 같으면 종속이 있다. 기본키가 (A, B)일 때 A만 같은 행들이 C도 같으면 A → C, 즉 부분 종속이다.

## 스토리지 RAID
출제: 22-1
형태: 설명 → RAID ( ) 숫자

### 개념

**RAID(Redundant Array of Independent Disks)**는 여러 디스크를 묶어 성능이나 안정성을 높이는 기술이다.

| 레벨 | 방식 | 핵심 단서 | 장애 허용 |
|---|---|---|---|
| **RAID 0** | **스트라이핑(Striping)** | 데이터를 나눠 병렬로 쓴다. **패리티 없음**, 복제 없음, 속도 최우선. 최소 2개 | 없음. 디스크 하나 고장이면 전체 손실 |
| **RAID 1** | **미러링(Mirroring)** | 같은 데이터를 두 디스크에 복제. 용량 효율 절반. 최소 2개 | 1개 |
| **RAID 5** | 스트라이핑 + **분산 패리티** | 패리티를 모든 디스크에 나눠 저장. 최소 3개 | 1개 |
| **RAID 6** | 스트라이핑 + **이중 분산 패리티** | 서로 독립적으로 계산한 패리티 2개를 분산 저장(같은 패리티를 복제하는 것이 아님). 최소 4개 | 2개 |
| **RAID 10 (1+0)** | 미러링 후 스트라이핑 | 성능과 안정성 모두. 용량 효율은 절반. 최소 4개 | 미러 쌍마다 1개 |

**패리티(Parity)**는 원본에서 계산해 둔 오류 검출·복구용 값이다. 디스크 하나가 고장 나면 남은 데이터와 패리티로 역산해 복구한다. 미러링보다 용량 효율이 좋다.

스토리지 연결 방식:

| 방식 | 내용 |
|---|---|
| **DAS(Direct Attached Storage)** | 서버에 케이블로 직접 연결한 전용 저장장치. 빠르지만 공유가 어렵다 |
| **NAS(Network Attached Storage)** | LAN(이더넷)에 연결한 파일 저장장치. 여러 서버가 파일 단위로 공유한다 |
| **SAN(Storage Area Network)** | 서버와 스토리지를 파이버 채널 같은 전용 고속 네트워크로 묶은 것. 대규모 환경용 |

## 옵티마이저·분산 DB·OLAP
출제: 없음

### 개념

**옵티마이저(Optimizer)**는 SQL을 가장 효율적으로 실행할 방법(실행 계획)을 고르는 DBMS 모듈이다. **규칙 기반(RBO, Rule-Based Optimizer)**은 미리 정한 우선순위 규칙으로, **비용 기반(CBO, Cost-Based Optimizer)**은 통계 정보로 예상 비용이 가장 적은 계획을 고른다.

**분산 데이터베이스**는 물리적으로 여러 곳에 흩어진 DB를 하나처럼 쓰게 한다. 사용자가 분산 사실을 의식하지 않게 하는 **투명성(Transparency)**이 목표다.

| 투명성 | 사용자가 몰라도 되는 것 |
|---|---|
| **위치 투명성(Location)** | 데이터가 어느 사이트에 있는지 |
| **분할 투명성(Fragmentation)** | 테이블이 여러 조각으로 나뉘어 있는지 |
| **중복 투명성(Replication)** | 같은 데이터가 여러 곳에 복제되어 있는지 |
| **병행 투명성(Concurrency)** | 여러 트랜잭션이 동시에 실행되는지 (그래도 결과는 일관) |
| **장애 투명성(Failure)** | 일부 사이트·통신에 장애가 났는지 (그래도 트랜잭션은 정확히 처리) |

**OLTP(OnLine Transaction Processing)**는 주문·이체처럼 짧은 INSERT·UPDATE·DELETE를 실시간으로 많이 처리하고, 현재·상세·정규화된 데이터를 다룬다. **OLAP(OnLine Analytical Processing)**는 의사결정을 위해 대량의 요약·이력 데이터를 다차원으로 분석하는 조회 위주 처리다.

| OLAP 연산 | 뜻 |
|---|---|
| **롤업(Roll-up)** | 상세 → 요약. 일별 → 월별 → 연별로 묶어 올라간다 |
| **드릴다운(Drill-down)** | 롤업의 반대. 요약 → 상세로 파고든다 |
| **슬라이스(Slice)** | 큐브를 한 차원 값으로 잘라 2차원 단면을 본다 |
| **다이스(Dice)** | 여러 차원에 조건을 걸어 작은 부분 큐브를 뽑는다 |
| **피벗(Pivot)** | 행과 열의 축을 돌려 보는 관점을 바꾼다 |
